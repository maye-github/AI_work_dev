# 知識飛輪規則（踩坑 → 規則化 → 検査追加 → 全隊免疫）

> **本規則の出所**: 社内 AI 実績 PPT `AI 在Harmony项目中的应用.pptx`（Harmony プロジェクト組、2026.06）。
> **要件源（PPT 2 份）には無い追加要素**である。登録は `docs/90_knowledge/ppt-deviation-register.md` §2 を参照。
> 詳細な実績値と 5 道ゲートの内訳は `docs/90_knowledge/internal/harmony-5gates.md` が唯一の定義。

**Summary**: 不具合やレビュー指摘を「直して終わり」にせず、**① 記録 → ② 分析 → ③ 規則化 → ④ 検査の自動化 → ⑤ 配布** の 5 段で組織へ固定する。本規則はその 5 段を本骨架の資産パスへ写像し、各段の責任者を定める。

---

## 1. 飛輪の 5 段（Harmony 実績の写像）

Harmony プロジェクト（Vue 2→3 移行、3 人チーム）が実運用した飛輪は次の 6 手順である（PPT 逐語）:

```
1. 踩坑 (G1-G5 失敗)
2. anomaly 自動創建
3. 5 問帰档分析
4. 更新 guides/traps.md
5. 新增 check スクリプト
6. git push 全隊免疫
```

これを本骨架の資産へ写像すると次のようになる。**写像先が違うだけで、段の数と順序は同じ**である。

| # | Harmony の段 | 本骨架での写像先 | 責任 |
|---|-------------|----------------|------|
| 1 | 踩坑（G1-G5 失敗） | `py -3 -m tools.trace_check --strict` の FAIL、または人レビューの指摘 | 実行した AI |
| 2 | anomaly 自動創建 | `docs/90_knowledge/review_diff_assets/<module>/review_comments.md` に 1 件追記 | AI（起案） |
| 3 | 5 問帰档分析 | **§2 の 5 問**（下記）に答える | 人（裁定）|
| 4 | 規則を書く（guides/traps.md） | `.claude/rules/**` へ 1 条追記（起動時に自動ロードされるため配布工程が不要） | 人（承認）|
| 5 | check スクリプト追加 | `tools/trace_check` に **gate を追加**（§3 の制約あり） | AI |
| 6 | git push 全隊免疫 | `.claude/rules/` は共有設定。commit した時点で全員に効く | 人（commit 承認）|

> **Harmony 実績値**（PPT）: 22 件の anomaly → 10+ の問題模式 → 11 本の check スクリプトのうち **4 本が飛輪から産出**。
> すなわち「検査の 36% は後から積み上がったもの」である。初期設計で完璧を狙う必要はない。

## 2. 帰档の 5 問（本骨架の定義）

Harmony PPT は「5 問归档分析」とだけ述べ、**5 問の中身は展開していない**。
したがって下記 5 問は **本骨架が定義した追加要素**であり、Harmony の 5 問そのものではない。混同しないこと。

| # | 問い | 答えることで防げること |
|---|------|---------------------|
| 1 | これは**再発する**か（一度きりか） | 一度きりの事故を規則化して規則を膨らませるのを防ぐ |
| 2 | 既存の**どの規則・どの gate** が捕まえるべきだったか | 検査の穴が「無かった」のか「あったが弱かった」のかを切り分ける |
| 3 | **機械で検出できる**か、人にしか判定できないか | 機械化できるものを人の注意力に頼らせない |
| 4 | 同じ穴が**他の場所**にもあるか | 1 箇所直して終わりにするのを防ぐ |
| 5 | 規則化するなら**どの層**か（紅线 / rules / テンプレート / 検査） | 何でも紅线にすると紅线が形骸化する |

> **問 5 の原則**: 紅线（`CLAUDE.md` §1）は **7 条から増減させない**。
> 紅线の本数は `docs/00_plan/review.md` CP-R-1 と `reports/AC-selfcheck.md` ほか
> **5 箇所の機械検査**が `7 条红线` の文字列に依存しているため、増やすと同時に複数が落ちる。
> 新しい横断規則は `.claude/rules/` 側に置く（実例: `.claude/rules/00-project-global.md` §13）。

## 3. 検査を追加するときの絶対制約

**走査範囲を狭める変更をしてはならない。追加のみ許可する。**

- 根拠となる事故: 旧版の `tools/trace_check` は `docs/00_plan/**` を「計画文書であり成果物ではない」として
  gate6 の走査対象から除外していた。**その除外区画から本番 Oracle 接続情報が漏洩していた**（2026-10 に撤廃）。
- 適用例: 取入機構（`tools/ingest`）が `reports/**` に YAML を書くようになったため、
  gate6 の `reports/**` 走査対象に `.yml/.yaml` を**追加**した（`tools/trace_check/__init__.py`）。
  既存の `.md/.txt/.json` はそのまま残している。
- **禁止**: `SECRET_EXEMPT_PATHS` に新しい除外路径を足すこと。
  除外は現在 `.claude/rules/01-security-redlines.md` の **1 箇所のみ**であり、これは
  L3 キーワードの定義場所そのものであるため例外的に許されている。

## 4. 記録の粒度（追記の書き方）

`review_diff_assets/<module>/review_comments.md` への 1 件は次の 4 点を持つ。
**対策が書けていない記録は記録ではない**（次に同じ穴を踏むため）。

| 項目 | 内容 |
|------|------|
| 事象 | 何が起きたか（再現手順。値は占位 `COL_1` / `VAL_1`）|
| 影響 | どの工程で発見され、どこまで波及したか |
| 原因 | §2 の問 2 の答え（どの検査が捕まえるべきだったか）|
| 対策 | §2 の問 3〜5 の答え（機械化 / 規則化 / 層）|

### 4.1 人の裁定を記録するときは出典を伴う（RC-SK-03 の規則化・2026-10-22）

`note` / `notes` など**自由記述の欄に「ユーザー裁定」「人裁定」「承認済」と書くとき**は、
**その裁定が記録されている場所（パス。可能なら節・行）を同じ行に書く**。
**出典を書けない裁定は、書いてはならない**——それは裁定ではなく AI の判断である。

- 正: `build_mode は greenfield のまま（出典: docs/90_knowledge/ppt-deviation-register.md A-22）`
- 誤: `build_mode を greenfield → migration へ変更（ユーザー裁定 2026-10-14）`
  → **その裁定は実在しなかった**（RC-SK-03）。**日付だけでは出典にならない。**
- **AI が自分で決めたことを人の裁定として書かない。** 自分の判断は「AI 案」と明記し、
  `answer` / `approved_by` は空のまま残す（紅线③）。
- **機械化はしていない（誇張しない）。** 出典パスの有無までは機械で見られるが、
  「そのファイルに本当にそう書いてあるか」は人が照合する。**門番は 6 道のまま。**

## 5. 運用のリズム

- **毎回**: 不具合・指摘・gate の FAIL を 1 件でも観測したら、その場で 1 行記録する。
- **週次（30 分）**: 未処理の記録を §2 の 5 問にかけ、規則化するもの / 検査化するもの / 記録のみで閉じるものを仕分ける。
- **四半期**: 追加した規則と検査を見直し、**使われていない検査**を特定する。
  （検査は「あること」ではなく「捕まえること」で評価する。）
- 関連: `docs/90_knowledge/ppt-deviation-register.md` §4（追加要素を必ず 1 行登録する）、
  `docs/00_plan/review.md`（独立検査 CP の追補）。

## 6. 本骨架がまだ持っていないもの（正直な線引き）

Harmony の 5 段のうち、本骨架で**まだ自動化できていない**のは次である。誇張しない。

| 段 | 現状 |
|----|------|
| anomaly の自動創建 | **未実装**。現在は人が `review_comments.md` へ手で追記する |
| 検査の自動追加提案 | **未実装**。§2 の問 3 は人の判断に委ねている |
| 週次レビューの起動 | **未実装**。リマインダ機構は持たない（運用で担保する）|

> これらは `ROADMAP_3PHASE.md` の Phase 2 以降の検討対象である。
> 「規則を書いた」ことと「規則が自動で守られる」ことは別である。混同しないこと。
