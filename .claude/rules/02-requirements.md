# 8 工程 要求管理手続き規則（R-ID 発号 SOP / Q-ID 確認票 / 状態機）

## 1. 適用範囲と唯一発号口
**Summary**: 本規則は R-ID を起点とする 8 工程の手続きを固定する。R-ID/Q-ID/F-ID/I-ID/D-ID/L-ID/E-ID/TC-ID の唯一発号口は `docs/00_registry/ids.yml`（単一ソース）、それ以外の野号（未登録番号）は `tools/trace_check.py` gate1 で Exit 1。
- 発号規則: 3 桁起步・連番・**不使用番号の再利用禁止**（無効化は `void` で明示）。
- **案件形態（`build_mode`）**: 既定は `greenfield`（從無到有・既存システム無し）。既存システム・旧設計書を持つ案件は `migration` 変種として `docs/00_plan/coach/<module>/case.yml` に**明示宣言**する（唯一の宣言場所）。
  本規則および 03/04 のうち `migration` にのみ適用される条項は、その旨を各所に明記している。宣言が無ければ `greenfield` とみなす。
- 参照: spec.md NFR-1 / FR-2 ・ 落地篇 PPT S9-S17

> **※ 落地篇 PPT 自身の「8 工程 / 7 工程」表記ゆれについて**（重要・混同しやすい）
> 落地篇 PPT は **両方の数え方**を使っている。矛盾ではなく、**粒度の違い**である。
> - 「**8 工程の全链路像**」（S2・S4）＝ 全体像。**框架・環境構築 を含む** 8 つ。
> - 「**7 工程の進め方（要件理解〜運用保守）**」（S8 以降の工程篇）＝ 各工程の**進め方**を述べる章立て。
>   **框架・環境構築 は他 7 工程に横断する準備作業**であり、独立した章を立てていないため 7 になる。
>
> **本骨架は 8 工程を採用**する（上表）。理由は、框架・環境構築を独立工程として扱わないと
> `docs/40_framework/framework-record.yaml`（技術選型記録）の置き場と人ゲートが定まらないため。
> したがって本骨架の文書に「7 工程」が出てきたら、それは PPT の章立てを引用している箇所である。

## 3. R-ID 発号 SOP
**Summary**: R-ID は要求の最小単位であり、全下流 ID（F/I/D/L/E/TC）の起点となる。発号は必ず `ids.yml` 経由、口頭・チャット上の仮番号も野号扱い。
1. 要求粒度の確認（1 R-ID = 1 業務機能。例: R-101 = R60Area マスタ検索登録修正削除）。
2. `ids.yml` の `registry.prefixes.R` に準拠し、**連番の次番**を払い出す（飛び番・再利用禁止）。
3. 登録必須字段: `status` / `name` / `description` / `used_by`（成果物パス）。
4. 発号直後の `status` は `open`。`used_by` の成果物 YAML 生成時に front-matter `req_ids` へ逆参照を張る。
5. 下流 ID（F/I/D/L/E/TC）は親 ID を必ず持ち、`ids.yml` に子→親のリンク（`r_id` / `f_id` / `i_id` / `l_id` / `d_id`）を記録。

### 3.1 発号チェックリスト
- [ ] `ids.yml` に登録済みか（野号でないか）
- [ ] 連番が直前番号 +1 か（飛び番なし）
- [ ] `used_by` が実在成果物パスを指すか
- [ ] 親 ID リンクが張られているか

## 4. Q-ID 確認票の運用
**Summary**: Q-ID は要求段階で未確定な点（質問・確認待ち）を管理する確認票で、**外部（日方/元請）への確認事項の 1 件 = 1 Q-ID**とする。
- 発号規則は R-ID と同一（`ids.yml` の `Q` プレフィックス、3 桁起步・連番）。
- Q-ID は必ず関連 R-ID を持ち、回答が得られた段階で状態を進める（`open` → `done`）。
- 未解決 Q-ID を残したまま要求を `baselined` に昇格してはならない。
- 確認票の本文には**真值・実データを書かず**、占位（`COL_1` / `VAL_1`）を用いる（01-security-redlines.md 準拠）。
- **★対客媒体（確認依頼書・質問票）の書き方**（2026-10-16 追加）。
  **内部 ID を出さない。** 対象：`R-` / `F-` / `I-` / `D-` / `L-` / `E-` / `TC-` / `Q-` / `BR-` / `ER-` / `AC-` など。
  これらは**我々の管理番号であり、顧客は見たことがない**。出すと顧客を混乱させるだけである。
  - **参照は「文書名 ＋ 節 ＋ 項目名」で書く。**
    誤：「`§3.2 #4` の値域」→ 正：「**ご要望書 §3.2 の「起動区分」**」
  - **端点名・テーブル名・関数名も、顧客が知らないものは書かない。** 役割で書く。
    誤：「`/init` の応答」→ 正：「**初期表示の処理で返す内容**」
  - **我々の内部成果物（`01_AI产出_…`）への参照も出さない**（`BR-201-xx` のような番号も同様）。
  - **実測（R60Login・2026-10-16）**：初版の確認依頼書に `ER-201-01〜05`・`ER-201-03`・`/init`・
    裸の `§3.2 #4` が混入していた。ユーザーの指摘＝
    「**§3.2 #4 是什么指哪本里的哪个、客户又不认识写清楚点好吗？**」
- **★対客媒体に載せるのは「顧客に聞くこと（A）」と「顧客に承認を求めること（B）」だけである**
  （2026-10-16 追加）。
  **我々が内部で決めたこと（C）は載せない。** 載せても**顧客の注意を食う**だけで、
  質問でも承認依頼でもない。**C は設計書に現れ、設計評審の門で顧客の目に触れる**——それが正しい出会い方である。
  - **記録の行き先**：C は `nNN.yml` の `open_questions`（`category: C`）に残し、**設計へ渡す**。
  - **実測（R60Login・2026-10-16）**：初版の確認依頼書に「**§5 参考（回答不要）**」の節を置き、
    C を 4 件並べていた（例：「画面候補が 0 件のとき」）。ユーザーの指摘＝
    「**…需求书有提到要处理这个吗？为何要拿出来说一说**」。→ **節ごと削除した。**
  - **注意**：`§4.1` の字母表は「C は確認票に『参考・回答不要』として載せてよい」と書いている。
    これは**許容であって義務ではない**。**既定は「載せない」**とする。
- **★回答書の最小書式**（2026-10-16 追加）。人が回答を書くときは、**これ以上書かせない**。
  理由：**回答が長いと、人が書くのをやめる**。書かれない回答は存在しないのと同じである。

  **A／B（顧客が書く）** — 1 行 1 問。**根拠・出典は書かなくてよい**（顧客は `file:line` を知らない。**当方が補う**）。

  ```
  確認-01: <回答を1〜2文で>
  確認-02: <回答を1〜2文で>
  提案-01: 承認 ／ 条件付き承認（条件） ／ 不承認（理由）
  ```

  **C（我方が書く）** — 1 行 1 問。

  ```
  Q-208: <裁定を1文で>（理由: <1文で>）
  ```

  - **★雛形は `tutorial/<案件>/节点N_*/0N_確認事項一覧.md` に置く**（演習 R60Login の実物が手本）。
    **審査項目・区分・質問・回答・裁定を 1 本に集める。**
    **人が記入し、AI は雛形を用意するだけ**（「AI 暫定」として先に埋めてよいが、人は上書きできる）。
    **様式は固定ではない**——使いにくければ人（ユーザー）の指示で改める。
  - **区分（区分欄）が空のものは「未判定」、回答欄が空のものは「未回答」である。**
    どちらも**空欄で放置しない**（空欄は「無かった」と区別できない）。

  **守ることは 3 つだけ**：
  1. **回答が無い項目は「未回答」と明示する**（空欄にしない。空欄は「無かった」と区別できない）。
  2. **問番号は動かさない**（突合の鍵だから）。**行の追加・並べ替えは自由**。
  3. **A／B の回答は顧客から、C の裁定内容は我方から**——**3 つとも揃って初めて次へ進める**（§7 鉄則 18）。
- **★`02_確認事項一覧.md` の表は「出典等級（E1〜E4）」列を持つ**（2026-10-20 追加。
  **節点 2 以降で必須**。**節点 1 の承認済み `02` は遡及改訂しない**——承認済みの内容を後から書き換えないため）。
  - **等級の定義は `docs/90_knowledge/answer-engine.md` §3.2 が唯一真源**。本条は定義を再記述しない。
  - 値域は `E1` / `E2` / `E3` / `E4` / `—`。**`—` は「未記載」であり、`E4` の代用ではない。**
    **提案（B）は等級必須**であり、等級の無い提案は「根拠の無い提案」として扱う。
  - `E2`（既存実装の実測）は `migration` でのみ根拠になる。`greenfield` では**使わない**
    （`answer-engine.md` §3.2）。
  - **等級は「列」に書く。本文の括弧内だけに書かない。** 本文だけに書くと、承認版へ転記した時点で
    等級が消え、読者は事実と提案値を区別できなくなる（実測: R60Login 節点1・`comparison.md` の A3）。
  - **列の有無と B の等級有無は、人のレビューで確認する。値の正否は機械判定しない**
    （§4.1 末尾の方針と同じ。門番は 6 道のまま）。
- **★回答の出所は「顧客の公式文書」である。実装（コード）を回答の出所にしない**（2026-10-16 ユーザー裁定）。
  対象：設計書・規約・マスタ定義・運用規程など、**顧客が公式に発行したもの**。
  - **理由**：顧客が答えるのは「**我々の業務が何を求めるか**」であり、それは**設計書の役割**である。
    **実装に無いことは「顧客の要求が無いこと」ではなく「人版の偏差」である**——
    つまり**測定対象**であって、**入力ではない**。
  - **もし実装を回答の出所にしたら**、**AI に答案（人版）を渡すことになり、対比が成立しない**
    （＝本骨架が最も避ける汚染。`CLAUDE.md` 紅线⑤ の趣旨）。
  - **注意**：回答が設計書と実装で食い違う場合、**回答は設計書側を採る**。
    その食い違いは `08-deviations.md` に登記されうる**測定値**である。
- **★顧客の回答は「きれいな形」では来ない。当方が取り込んで規格化し、顧客の確認を取る**
  （2026-10-16 追加）。**上がってくる形を問わない。**

  | 顧客から来る形 | 我々のやること |
  |---|---|
  | **口頭**（会議・電話） | **議事録に起こす**（1 行 1 問）→ **顧客に送り返して確認** |
  | **Excel への赤字** | **受控回流**（`00-project-global.md` §11）。正文は読まず、**指摘欄だけ**を読む |
  | **メール・チャットの断片** | 一覧にまとめる → 顧客に送り返して確認 |
  | **手書き・PDF・スクリーンショット** | 読み取って規格化 → 顧客に送り返して確認 |

  - **共通の規則**：**我方が規格化 → 顧客に確認 → それで確定。**
    **確認の取れていない原稿を入力にしてはならない**（誤読のまま設計へ流れ込む）。
  - これは `00-project-global.md` §13 の「**口頭合意だけで進めない**」と同じ原則である。
  - **★したがって必須なのは「回答書という形式」ではなく「回答が存在すること」である。**
    形式は**当方が作る記録**であり、**顧客に様式を守らせない**（守らせると回答が来なくなる）。

### 4.1 未確定事項の分類字母表（**唯一真源**）

**Summary**: 確認票・審査資料・教材が未確定事項を分類するときの `A` / `B` / `C` は、
**下記の 3 語以外の意味で使ってはならない**。本表が唯一真源であり、
教材（`tutorial/**`）・雛形・成果物はここを**参照するだけ**で、同じ定義を書き直さない（NFR-1）。

| 記号 | 意味 | 誰が決めるか | 確認票での扱い |
|------|------|--------------|----------------|
| **A** | **顧客が決める**（我方では決められない） | 顧客 | **必ず質問する**。当方が暫定値を置いてはならない |
| **B** | **我方が提案し、顧客が承認する** | 顧客（提案は我方） | 提案＋**根拠**を添えて承認を求める。根拠の無い提案を出さない |
| **C** | **我方内部で決定する** | 我方 | 顧客に聞かない（確認票には「参考・回答不要」として載せてよい） |

- **★技術選型は B である**（2026-10-16 追加。ユーザー裁定）。
  **方式・アルゴリズム・構成・ライブラリ・運用の設計**といった**技術選型**は、
  **顧客の業務事実ではない**。A に置くと **顧客には決められないことを押し付ける**ことになる。
  - **誤**：「暗号化の方式を決めてください」→ **A**
  - **正**：「方式は**弊社が提案します**（互換性の制約は御社の規約に従います）」→ **B**
  - **境界**：その選型が**顧客の統制（標準規約・他システムとの互換・セキュリティ方針）に従うべき場合**は、
    **従うべき規約・制約を確認したうえで**提案する。**「制約の確認」は A、「選型」は B** である。
    両者を混ぜて「方式を教えてください」と書くと、**A に寄ってしまう**。
- **★A は「顧客しか持っていない**資料・事実**」に限る。それ以外は B（我方が提案する）**
  （2026-10-16 ユーザー裁定）。
  - **理由（対客の姿勢）**：**A が並ぶほど、顧客には「我々は考えずに聞いている」と映る。**
    B は「考えたうえで提案している」と映る。**同じ情報を取るのに、印象が正反対になる。**
    ユーザーの言葉：「**尽可能使用 AI 能力使得它变成 B 类有提案给客户、而不是让客户看一大堆全都是问题
    一头误会或者认为你们 AI 开发也不思考就问、能力不行啊**」。
  - **A に残すもの（本当に案が作れないもの）**：顧客が発行した**文書・規約・マスタの内容**、
    顧客の**既存システムとのインタフェース仕様**。
    例：標準規約・画面マスタ・社員マスタ・他システムが使う URL の受信仕様。
  - **B に移すもの（我方が案を作れるもの）**：**運用の決め事**（セッション期限・ログアウト・
    ロック・多重ログイン・履歴・権限付与の時点）、**方式**（暗号化・エンコード・保持方式）、
    **異常時の挙動**、**非機能の水準**、**利用者に見える挙動**（画面遷移の方式・画面文言・
    稼働不可時にどの画面を出すか）、**外部との約束**（遷移 URL の有効期限）。
    **根拠を添えて提案し、承認をもらう。**
  - **★ただし「案を作れる」＝「B」ではない。B か C かは「顧客の業務・運用・統制に触れるか」で分ける**
    （2026-10-20 追加。ユーザーの指摘「**A 類太多了、C 類太少了**」を受けて）。
    - **C に落とす**：**実装・内部設計・表記の決め事で、顧客の業務に触れないもの**——
      入力値の正規化（trim・全角除去）、文字コード・URL エンコード、日時の取得元と更新頻度、
      環境設定の外部化、二重送信の抑止、URL 表示欄の編集値を遷移に使うか、
      エラー画面へ遷移させる主体（クライアントかサーバか）、暗号化処理を 1 本に統合するか、
      社員コードの先頭ゼロの許容、文書内の表記ゆれ（タイトルの全角空白等）の統一。
    - **境界**：同じ「方式」でも、**対外の互換性・顧客の規約に縛られるものは B**（暗号化方式・
      エラーコード体系）、**当方の実装内で閉じるものは C**（エンコード方法・文字コード・設定管理）。
      **迷ったら B** だが、**「顧客が読んでも判断できない」なら C である**——
      判断できない質問を出すのは、B ではなく単なる時間の浪費になる。
  - **★判定は「C → B → A」の順に疑う**（2026-10-20 追加）。
    1. **まず C を疑う**：「これは顧客に聞かなくてよい内部の決め事ではないか」。
    2. **次に A を疑う**：「案を作れるのに、顧客に丸投げしていないか」。
    3. **残ったものだけが A／B である。**
  - **★件数の目安（におい試験。機械判定はしない）**：**A ≦ 1/4、C ≧ 1/3**。
    - **A が多い＝調べていない・考えていないのサイン。** A は「顧客しか持っていない資料・事実」に限る。
    - **C が少ない＝内部で決めるべきことを顧客に投げているサイン。** 顧客は実装の詳細など決めたくない。
    - **実測**（R60Login 節点1・2026-10-20）：初版 **A40/B26/C5**（A 56%・C 7%）
      → 是正後 **A18/B26/C27**（A 25%・C 38%）。**AI の初版は A に寄り、C がほぼゼロになる。**
      これは能力の欠落ではなく**判定手順の欠落**であり、上の 1→2→3 の順で直る。
  - **★迷ったら B に倒す。ただし「C か B か」で迷ったときは、顧客が判断できるかを基準にする**
    （判断できなければ C）。**根拠の無い提案は出さない**——根拠が「業界慣例」「リスク」なら、そう明記する。
- **A と B の分かれ目**: 「その事実を**顧客しか持っていない**か」（顧客の業務事実・統制 → A）と、
  「我方が案を作れるが**採否は顧客**か」（→ B）。
- **B の必須要件**: 提案には**根拠**を併記する。根拠が「既存案件の慣例」しか無い場合は、
  その旨を明示する（既存システムを持つ案件（`build_mode: migration`）と持たない案件（`greenfield`）で
  根拠の出所が異なる。上記の分類自体は**両モード共通**である）。
- **★分類を変えたら、回答の形態も変える**（2026-10-20 追加。ユーザーの問い
  「重判分类以后、还需要重新回答吗？毕竟 B 类需要提案」に対する裁定）。
  分類は「誰が決めるか」を変えるだけでなく、**書かれる文の種類**を変える。取り違えると、
  分類だけ直して**中身が A のまま**の成果物ができる（＝提案のつもりの事実記述）。

  | 区分 | 回答の形態 | 出典等級（E1〜E4） | やってはならないこと |
  |------|-----------|--------------------|--------------------|
  | **A** | **質問**（＋当方の暫定案を置く場合は「AI 暫定案」と明示） | 顧客文書の節を示す。特定できなければ `—` | 当方の値を確定値として書く |
  | **B** | **提案＋根拠（等級 E1〜E4）＋ご承認いただきたい点**の三段 | **必須**（`greenfield` では E2 不可） | 「〜はこうなっている」という事実記述で終える |
  | **C** | **裁定＋根拠**の二段 | 推奨（E3／E4） | 「〜を提案します」という提案口調を残す |

  - **★等級は表の「列」に持たせる**（節点 2 以降）。本文の括弧内だけに書くと、転記の過程で
    等級が落ちる（上の §4 の★を参照）。

  - **B に移したら、書き直しが必須**である。A の答案は「資料にこう書いてある」であり、
    B の答案は「こうすることを提案します」である。**同じ内容でも文の種類が違う。**
  - **C に移したら、口調の修正が必須**である。提案口調が残ると、**顧客の承認が要る事項に見える**
    （＝ C の意味が消える）。
  - **A→B の移行では、根拠の等級を必ず付け直す**。旧版の実装に依拠した E2 は
    `greenfield` では**根拠にならない**（`answer-engine.md` §3.2）。
  - **対客媒体との突合**：B に移した件が対客の確認依頼書に**載っているか**を必ず確認する。
    載っていない B は「承認をもらう相手が存在しない提案」であり、**分類を変えた意味が無い**
    （実測: R60Login で 1 件欠落し、提案を追加した）。
- **A クラスの暫定値を勝手に埋めないこと**。これは工程 01 で最も起こりやすい違反であり、
  実例と対策は `docs/90_knowledge/review_diff_assets/_skeleton/review_comments.md` **RC-SK-02** を参照。
- **機械検査はしない**。`A`/`B`/`C` は `ids.yml` の発号対象ではなく（発号対象は `R/F/I/D/L/E/TC/Q/CR/BUG`）、
  本文中に無数に現れるため gate で走査すると誤検出だらけになる。
  **門番は 6 道のまま**（`docs/90_knowledge/ppt-deviation-register.md` §2 A-19）とし、本条は人読文案の層で守る。
  **「出典等級」列も同じ扱いである**——列が在るか、B に等級が付いているかはレビューで見るが、
  **等級の値が正しいかは機械で判定しない**（`E1` と書いてある文が本当に要求書の明文かは、人が原文と照合する）。

### 4.2 回答ファイルの受領と突合（受領 → 突合 → 人の裁定 → 反映）

**Summary**: 戻ってきた回答は、**必ず「受領 → 突合 → 人の裁定 → 反映」の 4 段**を通す。
突合を飛ばして `02_確認事項一覧.md` の回答欄へ直接書くと、**AI が補った推測と顧客の回答が
同じ欄に混ざり、下流はそれを顧客の回答として扱う**（紅线⑤・鉄則 18 の趣旨）。

| 段 | 何をするか | 誰が |
|---|---|---|
| 1 受領 | 回答の出所を **1 つのファイル**として受け取り、**受領記録**を残す（ファイル・日付・形式・受領者・突合した 02 の版）。**形式は問わない**——口頭は議事録に起こし、Excel 赤字は指摘欄だけを読み、メール断片は一覧にまとめる（§4 の表） | 我方（顧客には様式を守らせない） |
| 2 突合 | 各行を 02 の行（Q-ID・項番・審査 #）へ割り当て、**一致／差分あり／未受領／余剰**に分類する。回答ファイルに無く 02 が補ったものは **AI 補足**として別掲する | AI（機械的作業） |
| 3 裁定 | 差分・未受領・余剰・AI 補足の**採否**を決める（02 を採る／回答ファイルを採る／両方修正／未回答のまま保留） | **人** |
| 4 反映 | 裁定どおりに 02 を更新し、突合ファイルに**反映日・反映者**を記録する | AI（裁定の転記のみ） |

- **02 を黙って上書きしない。** 反映は段 3 の後だけである。
- **未受領が 1 件でもあれば、その節点は完了にできない**（鉄則 18）。**余剰**は「回答ファイル側の誤り」か
  「02 の設問漏れ」のどちらかであり、**黙って捨てない**（どちらかを人が決める）。
- **AI 補足は「回答」ではない。** `AI 合理案` と明記し、顧客の回答が来るまで `baselined` にしない。
- **回答ファイルの中で記述が食い違う場合**（要旨欄と具体値欄、§1 と補足節など）は、
  **具体値を採るのではなく、どちらが正かを人に確認する**。勝手に一方を選ばない。
- **根拠の等級を付け替えた場合は、付け替えたことを記録する。** 例：回答ファイルが旧実装の実測
  （E2）に依拠していた箇所を、`greenfield` では要求書の明文（E1）や弊社案（E4）へ付け替える。
  **付け替えは改善であり、隠してはならない**（`answer-engine.md` §3.2）。
- **記録先**：演習 `tutorial/<案件>/节点N_*/0N_回答受領チェック.md`、
  実案件 `docs/10_requirements/answer-reconciliation-<R-ID>.md`。
- **突合は「意味の一致」までは機械で判定できない。** 数値・コード・固有名詞の欠落は機械で拾えるが、
  文意の食い違いは人が読む。**機械一致＝内容一致と書かない。**
- 参照: `CLAUDE.md` §1 紅线⑤、`.claude/skills/trans-cosmos-ai-lifecycle-coach/nodes/n01-requirements.md` ステップ 3／4

**記入欄の書式例**（下記は形式を示すための例であり、**実在の Q-ID ではない**）:

| Q-ID | 関連 R-ID | 質問要旨 | 状態 | 回答反映先 |
|------|-----------|----------|------|------------|
| Q-0xx | R-xxx | （質問の要旨を 1 行で） | open / done | `docs/xx_xxx/….yaml` |

> **本骨架の現状**: **Q-ID は 1 件も発号していない**（`ids.yml` の `Q` プレフィックスは使われていない）。
> R-101/F-042 の確認事項は骨架構築段階で内部確定させたため、各成果物の `open_issues` も `[]` である。
> **これは「Q-ID が不要」という意味ではない** — 日方・元請への確認が必要な事項が生じた時点で、
> `ids.yml` で `Q-xxx` を発号し、本表に追記する。**未登録番号（野号）を本表に書いてはならない。**
> `open_issues` を空にする場合は「なぜ空でよいか」を人が説明できることが条件である
> （`docs/90_knowledge/ai-dev-playbook.md` §6 原則 6 を参照）。

## 5. front-matter 7 字段チェック（全成果物共通）
**Summary**: 全 `.md` / `.yaml` 成果物は冒頭 front-matter に **7 字段固定**を持ち、`trace_check --strict` gate3 がキー欠落・値域違反を検出する。
| # | 字段 | 意味 | 値域・例 |
|---|------|------|----------|
| 1 | `id` | 自身の ID | `R-101` / `RULE-002` / `TC-001` |
| 2 | `type` | 成果物種別 | `requirements-procedure` / `design-coding` / `testing` 等 |
| 3 | `req_ids` | 逆参照要求 ID 配列 | `[R-101]` |
| 4 | `status` | 状態機の現在値 | `draft/open/baselined/changed/done/void` |
| 5 | `sensitivity` | 機密区分 | `internal`（社内）等 |
| 6 | `owner` | 責任者位 | `AI-SE` / `AI-PG` |
| 7 | `version` | 版数（SemVer） | `0.1.0` |

> 注意: front-matter の 7 字段キー名は**全て snake_case 固定**。YAML テンプレート内部の I-ID 定義字段も snake_case（gate5 判定）。

### 5.1 物理書式（`.md` と `.yaml` で**非対称**・混同しやすい）
**Summary**: 同じ「front-matter 7 字段」でも、`.md` と `.yaml` では**区切りの書き方が違う**。取り違えると `yaml.safe_load` が YAML を解析できず、**門番 4 道が同時に FAIL** する（`.claude/rules/06-knowledge-flywheel.md` §4 の RC-SK-01）。
| 拡張子 | 区切り | 理由 |
|--------|--------|------|
| `.md` | 先頭の `---` と、本文直前の `---` の**二重区切りで囲む** | `parse_front_matter()` が手で `---` を探して前後を切り分ける |
| `.yaml` / `.yml` | **先頭の `---` 1 本のみ。収尾の `---` を書いてはならない** | `Repo._load()` は**裸の `yaml.safe_load()`**（単一ドキュメント前提）。2 本目の `---` は「第二の文書」と解釈され `ComposerError: expected a single document in the stream` を送出する。文書全体の最上位キーが front-matter と見なされる |

- 正例: `docs/10_requirements/R-101-R60Area.yaml`、`docs/01_context/case-profile-R60.yaml`（いずれも収尾 `---` なし）。
- **症状の出方**: gate4 と gate6 は PASS のままなので「**6 門中 4 門 FAIL**」となり、「規約違反が 4 つある」と誤診しやすい。実際は**物理書式 1 件の単一原因**である。
- **原因の特定手順**: `--strict` の既定出力には原因ファイルが出ない。`py -3 -m tools.trace_check --strict --report <path.json>` を取り、`stats.error` のメッセージを読むこと。当て推量で複数ファイルを触ると被害を広げる。
- 記録: `docs/90_knowledge/review_diff_assets/_skeleton/review_comments.md` **RC-SK-01**。

## 6. status 状態機（draft → open → baselined → changed → done、void は作废）
**Summary**: status は以下の一方向遷移を原則とし、逆行・飛躍は人レビュー記録なしには不可。
```
draft ──▶ open ──▶ baselined ──▶ done
  │         │           │
  │         │           └─▶ changed ──▶ baselined（再ベースライン）
  └─────────┴───────────┴─▶ void（作废・終端）
```
| status | 意味 | 遷移条件 |
|--------|------|----------|
| `draft` | 起案中（未レビュー） | 成果物新規作成時 |
| `open` | レビュー可能・確認待ち消化中 | 起案完了 |
| `baselined` | 基準化済（下流展開可） | 人レビュー是認 + 未解決 Q-ID なし |
| `changed` | 基準後の変更要 | `baselined` 後に CR-xxx で変更申請 |
| `done` | 完了・クローズ | テスト合格 / リリース完了 |
| `void` | 作废・無効 | 番号を無効化（後述 §7） |

- 逆行（`baselined` → `open` 等）は禁止。修正は `changed` を経由する。
- ベースライン後の変更は必ず `CR-xxx`（Change Request）を起票し、CR から `changed` へ遷移。

### 6.1 承認版は「結論だけ」を持つ（未確定事項を載せない）

**Summary**: `baselined` の成果物は、**未確定の事項を一覧・節として持たない**。判断が付いていないものは
その場で決めるか上流へ戻す。「未確定事項一覧」を承認版へ持ち込み、あとで決める形にしない。

- **承認版に書いてよいのは結論だけである。** 各記述は「〜とする」の形で書く。
  「〜を確認中」「〜待ち」「未確定」を本文に残さない。
- **区分（A/B/C）・出所等級・Q 番号は「出所」欄または冒頭 1 行のポインタに置く。**
  状態（「B 承認待ち」など）を本文の各所へ散らさない。**状態は状態ファイル
  （`docs/00_plan/coach/<module>/nNN.yml` の `open_questions`）と確認票が持つ。**
  成果物と状態ファイルで二重管理しない（NFR-1）。
- **演習（`case_kind: tutorial`）では、A／B が仮想答案である旨を文書冒頭の 1 行に置く。**
  各節で繰り返さない。
- **なぜか**：承認版に未確定が残ると、下流（製造・テスト）はどれが確定値かを判断できない。
  **承認とは「ここに書いてあるとおりに作ってよい」という宣言**であり、未確定を含む文書はその対象にならない。
- **実例（2026-10-21）**：R60Login 節点2 の承認版は §8 に 19＋7＋5＋11＝42 行の未確定・裁定一覧を持ち、
  本文の各節と二重になっていた。**上流 1 件の変更（CR-203）で節点1 と節点2 の両方を直す必要が生じた。**
  §8 を廃止し、結論を各節へ、追跡を冒頭 1 行へ移した（`05_承認版_基本设计书.md` v1.0.3）。

### 6.2 上流は下流に透明である（結論は使用箇所に書く・追跡は 1 行）

**Summary**: 下流成果物は上流の**確認票を写さない**。上流の結論を**使う場所に結論として書き**、
追跡は**冒頭 1 行のポインタ**で上流の単一ソースを指す。層をまたいで同じ表を持たない。

- **ISO 参照モデルと同じ考え方**：各層は隣接層の**インターフェース（結論）**だけを見る。
  上流の内部事情（未確定だった経緯・裁定の争点・確認票の行）を下流へ透過させない。
- **書くこと**：使う場所に結論（例「暗号化は〜とする」）。
  **書かないこと**：上流の Q 一覧の転記、上流の未確定事項、裁定の経緯。
- **追跡は 1 行で足りる**：
  `本設計の入力は節点1 承認版 <path>（vX.Y.Z）。業務ルールの出所は同 §11.2・§12、詳細は 02_確認事項一覧.md。`
  これで紅线⑤（`req_ids`）の追跡は閉じる。
- **上流の結論が変わったとき**は、下流の**使用箇所だけ**を直す（転記表を持たないため、直す場所が 1 箇所で済む）。
- **適用範囲**：節点 2〜8 の承認版すべて。**節点 1 の `02_確認事項一覧.md` は確認票そのものであり、
  本節の対象外**である（A／B／C・出所等級・状態を持つのは正しい——§4 を参照）。
- **機械判定はしない**（6 道の門番は不変）。本節は人読文案の層で守る。
- 出所：2026-10-21 ユーザー指示「**节点1对于节点2来说应该是透明的、类似与ISO七层模型**」
  「**最后生成的基本设计书不能有一堆待确认事项的细节**」。

### 6.3 変更は上流から下流へ（コード先行変更の禁止）

**Summary**: 承認済み設計（`baselined`）に依拠して作られたコード・テストは、
**設計を直さずに直してはならない**。変更は必ず上流（機読源）から入れ、下流をそれに合わせて作り直す。

- **順序は一方向**：設計（`.md` / `.yaml`）→ コード → テスト → 追跡。**コードを先に直して設計を後から合わせる**のは
  紅线②の逆向きであり、`design_ids` / `req_ids` の閉ループが切れる（紅线⑤）。
- **変更の入口は 1 つ**：`CR-xxx`（要求・設計の変更）または `BUG-xxx`（不具合）。n09 旁路環で起票し、
  **戻す起点ノードは人が裁定する**。`tools.impact <ID>` が出すのは影響の候補と規模であり、承認ではない。
- **凍結は「無記録の変更」を禁じるものであり、変更そのものを禁じるものではない。**
  「承認済みだから触らない」も誤りである——設計が古いままコードだけ進むと、追跡は通るのに内容が食い違う。
  `trace_check` は ID と字段しか見ないため、この食い違いは機械では捕まらない。
- **適用範囲**：`baselined` 以降の全成果物。承認前（`draft` / `open`）の改訂は自由であり、むしろ安い。
- **機械判定はしない**（門番は 6 道のまま）。本条は人のレビューで守る。
- 出所：2026-10-22 ユーザーの問い「**在编码之前生成的设计书和其他开发文档都不能随便更改、因为代码是根据设计书写的、不能来回改**」。
  骨子は同意し、**「変更禁止」ではなく「無記録の変更の禁止」**として条文化した（判断の根拠は §6 状態機と §6.1）。

## 7. void 作废標記の使用時機（番号再利用禁止）
**Summary**: 発号済みの ID が**不要・誤発号・設計撤廃**となった場合、番号を消す/再利用せず `void` を付けて履歴に残す。
- **使用時機**（限定的に）:
  1. 誤って払い出した ID（誤字・重複起案）。
  2. ベースライン前に要求自体が撤廃された。
  3. `CR-xxx` により既存 ID を論理削除し、別体系へ移行した。
- **禁止**: `void` となった番号の再利用（例: `BUG-001` を void にした後に別の不具合へ `BUG-001` を再割当てすることは禁止）。
- 記録形式（`ids.yml` 内）:
```yaml
BUG-001:
  status: void
  name: "無効バグレポート（void 記録例）"
  description: "void 作废标记の記入例。番号は再利用しない。"
  used_by: docs/00_registry/ids.yml
```
- `void` 以外の終端は `done`。`void` と `done` の混同禁止（完了と作废は別概念）。

## 8. 各工程の Claude Code 作業 × 人レビュー分担（RACI 詳細）
**Summary**: 工程ごとに「Claude Code が担う作業」と「人が是認すべき点」を分離し、Claude Code 単独で工程を閉じない。
1. **要件理解**: Claude Code=要求の構造化・R/Q 起案。人=要求妥当性・優先度(A/B/C)の決定。
2. **基本設計**: Claude Code=F/I 払出し・画面項目表。人=画面機能切れ目・例外系の承認。
3. **詳細設計**: Claude Code=L/E 払出し・SQL/エラー・境界値表。人=排他/被参照/重複の妥当性。
4. **框架構築**: Claude Code=選型記録・共通部品(R60Common/r60util)マッピング。人=技術選型の承認。
5. **製造**: Claude Code=設計→コード（R60Common 改変禁止）。人=コードレビュー・SKILL 遵守確認。
6. **単体テスト**: Claude Code=TC 観点設計(同値/境界/決定表)。人=合否判定・カバレッジ判定。
7. **結合総合テスト**: Claude Code=API シーケンス設計（`migration` は新旧 A/B 比較を含む）。人=e2e 合否・非機能確認。

## 9. 上流欄位の移送検査（節点 2・3 で必須・**第 7 の門ではない**）

**Summary**: 上流成果物の**表の 1 行・1 欄**が下流成果物に移送されたかを、**Q 欄に限らず**逐条で突き合わせる。
R60Login 節点2 の対比で、**`A2`（上流にあるのに読めていない）3 件がすべて「非 Q 欄」に落ちた**
（`reports/drill/R60Login/comparison.md` 節点2）。審査 #4 は Q-201〜219 しか見ておらず、
#3 は項目数を数えるだけ、出口門番は 1 語を `grep` するだけだった。

### 9.1 何を突き合わせるか
- **上流の表の各行・各欄**（例：承認版 §1 の各行、§11.3 の各条、§4 の各項目）を 1 単位とする。
- 落ちやすいのは**値そのものではなく、値に付いた限定と形**である。重点的に見る 4 種：
  1. **限定句**（「〜のみ」「〜に限る」「〜を除く」など、適用範囲を狭める語）
  2. **内部値・符号系**（画面に出す `Y`/`N` と内部の `1`/`0` が別、など）
  3. **形状**（URL のパス形・固定部分・桁数・区切り）
  4. **否定・例外**（「〜しない」「〜のときは除く」）
- **Q 欄（未確定事項）は対象の一部にすぎない。** Q に挙がっていない行ほど落ちやすい。

### 9.2 どこでやるか
| 節 | 何をするか |
|---|---|
| 入力側（節点 2 ステップ 1） | `01_输入_已填写.yaml` に **「上流欄位」槽**を置き、上流表の行を**そのまま写す**（要約しない） |
| 出口側（節点 2・3 の審査） | 上流の各行について「下流のどこに現れたか」を**節・行番号で**答える。答えられない行は**未移送**として列挙する |
| 検査の補助 | `grep -n "キーワード" <下流ファイル>` を**証拠として添える**。ただし **grep は補助であり判定ではない**——言い換えられた限定句は grep で捕まらない |

### 9.3 守ること
- **機械化できるのは「語が在るか」までである。**「意味が移送されたか」は人が読む。
  **grep 0 件＝未移送、とは書かない**（言い換えを未移送と誤判定する）。逆も同じ。
- **これは門番ではない。** `tools.trace_check` の 6 道は不変で、`stats.gates_run` は 6 のまま
  （`ppt-deviation-register.md` **A-28**）。節点の審査チェックリスト項目として実行する。
- **未移送を見つけたとき、下流の成果物を勝手に直さない。** 一覧にして人へ出す（紅线③）。
  上流自体が欠けている場合は **`R`（要求書缺陷）** として環 n09 へ回す（§10 の実例を参照）。

## 10. 機械判定の記録精度（**結論ではなく「命令＋実出力」を書く**）

**Summary**: 節点成果物・審査記録に「全文 0 处」「PASS」「一致」と**結論だけ**を書いてはならない。
**実行した命令と、その実際の出力**を併記する。結論だけの記録は、**後から検算できない**。

- **書き方**：`grep -nE "Vue|FastAPI|Oracle" <file>` → `0 行`（実出力）／`19 行`
- **書いてはならない**：「全文 0 处確認済み」「問題なし」「一致を確認した」
- **理由（実測）**：R60Login 節点2 の審査 #10 は「全文 0 处」と記録したが、**判定対象は初稿**
  であり、後に作られた `05` には同じ語を含む**否定文が 1 行**あった
  （「Vue3／FastAPI／Oracle の断定は本文に無い」）。記録が「全文」と書いたために、
  **どのファイルを・いつ・どう測ったのか**が読み取れず、検算に手間がかかった。
- **禁字 grep を門番にする場合の注意**：上のような**否定文が誤報になる**。
  機械判定を入れるなら、**否定文を除外する条件**を同時に定義するか、対象文を言い換える。
- **門番は 6 道のまま**（`ppt-deviation-register.md` **A-29**）。本条は記録の書き方の規約である。
