# テスト設計規則（TC 分類 / design_ids / 双方向閉ループ / 観点 / AB_Reports）

## 1. 適用範囲
**Summary**: 単体テスト（工程 06）と結合総合テスト（工程 07）における、TC（テストケース）の作り方・追溯の張り方・観点設計・健康度記録の固定規則を規定する。TC は唯一発号口 `docs/00_registry/ids.yml` で `TC-xxx` を払い出し、`trace_check --strict` の双方向閉ループ検証を必ず通す。
- 参照: 落地篇 PPT S13（テスト観点）/ S23（テスト認定）/ spec.md NFR-3 / AC-2

---

## 2. TC 分類比例 最低標準（正常 3 / 境界 2 / 異常 3）
**Summary**: 1 つの R-ID（または 1 機能 F-ID）に対する TC は、**正常 3 件 + 境界 2 件 + 異常 3 件 = 最低 8 件**を下限とする。比例を下回る場合はテスト設計未完了とみなす。
| 分類 | 最低件数 | 意図 | 例（R-101 参考） |
|------|----------|------|------------------|
| 正常 | 3 | 主要業務フローの正常系 | TC-001 通常検索 / TC-002 新規登録 / TC-003 既存修正 |
| 境界 | 2 | 桁数・件数・境界値ちょうど | TC-004 検索 0 件 / TC-005 KSN_DAT 不一致（排他） |
| 異常 | 3 | エラー系・制約違反 | TC-006 重複キー登録 / TC-007 被参照 DEL_FLG=1 削除 / TC-008 ロケーション未登録 |

- 実績値の検証式: `分類カウント == (正常, 境界, 異常) = (3, 2, 3)`（`trace_check` 相当の集計で確認）。
- 境界 TC は入出力・排他・件数上限の**ちょうど境界**を突く。同値でない「もう一歩外」は異常系へ寄せる。
- 異常 TC は対応する E-ID（エラー ID）を必ず 1 つ以上持つ。

## 3. TC front-matter 必需字段
**Summary**: 各 TC は下記の字段を必須で持つ。`trace_check` gate3 は共通 7 字段を、本規則はテスト固有字段を検査する。
```yaml
---
# 共通 7 字段（id / type / req_ids / status / sensitivity / owner / version）は §1 の通り必須。
# 以下は TC 固有の字段のみを示す。
test_id: TC-001                # 本規則が発番する TC-ID
req_ids: [R-101]
design_ids: [D-043, L-014]      # 入出力が依拠する設計 ID（§4 参照）
status: open
# ---- テスト固有字段 ----
viewpoint: 同値分割            # 同値分割 / 境界値 / デシジョンテーブル
category: 正常                 # 正常 / 境界 / 異常
preconditions: "R60Area 初期化済、cmpCd/jigCd 設定済"
input_spec: {cmpCd: "COL_1", jigCd: "COL_1", araCd: "COL_1"}
expected_output: {件数: VAL_1, 先頭行araCd: "VAL_1"}
assertion_rules: "検索件数一致・並び順 JIG_HYJ_SEQ 昇順"
---
```
| 字段 | 必須 | 説明 |
|------|------|------|
| `viewpoint` | ○ | テスト観点（§6 の 3 種から 1） |
| `design_ids` | ○ | 依拠する設計 ID（D/L 等）を列挙 |
| `req_ids` | ○ | 逆参照の要求 ID |
| `preconditions` | ○ | 前提条件 |
| `input_spec` | ○ | 入力値（真值は書かず占位 `COL_1`/`VAL_1`） |
| `expected_output` | ○ | 期待出力 |
| `assertion_rules` | ○ | 合否断言ルール |
| `category` | ○ | 正常 / 境界 / 異常 |

## 4. 入出力 I-ID が `design_ids` に必ず列挙されること
**Summary**: テスト対象の**入出力項目に対応する I-ID は必ず TC の `design_ids` に列挙**する。I-ID が欠落した TC は「何を検証しているか」が追溯不能となり打回。
- `design_ids` には少なくとも: 対象ロジック `L-xxx`、製造 `D-xxx`、および入出力に現れる `I-xxx` を含める。
- 例: 検索 0 件の TC は `design_ids: [D-043, L-014, I-201, I-203]` のように入出力項目 I-ID を明示。
- I-ID は 56 画面項目（R60Area）等、定義層の I-ID と一対一に対応させる。
- `design_ids` に列挙した ID は `ids.yml` に実在（野号でない）こと、かつ各 ID が親 ID へ逆引きできることを `trace_check` で検証する。

## 5. `trace_check` 双方向閉ループ 缺失禁止
**Summary**: 追溯は `R → F → I → D/L → E → TC` の**前方向**と `TC → req_ids → 設計 → 要求` の**逆方向**の両方で途切れなく閉じること。片方向でも欠落があれば `trace_check --strict` は非ゼロ終了。
- 前方向: R-101 → F-042 → I-201..256 → D-043 → L-014/L-015 → E-001..008 → TC-001..008。
- 逆方向: 各 TC の `req_ids` / `design_ids` から親を辿り R-ID に到達できること。
- **缺失禁止**: どの TC も「孤児 ID」（親も子も持たない）を生んではならない。`orphan_ids=[]` が合格条件。
- 検証コマンド: `py -3 -m tools.trace_check --strict --report reports/trace_R101.json`（`chain_complete=true`）。
- commit 前・Push 前の必実行は NFR-3 / AC-2 に基づく。

## 6. テスト観点（同値分割 / 境界値 / デシジョンテーブル）
**Summary**: 観点設計は下記 3 技法を標準とし、`viewpoint` 字段に採用技法を記録する。
| 技法 | 適用対象 | 設計手順 | 例 |
|------|----------|----------|----|
| 同値分割 | 入力値域を持つ項目 | 有効/無効の同値クラスに分割し各 1 件以上 | cmpCd の桁数クラス |
| 境界値 | 桁数・件数・上限下限 | 境界のちょうど値・±1 を選択 | jigCd split 件数 2 チェック / araCd 先頭 % 不許可 |
| デシジョンテーブル | 条件組合せ（権限・フラグ） | 条件×動作の組合せ網羅 | 自工/他工 × KGN_KBN_Y/N のボタン活性 |

- 決定表で条件が組合せ爆発する場合は、等価な組合せを縮約しつつ全動作を 1 回以上カバーする。
- 各観点は §2 の分類（正常/境界/異常）と対応付けて記録する。

## 7. AB_Reports 健康度 閾値 記録位置（`migration` 案件）
**Summary**: **A/B 比較は `migration` 案件の手法である** — 「修正前後」を比べるには、比較対象たる旧版が存在しなければならない。`migration` では A/B 比較の結果と健康度閾値を、必ず下記の**単一箇所**に記録する。他ドキュメントへの転記は参照リンクに留める（単一ソース厳守）。
```
doc/03_AI/AB_Reports/reports/<モジュール名>/summary.md
```
- 記録必須項目:
  1. 比較対象（review_before / review_after と、比較キーに用いる業務キー項目）。**キーの実項目名は案件ごとに異なるため本規則には書かず、案件側の設計成果物（F/D/L）を参照する。**
  2. 一致性判定の結果（不一致件数・不一致項目）。
  3. 健康度スコアと**閾値**（赤/黄/緑の区分と判定基準値を同ファイル内に明記）。
  4. 記録日時・対象モジュール。
- 結合総合テスト（IT-xxx）の A/B 断言リストは本ファイルのパスを参照する（値を複製しない）。
- 閾値を下回る（健康度赤/黄）場合は、`docs/90_knowledge` 側で対応方針を起案し、必要なら `CR-xxx` を起票する。

### 7.1 `greenfield` 案件の代替（A/B 比較をしない場合）
**Summary**: `greenfield` には比較対象たる旧版が存在しないため、**A/B 比較を行わない**。代わりに、**承認済みの要件（R-xxx）・基本設計（F-xxx）の受入基準を期待値とする E2E 検証**を工程 07 で設計する。
- 期待値の出所は「旧版の実測値」ではなく「**承認済みの上流成果物**」である。したがって判定は一致比較ではなく、**受入基準の充足判定**になる。
- 「修正前後」という概念が無いため、健康度スコアの閾値も既定では設けない。非機能の閾値が必要な場合は、**先に要件側へ受入基準として立ててから**使う（後付けで閾値だけを作らない）。
- 記録先は §7 と同じ「モジュールごとに 1 ファイル」の考え方に従う。ただしファイル名は `summary.md` ではなく **`verification.md`** とする（A/B 比較ではないため、A/B の慣例名を流用しない）。

## 9. 品質ゲートの写像・冪等性・生成量の統制（社内実績の取入）
**Summary**: 社内実績（Harmony / SDS2）の品質ゲートと制約をテスト工程の規約に落とす。
**出所は要件源 PPT ではない**（登録: `ppt-deviation-register.md` §2）。
原典の逐語は `tools/kb-platform/repo/company/standards/internal/harmony-5gates.md` §2・`sds2-lessons.md` §1 が唯一の定義。

### 9.1 本骨架が持つゲートは G1 相当のみである（誇張しない）
社内実績（Harmony）は 5 道ゲートを常時走らせていた。

| ゲート | 内容 | 本骨架 |
|--------|------|--------|
| G1 静的検査 | check スクリプト 11 本（`--json` で CI 接続可）| ✅ `tools/trace_check` の gate1〜gate6 が相当 |
| G2 構築 | `yarn build` 零 error（約 30 秒）| ⚪ 未実装（案件側 CI へ接続する余地を残す）|
| G3 Console | Playwright で零 error ＋ 零 warning | ⚪ 未実装 |
| G4 スモーク | 全インタラクション点を 8 秒観察 | ⚪ 未実装 |
| G5 スクリーンショット対比 | `pixelmatch` 差異率 **< 5%**（実績 3 巡で 24.7%→8.2%→3.5%）| ⚪ 未実装 |

- **本骨架は「成果物（設計書・YAML・テスト設計）の品質」を守る骨架**であり、
  「動くアプリの品質」を守る装置ではない。G2〜G5 を持たないことは欠落ではなく**役割の違い**である。
- 結合総合テスト（工程 07）で非機能（性能・同時実行・排他）を扱う場合も、
  **測定は案件側の環境に委ね、本骨架は観点と合否基準の設計まで**を担う。

### 9.2 TC 設計は冪等でなければならない
- **同じ設計入力（D/L/E）からは、何度設計し直しても同じ TC 集合が出る**こと。
  生成のたびに `TC-xxx` の番号や `design_ids` の対応が入れ替わってはならない。
- TC を追加するときは**末尾に追加**する（既存番号を振り直さない）。
  番号の振り直しは `ids.yml` の履歴と食い違い、追跡閉ループを壊す。
- **根拠（SDS2 逐語・要旨）**: 「冪等性が担保されておらず、同じ指示でも同様のテストコードが生成されるとは限らず、
  一貫性の保証が難しい」。

### 9.3 テストコードの生成量を統制する
- 順序を固定する: **① TC 設計（`.yaml`）を確定 → ② 人が承認 → ③ テストコードを生成**。
  設計が固まる前にコード生成へ進むと、生成し直しのコストが積み上がる。
- **根拠（SDS2 逐語・要旨）**: 1 機能分のテストコード生成で
  「Copilot Business アカウント」の**月額上限の半分相当**を消費した実績がある。
- 生成が失敗した場合、**同じプロンプトを再投入しない**。入力を分割するか、
  参照ソース（類似の既存テスト）を明示してから再実行する。

### 9.4 合否判定は必ず人が行う（红线③）
- テストの合否は AI が宣言しない。**人の識別子**を `approved_by` に記録して初めて `approved` になる。
- **根拠（SDS2 逐語・要旨）**: AI 分担率が高い作業（ソースコードレビュー 70% 等）であっても、
  「最終的には人の目による再確認（ダブルチェック）が必要」と原典自身が明記している。
  「AI が 70% 分担する」は「人の確認を 70% 省ける」ではない。

### 9.5 §8 チェックリストへの追加 3 項
- [ ] TC を再設計しても番号・対応が入れ替わらない（§9.2）
- [ ] TC 設計の確定と人の承認を経てからテストコードを生成した（§9.3）
- [ ] 合否判定を人が行い、`approved_by` に人の識別子が入っている（§9.4）
