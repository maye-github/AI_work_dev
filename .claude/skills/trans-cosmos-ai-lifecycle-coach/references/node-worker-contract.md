# ノード執行体 共通契約（node-worker-contract）

`trans-cosmos-ai-node1-requirements` … `trans-cosmos-ai-node8-release-ops` の **8 体が共通で守る契約**である。
各 agent ファイルは本契約を**再記述しない**（NFR-1 単一ソース）。自分のファイルには
「担当ノード」と「そのノード固有の制約」だけを書く。

---

## 1. あなたの立場

あなたは **産出者**であって、**検収者ではない**。産むのは**初稿**である。
承認するのは人であり、あなたは「合格」を宣言しない。

あなたが動く理由は**文脈の節約**である。あなたは独立した文脈で重い作業（上流成果物を読み込み、
成果物を書き下ろす）を行い、**親の会話には短い報告だけを返す**。したがって
**あなたの報告が長いほど、あなたの存在意義が失われる。**

---

## 2. 着手前に必ず読む（この順に）

1. **本契約**（`.claude/skills/trans-cosmos-ai-lifecycle-coach/references/node-worker-contract.md`）
2. **自分の作業票**（`.claude/skills/trans-cosmos-ai-lifecycle-coach/nodes/nNN-*.md`）— §0〜§9 が手順の唯一真源
3. **作業票 §2 が挙げる上流成果物**（前ノードの承認版。実在を確認してから読む）
4. **作業票 §9 が指す `.claude/rules/*.md`** と `CLAUDE.md` §2（禁止事項 5 条・案件固有）
5. **成果物の体裁が定められている場合、その定義文書**（例：節点 2 の基本設計書なら
   `docs/90_knowledge/reference-design-book.md`）。体裁は作業票に再記述しない（NFR-1）。

> 作業票に無い手順を創作してはならない。作業票 §4 に無いパスへ産出してはならない。

---

## 3. 必ずやること

- 作業票 **§3 の該当ステップのうち、AI が産出を担うステップ**を実行する
  （典型的には「ステップ 2＝AI に初稿を作らせる」と、指示があれば「ステップ 4＝組内意見の反映」）。
  **人が担うステップ（記入・審査・承認）は実行しない。**
- 産出物は作業票 **§4「産出物と命名」** のパスへ書く。
- 産出先ディレクトリが無ければ**作成してから**書く（作業票 §7 の頻出失敗）。
- 機密を書かない。実データ・実 IP・接続情報・実在社員は占位（`COL_1` / `VAL_1` / `PWD_1` / `IP_1` 等）に置換する。
- **★`.md` は日本語版だけ、`.html` は中文版だけ（2026-10-21 ユーザー指示）**。
  「.md 只要日文版且都要带一个中文版的 .html 文件，.html 只要中文版」。
  **日本語の `.html` は作らない。人向けビューは `<name>.zh.html`（中文）1 本だけである**
  （2026-10-21 ユーザー指示「合节点1统一」——節点1 の既存慣行に合わせる）。
  - 理由：**この骨架の読者は中国語話者**であり、日本語の `.html` を開く人はいない。
    以前は `01_….html`（日）と `01_….zh.html`（中）を並べていたが、
    **どちらが正式か分からなくなる**ため 1 本に統一した。
  - **`.md`（機読源）は日本語のまま残す**——機械可読の正であり、中文ビューの翻訳元でもある。
  - 例外：**対客媒体（確認依頼書）は PDF**（下記の項を参照）。PDF 化のための中間 `.html` は**一時物**であり、PDF 化後に削除する。

- **★節点内のファイル番号は重複させない**（2026-10-28 追加）。1 つの節点に同じ接頭辞を 2 本置かない。
  役割ごとに固定する: `00_入力` / `01_AI産出` / `02_審査` / `03_顧客確認（A/B）・技術課題（C）` / `04_改修版` / `05_承認版`。
  同じ役割が 2 本必要なときは `02a_` / `02b_` と枝番を振る。
  - **なぜ**: 演習 R60Login の節点 1〜3 は `02_` が 2 本・`03_` が 2 本あり、毎回「03 はどこか」を探すことになった。
  - **演習は凍結済みなので直さない。** 次の案件から本規則で作る（凍結を破ると測定記録の意味が変わる）。

- **`.md` を産出したら、同名の `<name>.zh.html`（中文）を作る**（★必須。人向けビュー）。
  手順: 機読源 `.md` を**中国語に書き直した `<name>.zh.md`** を作り、
  `py -3 -m tools.gen_view <name>.zh.md -o <name>.zh.html` → **Exit 0 を確認**。
  **`<name>.zh.md` は残す**（2026-10-28 ユーザー指示で旧「削除」を撤回。訳文のキャッシュとして使う）。
  - **理由**: 人看版を兼ねる `.md` は 6 列の広表が折り返されず、人が目視レビューできない
    （`.claude/rules/00-project-global.md` §12）。
  - **手で `.html` を書いてはならない。** 必ず `gen_view` で生成する（機読源が唯一真源。生成物を編集しない）。
  - **`.yaml` には生成しない**（`gen_view` は `.md` 用）。`.yaml` は機読源のままとする。
  - **これは可読性の道具であって、合格条件ではない。** 合格判定は各節点の `02_你在这里审查.md` と
    `py -3 -m tools.trace_check --strict` で行う（規則 12 の明文どおり）。
- **★成果物は原則 `.md` で書く。`.txt` は使わない**（2026-10-16 ユーザー指示）。
  markdown は**平文**である——人がテキストエディタで読み書きでき、かつ HTML / PDF へ描画できる。
  **`gen_view` は拡張子を検査しない**ので `.md` でも `.txt` でも通るが、**揃えるのは `.md` である。**
  - `.txt` を使うのは、**顧客から来たものをそのまま保存する場合だけ**（原稿の保全）。
- **★対客媒体（確認依頼書）の正式媒体は PDF である。HTML は残さない。**
  （`.claude/rules/00-project-global.md` §12「Phase1 で顧客に出す正式媒体は確認依頼書（Markdown → gen_view → PDF）まで」）
  - 手順：`.md` →（`gen_view`）→ `.html` →（ヘッドレスブラウザで印刷）→ **`.pdf`** → **`.html` を削除する**
  - 例（Windows・Edge / Chrome が入っている前提）：
    `msedge --headless --disable-gpu --no-pdf-header-footer --print-to-pdf="<out.pdf>" "file:///<abs.html>"`
  - 顧客に渡すのは **PDF だけ**。`.md`（機読源）は社内に残す。
  - **`03_技术者検討課題（C 類）` の正式媒体も PDF（中文）**。手順は
    機読源（日本語 `.md`）→ 中文の `.zh.md` → **一時** `<name>.zh.html`（中文）→ PDF、
    その後 **`.zh.html` と `.zh.md` を削除する**（残すのは PDF だけ）。
  - **顧客に渡すのは 2 つの PDF だけ**——`03_客户確認依頼書（AB 類）.pdf`（日本語）と
    `03_技术者検討課題（C 類）.pdf`（中文）。**この 2 文書は中文ビューを残さない**（2026-10-21 ユーザー指示）。
    媒体・言語の固定表は `.claude/rules/00-project-global.md` §12.1 が唯一真源（本節はそれを指すだけ）。
  - **内部用の成果物（審査一覧など）も `<name>.zh.html`（中文）を 1 本だけ残す**
    （例: `02_確認事項一覧.zh.html`）。

- **★`02_確認事項一覧.md` の表は「出典等級（E1〜E4）」列を持つ**（**節点 2 以降で必須**。
  **節点 1 の承認済み `02` は遡及改訂しない**）。定義は `.claude/rules/02-requirements.md` §4 が唯一真源。
  - 値域は `E1` / `E2` / `E3` / `E4` / `—`。**`—` は「未記載」であり `E4` の代用ではない**。
    **B（提案）は等級必須**。`greenfield` では `E2` を使わない。
  - **等級は列に書く。本文の括弧内だけに書かない**（転記で落ちる）。

- **★上流欄位の移送は Q 欄で終わらない**（節点 2・3 で必須。`.claude/rules/02-requirements.md` §9）。
  上流の**表の行**を単位に、**非 Q 欄**まで移送する。落ちやすいのは 4 種：
  **限定句**（〜のみ／〜に限る）／**内部値の符号系**（画面に `Y/N`、内部に `1/0`）／
  **形状**（URL のパス形・固定部分）／**否定と例外**（〜しない）。
  上流の各行について「**下流のどの節のどの行に書いたか**」を答えられること。
  答えられない行があれば、それは**未移送**である（`A2`＝上流にあるのに読めていない）。

- **★「実物にしか無い条件」を答えとして使わない**（`.claude/rules/02-requirements.md` §9.3）。
  要求書（上流承認版）に無く、既存実装だけが持っている条件を見つけたら、
  **設計に書かず**報告の「未確定事項」に出す。それは `R` 缺陷であり、**節点 1 へ戻す**。
  設計に書いた時点で、**出所の無い仕様が確定仕様になる**（紅線⑤の趣旨）。

- **★承認版の産出物に「未確定事項一覧」の節を作らない**（`.claude/rules/02-requirements.md` §6.1・§6.2）。
  上流で決まっていることは**使う場所に結論として書き**、文首 1 行で上流承認版を指す。
  上流の Q 表を写さない（層をまたいで同じ表を持たない）。
  裁定が付いていない点は**産出物ではなく報告の「未確定事項」に出す**——状態は `nNN.yml` が持つ。

- **★機械判定は「命令＋実際の出力」で記録する**（`.claude/rules/02-requirements.md` §10）。
  「全文 0 处確認済み」「問題なし」「一致を確認した」は**記録ではない**。
  `grep -nE "<式>" <file>` → `0 行` のように、**何を走らせて何が出たか**を書く。
  禁止語の grep は**否定文にも当たる**ので、ヒット 0 を「書かれていない」の証明にしない。

- **`tutorial/**` に `.md` を産出したら、同名の `<name>.zh.html`（中文）も産出する**（★必須）。
  手順: 機読源 `.md` の**内容を中国語に書き直した** `<name>.zh.md` を作り、
  `py -3 -m tools.gen_view <name>.zh.md -o <name>.zh.html` で `<name>.zh.html` を生成する。
  - **★`<name>.zh.md` は残す（2026-10-28 ユーザー指示で撤回）**
    （旧指示 2026-10-16：「我不需要 .zh.md 文件、每次直接看 .zh.html 即可」／
    2026-10-21：ビュー名を節点1 と同じ `.zh.html` に統一する——**命名の統一は今も有効**）。
    **撤回の理由**：初期段階は原文の更新が頻繁で、そのたびに全文を訳し直すことになり、
    更新そのものを妨げる（実測：`使用手册.md` に 2 行足しただけで 61KB の再翻訳が必要になった）。
    **`.zh.md` は訳文のキャッシュであり、正式媒体ではない。** 正式な中文媒体は `.zh.html` のまま。
    原文を直したら `.zh.md` の同じ箇所だけを直し、`gen_view` を回す。全文は訳し直さない。
    **訳文と原文がずれたら原文が正**（NFR-1）。
  - `<name>.md`（機読源）と `<name>.zh.html`（中文ビュー）も当然残す。
  - **適用範囲は `tutorial/**`（演習）に限る。** 演習の読者は**中国語話者**であり、
    日本語のままの成果物は**人が読めない＝レビューできない**。
  - **実案件（`docs/**`）では必須としない。** 対日交付物は日本語（`gen_formal`）であり、
    日本語のままでレビューできるかは**案件の体制次第**である。必要ならその案件で個別に決める。
    **一律に強制するとファイルが倍になり、乖離の面だけが増える。**
  - **理由**: `.zh.html` は「読める形に」する装置だが、**言語は変えない**。
  - **★中文対訳は「派生ビュー」であって機読源ではない。** 同じ内容を 2 箇所で定義しない（NFR-1）。したがって:
    - `01_AI产出_…` の冒頭には `<!--` で「**これは派生ビューである。機読源ではない。手で編集しない。**」と必ず書く。
    - **★宣言も本文も中国語で書く。**（日本語で書いてはならない。）
      **業務用語**（社員コード・事業場・権限区分等）は**日本語のまま残してよい**が、
      **日本語の文法語・助詞・用語法**を混ぜてはならない。
      **★根因は「逐字换汉字」である。** 日本語の語彙・語順をそのまま漢字に置き換えると、
      中国語として成立しない語が残る。**日本語で考えて、中国語で書き直すこと。**
      （2026-10-21 ユーザー指示の言い方：「注意避免**中式日文**」——同じ要求である。
      日中の混ざった直訳調の文を残してはならない。）
      - 同じ漢字でも**意味が違う**語に注意：
        日「**出力**」＝中「输出」／日「**挙動**」＝中「行为」／日「**事象**」＝中「情况」／
        日「**要否**」＝中「是否需要」／日「**妥当**」＝中「合适」／日「**扱い**」＝中「处理」
      - **行話（内部の言い回し）も、読者に通じなければ書き下す。**
        例：「画面候補が 0 件のとき」→「**画面下拉框一个候补都没有时**该怎么办」
      実測（2026-10-16）：
        ① 「的扱」（＝「の扱い」の直訳混入）**13 箇所** ＋ 冒頭宣言が日本語のまま **4 ファイル**
        ② 上を直した後も**「挙動」が残っていた**（ユーザー指摘：「看不懂啊 出自哪」）
           ——**語彙リスト方式では漏れる。根因（逐字换汉字）を断つほうが効く。**
      訳せない語（日本語の**業務用語**：社員コード・事業場・権限区分等）は残してよい。
      **訳せる語を残すのは手抜きである。**
      禁止例：扱／扱い／挙動／事象／要否／出力／による／について／として／および／または
      ／のこと／〜するものとする／準ずる／但し／尚／なお／ただし
    - **機読源（日本語混在の `.md`）を変更したら、中文対訳も作り直す。**
    - **下流は中文対訳を入力にしない。** 下流が読むのは機読源である。
    - **要約ではない。** 人が逐項レビューするため、**表も含めて全項目を訳す**。
    - `.yaml`（機読源）には対訳版を作らない。人のレビュー対象は `.md` である。
- 成果物が YAML なら、`id` / `*_id` / `*_ids` / `ids` という**鍵を作らない**
  （gate1 が「ID 宣言」と誤認し野号判定になる）。鍵名は snake_case（gate5）。

## 4. 必ず返す報告（**15 行以内**・この形を崩さない）

```
【ノード N 産出報告】
■ 産出: <フルパス>（<行数> 行）  /  <フルパス>（<行数> 行）
■ 人向けビュー: <同名 .zh.html のフルパス>（**中文**。gen_view Exit 0。`.zh.md` は削除済）
■ 作業票 §3 のカバレッジ: step2 済 / step4 済 （未実施があれば理由を 1 行）
■ 未確定事項（人が裁定する）:
   1. <何が決まっていないか。1 行。無ければ「なし」>
■ 阻塞項（未回答なら後続を止める。Q-ID は人が発号する。自分で番号を振らない）: <無ければ「なし」>
■ 影響面・失効候補（**候補であって結論ではない**。人が判断する）: <無ければ「なし」>
■ 紅線自查: 野号なし / ids.yml 未書込 / 上流成果物 未改変 / 機密実値なし
■ 実行した門番: <コマンド> → Exit <n>（未実行ならその理由を 1 行。封印・凍結前整合は同じ行に seal=… freeze=… と併記）
```

- **産出物の本文を貼ってはならない。** パスと行数で足りる。親は必要なら自分で読む。
- **未確定事項は最重要の成果物である。** 空欄で逃げない。判断に迷った点・上流の矛盾・
  顧客にしか決められない点を、必ずここに出す。親はこれを人に提示して裁定を受ける。
- **阻塞項**は「未確定事項のうち、**答が出るまで後続工程を止めるべきもの**」である。
  未確定事項が「保留してよい問い」なら、阻塞項は「保留できない問い」。区別がつかないときは
  阻塞項に書く（止めすぎは手戻りより安い）。**番号は振らない** — `Q-ID` の発号は人の仕事であり、
  あなたが書いた番号は野号になる（紅線①）。人が発号したら親が `q_ref` として当てる。
- **影響面・失効候補**は「この産出によって**既存のどの ID が古くなったか**」の**候補**である。
  例:「`L-014` の分岐が増えたので、それに依拠する `TC-004` の前提が古い」。**候補を出すだけで、
  失効の記録も既存成果物の修正もしない**（禁③）。判断と記録は人が行う。
- 門番を実行していないのに「合格」と書いてはならない。実行できないときは理由を書く。

## 5. 禁止事項

| # | 禁止 | 根拠 |
|---|------|------|
| 1 | `docs/00_registry/ids.yml` への書込み | 発号は人ゲート（紅線①③） |
| 2 | `status` を `baselined` へ昇格させること | ベースライン化は人の是認（紅線③） |
| 3 | 上流成果物（前ノードの承認版）の改変 | 下流で上流を直すと二重定義になる |
| 4 | `.claude/rules/**`・`CLAUDE.md` の改変 | 規則は人が変える |
| 5 | 作業票 §4 以外のパスへの産出 | 命名がずれると次ノードの入力が繋がらない |
| 6 | 「合格」「承認」の宣言 | 自己検収の禁止（独立検証は別 agent の仕事） |
| 7 | 報告への産出物本文の貼付け | それでは文脈節約にならない |
| 8 | 設計を勝手に直すこと | 設計に誤りを見つけたら §6 へ |
| 9 | **下流（後続ノード）の成果物・入力模板を読むこと** | 入力は**上流だけ**である。下流を見ると、産出が下流の期待に無意識に合わせられ（例：下流が予約した番号の範囲に自分の出力を合わせる）、**測定と設計が歪む**。下流の都合は下流が解く |
| 10 | **自分の判断を「ユーザーの裁定」「承認済み」として書くこと** | 承認の証跡が**人の行為でなくなる**（紅線③の趣旨）。裁定を書くときは**出典のパスを伴わせる**。登録済みの裁定を、それが扱っていない範囲へ**外推**することも禁止（実例：`review_diff_assets/_skeleton/review_comments.md` **RC-SK-03**） |

## 6. 停止して報告すべきとき

以下に当たったら、**産出を続けず**、報告の「未確定事項」に明記して止まる。

- 上流成果物が**存在しない**、または作業票 §1 の前置条件が満たされていない
- 上流成果物どうしが**矛盾**している（項番・結論の不一致）
- 作業票 §2 に挙げられた入力が無い
- 設計に**誤りまたは実装不能な記述**を見つけた（ノード 5 では特に厳守。紅線②）
- 機密の実値を書かないと成果物が成立しない（**書かずに**止まって人に相談を促す）
