# 要求書審査スキル（要求書から「確認すべき点」を立てる）

> **このファイルと `references/lenses.md` を読めばよい。** 本ファイルが手順の唯一真源、
> `references/lenses.md` が観点（レンズ）の唯一真源。

---

## 0. 立場

### 0.1 何をするか（1 文）

**顧客の要求書を読み、①内部矛盾 ②記述の穴 ③業務上の暗黙の前提 ④実装に降りるときに効く論点
——を、根拠つきで列挙する。**

### 0.2 何をしないか

| しないこと | 誰の仕事か |
|---|---|
| 要求書を書き換える | 顧客と我々（受控回流。規則 00 §11） |
| Q-ID を振る | 人（`tools.registry`。紅線①） |
| 質問に回答する | 顧客（または裁定する人） |
| 「問題がある／ない」を**断定する** | 人。本スキルは**候補と根拠**まで |
| 案件の合否判定 | 人（紅線③） |

### 0.3 姉妹スキルとの関係（取り違えやすい）

| スキル | 役割 |
|---|---|
| **本スキル** | 要求書を**読んで問いを立てる**。**真の案件でも使う**（顧客が要求書をくれる） |
| `virtual-requirement-author` | **顧客も要求書も無いとき**に、履歴案件の資産から**要求書を仮に作る**（＝訓練用の代替入力）。**本スキルの代わりではない** |

> **ユーザーの言葉（2026-10-15）**：「虚拟需求书那个技能**只是因为临时没有真实项目和客户能给新的项目设计书**、
> 所以让你先帮我虚拟出来一个」。すなわち**本スキルの方が本質**であり、
> 仮想需求書スキルはその入力を用意するための**暫定の手段**である。

## 1. この技能の正体（★ここを外すと使い物にならない）

**実測（R60 案件・2026-10-16 調査）**：`D:\AI_work\doc\00_管理\【QA票】共通マスタ.xlsx`（+ `_102~`）に、
**オフショアが顧客の設計書を読んで起票した質問が 177 件**、生のまま残っていた。
別に `オンサイト修正対応一覧.xlsx`（23 件）がある。

**その 177 件を分類した結果**：

> **大多数が「設計書と現行ソースの不一致」または「設計書内の矛盾」である。**
> そして「なぜ気づいたか」は共通して——
> **① 要求書の記載を 1 項目ずつ現行実装と突合した**
> **② 同一の ID・数値・項目名を文書内で検索し、食い違いを探した**
>
> ——**個別の業務知識ではなく、この機械的突合がほとんどのレンズの起点になっている。**

**この事実が意味すること**：

- この技能は「経験者の勘」ではない。**大部分が手順化できる。**
- したがって **AI でも実行できる**。むしろ AI の方が得意な部分（網羅的な突合・全文検索・
  同一 ID の照合）が大きい。
- 「人の経験」が本当に必要なのは**第 3 段だけ**である（下記）。

---

## 2. 手順（3 段。上から順に、全て出す）

### 第 1 段　機械突合（**最も効く。全案件で必ずやる**）

| # | 何をするか | 具体のやり方 |
|---|---|---|
| 1-1 | **要求書 vs 現行実装** の逐条突合 | 要求書の「業務処理説明」「取得項目」「検索条件」「ソート順」「メッセージ ID」を 1 項目ずつ、実装と突き合わせる。**要求書に具体的に列挙されている箇所を最優先**（列挙がある＝突合できる） |
| 1-2 | **文書内の同一 ID・同一数値・同一項目名** を全文検索 | 同じメッセージ ID・同じ項目名・同じ数値が**複数箇所**に現れたら、**全部並べて食い違いを探す**（`変更履歴` と本文、`項目移送表` と `業務処理説明`、`単項目チェック` と `項目間チェック` は食い違いの宝庫） |
| 1-3 | **台帳・一覧の申告値を実測する** | 「端点 4 本」「画面 56」「項目 113」等の申告は**数え直す**。申告と実物が食い違う例は履歴案件で 3 件（全件数・端点一覧・画面数）あった |
| 1-4 | **要求書が「別途提供」「標準規約に従う」と言っているもの**を全部拾う | それは**我々が持っていない入力**である。無いと設計できない箇所と、**提供元・提供時期**を確認事項にする |

> **1-1 と 1-2 だけで、履歴案件の QA 票の過半が再現できる。**
> 逆に言えば、**この 2 つをやらずに「経験」を語っても当たらない。**

### 第 2 段　レンズを当てる

`references/lenses.md` の一覧を、要求書の記述に当てる。
**レンズは網羅的に当てる**（当てて出なかったものは出さない。無理に絞らない）。
とくに**発火条件**（「どんな記述があると当てるか」）で絞ると効率がよい。

### 第 3 段　業務の含意を想像する（**ここだけが人の経験に近い**）

レンズにも乗らない、**要求書と実装のどちらにも書かれていないが業務上効く**論点。
本スキルが列挙するのは**次の 6 つの問いの形**である：

| # | 問い | 例（R60Login の要求書） |
|---|---|---|
| 3-1 | **矛盾していないか**——別の節で別のことを言っていないか | §3.1「利用権限保持者のみ」↔ §3.4「判定は社員コードの存在だけ。権限は見ない」 |
| 3-2 | **書いてあるとおりに運用できるか**——現場の実態に合うか | 「権限区分」が初期値「更新あり」——現場は毎回選び直すのか。選び忘れると何が起きるか |
| 3-3 | **誤操作したらどうなるか** | 候補に「シミュレーション版」が混在。現場はどれを選ぶのか |
| 3-4 | **危険な状態にならないか** | 「閉じてもログイン状態は保持される」→ **共用端末で次の人がそのまま入れる** |
| 3-5 | **送っているのに使っていない項目は無いか** | `/login` は 4 パラメータを受けるが、処理で使うのは `stfCd` だけ（3 つが死んでいる） |
| 3-6 | **過去案件で同型の穴が無かったか** | `references/lenses.md` の群 3・群 4 を想起する |

> **第 3 段は「思いつきを書く」場ではない。** 出したものには**必ず根拠（要求書の該当箇所）**を付ける。
> 根拠を付けられないものは**出さない**。

## 3. 産出

**確認事項一覧**（`.md`。人が読むので `py -3 -m tools.gen_view` で `.html` も作る）。

1 項につき：

| 項目 | 内容 |
|---|---|
| 何が | 確認したい事項（1 文） |
| **なぜ気づいたか** | 当てたレンズ（`L01`・`内部矛盾` 等）と**要求書の該当箇所** |
| **根拠** | 要求書の節・行、または実装の `file:line` |
| 区分の素案 | **A／B／C**（A＝顧客が決める／B＝我方が提案し顧客が承認／C＝我方内部で決定）。**素案であり、確定は人** |
| 影響 | 決まらないと止まる工程（設計／製造／テスト） |

> **★区分の素案で最も間違えやすい点：技術選型は B である。**
> **方式・アルゴリズム・構成・ライブラリ・運用の設計**は、**顧客の業務事実ではない**。
> A に置くと **顧客には決められないことを押し付ける**ことになる。
> - **誤**：「暗号化の方式を決めてください」→ A
> - **正**：「方式は**弊方で提案します**（互換性の制約は貴社の規約に従います）」→ B
> - **境界**：その選型が**顧客の統制**（標準規約・他システムとの互換）に従うべき場合は、
>   **従うべき規約・制約の確認（A）**と、**選型の提案（B）**を**分けて**書く。
>   素案では `A` と `C` に偏りやすい。**技術の話が出たら B を疑う**。
> - 唯一真源：`.claude/rules/02-requirements.md` §4.1。

**冒頭に必ず書く**：

```
- 本一覧は「確認すべき点の候補」である。**問題の断定ではない。**
- Q-ID は振っていない（発番は人の仕事。紅線①）。
- 回答もしない（顧客または裁定する人の仕事）。
```

---

## 4. 禁止事項

1. **推測で「問題」を作らない。** レンズに当てて出たもの、または根拠を添えられるものだけ。
2. **要求書を書き換えない。** 指摘のみ。
3. **Q-ID を振らない。** 発番は `tools.registry` を人が実行する（紅線①）。
4. **回答しない。** 「たぶんこうだ」を書くと、**推測が設計に混入する**。
5. **レンズを増やしすぎない。** 観点の追加は `references/lenses.md` に対して行い、
   **実例（履歴案件の `D-NN` / QA 票項番 / `file:line`）を伴わないレンズを足さない。**
6. **実データ値を書かない**（占位を用いる。紅線⑦）。
