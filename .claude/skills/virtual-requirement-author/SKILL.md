# 仮想需求書 産出スキル（実在資産からの倒推）

> **このファイルだけ**読めばよい。手順の本体は本ファイルが唯一真源である。
> 節点の進行役は `trans-cosmos-ai-lifecycle-coach`、実在資産の読み方は `legacy-case-navigator`。
>
> **本文中の `<P-ID>` と「旧案件リポジトリのルート」は、案件ごとに読み替える。**
> - `<P-ID>`（知識庫の案件 ID。例 `P-R60-001`）と旧案件リポジトリのルート（例 `D:\AI_work`）は、
>   `docs/00_plan/coach/<module>/case.yml` と案件プロファイル
>   `docs/01_context/case-profile-<案件>.yaml` が宣言する。**本スキルには固定値として書かない**
>   （`.claude/rules/06-knowledge-flywheel.md` §8）。
> - 取入対象の範囲は `docs/00_registry/ingest-manifest.yml`（人が編集する唯一の入力）が持つ。
> - 本文に残る `R60Login` / `D:\AI_work` は**実測記録の出所**であり、**規則ではない**。

## 0. 立場

### 0.1 何をするか（1 文）

**実在の歴史案件の資産から、AI 全链路訓練の入力になる「仮想需求書」を倒推で作り、凍結する。**

### 0.2 何をしないか

| しないこと | 誰の仕事か |
|---|---|
| 基本設計・詳細設計・製造・テスト | coach と 8 体の実行体（節点 2〜8） |
| 番号を振る（`R-xxx` 等） | `tools/registry`（節点1 の実行体が発番。本スキルは**発番しない**） |
| 承認する | 人（紅線③）。本スキルは承認を代行しない |
| **「答え」を書く** | 誰の仕事でもない。**既存資産は「答案の出所」ではなく「客户要求的材料」**（A-22 逐語） |

### 0.3 なぜ必要か

対日案件では、**顧客が持っているのは動いているシステムであって、きれいな需求書ではない**ことが多い。
節点1 の実行体（`trans-cosmos-ai-node1-requirements`）は「顧客要求書」を入力に取るので、
**その入力が実在しないと全 8 節点が始まらない**。

そこで、実在資産（設計書・実装）から**要求として書き直した**仮想の需求書を作る。
これが本スキルの唯一の役割である。

> **本骨架の既定は `greenfield`**（`tools/kb-platform/repo/company/standards/ppt-deviation.md` A-22）。
> 「既存がある」＝`migration` と即断しない。`migration` は**宣言された変種**であり、
> 宣言の唯一の故郷は `docs/00_plan/coach/<module>/case.yml` の `build_mode` である。

### 0.4 これは「節点 0」である（8 工程の外側）

本スキルは **8 節点のどれでもない**。節点1 の**前**に走る準備工程である。
したがって：

- `docs/00_plan/coach/<module>/nNN.yml` を**更新しない**（節点の状態は coach の管轄）。
- 産出物は `n01.yml` の `artifacts` に**本スキルが直接書かない**。節点1 が走った時点で coach が記録する。
- 進捗は本スキル自身が会話上で数える（`k/6 步`）。

## 1. 起動したら最初に必ずやること

### 1.1 前置条件（満たさなければ始めない）

- [ ] 対象の**画面が 1 つに絞られている**（1 画面 = 1 需求書。混ざっていたら先に分ける）
- [ ] `docs/00_plan/coach/<module>/case.yml` が実在し、`build_mode` を確認した
- [ ] 実在資産の在り処を知っている（`tools/kb-platform/repo/projects/<P-ID>/00-index.md` §4）

**`build_mode: migration` だった場合**：本スキルは**そこで止めて人に確認する**。
`migration` なら既存実装が**入力**になるので、倒推ではなく「移行要件の整理」になり、**別の作業**である。
勝手に `greenfield` 前提で進めない。

### 1.2 一度に 1 ステップだけ出す

coach と同じ鉄則。**1 回の返答で 6 ステップ全部を出さない。**
人が「下一步」「好了」「继续」等と言ったら次を出す。
**語調を指定しない**（言い回しを強制してはいけない）。

**やること**：集めた事実を、**顧客要求書の形**に書き直す。**実装の言葉ではなく、顧客の言葉で書く。**

章立て（既存の実物に合わせる）：

| § | 見出し | 何を書くか |
|---|---|---|
| 1 | 背景 | なぜこの画面が要るか（業務の文脈） |
| 2 | 対象範囲 | 対象画面と API、**含まないもの**（他画面） |
| 3 | 業務要求 | 3.1 画面の役割 / 3.2 画面項目 / 3.3 イベント / 3.4〜 業務ルール |
| 4 | セキュリティ・運用 | 機密の扱い方針（**方式は書かない**。§5.2 参照） |
| 5 | 貴方にお願いする作業 | 顧客が求める作業（読む・食い違いは実装を正とする 等） |
| 6 | 弊社にお尋ねいただきたい事項 | **故意に空けた項目だけ**を列挙（§5.3） |
| 7 | 参照すべき既存資料 | 顧客が「読め」と言う資料の一覧 |

### ステップ 4／6　★人に問う（**最も汚染しやすいステップ**）

**やること**：草稿のうち、**あなた自身が決められない点**を人に出す。**2 種類しか出してはいけない**：

| 出してよい質問 | 例 |
|---|---|
| **A. 措辞・粒度** | 「この画面項目の説明は現行のままにするか、業務の言葉に書き換えるか」 |
| **B. 空白の取舍** | 「この項目は顧客に聞く形で空けておくか、要求書から落とすか」 |

**出してはいけないもの**：

- **内容そのものの回答**を求めること。例：「パスワードは 8 桁にしましょうか」→ **禁止**。
- 理由：ここで人が内容を補うと、需求書は**「実在資産から倒推したもの」ではなくなり**、
  AI 版と人版の対比という**測定の意味が消える**。測定対象が汚染される。

**人に伝えること**（そのまま使ってよい）：

> この 4 件は**顧客に確認する事項として空けたまま**にします。
> ここで答えを入れてしまうと、要求書が「実在資産からの倒推」でなくなり、後の対比が無意味になります。
> どうしても決めたい場合は、**別の項目として `【我が方の暫定前提】`** と明示して書きます（顧客の回答ではないと分かる形で）。

もし人が内容を答えてしまった場合：**要求書には書かず**、台账の該当項を `未確認` のまま残し、
`open_questions` 相当の欄に「人が内容を回答したが、測定保護のため要求書には反映していない」と記録する。

**産出**：人の裁定（会話上）。

**チェック**：
- [ ] 質問が A（措辞）と B（取舍）の**どちらか**である（C＝内容 を出していない）
- [ ] 人が内容を答えた場合、要求書に反映せず台账に記録した
- [ ] 「なぜ内容を問わないか」を人に説明した

### ステップ 6／6　凍結する

> **★凍結の前に、必ず `requirement-interrogator` skill を通すこと（飛ばしてはならない）。**
> 手順：要求書を `.claude/skills/requirement-interrogator/SKILL.md` の 3 段に当て、
> 確認事項一覧を産出させる（産出先は `reports/drill/<module>/interrogation.md`）。
>
> - **出た論点は、①要求書に書き戻す ②未確定事項として残す ③「対象外」と明記する** のいずれかに振り分ける。
>   **黙って捨てない。**
> - **これをやらないと凍結できない。** 理由：**凍結した要求書は下流の唯一の入力になる。**
>   内部矛盾が残ったまま凍結すると、**その矛盾が設計に流れ込む**（署名の無い契約を結ぶのと同じ）。
>
> **実測（R60Login・2026-10-16）**：v2.0 の要求書に審査をかけたところ **23 件**の論点が出た。
> そのうち **5 件は内部矛盾**で、**作成者（当方）が気づいていなかったもの**が 3 件含まれていた
> （`§3.4 Session に保存` ↔ `§3.9 サーバは保持しない`／「有効な社員」の定義／`/generateUrl` に稼働チェックが無い）。
> **自分で作った要求書を自分で審査すると、必ず見落とす。** だから別の文脈で走らせる。

**やること**：要求書を**凍結**し、以降**下流は実在資産を読み返さない**ことを宣言する。

> **★凍結前の三段整合チェック（sha256 を計算する前に、必ずこの 3 つを行う）**
> 下流は凍結後の要求書しか読まない。**ここで見逃した矛盾は、設計工程で初めて表面化する。**
> 実測（R60Login・2026-10-20 の対比）：節点 1 の R 類 3 件は、いずれも**この 3 つの型**だった。
>
> 1. **表 ↔ 注記**：同じイベント・端点について、**表の行と、その直後の注記が一致しているか**。
>    （実例：§4.1 の表は「イベント 2・3」と書き、直後の注記は「イベント 3 は端点を持たない」と書いていた）
> 2. **自由記述 ↔ 必須記述**：同じ対象について「貴方の提案／任意」と「必須／互換」が併存していないか。
>    併存していれば、**A の制約確認（何に合わせるべきか）と B の方式提案（どう作るか）に分解する**。
>    （実例：§4.5 は暗号化方式を任意提案とし、§3.6 は既存方式との互換を必須としていた）
> 3. **宙に浮いた参照**：`標準規約` / `別途提供` / `共通部品` / `貴社標準` など、
>    **実体・版・提供元が書かれていない参照**を洗い出し、**1 件ずつ Q に落とす**。
>    （実例：§3.8 は標準規約一式・画面マスタ・社員マスタ・共通部品 I/F を「別途提供」として外部委ねしていた）
>
> **3 つとも「読めば分かる」検査である。機械では判定できない。だから手順として固定する。**

1. `00_输入_客户需求书.md` の sha256 を計算する。

   ```bash
   py -3 -c "import hashlib,pathlib;print(hashlib.sha256(pathlib.Path(r'tutorial/<案件>/节点1_需求/00_输入_客户需求书.md').read_bytes()).hexdigest())"
   ```

2. `freeze.yaml` に記録する（§4.3）。
3. 人に宣言する：

## 5. 粒度の規則（既定＝**中等**）

### 5.1 書くもの

- **画面項目の一覧**（数と役割。桁・型は書いてよいが、内部名は書かない）
- **イベントの一覧**（数と役割。例：初期表示 / ログイン / メニュー / URL出力 / 閉じる）
- **API の概要**（端点と役割。**実装の詳細は書かない**）
- **業務ルール**（何を確認し、何を Session に残し、どんなときに遷移するか）
- **権限区分**のような区分値の**存在**（「更新あり／更新なし」がある、というレベル）
- **やってはいけないこと**（Non-Goals）

### 5.2 書かないもの

| 書かないもの | なぜ |
|---|---|
| 暗号化の**方式**・前後端の**責任分界**・鍵の管理主体 | 実装詳細。節点3（詳細設計）の領域であり、要求書に書くと設計を決めてしまう |
| **新旧の符号系が混在している**という実装上の事実 | これは**実装の観察結果**であって顧客の要求ではない。書けば「答え」を渡すことになる |
| 内部の関数名・変数名・テーブル名・SQL | 実装の言葉。顧客はこうは書かない |
| 実在の社員コード・氏名・接続情報・実データ値 | 機密（紅線⑦）。`tutorial/` は gate6 の走査対象 |
| ★**「旧システム」「現行」への参照**（「〜と同じく」「現行どおり」等） | **倒推の痕跡である。** 要求書は**前を向いた文書**であり、顧客はそんなものを読まない。**「旧システム」は当方の作業場にだけ存在する**（ユーザーの言葉・2026-10-16） |

### 5.3 故意に空ける 4 項（**文書に書かない＝列挙しない**）

| # | 類 | 事項 |
|---|---|---|
| 1 | 範囲 | **パスワード関連**（変更・有効期限・複雑性）を本画面の範囲に含めるか |
| 2 | 業務ルール | **ログイン失敗時のロック**を本画面で行うか（回数・期間・解除方法） |
| 3 | データ | **権限区分の符号系**をどちらに統一するか |
| 4 | 運用 | **Session の有効期限** |

> **★「空ける」の意味を誤らないこと。** これは「**要求書の§6 に質問として列挙する**」ではない。
> **要求書のどこにも書かず、項目として存在させない**のである。
>
> 列挙してしまうと、節点1 は**それを写すだけ**になり（「発見」ではなく「転記」）、
> 本訓練の目的である**「顧客が言っていないことを洗い出す」能力が測れない**。
> 実在の顧客要求書は、**自分が何を書いていないかを教えてはくれない。**
>
> したがって要求書の章立てに「弊社にお尋ねいただきたい事項」のような**列挙節を置かない**。
> あっても「ご不明な点はお問い合わせください」の 1 行までとする。

> **★この 4 項は「既定の候補」であって、決め打ちではない。** 段階 4 で人が次の**どちらか**を裁定する。
>
> - **空白のまま残す** — 節点1 が発見すべき缺口として残す（既定の推奨）
> - **明記して外す** — 例：「パスワード関連は本件の範囲に含まない」と §2 に対象外として書く。缺口は閉じる
>
> どちらでもよい。**重要なのは、どちらを選んだかを台帳の `human_decisions` に記録すること**（§4.2）。
> 記録が無いと、後段の対比で「**なぜこの缺口が無いのか**」を説明できなくなり、
> 「AI が発見できなかった」という**誤った帰因**を生む。

> **★注意（正直に書いておく）**：5.2 で「新旧符号混在の実情を書かない」と決めた以上、
> 節点1 は #3 を**「混在している」とは発見できない**。「符号系が未定義である」ことしか発見できない。
> これは**本スキルの粒度設定に由来する既知の制約**であり、
> **訓練報告の「需求書缺陷」に必ず記録する**（対比の担当の仕事。方法: `tools/kb-platform/repo/projects/P-R60-001/knowledge/agent-run-record.md` §5.1）。欠陥を隠さない。

### 5.4 ★完成度の基準（**これを満たさない要求書は「未完」である**）

**判定テスト（1 文）**：

> **この要求書だけを渡された設計者が、何も質問せずに基本設計を書けるか。**
> **書けないなら、足りないのは要求書であって、設計者ではない。**

**実測（R60Login・2026-10-15。3 回作り直した）**：

| 要求書の状態 | ノード1 が出した未確定事項 |
|---|---|
| 初版（画面項目とイベントだけ。用途・標準規約の条項が無い） | **26 件**（うち A＝20 件） |
| §3.8「標準規約・共通部品」を補った版 | 12 件 |
| **v2.0（用途・入力チェック・引継ぎ・API 仕様・エラー処理・「設けない」ことを明記）** | **大幅に減（人が判断を求められる項目が消えた）** |

**★この表が示すこと**：未確定事項の件数は、**AI の能力ではなく要求書の完成度を映している**。
件数が多いとき、まず疑うべきは**要求書**である。

**最低限、次を含めること**（画面 1 枚の要求書なら、この程度は要る）：

| 項目 | なぜ要るか |
|---|---|
| 画面項目の**用途** | 「項目がある」だけでは、その項目が**何に使われるか**分からない |
| **入力チェック**（必須・桁・文字種）と **NG 時の扱い** | 「7 桁」だけでは、**違反したときどうするか**が決まらない |
| **遷移と引継ぎ**（何をどこへ渡すか） | 「遷移する」だけでは、渡す値が決まらない |
| **インタフェース**：端点・請求・応答・**値の体系** | コード値を「決めていない」ままにすると、必ず Q になる |
| **エラー処理**（事象ごとの扱い） | 「区別できること」だけでは、各事象の扱いが決まらない |
| **セッション・運用**：★**「設けない」ことも明記する** | **「書いていない」と「設けない」は、設計者には区別できない。** ここが最も多い穴 |
| **標準規約・共通部品**（「弊社標準に従う」の一言） | **この 1 文で大量の問いが消える**（エラー形式・コード体系・非機能・遷移方式…） |

**線引き（何を書かないか）**は依然として §5.2 のとおり。
**「何をするか」は全部書く。書かないのは「どう実装するか」だけである。**

## 6. ★ステップ4 の鉄則（汚染防止）

**本スキルで最も壊れやすいのはここである。** 4 行にまとめる：

0. **★人に問う前に、必ず実在資産を検索する。**
   「これは顧客に聞くしかない」と思った事項の**大半は、実装の中に答えがある**。
   **実測（R60Login・2026-10-15）**：業務上の問い 9 件のうち **6 件は実装に答えがあった**
   （ログイン判定の範囲／起動区分の効果／権限区分の用途／画面ごとの権限の有無／
   閉じる時のセッション／失敗時の表示／候補 0 件時）。
   **答えが資産にあるものを人に聞くのは、人を検索代わりに使うことである。** 失礼であり、無駄である。
   → 検索して**答えが出たものは要求書へ書き戻す**。**答えが出なかったものだけ**が「本物の缺口」である。
1. **人に問うのは「措辞」と「空白の取舍」だけ。内容は問わない。**
2. **人が内容を答えたら、要求書には書かない。** 台账に `未確認` のまま残し、その旨を記録する。
3. **「AI が勝手に埋める」も同じくらい悪い。** 空白は空白のまま §6 に載せる。

理由：本スキルの産出物は**測定器の一部**である。ここで内容を注入すると、
後段の「AI 版 vs 人版」の差が**「設計力の差」ではなく「入力の差」**になり、測定が成立しない。

## 9. よくある失敗と対策

| 症状 | 原因 | 対策 |
|---|---|---|
| 要求書が**実装の説明**になっている | 実装の言葉で書いた | 「顧客はコードを読まない」と自問し、業務の言葉へ書き直す |
| 節点1 の未確定事項が**ゼロ**になる | 全部自分で埋めてしまった | §5.3 の 4 項は**必ず空ける**。埋まっていたら失敗を疑う |
| 人が内容を答えて要求書に反映してしまった | §6 の鉄則を守らなかった | 台账を `未確認` に戻し、報告に記録する |

| `migration` 案件に `greenfield` の手順を当てた | `case.yml` を確認しなかった | §1.1 に戻る。`migration` は**別の作業**である |
| 図表（画面レイアウト図）から仕様を取ろうとした | 画像は正確に読めない（規則 03 §7.3） | **人が先にテキスト化する**。図のまま進めない |
