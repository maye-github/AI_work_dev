# 知識ベース構築ガイド（公司級／案件級）

> 対日受託開発における AI 全鏈路導入のためのナレッジベース構築手順。

> 案件終了時に「昇格」により公司級知識へ育てる方式を採る。

## 0. 本ガイドの位置づけ

| 項目 | 内容 |
|---|---|
| 対象 | 対日受託開発プロジェクトの SE リーダー、品質管理担当、AI 推進担当 |

## 1. 設計の全体像

### 1.1 基本原則

**Git を唯一の真実源（source of truth）とし、ベクトル索引はいつでも再構築できる派生データとして扱う。**

これにより以下が追加実装なしで手に入る。

- 版管理・差分レビュー（Pull Request）
- 権限制御（リポジトリ／ディレクトリ単位）
- 監査ログ（コミット履歴・承認履歴）
- 索引の再構築（モデル変更時も全件再 embed するだけ）

### 1.2 二層構造

公司級と案件級は**別システムではなく、同一基盤上の 2 つのスコープ（namespace）** とする。

| 観点 | 公司級（company） | 案件級（project） |
|---|---|---|
| 目的 | 他案件でも再利用できる資産 | 案件固有の文脈・成果物 |
| 内容 | 規約・用語辞書・設計パターン・共通部品・テンプレート・実績値 | 要件・設計・テスト・議事録・ADR・案件用語 |
| 更新 | 治理されたタイミング（半期棚卸し・昇格時） | 成果物のコミットごと（即時） |
| 責任者 | KB 責任者（公司級） | 案件 KB 担当（通常 SE リーダー） |
| 品質基準 | 匿名化・汎用性・重複なし | 機密区分の正確性・網羅性 |
| 寿命 | 永続（版管理） | 案件終了後 read-only アーカイブ |

### 1.3 昇格パイプライン

```
案件級（即時取り込み・案件閉域）
      │  結案レビュー ＋ 匿名化 ＋ 抽象化 ＋ owner 承認
      ▼
公司級（治理・版管理・レビュー）
      │  検索（作用域ルーティング）
      ▼
新規案件（公司級から開始し、案件級を積み上げる）
```

> **このパイプラインが無いと公司級は空のまま。匿名化が無いと公司級は情報漏洩源になる。**

## 2. 公司級知識ベース

### 2.1 収録内容

| カテゴリ | 具体例 | 粒度 |
|---|---|---|
| 規約・標準 | コーディング規約、設計規約、レビュー観点、テスト観点カタログ | 条文単位 |
| 用語・ドメイン | 業界用語辞書、日英対訳、業務フロー類型 | 語単位 |
| 設計パターン | 画面パターン、帳票パターン、I/O 設計雛形、アーキテクチャ型 | パターン単位 |
| 資産 | 共通部品、CI 設定、成果物テンプレート（機読源＋日文正式版） | モジュール単位 |
| 実績データ | 見積実績、工数実績、品質実績（工程別） | 集計値 |

### 2.2 入庫基準（品質ゲート）

1. **匿名化済み** — 顧客名・個人名・固有業務名・金額が残っていない
2. **汎用性** — 他案件で再利用できる形に抽象化されている
3. **重複なし** — 既存資産と重複していない
4. **出典あり** — 元案件 ID を `source_project` に記録
5. **owner 承認済み** — PR レビューで承認されている

### 2.3 治理

| 項目 | 内容 |
|---|---|
| owner | `doc_type` ごとに 1 名（規約＝品質管理、パターン＝アーキテクチャ担当…） |
| 棚卸し | 半期ごと。陳腐化した記述を削除または更新 |
| 版管理 | front matter の `version` を更新し、PR で差分管理 |
| 禁止事項 | 顧客固有情報の直接投入（匿名化前の議事録など） |

> owner 不在の公司級 KB は半年で陳腐化する。必ず人を割り当てる。

## 3. 案件級知識ベース

### 3.1 収録内容

| 成果物 | 内容 |
|---|---|
| 要件 | 要件構造化シート、確認事項一覧、用語辞書 |
| 設計 | 基本設計書・詳細設計書（機読源)、項目定義、SQL 一覧 |
| テスト | テスト仕様書、テスト結果、カバレッジ |
| 判断記録 | ADR（設計判断の記録） |
| 外部入力 | 議事録・メール（**匿名化してから**投入） |

### 3.2 即時取り込み

**事後整理ではなく、生成時点で取り込む。**

成果物の二重化により AI の出力はもともと構造化ソース（Markdown/YAML＋ID）であるため、再解析なしでそのまま索引化できる。攪取パイプラインが別途対応すべきは外部入力（議事録・メール・日方発行の Excel）のみ。

### 3.3 メタデータ

`案件ID / 工程 / 文書種別 / 要件ID / 機密区分 / 版 / 作成日` を必須とする。これにより作用域ルーティングとトレーサビリティが成立する。

## 4. 実装

### 4.1 リポジトリ構成

```
kb/
├── company/                      # scope: company（最初は空でよい）
│   ├── standards/coding/general.md
│   ├── glossary/terms.yaml
│   ├── patterns/screen/list-search.md
│   └── templates/basic-design/
├── projects/
│   └── P-2026-001/               # scope: project
│       ├── README.md             # 案件概要・顧客・機密区分
│       ├── requirements/         # REQ-*.md
│       ├── design/basic/         # BS-*.md
│       ├── design/detail/        # DS-*.md
│       ├── test/                 # TC-*.md
│       ├── adr/                  # ADR-*.md
│       └── glossary/             # 案件固有用語
├── templates/                    # 成果物テンプレート
├── eval/golden.yaml              # 評価用質問集
└── .kbci/                        # 取り込みスクリプト
```

**ルール**：1 案件 = 1 ディレクトリ。案件コードは既存の採番規則（`P-YYYY-NNN`）に従う。成果物は必ずこのリポジトリに置く。

### 4.2 文書フォーマット（front matter 必須）

```yaml
---
doc_id: BS-001
scope: project
project_id: P-2026-001
phase: basic_design
doc_type: design
confidentiality: internal
req_ids: [R-101, R-102]
version: 1
owner: tanaka
lang: ja
updated: 2026-10-20
---
```

**CI lint ルール**（未記入なら merge 不可）

- `doc_id` 必須・リポジトリ内で一意
- `scope` 必須（`company` の場合 `project_id` は禁止）
- `confidentiality` 必須
- `doc_type` は固定 enum
- 本文が空でない

`doc_type` の enum：

```
requirement | design | test | meeting | adr | standard | pattern | template
```

`phase` の enum：

```
requirements | basic_design | detail_design | framework | coding | unit_test | integration_test | release
```

### 4.3 DB スキーマ

```sql
CREATE TABLE KB_DOC (
  DOC_ID       VARCHAR2(64) PRIMARY KEY,
  SCOPE        VARCHAR2(10) NOT NULL,      -- company | project
  PROJECT_ID   VARCHAR2(32),
  PHASE        VARCHAR2(32),
  DOC_TYPE     VARCHAR2(32),
  CONF_LEVEL   NUMBER(1)    NOT NULL,      -- 1=public 2=internal 3=confidential 4=client_only
  VERSION_NO   NUMBER(6),
  OWNER_ID     VARCHAR2(32),
  REPO_PATH    VARCHAR2(512),
  CONTENT_HASH VARCHAR2(64),               -- 変更なしスキップ用
  UPDATED_AT   DATE
);

CREATE TABLE KB_CHUNK (
  CHUNK_ID     VARCHAR2(64) PRIMARY KEY,
  DOC_ID       VARCHAR2(64) NOT NULL,
  SECTION_PATH VARCHAR2(512),
  ORD_NO       NUMBER(6),
  CONTENT      CLOB NOT NULL,
  EMBEDDING    VECTOR(1024, FLOAT32),      -- Oracle 23ai の場合
  UPDATED_AT   DATE
);

CREATE INDEX IX_CHUNK_DOC ON KB_CHUNK(DOC_ID);
```

**ベクトルストアの判断**

| 環境 | 選択 | 理由 |
|---|---|---|
| Oracle 23ai 以降 | `VECTOR` 型 ＋ `VECTOR_DISTANCE` | 追加ミドルウェア不要 |
| Oracle 19c 以前 | **Qdrant をサイドカーで構築** | 19c でベクトル検索を自作しない |

### 4.4 取り込みパイプライン

```
1. git diff --name-only で変更された .md を抽出
2. front matter をパース
3. doc_type ごとにチャンク分割
4. 32〜64 件ずつバッチで embed
5. doc_id 単位で DELETE → INSERT（冪等）
6. CONTENT_HASH が同じならスキップ
```

- **冪等性が必須**：`DELETE FROM KB_CHUNK WHERE DOC_ID=:doc_id` の後に挿入する。これを怠ると文書を 1 回編集するたびに chunk が重複する。
- **初回投入**は `--all` モードで全件、以後は差分のみ。

### 4.5 チャンク分割規則

| doc_type | 分割単位 | 備考 |
|---|---|---|
| standard / design（本文） | `##` / `###` 見出し | `section_path` を metadata に保持 |
| design（項目定義表） | **1 行 = 1 chunk** | 表を跨いで切らない |
| design（処理フロー） | `logic_id` 単位 | |
| test | テスト ID 単位 | |
| meeting | 議題単位 | 議題見出しを metadata に |

サイズ 500〜800 token、overlap 10%。

> 表形式の文書は最大の失敗要因。表全体を 1 chunk にすると「型が NUMBER(9,0) の項目は？」といった問い合わせに応答できない。

> **設計書 Excel は再パースしない。** 既存の `code-from-design-excel` の解析結果を Markdown に書き出してから取り込む（解析品質が揃い、二重実装を避けられる）。

### 4.6 検索

```python
@router.post("/kb/search")
def search(req, conn=Depends(get_engine_conn)):
    # 権限・作用域は SQL に下推（後置フィルタは禁止）
    where, params = build_filter(req.user, req.scopes, req.project_id)

    dense = conn.execute(text(f"""
        SELECT c.CHUNK_ID, c.DOC_ID, c.SECTION_PATH, c.CONTENT,
               1 - VECTOR_DISTANCE(c.EMBEDDING, :qv, COSINE) AS score
        FROM KB_CHUNK c JOIN KB_DOC d ON d.DOC_ID = c.DOC_ID
        WHERE {where}
        ORDER BY VECTOR_DISTANCE(c.EMBEDDING, :qv, COSINE)
        FETCH FIRST 50 ROWS ONLY
    """), {"qv": embed(req.text), **params}).fetchall()

    # dense + sparse を RRF 融合 → rerank → 引用付きで返す
    top = rerank(req.text, rrf(dense, sparse), 8)
    return [{"text": t.content, "doc_id": t.doc_id,
             "section": t.section_path} for t in top]
```

**必須 3 点**

1. **権限フィルタは SQL 内に下推** — 検索後にフィルタすると漏洩かつ recall 低下
2. **作用域ルーティング** — 型番・規約系の query → company、案件固有用語 → project、不明なら両方を重み付き統合
3. **rerank 必須** — ベクトル top50 の上位 5 件精度は概ね 60% 程度。rerank で 85% 超まで改善する

### 4.7 権限

| ルール | 内容 |
|---|---|
| 公司級 | `CONF_LEVEL <= ユーザレベル` |
| 案件級 | 上記 **かつ** `PROJECT_ID IN (ユーザの所属案件)` |
| `confidential` / `client_only` | 案件メンバーのみ |
| `client_only` | **社外提出物の生成時には引用させない**（フラグで抑制） |

### 4.8 評価（golden set）

`eval/golden.yaml` に 30 問程度。

```yaml
- q: "在庫引当で在庫不足のときのエラーコードは？"
  expect_doc: DS-001
  expect_section: "エラー処理一覧"
- q: "数値項目の最大桁数の規約は？"
  expect_doc: STD-CODING-001
```

- 指標：**recall@5 ≥ 0.85** を合格ラインとする
- 実行タイミング：チャンク戦略・埋め込みモデル・rerank を変更したとき
- 記録するログ：`query / 命中 doc / 採用可否 / 誤り報告`

> golden set の無い KB は改善できているか判断できない。構築初日から用意する。

### 4.9 技術選定

| 组件 | 推奨 | 理由 |
|---|---|---|
| 埋め込みモデル | **bge-m3** | 日/中/英 を 1 モデルで対応。dense + sparse を同時出力でき、BM25 を別途持たなくて済む |
| ベクトルストア | Oracle 23ai VECTOR / Qdrant | 数十万 chunk 規模なら上記で十分 |
| rerank | bge-reranker-v2-m3 | 多言語対応、CPU でも動作 |
| 全文検索 | bge-m3 sparse または Elasticsearch + kuromoji | **Postgres/Oracle 標準の FTS は日本語に弱い** |

> ⚠️ 日本語の全文検索を標準 FTS で実現しようとすると精度が出ない。bge-m3 の sparse ベクトルで代替するか、kuromoji 付きの検索エンジンを併用する。

## 5. 新規案件を起点とした構築手順

### STEP 0｜体制とルールを決める（キックオフ前・1 日）

| 決めること | 内容 | 成果物 |
|---|---|---|
| KB 責任者（公司級） | 昇格可否の最終判断、棚卸しの主催 | 任命 |
| 案件 KB 担当 | 案件内の取り込み・品質管理（通常 SE リーダー） | 任命 |
| **機密区分** | `1=public / 2=internal / 3=confidential / 4=client_only` の定義 | 機密区分表 |
| **KB 対象成果物一覧** | 何を入れるか。**「入れないもの」を先に決める** | 対象一覧 |
| 技術選定 | 埋め込みモデル・ベクトルストア | 選定メモ |

> 最初に決めるべきは「入れないもの」。議事録には顧客名・個人名・見積金額が混入しやすい。除外基準が無いと後で全件洗い直すことになる。

**完了条件**：責任者 2 名が決まり、機密区分表と対象一覧が文書化されている。

### STEP 1｜リポジトリとディレクトリを作る（0.5 日）

4.1 の構成を作成する。

**完了条件**：`kb/projects/P-YYYY-NNN/` が作成され、README に案件概要が入っている。

### STEP 2｜文書フォーマットを固定する（0.5 日）

4.2 の front matter テンプレートと CI lint を用意する。

**完了条件**：front matter の無いファイルを PR すると CI が落ちる。

### STEP 3｜DB スキーマを作る（1 日）

4.3 の DDL を適用し、ベクトルストアを確定する。

**完了条件**：`KB_DOC` / `KB_CHUNK` に対する insert / delete / vector search が動作する。

### STEP 4｜取り込みパイプラインを作る（3 日）

4.4・4.5 を実装する。

**完了条件**：`--all` で全件投入でき、同じファイルを 2 回流しても chunk 数が増えない。

### STEP 5｜CI に組み込む（0.5 日）

| タイミング | やること |
|---|---|
| PR 作成時 | front matter lint のみ（**embed しない**） |
| main へ merge | 差分取り込み |
| 週次 | 全件整合チェック（doc_id 重複・孤児 chunk） |

> PR 時に embed すると、レビュー前の草案が索引に入ってノイズになる。

### STEP 6｜検索 API を作る（2 日）

4.6 を実装する。

**完了条件**：golden set の query に対して、期待 doc が top5 に入る。

### STEP 7｜権限を実装する（1 日）

4.7 を実装する。

**完了条件**：権限外の案件の chunk が検索結果に一切出ないことをテストで確認。

### STEP 8｜golden set を作る（1 日）

4.8 を整備し、**recall@5 ≥ 0.85** を確認する。

### STEP 9｜案件キックオフ時の手順（案件ごと・0.5 日）

新規案件が始まったら、この 7 つを必ず実施する。

1. 案件コードを採番し `projects/<code>/` を作成する
2. `README.md` に顧客・期間・機密区分を記入する
3. KB に `project_id` を登録する（案件マスタ）
4. 案件固有用語を `glossary/` に登録する
5. `templates/` から成果物テンプレートをコピーする
6. 顧客固有の機密区分を確定する（既定 `3=confidential` から開始）
7. 初回投入対象（既存の要件定義書・議事録）を確定する

### STEP 10｜工程ごとの継続作業

| 工程 | 投入するもの | タイミング |
|---|---|---|
| 要件理解 | 要件構造化シート、確認事項一覧 | 成果物確定時 |
| 基本設計 | `BS-*.md`（機読源） | PR merge 時 |
| 詳細設計 | `DS-*.md`、項目定義 | PR merge 時 |
| 製造 | ソース（別インデックス推奨） | merge 時 |
| テスト | `TC-*.md`、結果報告 | merge 時 |
| 全工程 | ADR（設計判断の記録） | 判断のたび |

> **鉄則：成果物のコミットと同じ PR で入れる。** 後回しにすると必ず溜まる。

### STEP 11｜日常・週次運用

| 頻度 | 作業 | 所要 |
|---|---|---|
| 日次 | 取り込みエラー確認（CI 通知） | 5 分 |
| 週次 | 未コミット成果物の検出、誤り報告の処理、golden set 回帰 | 30 分 |
| 月次 | ヒット率・採用率のレビュー | 1 時間 |

### STEP 12｜結案と company への昇格（案件終了時・2 週間）

1. **結案レビュー会**（1 時間）：再利用価値のある設計判断・パターン・用語を抽出
2. **匿名化・抽象化**：顧客名・固有業務名を一般化
   （例：`A社の受注処理` → `受注処理の共通パターン`）
3. **owner レビュー**：KB 責任者が PR で承認
4. **昇格**：`git mv projects/<code>/... company/...` し、front matter を `scope: company` に変更
5. **案件庫を read-only へ**：アーカイブ扱いにし、以後は参照のみ

**昇格チェック**

| 条件 | 確認内容 |
|---|---|
| 匿名化 | 顧客名・個人名・金額が残っていない |
| 汎用性 | 他案件で使える形になっている |
| 重複 | 既存の company 資産と重複していない |
| 出典 | 元案件 ID を `source_project` に残す |

## 6. スケジュール

| 週 | 作業 |
|---|---|
| 1 週目 | STEP 0〜2、STEP 4 の設計 |
| 2 週目 | STEP 3〜5（初回投入まで） |
| 3 週目 | STEP 6〜7（検索 API・権限） |
| 4 週目 | STEP 8（golden set）＋ パイロット検証 |

**全体の完了条件**：基本設計フェーズで、AI が案件 KB から類似設計を引用して初稿を出せる状態。

---

## 7. 運用（日常・週次・結案）

### 7.1 日常

- CI の取り込み失敗通知を確認する（5 分）
- 失敗の典型：front matter 不備、表崩れ、embedding API のレート制限

### 7.2 週次

- 未コミット成果物の検出：成果物がリポジトリ外に作られていないか
- 誤り報告の処理：AI が古い設計を引用した等の報告を一次受け
- golden set の回帰：チャンク戦略を触った週は必ず実行

### 7.3 月次

- ヒット率・採用率のレビュー
- 低ヒットの query を抽出し、用語辞書の不足やチャンク分割の問題を特定

### 7.4 結案

STEP 12 を実施する。案件庫は read-only アーカイブとして残す。

## 8. アンチパターン

| # | アンチパターン | 結果 |
|---|---|---|
| 1 | 過去の全案件を一括投入 | ノイズで精度が落ち、評価不能になる |
| 2 | 整篇をそのまま embed | 大段落が返り続ける。必ず chunk する |
| 3 | 権限を検索後にフィルタ | 漏洩かつ recall 低下 |
| 4 | front matter なしで取り込み | 出典も権限も辿れなくなる |
| 5 | owner 不在の company 庫 | 半年で陳腐化する |
| 6 | 顧客固有情報を匿名化せず昇格 | 他案件への情報漏洩 |
| 7 | 設計書 Excel を毎回フルパース | 解析品質のばらつき・二重実装 |
| 8 | 日本語 FTS を標準機能で実装 | 検索精度が出ない |
