# AI 全流程開発プレイブック（工程別・人が入力/レビューするもの付き）

> **根拠（2026-10-28 改）**: `AI全链路软件工程平台_实施规格书.md` §5（8 工程の詳細作業方式）・
> §9（成果物体系）・§10（工程間連携）・§13（KPI）。旧 PPT の `(Sxx)` 表記は**出典の履歴**として残す
> （PPT は仕様書の母体であり、判定基準ではない）。
> **対象**: Claude Code を実行主体として trans-cosmos-ai 骨架を回す SE / PG / テスター。
> **前提**: Claude Code が 8 工程すべてを実行し、**人はレビューゲートで拍板する**。
> 人が「何を入力し、何をレビューするか」を工程ごとに明記した。ここが本ガイドの主眼。
> **仕様書との役割分担**: 仕様書は「何をすべきか」、本ガイドは「人がその工程で実際に何を渡し、何を見るか」。
> 食い違ったら仕様書が正。

---

## 0. このガイドの使い方

1. 作業を始める前に、**該当工程の節**を開く。
2. 「**人が入力するもの**」を用意する（これが無いと Claude Code は動けない）。
3. 「**Claude Code に頼むこと**」をそのまま（または自分の言葉で）伝える。
4. 出てきた成果物を「**人がレビューする観点**」でチェックする。
5. 「**合格サイン**」を満たしたら次工程へ。満たさなければ差し戻す。

> **大原則**（PPT S17）：**AI は実行主体、人は責任主体**。どの工程でも最終責任は人に残る。
> AI の出力は常に**初稿**である。レビューを飛ばして次工程に流してはならない（CLAUDE.md 紅线③）。

## 1. 何が変わるのか（PPT S5：従来 vs AI 全链路）

| 観点 | 従来（人力駆動） | AI 全链路（AI 駆動＋人の統制） |
|------|----------------|---------------------------|
| チーム構成 | SE/PG/テスターを大量配置、規模に比例して人員増 | 少人数＋AI。小規模案件は 3〜5 名でも全工程可 |
| 工数配分 | 設計 30%・製造 35%・テスト 35% | **人は要件定義とレビューに約 6 割** |
| 成果物 | 手書き日文設計書、粒度ばらつく | 機読構造化成果物を源とし、日文正式版は自動生成 |
| 日中連携 | メール・口頭・レビューで都度すり合わせ | 構造化入力で曖昧さを事前排除、変更影響は自動分析 |
| 品質 | レビュー工数依存、指摘密度ばらつく | 全量レビュー＋自動検査、指摘密度・採用率を計測 |
| 引継ぎ | 属人化しやすい | ナレッジベースに蓄積しコンテキスト再利用 |
| リードタイム | 工程間の待ちと手戻りで長期化 | 受け渡しが構造化され待ち・手戻り削減 |

> **要するに**：人が「書く量」を減らし、「**定義・検証・判断の質**」に集中する。
> この表のとおりに運用できているかは、後述の 6 KPI（§8）で測る。

## 3. 工程別プレイブック

### 工程① 要件理解（PPT S9）→ G1 要件合意

**人が入力するもの**
- 日方の要件定義書・議事録・メール（`D:\AI_work\doc\02_INPUT/` 配下の連携資料）
- 既存システムの仕様書、過去案件のナレッジ（`tools/kb-platform/repo/projects/P-R60-001/review/`）
- 今回のスコープ上限（何をやらないか）の当たり

**Claude Code に頼むこと**
> 「`doc/02_INPUT/2026xxxx_連携/` の資料を読んで、業務フローと用語を抽出し、**曖昧点・矛盾点・前提不足**を Q-ID で列挙してください。
> 要件を構造化シートにし、ID は `docs/00_registry/ids.yml` で **R-ID を発号**してから `docs/10_requirements/` に置いてください。」

**成果物**：要件構造化シート（`R-xxx-*.yaml`）・確認事項一覧（Q-ID）・用語辞書（`glossary.yml`）・スコープ見積り

**人がレビューする観点（G1）**
- [ ] **確認事項一覧の取捨選択**：Q-ID のうち、どれを日方に質問するか／自分で決めてよいかを判断したか
- [ ] **日方への質問**：曖昧点を推測で埋めず、質問として立てたか
- [ ] **スコープ承認**：やらないことを明示したか（Non-Goals）
- [ ] **ID の妥当性**：発号が `ids.yml` 経由か（野号ゼロ）

**合格サイン**：`py -3 -m tools.trace_check --strict --only-check id-chain` が Exit 0 ／ Non-Goals が 3 条以上書かれている
**下流連携**：**R-ID を全成果物の共通キーとして確定**（これがトレーサビリティの起点）

### 工程② 基本設計（PPT S10）→ G2 設計評審

**人が入力するもの**
- 工程①の要件構造化シート（R-ID 確定済み）
- 日方の設計規約（`doc/02_INPUT/10.規約/` の画面共通仕様書・画面規約・コーディング規約）
- アーキテクチャ上の制約（既存スタックからの逸脱可否）

**Claude Code に頼むこと**
> 「R-101 から機能一覧・画面一覧を起こし、**入出力一覧に I-ID を付与**（型・桁・必須・由来要件 ID）してください。
> 非機能要件と制約のチェックリストを適用し、`docs/20_basic_design/` に置いてください。」

**成果物**：基本設計書（機能一覧・画面一覧・入出力一覧）・アーキテクチャ案

> **画面単位の基本設計書は「画面編」の標準構成で書く**（2026-10-21 追加・登録 A-31）。
> 章立て・列構成・粒度は [reference-design-book.md](reference-design-book.md) が唯一の定義で、
> `tools/gen_formal.book` が同じ md から参考書体裁の Excel を生成する。
> **構成は参考書に倣うが、業務内容（項目・値域・条件・メッセージ）は写さない**——
> 事実は上流の承認版からのみ取る。参考書の同じ位置に答えらしきものがあっても使わない。

**人がレビューする観点（G2）**
- [ ] **アーキテクチャ妥当性**：機能の切り方・画面分割は業務に合っているか
- [ ] **入出力一覧の網羅**：項目の欠落・余剰はないか（**飛び番禁止** — 紅线①）
- [ ] **特殊要件の補完**：AI が拾えなかった業務固有の事情を足したか
- [ ] **日方との仕様合意**：合意が必要な点を質問として立てたか

**合格サイン**：`I-ID` が連番で欠落なし ／「入出力の明示」（6 原則③）が守られている
**下流連携**：**項目 ID（I-ID）を詳細設計・テストと共通化**

### 工程③ 詳細設計（PPT S11）→ G2 設計評審（続き）

**人が入力するもの**
- 工程②の基本設計書
- 実装上の非機能制約（性能・排他・桁あふれなど、AI が判断できないもの）

**Claude Code に頼むこと**
> 「F-042 から処理フローを **L-ID 単位**に分割し、項目定義（物理名/論理名/型/桁/初期値/編集仕様）、
> テーブル定義・SQL 一覧、**エラー処理一覧（E-ID）**、境界値と例外パターンを生成してください。
> `docs/30_detail_design/` に置いてください。」

**成果物**：詳細設計書（処理フロー・項目定義・SQL 一覧・エラー処理一覧）

**人がレビューする観点（G2）**
- [ ] **業務ルールの妥当性**：分岐条件は実業務と一致するか
- [ ] **排他制御・性能**：非機能面の設計判断（AI は weakest）
- [ ] **エラー一覧の網羅**：異常系が漏れていないか
- [ ] **項目名の単一ソース**：同じ項目を 2 箇所に定義していないか（`grep` で 1 hit を確認）

**合格サイン**：`grep -rn "受払場所コード" docs/10_requirements docs/20_basic_design docs/30_detail_design | wc -l` == 1
**下流連携**：**処理ロジック ID（L-ID）と設計 ID を付与** → 製造と単体テストの起点

**人が入力するもの**
- 技術選定の判断（**PPT S28 の選定順序：機密データの扱い → 成果物の形式 → モデルと工具**）

**人がレビューする観点**
- [ ] **技術選定の承認**：既存スタックから逸脱していないか（紅线④）
- [ ] **セキュリティ確認**：機密データが外部に出る経路がないか

**合格サイン**：`framework-record.yaml` のスタック欄が実測値で埋まっている

### 工程⑤ 製造（コーディング）（PPT S12）→ G3 コードレビュー

**人が入力するもの**
- **無し**（設計が確定していれば、人が入力を足す必要はない。ここが AI 化の効き目が最大の工程）
- ただし**レビューの時間は必ず確保する**

**Claude Code に頼むこと**（CLAUDE.md §5 のテンプレート）
> 「`docs/30_detail_design/L-xxx-*.yaml` を読んで実装してください。設計は変更せず、実装のみ。
> `R60Common.ts` の既存関数にマッピングし、既存の並行新版は作らないこと。
> 完了後に `py -3 -m tools.trace_check --strict` を実行して結果を報告してください。」

**成果物**：ソースコード・単体テストコード・設計-コード対応表・解析レポート

**人がレビューする観点（G3）**
- [ ] **設計との一致**：実装が L-ID の記述どおりか
- [ ] **可読性・例外処理**：エラーの握り潰しがないか
- [ ] **業務ロジックの最終確認**：AI が解釈を誤った箇所はないか
- [ ] **禁止事項 5 条**（案件固有・CLAUDE.md §2）：`R60Common.ts` 改変・`BaseCamelModel` 変更・野号・`trace_check` 跳过・未マスク外部送信がないか

**合格サイン**：`trace_check --strict` が Exit 0、`chain_complete=true`、`orphan_ids=[]`
**下流連携**：生成コードを設計 ID と紐付けたまま単体テストへ

**人が入力するもの**

**Claude Code に頼むこと**
> 「L-014/L-015 からテスト観点（同値分割・境界値・デシジョンテーブル）を生成し、

**成果物**：単体テスト仕様書（テスト観点を明示）・テストデータ・実行結果・カバレッジレポート

**人がレビューする観点（G4）**
- [ ] **観点の妥当性**：業務上重要な観点が落ちていないか
- [ ] **失敗時の原因判断**：落ちたのは実装バグか、テストの誤りか
- [ ] **修正方針の決定**
- [ ] **未検証観点の把握**：カバレッジの穴を認識したか

**合格サイン**：全 TC に `design_ids` がある ／ 未検証観点が一覧化されている
**下流連携**：**未検証観点と残課題を結合テストへ引き継ぐ**

## 4. 人のゲート総覧（各ゲートで答えるべき質問）

| ゲート | タイミング | あなたが答える質問 | 満たさない場合 |
|-------|-----------|------------------|--------------|
| **G1 要件合意** | 工程①の後 | この要求で本当に合っているか？ やらないことは何か？ 日方に聞くべきことは何か？ | 要件理解に差し戻し |
| **G2 設計評審** | 工程②③の後 | 業務ルールは正しいか？ 項目に漏れはないか？ 非機能面で危険はないか？ | 設計に差し戻し |
| **G3 コードレビュー** | 工程⑤の後 | 設計どおりか？ 例外処理は適切か？ 禁止事項 5 条を破っていないか？ | 製造に差し戻し |
| **G4 合否判定** | 工程⑥⑦の後 | 観点は妥当か？ 落ちた原因は何か？ 合格と言えるか？ | 修正して再テスト |
| **G5 リリース判定** | 工程⑧ | 出してよいか？ 切戻せるか？ 顧客に説明できるか？ | 保留・差し戻し |

**ゲートを「通した」証跡**は commit の `Review:` 行に人の識別子を書くことで残す（CLAUDE.md §3）。
AI の識別子を書いてはならない — それは「人が拍板した」ことの記録なので。

## 6. 成果物 6 原則（PPT S20）— これが守られているかで品質が決まる

1. **構造化**：自然文の塊をやめ、項目単位の表・フィールドで書く
2. **ID 付与**：要件 ID・設計 ID・テスト ID を全成果物に付与し追跡可能にする
3. **入出力の明示**：入力・出力・例外・条件を必ず明記し、曖昧な語を排除する
4. **単一ソース**：同じ情報を二箇所に書かない（重複は不整合の温床）
5. **二重の形態**：機読源（Markdown/YAML）から人読用（Excel/Word）を自動生成する
6. **前提の明示**：前提・仮定・未確定点を必ず残す（AI 誤生成を防ぐ最大の策）

> 6 原則のうち 1・2・4 は `trace_check` の gate1/gate3/gate5 が機械的に検査する。
> 3・6 は人がレビューで確認する。
>
> **原則 6（前提の明示）の正しい読み方**：求められているのは「未確定点を**隠さず残す**」ことであり、
> `open_issues` を空にすること自体が違反なのではない。**空にしてよいのは、空である根拠を人が
> 説明できる場合だけ**である（例: 内部構築段階で確定済み）。空でない場合は、後述のとおり
> 各項目を `ids.yml` の `Q` プレフィックスで発号し、`Q-ID` として管理する。
> 根拠を言えない `open_issues: []` は「未確定点を書き漏らした」のと同じである。

## 9. よくある詰まり

**Q. Claude Code が設計を勝手に変えてしまいそうで怖い。**
A. 依頼文に「設計は変更せず、実装のみ」と明記する（CLAUDE.md §5 のテンプレートに含まれている）。さらに `trace_check` の gate1/gate5 が、設計 ID の無断変更や命名の混写を機械的に検出する。

**Q. レビューで何を見ればいいか毎回迷う。**
A. §3 の各工程の「人がレビューする観点」をチェックリストとしてそのまま使う。全部見るのではなく、**AI が弱いところ（業務ルールの妥当性・非機能・例外）に時間を集中させる**のがコツ。

**Q. 人が入力を用意する時間が無い。**
A. 工程⑤ 製造は人力入力がほぼゼロ（設計が確定していれば）。逆に 工程① 要件理解は人が最も関与すべき工程で、ここを省くと後工程が全部崩れる（PPT S6 の「人は要件定義とレビューに約 6 割」）。

**Q. どこまで AI に任せていいか。**
A. PPT S5 の原則：**AI は実行主体、人は責任主体**。判断（合否・リリース・優先度・業務ルールの正しさ）は人。作業（生成・整理・検査・集計）は AI。
