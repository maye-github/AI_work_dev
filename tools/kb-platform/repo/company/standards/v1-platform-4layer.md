# 方案 v1（认知層）× 落地篇 7 層 の対応マップ

本ドキュメントは、要件源である **2 つの PPT のうち、これまで本骨架が扱っていなかった側**を補うものである。

| 資料 | 層 | 役割 | 本骨架での扱い |
|------|----|------|---------------|
| `基于统一 AI 平台的全生命周期软件工程方案_v1.pptx`（中文 13 页） | **認知・範式層**（宏观） | なぜ AI で工程を作り替えるのか（痛点・誤解・思考転換）＋ 統一プラットフォームの四層概念図 | **本ファイルで補完** |
| `AI実践に基づくソフトウェア開発プロセスの再考_落地篇.pptx`（日文 30 页） | **工程・実装層**（微观可执行） | 8 工程・RACI・成果物 6 原則・7 層アーキ | `tools/kb-platform/repo/company/standards/platform-map.md` ほか既存文書 |

> **両者の関係**（kb 側で確定済みの定位）: **v1 は認知と範式の共有**（宏观）であり、
> **落地篇は工程の落地細則**（微观可执行）である。**二者は互いに表裏**であり、
> 先に認知を統一し（v1）→ そのうえで落地篇の工程篇／成果物篇／平台篇を進める、という順序になる。
> したがって本骨架が落地篇だけを実装していたのは**片翼**であり、本ファイルで v1 側を接続する。

## 1. v1 の認知層（為什麼要改）

### 1.1 四つの痛点（S4）

| # | 痛点 | 本骨架での対応物 |
|---|------|-----------------|
| 1 | 流程分层割裂，AI 无法串联全链路（文档碎片化・口语化・非标准化） | `docs/00_registry/ids.yml` の単一発号 ＋ `traceability.yml` の双方向リンク |
| 2 | 所有环节重度依赖人的逻辑与表达（无标准化结构化输入） | 7 字段 front-matter ＋ 8 工程 YAML テンプレート |
| 3 | 把 AI 当成附属小工具，而非核心生产力 | `.claude/skills/code-from-design-trans-cosmos-ai/`（設計→製造を一気通貫で AI が実行） |
| 4 | 工具碎片化，质量与安全不可控（AI 产出无审查・无追溯・无度量，泄露风险） | `tools/trace_check`（6 ゲート）＋ `tools/masking` ＋ `secret-auditor` |

### 1.2 三つの誤った認知（S9）

1. **不是 AI 笨，是流程和输入不适配 AI** — 写给人的、可脑补的文档 AI 读不懂。
   → 対応: 成果物を「機械可読源（`.md`＋`.yaml`）」に統一する（規則 00 §11）。
2. **不需要执着于「训练 AI」，核心是训练人的思维** — 人输出标准・结构化・逻辑闭环的输入，AI 自然输出高质量。
   → 対応: テンプレート（`req-template.yaml` 等 8 份）で入力の形を強制する。
3. **V 模型分层思维限制了 AI 全链路能力释放** — 同一上下文从需求到测试自动流转。
   → 対応: R→F→I→D/L→E→TC の ID 链が工程をまたいで途切れない（`trace_check` gate2）。

### 1.3 四つの思考転換（S10）

| # | 転換 | 本骨架での体現 |
|---|------|---------------|
| 1 | 「工具思维」→「范式思维」 | 「Claude Code は実行主体、人は責任主体」（CLAUDE.md §0） |
| 2 | 「人工经验兜底」→「标准规范兜底」 | 6 份工程別ルール（`.claude/rules/`）が判断を規約化 |
| 3 | 「分层割裂开发」→「全链路闭环开发」 | 8 工程 YAML ＋ ID 追溯閉ループ |
| 4 | 「命令式使用 AI」→「结构化协作 AI」 | CLAUDE.md §5 の依頼テンプレート（自然言語・構造化） |

### 1.4 落実の四歩（S11）

| 步 | v1 の記述 | 本骨架での状況 |
|----|----------|---------------|
| 1 | 梳理标准化输入（业务描述模板・设计规范・需求模板） | ✅ 8 工程テンプレート済み |
| 2 | 小范围全链路验证（放弃碎片化，小项目全链路跑通） | ✅ R60Area を R-101 として全链路貫通（`ppt-example-walkthrough.md`） |
| 3 | 沉淀协作标准（统一输入/校验/产出标准，建立评测） | 🔶 規約はあるが **評測（KPI）は未実測**（ROADMAP Phase2） |
| 4 | 持续认知升级 | 🔶 運用フェーズの継続課題 |

## 2. v1 の統一プラットフォーム四層（S11 / S12）

v1 が示すのは **概念藍図であり成熟製品ではない**、という但し書きが PPT 本文に明記されている点に注意。

```
┌─────────────────────────────────────────────┐
│ 接入層      統一入口                          │
│   Prompt 模板库（需求/设计/编码/测试模板）      │
│   权限管理 ・ 生成内容审计追溯                  │
├─────────────────────────────────────────────┤
│ 能力编排層  Agent 工作流                      │
│   业务理解Agent → 设计Agent → 编码Agent → 测试Agent │
│   前序产出自动作为后序输入（上下文不丢失）        │
│   人工校验节点（设计评审・代码评审で停止）        │
├─────────────────────────────────────────────┤
│ 知识庫層    RAG 检索增强                      │
│   业务术语库・项目历史设计文档・接口文档          │
│   编码规范・测试规范・历史决策记录与原因          │
├─────────────────────────────────────────────┤
│ 模型網関層  模型接入与管控                     │
│   对接大模型 API・按任务类型路由                │
│   输出安全过滤・敏感信息脱敏・合规校验            │
│   输出质量初筛・Token 用量统计・成本分摊          │
└─────────────────────────────────────────────┘
```

**v1 が明示する落地優先順位**: 先做 **接入層模板庫 ＋ 知識庫 RAG**（投入小・見效快）、
再逐步建設編排層和模型網関層。本骨架の重心が「テンプレート ＋ ナレッジ」に置かれているのは、
この優先順位と整合している。

## 3. 【重要】二つのアーキテクチャの対応関係

v1 の **4 層** と落地篇 の **7 層** は、**同じプラットフォームを異なる粒度で描いたもの**である。
両者を無関係に併記すると「同一概念が二箇所で定義される」状態（NFR-1 単一ソース違反）になるため、
**ここで 1 対 1 の対応を確定させ、以降の文書はこの表を参照する**（再定義しない）。

| v1 の 4 層（S12） | 落地篇 の 7 層（S26） | 本骨架の資産 |
|------------------|---------------------|-------------|
| **接入層**（Prompt 模板庫・権限・監査） | **利用層**（人が使う面）＋ **統制・ガバナンス層**（権限・監査の部分） | `docs/*/**/*-template.yaml`（8 份）・`CODEOWNERS`・`.claude/agents/secret-auditor` |
| **能力編排層**（Agent 工作流・人工校验节点） | **編成層**（工程別 Agent）＋ **能力層**（Skill/ツール） | `.claude/skills/code-from-design-trans-cosmos-ai/`（Step1-4）＋ `.claude/skills/trans-cosmos-ai-lifecycle-coach/`（8 工程の進行役）＋ `.claude/agents/`（検証系 4 体 ＋ 工程実行系 8 体）＋ `tools/**` |
| **知識庫層**（RAG） | **知識層** | `tools/kb-platform/repo/**`・`docs/00_registry/glossary.yml`・`review_diff_assets/` |
| **模型網関層**（モデル接入・安全过滤・コスト） | **能力層の モデルゲートウェイ** ＋ **基盤層**（統制・基盤の部分） | ⚠ **未実装**（Claude Code が直にモデルを呼ぶ。独立した網関は持たない） |

> **差分の扱い**: v1 の「模型網関層」に対応する独立コンポーネントを、本骨架は**持たない**。
> これは本骨架が「Claude Code 単一ツール」構成であり、モデル選択・ルーティング・
> コスト配分を Claude Code 側に委ねているためである（CLAUDE.md §0）。
> **欠落ではなく、単一ツール構成における意図的な非実装**として記録する。
> 将来マルチモデル化する場合の入口はここになる。

## 5. 能力編排層の粒度差（既知の偏差）

v1（S12）は「**业务理解Agent → 设计Agent → 编码Agent → 测试Agent**」という **4 つの工程別 Agent** を描く。
落地篇（S27）も「要件・設計・製造・テストの各 Agent」を編成層の中核に置く。

本骨架の実装は次のとおりで、**粒度が一致しない**：

| 工程別 Agent（PPT） | 本骨架での実現 |
|-------------------|---------------|
| 业务理解 Agent | `trans-cosmos-ai-node1-requirements`（要件理解）／`.claude/skills/code-from-design-trans-cosmos-ai/` **Step 1**（R-ID 受理） |
| 设计 Agent | `trans-cosmos-ai-node2-basic-design`・`trans-cosmos-ai-node3-detail-design`・`trans-cosmos-ai-node4-framework`／同 **Step 2 / Step 3**（BD 生成 / DD 生成） |
| 编码 Agent | `trans-cosmos-ai-node5-coding`／同 **Step 4**（製造） |
| 测试 Agent | `trans-cosmos-ai-node6-unit-test`・`trans-cosmos-ai-node7-integration-test`（テスト設計の専用 agent は置かない） |
| （発表・運用） | `trans-cosmos-ai-node8-release-ops`（PPT の 4 Agent には対応物が無い工程） |

> **偏差の内容**: PPT は 4 つの**独立エージェント**を想定する。本骨架は**2 系統**で実現している。
>
> 1. `.claude/skills/code-from-design-trans-cosmos-ai/` の **単一 Skill 4 Step** — `R-101` の設計→製造を
>    **1 セッション内で貫く**。工程をまたぐ **ID 連鎖を同一コンテキストに保持する**ほうが
>    追跡閉ループを壊しにくいためである。
> 2. `.claude/skills/trans-cosmos-ai-lifecycle-coach/` が派発する **8 体の工程実行体**
>    （`trans-cosmos-ai-node1-requirements` … `trans-cosmos-ai-node8-release-ops`）— 各工程の産出を
>    **独立したコンテキスト**で行い、長い工程で文脈が溢れないようにするためである。
>
> **①と②は役割が違う**（①は設計→製造の貫通、②は工程の進行と産出の分離）ので、優劣ではなく**併用**である。
> ただし **PPT の「4 つの独立 Agent」の姿とは一致しない**ことは事実であり、隠さずここに記録する。
