# 未確定事項の A・B・C 分類（誰が決めるか）

> **本条は判定手順だけを書いた要約であり、正本ではない。**
> 正本は `.claude/rules/02-requirements.md` §4.1（分類の定義・境界事例・対客媒体の書き方）。

## 1. 三つの記号

| 記号 | 意味 | 誰が決めるか | 確認票での扱い |
|---|---|---|---|
| **A** | 顧客が決める（我方では決められない） | 顧客 | **必ず質問する**。当方が暫定値で埋めてはならない |
| **B** | 我方が提案し、顧客が承認する | 顧客（提案は我方） | 提案＋**根拠**＋ご承認いただきたい点の三段 |
| **C** | 我方内部で決定する | 我方 | 顧客に聞かない |

## 2. 判定は「C → B → A」の順に疑う

1. **まず C を疑う** — 顧客に聞かなくてよい内部の決め事ではないか。
   実装・内部設計・表記の決め事（入力の正規化、文字コード、設定の外部化、二重送信の抑止 等）は C。
2. **次に A を疑う** — 案を作れるのに顧客へ丸投げしていないか。
   運用の決め事・方式・異常時の挙動・非機能の水準は B（根拠を添えて提案する）。
3. **残ったものだけが A である。** A に残すのは「顧客しか持っていない資料・事実」に限る
   （顧客が発行した規約・マスタの内容、既存システムとのインターフェース仕様）。

**技術選型は B。** 方式・構成・ライブラリの選定は顧客の業務事実ではない。
ただし**従うべき顧客規約・制約の確認は A** であり、選型と混ぜて「方式を教えてください」と書くと A に寄る。

## 3. 件数の目安（機械判定はしない）

- **A ≦ 1/4、C ≧ 1/3。**
- A が多い＝調べていない・考えていないサイン。C が少ない＝内部で決めることを顧客へ投げているサイン。
- AI の初稿は A に寄り C がほぼゼロになる傾向がある。これは能力ではなく判定手順の欠落であり、
  上の 1→2→3 の順で直る。

## 4. 分類を変えたら、答えの形も変える

| 区分 | 答えの形 | やってはならないこと |
|---|---|---|
| A | 質問（暫定案を置くなら「AI 暫定案」と明示） | 当方の値を確定値として書く |
| B | 提案＋根拠（出典等級）＋ご承認いただきたい点 | 「〜はこうなっている」という事実記述で終える |
| C | 裁定＋根拠 | 「〜を提案します」という提案口調を残す |

**A→B に移したら書き直しが必須**（「資料にこう書いてある」→「こうすることを提案します」）。
**B→C に移したら口調の修正が必須**（提案口調が残ると顧客の承認が要る事項に見える）。
