### Step 2. 作業フォルダを作る

- `app/` の下に **`AI/`** フォルダを作り、その下に **API ごとのフォルダ**を作る（フォルダ名＝API 名）。
- そこに **① テンプレート、② 例示コード、③ AI 生成後のコード**を置く。

### Step 3. テンプレートを直す

- `template.txt` を開き、**画面設計書の内容に合わせて該当箇所を修正**し、API フォルダに置く
  （詳細は `template` シート＝[§3](#3-テンプレートの構造実測)）。

### Step 4. 真のテーブル名・フィールド名を登録する

- `table_mask_tool/config.py` の **`REAL_TABLE_NAMES`** と **`REAL_COLUMN_NAMES`** に
  **画面設計書を見ながら真名を追記**する（`config.py` シートに例がある）。

### Step 5. 假名へ置換する

- **`mask_tool.exe` を起動 → `1` を選ぶ → `AI` フォルダ下のテンプレートをターミナルへドラッグ＆Enter**
  → **同じディレクトリに置換後のテンプレートが生成される**。

### Step 6. 例示コードも假名化する

- **例示コードにも真名が入っているので、同じく假名化する。**
  **先にそのコードで使うテーブル／フィールド名も `config.py` に足しておく。**

### Step 7. 假コードを生成させる（**Lingma のチャット**）

**投入する 4 種**（【実測】逐語の一覧）：

| # | 種別 | 実例 |
|---|---|---|
| 1 | **例示コード** | `R60SezKnoItemController(5).py`（**実情に合わせて調整可。名前は固定しない**） |
| 2 | **テンプレートファイル** | `template_mask.txt` |
| 3 | **ツール類** | `r60sim_util.py` / `r60util.py` / `r60string_util.py` / `r60csv_utils.py` / `r60get_select_column.py` / `r60const.py` |
| 4 | **対話文本（プロンプト）** | 下記逐語 |

> ⚠ **逐語の注意**：「**示例代码包含真字段名和表名，发给AI前需要先替换成假名**」
> ／「**※切记一定使用 mask 后的模板文件，否则会把真字段名名表名传给 AI**」
> ／「**由于 python 中导入的方法或文件未在代码中使用会报错，所以可根据需求适当增减上传的工具类**」

**★プロンプトの逐語**：

```
根据template_mask.txt的模板文件，模拟R60SezKnoItemController(5).py的模板代码文件的写作风格，

为避免因上下文过长导致任务中断，接口请先生成至initEdit接口之前，
```

> ★★ **「模拟…的写作风格」（＝書き振りを真似せよ）が指示の中核である。**
> **「設計書のとおりに作れ」ではない。** **これが向こうの作り方の本質である。**（[§6](#6-骨架との対比)）
>
> ★ **分割生成が明示されている**：**「上下文过长导致任务中断」を避けるため、
> `initEdit` の手前までで一度止め、続きは聞いてから生成**する。**規則 03 §7.4 と同じ判断**である。
> 併せて「**生成前にテンプレートから行数を概算し、どの接口まで生成するか自分で判断せよ**」ともある。

### Step 8. 結果を置く

- **API フォルダの下に `result_` ファイルを新規作成**（命名：`result_xxxController.py`）し、

- **`mask_tool.exe` → `2` を入力 → 生成された `result` ファイルをターミナルへドラッグ**
  → **置換後のコード（`_real` で終わるファイル名）が生成される**。

## 3. テンプレートの構造（【実測】`template` シート 269 行）

**5 つの区切り**があり、それぞれ「どこから中身を持ってくるか」が指定されている。

| # | 区切り | 中身の出所（【実測】逐語） |
|---|---|---|
| 1 | **模板介绍** | 「全体紹介。**具体的な需要に応じて少し修正可。固定要求ではない**」 |
| 2 | **API 路由** | 「**`プログラム一覧（画面）` の `API一覧` の【画面ID】に合わせて修正**」 |
| 3 | **`PGM_ID`** | 「**常量。設計中の『検索最大件数』の共通メソッドの第 2 引数に合わせて修正**」 |
| 4 | **API 基本信息** | **request**：「画面設計書の【画面.xxx】・【項目移送表(DB)】・【画面項目内容】の【**検索条件部**】」／**response**：「【**検索結果部**】」 |
| 5 | **API 詳細情報** | 「【**api 路径**】は `API一覧` の【**ルーターパス**】に合わせる。**請求方式都是 POST，異步請求都是是**」／「【**詳細需要**】は画面設計書の【**業務処理説明**】」 |

> ★★ **3 点、そのまま重要**：
>
> 1. **【差異】D-14 の増幅**：「**api 路径は `API一覧` に合わせる**」と手順が指示している。
>    **ところが `API一覧` は実装から乖離している**（R60Login で 4 端点中 2 件しか載っていない）。
>    **→ 台帳の古さが、手順を通じて生成物へ伝播する。**
> 2. **「請求方式都是 POST」が手順書に明記**＝ [06](06-api.md) §2.2 の実測（351/354 が POST）と一致。
> 3. **`PGM_ID` は「検索最大件数の共通メソッドの第 2 引数」**
>    ＝ [05](05-database.md) §5 の `R60_CODE_MES_M_TBL.KEY_ID`（＝プログラム ID）。
>    **テンプレートではこれを常量として埋め込む。**

> **★テンプレートで埋められないもの（逐語）**：
> 「**每个 API 都有若干共通的参数，例如【`sim_kbn`】、【`sim_tbl_id`】，
> 这类的参数在画面设计书中无法体现，需根据现行示例代码和模板文件自行判断是否需要添加**」
> → **★設計書に無いパラメータが存在する。** 補う手段が「**例示コードを見て判断せよ**」である。
> **これも「模倣」で埋めている。**

> ⚠ **`download` と `dataInit` は「修正が少ない（再利用率が高い）」（逐語）**。
> **＝画面ごとの差分が小さい定型接口である。** 作るときは既存のものをほぼ流用する。

## 4. 脱敏ツールの仕組み（【実測】`config.py` シート）

```python
REAL_TABLE_NAMES  = ["…", …]      # 人が画面設計書を見て追記する
REAL_COLUMN_NAMES = ["…", …]

def build_map(real_list, prefix):          # 自動生成。触らない
    …  mask = f"{prefix}_{idx}"  …        # 1 から始まる連番

TABLE_MASK, TABLE_REAL = build_map(REAL_TABLE_NAMES,  "table")
COL_MASK,   COL_REAL   = build_map(REAL_COLUMN_NAMES, "col")
MASK_MAP = {**TABLE_MASK, **COL_MASK}      # 真名 → 假名（生成に渡す）
REAL_MAP = {**TABLE_REAL, **COL_REAL}      # 假名 → 真名（戻す）
```

- **假名の形は `table_1` / `col_1`**（1 始まりの連番）。**真名の順序が変われば假名も変わる**
  → **同じ画面でも `config.py` の並び順が違えば別の假名になる**（【推測】）。
- **`mask_tool.exe` は 2 モード**：`1`＝真名→假名（テンプレート／例示コードを AI に渡す前）／
  `2`＝假名→真名（AI の出力を戻す）。
- **★この発想はわれわれの `tools/masking` と同じ**。**骨架紅线⑦の実装そのものである。**

> ⚠ **【実測】`config.py` シートに載っている例は汎用の英語名**（`user_info` / `order_record` /
> `user_id` / `order_no` …）であり、**実案件の真名ではない**。**シートの例を実名と誤認しないこと。**

## 6. A/B 対比レポート（【実測】`AB_Reports/reports/`・34 モジュール）

**方法（`reports/README.md` 逐語の要旨）**：

```
老系统（Struts Java）和新系统（FastAPI）用同样的参数、同样的数据库跑一遍，比结果。
  老系统 → 直接执行原始 SQL → 结果 A
  新系统 → 调你的 API     → 结果 B
  A == B 就过，不等就报差异
※所有测试用的都是真数据、真参数、真 API。没有 mock 返回、没有假数据。
```

**判定タグ（逐語）**：

| タグ | 意味 | 誰の責任か（逐語） |
|---|---|---|
| 💥 500 | API 内部崩溃 | **你的** |
| 🚫 404 | 端点不存在 | **你的** — 没实现或路径不对 |
| 🟡 422 | 参数校验不通过 | 可能是**必填参数名不一致** |
| ⚠️ 値差異 | データは返ったが値が違う | **通常是 API 多返回了下拉框/元数据，设计差异** |

**API 健康度（逐語）**：`🟢 正常` / `🔴 全线崩溃（75%+ 用例 500）` / `⚫ 无 API（端点全 404）` /
`🟡 部分缺失`（＋ `🔷 structural` / `🟤` / `⚫`）。

- **再現できる形で書かれている**：各失敗行が `actionId` / エラー / **リクエスト** / **パラメータ** を持ち、
  **そのまま `curl` に組み直せる**（README に例がある。`POST /api/<画面ID>/<イベント>`、
  本文は `{"params":{…}}` 形式）。
- **モックデータ**：`AB_Reports/mock/` に `global_seed/`（`r60_area.sql` 等のシード）と
  **`module_mocks/` 32 個**がある（【実測】）。
  ※ README は「mock は使っていない」と書くが、**フォルダは存在する**。**【未確認】** 用途は不明。

> **★われわれへの示唆**：**この形式（失敗行 → そのまま再現できる要求）は真似する価値がある。**
> **われわれの対比レポートも「コピーして再現できる」形で書く。**
> **ただし測る軸は違う**（[07](07-traceability.md) §6.1：向こう＝移植の忠実さ／われわれ＝生成の再現性）。

## 7. 骨架との対比（★このファイルの主眼）

| 論点 | 向こう（R60） | われわれ（trans-cosmos-ai） |
|---|---|---|
| **生成のさせ方** | **類似の既存実装の「書き振りを真似させる」**（逐語：模拟…的写作风格） | **設計（D/L/E）から起こす**（[SKILL](../../.claude/skills/code-from-design-trans-cosmos-ai/SKILL.md)） |
| **機密保護** | **`mask_tool.exe` で真名→假名→戻す**（手順書に「**必ず**」と明記） | **紅线⑦ ＋ `tools/masking/mask_demo.py`** |
| **分割生成** | **接口単位で分割。`initEdit` 手前で一度止め、継続を問う** | **規則 03 §7.4：1 画面 1 生成が既定、複雑な機能は分割** |
| **設計書に無い項目** | **例示コードを見て人間が判断して足す** | **`open_questions` として列挙し、人が裁定**（規則 04 §9.4・紅线③） |
| **検証** | **旧 Java と応答を突き合わせる**（34 モジュール・実データ） | **`trace_check --strict` ＋ 人が合否判定** |
| **追跡** | **Excel の台帳（人手・乖離あり）** | **`ids.yml` ＋ 機械検査**（[07](07-traceability.md)） |
| **生成物の性格** | **既存実装に似たもの**（＝**現状の再生産**） | **設計に忠実なもの**（＝**設計が先**） |

### 7.1 ★最も重要な違い（1 行）

**向こうは「模倣」で作り、われわれは「設計から起こす」。**

- **模倣の長所**：**その画面の既存の作り方（`sim_kbn` のような設計書に無い項目）が自然に引き継がれる。**
  **短期間で大量に作れる**（56 画面をこの手順で通した実績がある）。
- **模倣の短所**：**既存実装の誤りも一緒に写る。** **設計と実装が乖離しても気づけない**
  （→ **そのため A/B で旧 Java と突き合わせる装置を別に持つ**）。
- **設計からの長所**：**出典が明確。追跡が閉じる。**
- **設計からの短所**：**設計書に無い項目（`sim_kbn` 等）を落とす**。**われわれは `open_questions` で拾う。**

> **★対比の設計に効く含意**：
> **われわれの生成物が人間版とずれる最大の原因は、この「模倣」の有無である。**
> **ずれを見つけたら、「設計書に無いから落ちた」のか「設計書にあるのに読めていない」のかを切り分ける。**
> **前者は向こうの正解（実装が先行している）、後者はわれわれの欠落である。**
> **この切り分けをせずに「AI の方が劣る」と結論してはならない。**

### 7.2 揃っている点（誇張しない）

- **脱敏してから AI に渡す**：**向こうもわれわれも同じ**（向こうは手順書に明記、われわれは紅线⑦）。
- **分割生成**：**同じ判断**（向こうはトークン長、われわれは規則 03 §7.4）。
- **人が最終確認**：向こうも「人の目による再確認」を要する（[04](04-common-parts.md) の外部教訓と同じ）。
- **再現可能な形で失敗を残す**：向こうの A/B レポートは**curl で再現できる**形になっている。
  **われわれの対比レポートもこの形式を採る。**
