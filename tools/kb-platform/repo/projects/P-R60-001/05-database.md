## 2. オブジェクトの目録（【実測】`テーブル一覧`）

**データ行は 192 件**（`№` 列が 1〜192。シートの 194 行 ＝ 題名 1 ＋ 見出し 1 ＋ データ 192）。

| 種別 | 件数 |
|---|---|
| `TABLE` | **171** |
| `VIEW` | **20** |
| `SYNONYM` | **1**（`R3B_TSHIMETSUKI_KANRI_TBL` 締め月管理 — **他システム由来のシノニム**） |
| **計** | **192** |

> **【実測】再現**：`py -3 -m tools.legacy "…テーブル一覧_v1.0.xlsx" --sheet テーブル一覧 | awk -F'| I:' 'NF>1{…}' | sort | uniq -c`
>
> ⚠ **数え違えの罠**：見出し行の `I` 列は「`TABLE/ / VIEW/ / SYNONYM`」と 3 語を含む。
> **`grep -o 'SYNONYM' | wc -l` とやると 2 になり、SYNONYM が 2 件あるように見える。** 必ず**行単位**で数える。
> （`テーブルレイアウト一覧` のテーブル数も **171** で一致する — 【実測】）
>
> **【差異】D-17**：`doc/02_INPUT/20.DB定義書/テーブル一覧` の 1 行目には `Sim` 列（`H`）がある。
> **シミュレーション用の別系統**が同じ表に混ざる余地がある。**種別列 `I` だけでなく `H` 列も見ること。**

### 2.1 一覧が持つ列（【実測】`テーブル一覧`）

```
No. / テーブル名 / テーブル名称 / レコード数(件) / レコード長(byte) / 平均レコード長(byte) / 合計容量(Mb) / Sim / TABLE・VIEW・SYNONYM
```

> ⚠ **レコード数・容量は現行本番の実測値**である。**対外提出物には載せない**
> （規則 01 §10「32 モジュール業務データ実値」＝ L3 に触れうる）。**内部の作業では参照してよい。**

## 3. 全項目一覧（`テーブルレイアウト一覧`）の読み方（★ここが主戦場）

**【実測】** 5532 行 ＝ 題名 1 ＋ 見出し 1 ＋ **項目 5530 行**。**1 行 = 1 カラム**。

### 3.1 列の対応（【実測】）

| 列 | 内容 |
|---|---|
| `A` | No（テーブル通番） |
| `B` | テーブル名称（日本語） |
| **`C`** | **テーブル物理名**（`R60_USER_M_TBL` 等） |
| `D` | 項目 No |
| **`E`** | **項目名称**（日本語） |
| `F` / `G` / `I` / `K` / `O` | **`CREATE TABLE` の断片**（`,` `(` `)` など。連結すると DDL になる） |
| **`H`** | **物理カラム名**（`STF_CD` 等） |
| `J` | データ型（`VARCHAR2` / `DATE` / `NUMBER` 等） |
| `L` | 長さ |
| `N` | 小数 |
| **`P`** | **必須**（`Y`） |
| **`Q`** | **主キー**（`1`,`2`,… の順序番号） |
| `R`〜`AA` | **FK1〜FK10** |
| `AB` | パーティションキー |
| `AC`/`AD` | IDX1 / IDX2 |
| `AM` / `AN` | **コード値マスタ（明細）への参照**（コード値を使う列に付く） |
| `AP` / `AQ` | **`COMMENT ON TABLE` / `COMMENT ON COLUMN` の全文** |

> **★便利な性質**：`F`〜`Q` を連結すると**そのまま `CREATE TABLE` 文**になる。`AP`/`AQ` が
> **コメント文**を持つ。**つまり設計書 1 冊に DDL が完全に入っている。**

### 3.2 抽出の記法（【実測】動くコマンド）

```bash
# ある 1 テーブルの全カラム（No / 物理名 / 名称）を順に出す
py -3 -m tools.legacy "…テーブルレイアウト一覧_v1.0.xlsx" --sheet テーブルレイアウト一覧 \
  | grep "C:R60_USER_M_TBL " \
  | sed -E 's/.*D:([0-9]+) \| E:([^|]*)\|.*H:([A-Za-z0-9_]+) \|.*/\1\t\3\t\2/'
```

## 4. 共通監査列（★全テーブル共通の「お作法」）

**【実測】171 テーブル中、次の列を持つテーブル数：**

| 列 | 物理名 | 名称 | 数 |
|---|---|---|---|
| 更新時刻 | `KSN_DAT` | 更新時刻 | **166** |
| 更新者ＩＤ | `KSN_STF_ID` | 更新者ＩＤ | **166** |
| 論理削除フラグ | `DEL_FLG` | 論理削除フラグ | **167** |
| 登録時刻 | `REG_DAT` | 登録時刻 | **167** |
| 更新プログラムＩＤ | `KSN_PGM_ID` | 更新プログラムＩＤ | **162** |
| リビジョン | `REV_NO` | リビジョン | **162** |
| 登録者ＩＤ | `REG_STF_ID` | 登録者ＩＤ | **162** |
| 登録プログラムＩＤ | `REG_PGM_ID` | 登録プログラムＩＤ | **162** |
| 登録区分 | `REG_KBN` | 登録区分 | **162** |
| 更新区分 | `KSN_KBN` | 更新区分 | **162** |
| 登録ステータス | `REG_STS` | 登録ステータス | **152** |
| 送信ステータス | `SEND_STS` | 送信ステータス | **152** |
| 送信区分 | `SEND_KBN` | 送信区分 | **152** |

### 4.1 構造の読み方（【推測】）

- **末尾 10 列はほぼ全テーブル共通**（`DEL_FLG` / `REG_KBN` / `REG_STF_ID` / `REG_DAT` / `REG_PGM_ID` /
  `KSN_KBN` / `KSN_STF_ID` / `KSN_DAT` / `KSN_PGM_ID` / `REV_NO`）。
- **その手前に 3 列**（`REG_STS` / `SEND_STS` / `SEND_KBN`）が付く**152 テーブル**がある。
  **【推測】** この 3 列は**オンライン更新と緊急配信を扱うテーブル**の印である
  （`SEND_STS` は送信ステータス＝緊急配信の状態）。

### 4.2 ★排他は `KSN_DAT` ＋ `REV_NO`（【推測】— 明文は無い）

- **本知識庫で唯一の推測に依存する重要事項**である。**DB 定義書に「排他」と書いた行は 1 つも無い**（【実測】）。
- 根拠は**列構成**：`KSN_DAT`（更新時刻）と `REV_NO`（リビジョン）が**セットで 162/166 テーブルに存在**し、
  骨架規則 03 §4 の snake/camel 対応表も **`ksn_dat`=更新日時（排他）** / **`rev_no`=改訂番号（排他）** と
  **「排他」を明記している**。
- **コード側はこの前提で実装されている**（[06](06-api.md) §5 の `KSN_DAT` 不一致検出）。
- **【未確認】** 明文の規約は見つけていない。**設計判断に使う前に、`R60_USER_M_TBL` 等の
  実際の更新系 API を 1 本読んで確かめること。**

## 5. 検索上限件数（★全画面共通・コードにハードコードしない）

**【文書】`10.規約/…画面共通仕様書_v1.2.xlsx` シート `３．画面処理`（４）** 逐語：

> 「検索条件画面にて検索条件を指定し、表示ボタン（仕掛表示ボタン）を押下した際に取得した該当レコード件数が
> **上限件数を超過した場合エラーダイアログを表示する**。」
> 「検索時の上限件数は**各画面毎にコード値明細マスタ（`R60_CODE_MES_M_TBL`）に定義されている**。」

**取得方法（【文書】同シートの表）**：

| 項目 | 値 |
|---|---|
| テーブル | `R60_CODE_MES_M_TBL`（コード値明細マスタ） |
| 検索条件① `JOH_ID`（情報ＩＤ） | **`"000000024"`** ← **検索上限件数に予約された情報 ID** |
| 検索条件② `KEY_ID`（ＫＥＹＩＤ） | **プログラムＩＤ（例：`R60Ssk`）** ＝ 画面 ID |
| 検索条件③ `DEL_FLG` | **`"0"`**（未削除） |
| 取得項目 | **`CD_CHI_NM`（コード値名称）** ＝ 上限件数（例：`1000`） |

> **★含意**：**上限件数はコードに書かない。** 画面を作るときは
> `r60util.get_cod_mes_info`（[04](04-common-parts.md) §2.1）経由で**データから引く**。
> **画面 ID を変えれば `KEY_ID` が変わる**ので、**キーを間違えると件数 0 件扱いになる**危険がある。

## 6. R60Login に関係する 4 テーブル（【実測】全カラム）

### 6.1 `R60_USER_M_TBL`（ユーザマスタ・**28 列**）

```
PK  STF_CD            社員コード            VARCHAR2(8)
    SZK_CMP_CD        所属会社コード        VARCHAR2(4)    ← コード値マスタ参照
    HTR_YMD           発令日                VARCHAR2(8)
    STF_NM            社員日本語名称        VARCHAR2(30)   ← 実在氏名が入る（L3）
    SSK_UNIT          組織ユニット          VARCHAR2(8)
    MAIL_ADRS_1       メールアドレス１      VARCHAR2(50)   ← 社内メール（L3）
    PWD_STE_YMD       パスワード設定日      VARCHAR2(8)
    MAIL_ADRS_2       メールアドレス２      VARCHAR2(50)
    S_CMP_CD          Ｓ会社コード
    S_JIG_CD          Ｓ事業場コード
    YAK_CD            役割コード
    HYO_KYO_GRP_CD    帳票共有グループコード
    GRP_KJN_FLG       グループＯＲ個人フラグ
    HYO_ACS_CD        帳票権限コード
    USER_TYP_CD       ユーザタイプコード
    ＜以下 13 列は §4 の共通監査列＞
    REG_STS / SEND_STS / SEND_KBN / DEL_FLG / REG_KBN / REG_STF_ID / REG_DAT / REG_PGM_ID
    KSN_KBN / KSN_STF_ID / KSN_DAT / KSN_PGM_ID / REV_NO
```

> ★ **`PWD_STE_YMD`（パスワード設定日）— パスワードそのものの列は無い。**
> **【推測】** 認証は当日鍵（`yyyymmdd`）で復号する方式であり、**復号関数は DB 側**にある
> （骨架 `CLAUDE.md` §「R60_DECRYPTION_FNC を必ず使用」／`.claude/rules/00-project-global.md` §1）。
> **【未確認】** 復号の実装は本知識庫では確認していない（`要件` 側の担当）。

### 6.2 `R60_CODE_MES_M_TBL`（コード値明細マスタ・**31 列**・PK は複合）

```
PK  JOH_ID           情報ＩＤ              ← §5 の "000000024" がここに入る
PK  KEY_ID           ＫＥＹＩＤ            ← 画面 ID がここに入る
    CD_CHI_NM        コード値名称          ← §5 の上限件数がここに入る（例 1000）
    ANM              カナ名称
    HYJ_SEQ          表示順
    KOB_KMK_NM_1..10 個別項目名１〜１０
    BKO_KMT          備考コメント
    TEK_KIK_BGN_YMD  適用開始日
    TEK_KIK_END_YMD  適用終了日
    ＜以下 13 列は共通監査列＞
```

> **★これがドロップダウンの中身である。** 支援画面・選択リストはこの表を引く。
> **`HYJ_SEQ` が表示順**、**`TEK_KIK_BGN/END_YMD` が有効期間**（＝**適用日で値が変わる**）。

### 6.3 `R60_MESSAGE_TBL`（メッセージ・**13 列**）

```
PK  MSG_NO           メッセージ番号
    MSG              メッセージ
    HYJ_SEQ          表示順
    ＜以下 10 列は共通監査列（REG_STS/SEND_STS/SEND_KBN は無い）＞
```

> **【実測】** R60Login の設計書 `画面項目内容` は「画面タイトル」について
> **「対象テーブル：メッセージ管理情報 / 背景色項目：メッセージ」** と書く。
> → **画面タイトルの文字列と背景色は `R60_MESSAGE_TBL` から引く**。
> **【推測】** `r60util.get_cod_mes_info` / `get_title_color` がこの経路。

### 6.4 `R60_SYSTEM_TBL`（システム・**17 列**）

```
PK  SYS_ID           システムID
    ONL_SIY_KHI_FLG  オンライン使用可否フラグ   ← ★これが false なら画面は使えない
    MSG_NO_1..5      メッセージ番号１〜５
    ＜以下 10 列は共通監査列＞
```

> **【推測】** `r60util.chk_onl_flg`（[04](04-common-parts.md) §2.1）はこの列を見ている。
> **オンライン停止中の画面は、初期表示の時点で弾かれる**はず。
> **【未確認】** R60Login の `init` がこれを呼んでいるかは未確認（[06](06-api.md) §6 を参照）。

## 7. ★L3（禁止外投）に当たる区画（要注意）

**【実測】** `doc/02_INPUT/92.現行DB構築/…コード値・区分値定義_v1.1_オフ提供版.xlsx` は 5 シート：

| シート | 行数 | 扱い |
|---|---|---|
| `変更履歴` | 27 | 可 |
| `汎用マスタ（ヘッダ）` | 127 | **定義**（可） |
| **`汎用マスタ（明細）`** | **9489** | **★L3：業務データ実値。外へ出す前に必ず脱敏** |
| `コード値マスタ（ヘッダ）` | 527 | **定義**（可） |
| **`コード値マスタ（明細）`** | **15249** | **★L3：業務データ実値。同上** |

- **【重要】この 2 シートは「本番の業務データそのもの」である**（規則 01 §10：
  部門コード / 品番 / 金額 / 受注番号などの実データ＝ **禁止外投**）。
- **対外提出物（顧客確認依頼書・日文正式 Excel・報告書）に載せる場合は、
  `tools/masking/mask_demo.py` を通し、`COL_1 = VAL_1` の形へ占位してから出す**（紅线⑦）。
- **本知識庫には値を書いていない。** 構造と行数だけを記録した。
