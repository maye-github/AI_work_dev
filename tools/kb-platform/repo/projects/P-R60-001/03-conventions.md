# 03 規約 — 作る前に必ず当たる 4 冊

> **これは「好み」ではなく「契約」である。** R60 の規約は 3 システム
> （**酒税計算システム / 生産系共通マスタシステム / Tops履歴検索システム**）の共通規約であり、
> 表の列がシステムごとに分かれている。**本案件（共通マスタ）は常に「共通マスタ」列を読む。**
>
> ★ **列の読み違いが最大の罠**。例えばフォントは「酒税 14px / 共通マスタ 12px / 履歴検索 12px」であり、
> **左端の値を読むと 2px ずれる。**

## 4 冊の在処（`doc/02_INPUT/10.規約/`）

| ファイル | 何を決めているか | シート |
|---|---|---|
| `…画面規約_v1.1.xlsx` | 画面の**寸法・領域・フォント・色**。**v1.1 が現行**（v1.0 は旧） | 表紙/変更履歴/目次/1．画面構成/２．支援画面構成 |
| `…コーディング規約_v1.0.xlsx` | **変数名・字下げ・型注釈・ディレクトリ構成・バージョン** | 表紙/変更履歴/目次/1．Vue/2．Python |
| `…画面共通仕様書_v1.2.xlsx` | **全画面共通の処理**（検索上限件数・二重送信・権限など） | 変更履歴/目次/1．画面構成/２．画面遷移/３．画面処理/４．使用コンポーネント/５．複数画面起動 |
| `…共通部品利用ガイドライン(画面)_v1.0.xlsx` | **部品の作り方 27 種**（ヘッダ・明細一覧・日付・トースト…） | **27 シート** |

> ⚠ **`変更履歴` シートを必ず見る**。規約の本文には**旧版の記述が残っている**ことがある
> （例：画面規約 v1.1 の本文には「倍率125%を基準に」と「推奨倍率の150%を基準として」が**両方残っている**。
> `変更履歴` を読むと「**1.1：ディスプレイ倍率150%をアサヒ標準とし、規約を修正する**」と書いてあり、
> 150% が正しいと分かる）。
>
> ⚠ **我々の抽出器は「取り消し線」を見分けられない**。したがって**古い記述も等しく出てくる**。
> 迷ったら `変更履歴` が唯一の判定材料である。

## 1. 画面規約 v1.1（現行）

### 1.1 基本構成（【文書】`1．画面構成`）

| 項目 | 値 |
|---|---|
| 利用端末 | **PC（ASN端末）** |
| ブラウザ | **Google Chrome** |
| OS | Windows11 Pro & Home、Windows10 Pro DG |
| 画面解像度 | **1920×1200px** |
| サイズ変更 | 可能 |
| **基準倍率** | **150%（アサヒ標準）**。フルスクリーン使用前提 |

### 1.2 画面サイズ（★列の対応に注意）

`1．画面構成` の表は **3 つの倍率**を並べている。**現行の基準は 150%**。

| 構成 | 画面解像度 | ヘッダ領域 | 業務領域 | フッタ領域 |
|---|---|---|---|---|
| ① 倍率125%（1366×768） | 1920×1200 | 1366 × **97**px | 1366 × **607**px | 1366 × **64**px |
| ② 倍率100%（最大化時） | 1920×1200 | 1920 × **97**px | 1920 × **903**px | 1920 × **64**px |
| **③ 倍率150%（現行基準）** | 1920×1200 | 1280 × **60.67**px | 1280 × **564.63**px | 1280 × **40.03**px |

- 倍率150% のとき、ブラウザヘッダとタスクバーを除いた業務画面は **1280×665.33px**。
- **【実測】実装は ③（150%）に従っている**：`styles.css` の `.contents_area` は
  `min-width: 1280px; min-height: 564.63px;`、`AppHeader.vue` の `.header_area_title` は
  `height: 56.67px;`。**→ 実装が規約に一致している（差異なし）。**

### 1.3 フォント（【文書】`1．画面構成`（4））

フォント形式は 3 システムとも **メイリオ**。サイズは次の 2 ブロックに分かれている
（**ブロックの見出しに倍率の記載が無く、抽出器では区別できない**。
§1.2 と実装から **ブロック② が 150% 基準**と判定した＝【推測だが実装と一致】）。

| ブロック | 酒税 | **共通マスタ** | 履歴検索 |
|---|---|---|---|
| ①（125%/100% 相当） 全体 | 18px | **14px** | 14px |
| ① 画面名 | 42px | **42px** | 42px |
| **②（150% 相当＝現行） 全体** | 14px | **12px** | 12px |
| **② 画面名** | 28px | **28px** | 28px |

- **【実測】実装は ② に従っている**：`styles.css` の `body { font-family: "メイリオ"…; font-size: 12px; }`、
  `AppHeader.vue` の `.header_area_title { font-size: 28px; }`。**→ 一致。**
- 画面名が複数行（`<br>` 含む）の場合は**ヘッダ領域に収まるよう自動縮小**する（規約逐語）。
  **【実測】** `AppHeader.vue` は `currentFontSize` を既定 **28**、タイトルに `<br>`/`\n` があるか
  `scrollHeight > clientHeight + 5` のとき **20** に落とす。**→ 実装が規約の「自動縮小」を満たしている。**

### 1.4 ヘッダ領域・フッタ領域の中身（【文書】`1．画面構成`（6））

| 領域 | 内容 |
|---|---|
| **ヘッダ領域** | **画面名**（背景色はシステム別：共通マスタは **青 `rgb(0,0,144)`**）。**画面上部固定** |
| **フッタ領域** | **ボタン**（内容は画面ごとに異なる）。**画面下部固定** |
| 業務領域 | 背景色：検索条件部はシステム別（共通マスタは **`rgb(238,242,255)`** 系） |

**【実測】** `AppHeader.vue` は `title` / `subTitle` / `HELP` / **`表示日時：<AppSysDate />`** /
`userInfo.stf_nm`（職員名） / `userInfo.cmp_nm`（会社名） / `userInfo.jig_nm`（事業場名） を出す。
`AppSysDate.vue` は `moment().format("YYYY/MM/DD HH:mm:ss")` を **1000ms ごとに更新**する。

> ✅ **「表示日時は未実装」という指摘は誤り。** ヘッダは `AppHeader.vue:15` の `<AppSysDate />` で実装済みである
> （設計書 `画面項目内容` の「システム日時／YYYY/MM/DD hh:mm:ss／標準仕様参照」に対応）。

**【実測】** `FooterButtons.vue` の標準ボタン：**データ初期化 / 戻る / 業務終了 / 検索**（支援画面のとき）
＋ 画面ごとの `extraButtons`（R60Login は **閉じる**）。

## 2. コーディング規約 v1.0

### 2.1 Vue（【文書】`1．Vue`）

| 項目 | 規約 |
|---|---|
| 宣言 | **`Composition API` のみ**（`<script setup>`）。Options API は禁止 |
| 変数 | **`const` / `let` のみ**。**`var` 禁止**。1 宣言 1 行 |
| 命名 | 変数・メソッド **camelCase** / コンポーネント **PascalCase**（**必ず 2 語以上**） |
| 字下げ | **スペース 2** |
| チェッカ | **eslint** |
| エディタ | VSCode |

**ディレクトリ構成**（逐語：「任意に作成は行わない」）：

| ディレクトリ | 説明 |
|---|---|
| `assets` | 画像ファイルや CSS |
| `common` | 共通ライブラリ |
| `components` | 画面情報 |
| `router` | ルーティングによる画面遷移制御 |
| `stores` | 固有ファイルは `index.ts` |
| `views` | メニューからリンクする画面 |

**ファイル命名**：`components` は `[画面ID] + List等`（拡張子 `.vue`）／`views` は `[画面ID]`（`.vue`）。

> **【差異】D-11**：規約の一覧に **`service` が無い**のに、実物は `src/service/` に **56 本**の
> `[画面ID]Service.ts` を持つ。**API 呼び出しは全部ここを通る**ので、**重做のときは必ず作る**。
> → [08-deviations.md](08-deviations.md)

**宣言されたライブラリとバージョン**（規約の表）：

vue `3.5.x` / vue-router `4.5.x` / @primeuix/themes `1.2.x` / vue-axios `3.5.x` /
primeicons `7.0.x` / **primevue `4.3.x`** / typescript `5.8.x` / bootstrap `5.3.x` /
moment `2.30.x` / **pinia `2.1.x`** / qs `6.14.x` / **@auth0/auth0-spa-js `2.0.x`** /
**vite `7.1.x`** / @vitejs/plugin-vue `6.0.x` / @vue/tsconfig `0.7.x` / vue-tsc `3.0.x`。
逐語：**「Vueプロジェクトの実行にはNode.jsが必要であるが、Node.jsのバージョンは24.7を想定している。」**

**【実測】一致**：`package.json` の実値（[02-architecture.md](02-architecture.md) §1）はすべて規約の範囲内。
ただし `axios` は規約表には `vue-axios 3.5.x` とあるが**実装は `axios 1.16.1` を直接使う**（`http-common.ts`）。

### 2.2 Python（【文書】`2．Python`）

| 項目 | 規約 |
|---|---|
| 準拠 | **PEP8** |
| 字下げ | **スペース 4**（タブ禁止） |
| 行長 | **最大 120 文字** |
| 空行 | トップレベルの関数・クラス定義の間に **2 行** |
| 命名 | 変数・関数 **snake_case** / クラス **PascalCase** / 定数 **UPPER_SNAKE** |
| 型 | **変数の型を明示的に書く**（規約の内部ルール） |
| 引用符 | **ダブルクォーテーションで統一**。理由（逐語）：**「SQL文の作成を考慮して」** |
| 整形 | **BlackFormatter**（既定設定） |
| チェッカ | **Flake8** |

**ディレクトリ構成**（逐語：「任意に作成は行わない」）：

```
(A) bashapp（バッチ処理のプロジェクト）
    python/ ├── common（共通処理）
            └── module1.py, module2.py …（python ディレクトリ直下に機能毎のファイル）

(B) fastapi（画面バックエンド処理のプロジェクト）
    app/ ├── common（共通処理）
         ├── models（api 通信用のモデル管理）
         └── routers（api によるルーティング管理）
```

**ファイル命名**：`models` / `routers` は **`[画面ID].py`**（`routers` の固有ファイルは `common.py`）。

> **【差異】D-12**：実物の `app/` には規約の 3 つ以外に **`auth/` `script/` `utils/` `config.py` `dbsession.py`** がある。
> → [08-deviations.md](08-deviations.md)

**宣言されたライブラリとバージョン**（規約の表）：

### 3.1 検索時の上限件数（★見落とすと必ず手戻る）

**【文書】`３．画面処理`** 逐語：

> **（４）検索時の上限件数**
> 「検索条件画面にて検索条件を指定し、表示ボタン（仕掛表示ボタン）を押下した際に取得した該当レコード件数が
> **上限件数を超過した場合エラーダイアログを表示する**。」
> 「検索時の上限件数は**各画面毎にコード値明細マスタ（`R60_CODE_MES_M_TBL`）に定義されている**。」
> 情報ＩＤ … `K:` ／ キー `L:`（**`KEY_ID` が画面 ID に対応する**）

- つまり**上限値はコードにハードコードしない**。**コード値明細マスタのデータ**である。
- 読み方は [05-database.md](05-database.md) §5 を参照。

### 3.2 その他の共通処理

`３．画面処理` に「（１）〜（４）」の形で共通処理が並ぶ。**`４．使用コンポーネント`** は
どの PrimeVue 部品をどの場面で使うかを固定する。`５．複数画面起動` は
「1 画面から別画面を開く」ときの規約（本案件は支援画面・登録/修正画面が別コンポーネントなので頻出）。

**【未確認】** `３．画面処理` の（１）〜（３）の逐語は未採取。**画面を作る直前にこのシートを読むこと。**

## 5. 画面設計書の読み方（`50.設計書/画面設計書/*.xlsx` 8 シート）

**【実測】R60Login の設計書は 8 シート**（画面ごとに同じ構成）：

| # | シート | 何が書いてあるか | 主な使い方 |
|---|---|---|---|
| 0 | `変更履歴` | 改版履歴（27 行の定型） | **版の判定に使う** |
| 1 | `画面概要` | 42 行。前提条件・利用対象者・処理概要 | 要件・基本設計の材料 |
| 2 | `画面遷移図` | 16 行 → **【未確認】画像** | 遷移の確認（人の手でテキスト化する） |
| 3 | `画面レイアウト` | 11 行 → **【未確認】画像** | レイアウト（同上） |
| 4 | **`画面項目内容`** | **91 行。項目 × 15 列** | **最も重要。I-ID の原料** |
| 5 | `イベント一覧` | 17 行。ボタン × イベント × 呼び出し | 業務ロジックの入口 |
| 6 | `業務処理説明` | 61 行 | **現行 Java の処理手順**（★Struts の署名が出てくる） |
| 7 | `R60XxxAction` | 24 行。Action クラスの構造 | 現行側の対応表 |

### 5.1 `画面項目内容` の列構成（【実測】）

```
No. | 項目名称 | 種別(属性) | I/O | 必須 | エンティティ(型/桁/エンティティ名/項目名) | 画面表示(型/桁/位置/ソート/表示形式) | 表示・入力仕様
```

- `A:No.` / `B:項目名称` / `G:種別(属性)` / `K:I/O`（`I`入力・`O`出力） / `L:必須` /
  `M:型`・`N:桁`・`O:エンティティ名`・`S:項目名` / `W:型`・`Y:桁`・`Z:位置`・`AA:ソート`・`AB:表示形式` /
  `AF:表示・入力仕様`
- **`画面構成部`** 列（`A` の右）で「ヘッダー部 / 検索条件部 / ボタン部」に区切られる。
- シート末尾に **`画面項目リスト仕様`**（画面 ID → テーブル名の対応）が付く。

> **【推測】** `エンティティ名`＋`項目名` の組が、その項目の**物理的な出所**（＝ テーブルと列）を示す。
> 例：R60Login の「ユーザーＩＤ」は **エンティティ名 `ユーザーマスタ` / 項目名 `社員コード`** →
> 物理は `R60_USER_M_TBL.STF_CD`。
