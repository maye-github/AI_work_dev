# 08 【差異】登記簿 — 骨架規則 vs 実物、向こうの文書 vs 向こうの実装

> **本書の立場**：**裁定は「実物を正とし、差異を残す」**（2026-10-13 人裁定）。
> **骨架規則の条文は、ここで勝手に書き換えない。** 差異を記録し、必要な修正は**人が判断する**。
>
> **★読み方**：ここに挙がった差異は**「誤り」ではない**。
> **規則が書かれた時点のスナップショット**と、**その後育った実物**の**時刻差**であることが多い。
> **だから「どちらが正か」ではなく「どちらに合わせて作るか」を決める材料として使う。**

## A. 骨架規則 vs 実物 — 詳細

### D-1 `extra="ignore"`（★最も影響が大きい）

| | |
|---|---|
| **規則** | `.claude/rules/03-design-coding.md` §2：`extra='forbid'`（「未定義項目は 422 で拒否」） |
| **実物** | `extra="ignore"` **128 箇所** ／ `extra="allow"` 1 ／ **`forbid` は 0** |
| **根拠** | 【実測】`app/routers/R60LoginController.py:23-30` ほか。`grep -rho 'extra="' app --include=*.py \| sort \| uniq -c` |

**含意**：**実物は定義外のキーを黙って捨てる。規則どおり `forbid` で作ると、
人間版では正常に動く要求が 422 で落ちる。** 対比の前にここを揃えないと、差異が全部この 1 点に吸収されてしまう。

**併せて**：§2 は「改定・項目追加の検知」を `forbid` の目的として挙げるが、
**実物は `ignore` で運用している**（＝**追加項目の混入は検知されない**）。
**【推測】** 実案件では**入力項目が頻繁に増える**ため、`forbid` では運用が回らなかったと考えられる。

> **対処**：**`ignore` に合わせて実装する。** 骨架規則 03 §2 の修正可否は**人が裁定**する。

### D-2 `BaseCamelModel` は 54 ファイルに写されている

| | |
|---|---|
| **規則** | 規則 03 §2／§4：派生モデルは `model_config` を再定義しない（＝共有基類が 1 箇所） |
| **実物** | **`class BaseCamelModel` の定義は 54 ファイルに在る**（すべて `app/routers/` の下）。**同一の定義が各ファイル冒頭に 1 回**置かれている |
| **根拠** | 【実測】`grep -rl '^class BaseCamelModel' app/ \| wc -l` → **54** |

**★数え方（混同しやすい）**：**controller は 55 本、うち `BaseCamelModel` を持つのは 54 本**である。

```
# 【実測】2026-10-14
ls app/routers/R60*Controller.py                        → 55
grep -rl '^class BaseCamelModel' app/routers/ | wc -l   → 54
for f in app/routers/R60*Controller.py; do grep -q '^class BaseCamelModel' "$f" || echo $f; done
                                                        → R60CommonController.py   ★これ 1 本だけが持たない
```

> **`R60CommonController.py` だけが例外である**（`from pydantic import BaseModel` を使う。→ [06](06-api.md)）。
> **`default.py` と `__init__.py` は controller ではない**（`include_router` は 56 本 ＝ 55 controller ＋ `default.py`）。
> **★「55」と書いてある記述を見たら「54 ＋ `R60CommonController`」と読み替えること。**

**含意**：**「1 箇所直せば全部に効く」が成立しない。** **54 本が独立に写し取られている。**
**【推測】** AI 生成の都合（1 ファイル完結で生成させる）だと考えられる（[09](09-ai-workflow.md)）。

> **対処**：**新しい画面もファイル冒頭に置く**（実物に合わせる）。
> インポートで共有する形にすると、**人間版と行数・構造が変わる**。

### D-3 `R60Common.ts` は 54 ではなく 60

| | |
|---|---|
| **規則** | `CLAUDE.md` §2 禁①・規則 00 §8：「**54 関数の唯一真源**」 |

**含意**：**規則の 54 は「同期関数だけを数えた値」**である。**非同期 6 本が数えられていない。**

**「54 あるはず」と決め打ちして照合すると 6 本を取りこぼす。**

> **対処**：**照合は 60 で行う。** 6 本の非同期のうち `showErrorAndFocus`（:1509）は
> **規則 03 §3 の 13 関数に含まれている**ので、**規則内でも数え方が揺れている。**

### D-5 分頁は `ROWID` 一本ではない

| | |
|---|---|
| **規則** | 規則 00 §5：「ページングは**原則 `ROWID` 方式**、`OFFSET-FETCH` は **doc/01 の報告書に基づき必要時のみ**」 |

> **対処**：**「全面 `ROWID`」と仮定して一括変換しない。** 画面ごとに**実物を読んで決める**。
> **`ALLOWED_SORT_FIELDS` 白名单の方式は規則と一致**している（こちらは素直に従ってよい）。

### D-6 派生モデルの `model_config` 再定義は「無い」と言えない

|---|---|
| **規則** | 規則 03 §2：「派生モデルでは `model_config` を**再定義しない**」 |

> **ただし `alias_generator` / `populate_by_name` / `serialize_by_alias` の 3 行は必ず引き継ぐ**
> （書き漏らすと**蛇↔駝の変換が静かに壊れる**）。

### D-24 暗号化ロジックの二重実装 ＋ 環境時計依存 ＋ 同名フィールドの意味反転（★禁①の趣旨に触れる）

| | |
|---|---|
| **実物** | **TS**：`Front-end/src/common/utils.ts:401-455` `encryptStaffCode` |
| **実物** | **Python**：`app/routers/R60LoginController.py:447-505` `encrypt_stf_cd` |
| **実物** | 両者の docstring が**同じ旧 JS を引用**（`旧JS: if (iCnt == 4)` / `switch`）。**アルゴリズムは同一**（`9`→`10`、5 桁目でブロック分割、`+1`＋ゼロ埋め） |
| **実物** | **当日日付を実行環境の時計から取る**：TS `new Date()` ／ Python `datetime.now()` |
| **実物** | **同名 `stf_cd` の意味が端点で反転**：`/login` は**暗号化済み**を期待（`Field(..., description="社員コード（暗号化済み）")`）／`/generateUrl` は**平文**を期待（`:404` のコメント「generateUrl は平文の stfCd を受け取り、サーバー側で暗号化する」） |
| **根拠** | 【実測】`sed -n '395,430p' Front-end/src/common/utils.ts` と `sed -n '466,500p' …/R60LoginController.py` の突き合わせ ／ `grep -rn "R60_ENCRYPT_STF_CD_FNC" --include=*.py --include=*.ts .` → **docstring の 1 行のみ** |

**含意 1（唯一真源）**：**同じ 1 つの算法が 2 言語に写されている。** `r60util.py` には**暗号化関数が無い**
（`grep -nE "def .*(encrypt\|decrypt)" app/utils/r60util.py` → **なし**）。
**禁①（並行新版の作成禁止）の趣旨からすれば、本来到達点は「1 箇所」であるべき。**

**含意 2（決定性）**：**当日日付がクライアントの時計に依存する。**
日付が変わった直後にクライアントとサーバの日付がずれると、**復号が失敗して「存在しない社員」扱い**になる。
規則 03 §7.1「**現在時刻を出力へ埋め込まない。必要なら引数として注入する**」の**実例**である。

**含意 3（境界）**：**同名フィールドの意味が端点で反転している。**
型はどちらも `str` なので **422 にならず、静かに壊れる**。

> **対処**：**対比ではこの 3 点を毎回明示する。**
> - アルゴリズムは**設計書に完全には書かれていない**（§12.2【未確認】1）→ **再実装では確定で差異が出る**
> - **規約の「唯一の変換点は `BaseCamelModel`」に反する形**（規則 03 §4.1）
> - **`stf_cd` の意味は端点ごとに確認する**（名前で判断しない）

### D-25 同一業務フィールドの符号系が 3 系統ある

| | |
|---|---|
| **文書** | `画面項目内容` No.9 権限区分：ドロップダウンの表示は**「更新あり」／「更新なし」**（**符号値は書いていない**） |
