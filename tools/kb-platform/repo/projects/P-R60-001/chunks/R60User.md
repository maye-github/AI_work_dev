## R60User / 検索条件・件数上限・ソート・ページング（L-US-02〜05）

## R60User / 自工／他工判別と登録ボタンの活性制御（L-US-09〜10）

`USR-LGC-004` / `logic`
設計の自工判別は OR 条件：ログインユーザーの所属会社／事業場が経理用会社／事業場と一致、または S 会社／S 事業場と一致すれば自工、それ以外は他工、S 会社／S 事業場のいずれかが空白なら他工。実装は『経理用が入力されていれば経理用とだけ比較し、無ければ S と比較する』に単純化しており、両方が入力されて異なる場合に結果が変わりうる（D-US-05）。登録ボタンの制御は、権限区分が 'Y' 以外なら非活性。自工更新フラグ='0' かつ他工更新フラグ='0' なら非活性。両方='1' なら活性。それ以外は自工なら活性、他工なら非活性。差異：活性判定はモーダル初期化時に 1 回だけ行われ、経理用会社を変更しても再判定しない（D-US-12）。ストアの registBtnEnabled / deleteBtnEnabled は true が『非活性』を意味する反転命名である。

## R60User / 登録処理の順序とチェック（L-US-11〜15）

`USR-LGC-005` / `logic`
登録は次の順で処理する。変更なし判定（R60W0016）→ 緊急配信オンのとき 5 項目必須（R60W0012）→ メールアドレス２の桁（R60W0103）と '@'（R60W2001）→ 経理用会社と経理用事業場のセット（R60W2002）→ 登録確認（R60A0003）→ 排他（R60W0006）→ UPDATE 15 列 → 緊急配信 → commit → R60I0001。排他は画面が保持する KSN_DAT と DB の KSN_DAT を比較し、更新区分='1' かつ不一致なら中断する。一致時は KSN_DAT をシステム日時で更新し REV_NO を +1 する。差異：単項目・項目間・緊急配信必須のチェックはすべてフロントエンドで行い、更新端点は排他と REG_STS 以外を再検証しない（D-US-06）。対象行が存在しない場合も R60W0006 を返す（D-US-07）。更新者 ID はクライアントから受け取る（D-US-15）。

## R60User / 緊急配信と REG_STS 判定（L-US-14 / L-US-16）

REG_STS は役割・帳票共有グループ・帳票参照・帳票権限・ユーザタイプの 5 項目がすべて非空なら '1'、いずれかが空なら '0'。R60Plc の REG_STS（18 項目＋タンク 6 項目）と違い、条件付き必須は無い。緊急配信チェックがオンのときだけ、テーブル ID（R60_USER_M_TBL）・ログインユーザの社員コード・プログラム ID（R60User）を引数に緊急配信パッケージを呼び、commit の前に実行する。設計の引数と実装の引数は一致しており、良い対比になる。ただし実装は画面から渡された ksn_stf_id をそのまま緊急配信の引数にも使う（D-US-15）。
