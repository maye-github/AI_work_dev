### RC-01 排他制御が `ksnDat` の一致のみで判定され `revNo` が比較されない

- 対応スナップショット: `review_before/RC-01_*.py` ↔ `review_after/RC-01_*.py`
- 問題点: edit / delete の事前チェックで `ksnDat`（改竄日時）だけを比較し、`revNo`（リビジョン番号）を比較していなかった。同一秒内に 2 ユーザが更新すると、後勝ちで先行更新が無警告に上書きされる（ロストアップデート）。`E-002`（R60W0006）が検知されないケースが残る。
- 根本原因: 楽観ロックの比較キーを「日時 1 項目」と誤認した。`ksnDat` の分解能（秒）を排他キーとして過信し、`revNo` を表示専用項目として扱っていた設計合意の欠落。
- 修正方針: 更新系の WHERE 条件に `AND ksnDat = :ksnDat AND revNo = :revNo` を必ず含め、更新件数 0 件を `E-002` にマップする。`revNo` は更新成功時に `+1` する。
- 予防策（ルール）: **更新系 DML の WHERE 句は `ksnDat` と `revNo` の 2 項目を必須とする。どちらか一方のみの排他条件を許可しない。**
- 関連 R-ID: R-101

### RC-02 被参照チェックが参照側の `DEL_FLG` を考慮せず論理削除済み参照を数える

- 対応スナップショット: `review_before/RC-02_*.py` ↔ `review_after/RC-02_*.py`
- 問題点: 削除前の被参照件数集計で参照側テーブルの `DEL_FLG`（削除フラグ）を絞り込まず、論理削除済み（`DEL_FLG=1`）の参照行まで「参照あり」と数えていた。実質参照が無いレコードの削除が `E-004`（R60W0024）で拒否され、操作者が回避手段を持てない。
- 根本原因: 被参照チェックを「物理的な行の存在」で判定した。本システムの論理削除方針（`DEL_FLG=1` は無効行）を参照チェックに反映していなかった。
- 修正方針: 参照側の集計クエリに `WHERE DEL_FLG = 0` を付与し、有効参照が 0 件のときのみ物理削除（または対象行の論理削除）を許可する。
- 予防策（ルール）: **被参照チェックの集計は参照側テーブルの `DEL_FLG=0` を必須条件とする。論理削除済み行を参照ありとして計上してはならない。**
- 関連 R-ID: R-101

### RC-03 キー重複チェックが `araCd` 単独で行われ三鍵複合になっていない

- 対応スナップショット: `review_before/RC-03_*.py` ↔ `review_after/RC-03_*.py`
- 問題点: 新規登録・複製時の存在チェックが `araCd` 単独で行われ、`cmpCd`（会社コード）＋ `jigCd`（事業場コード）が異なる正当なレコードまで重複扱いされた。逆に、複合キー観点での重複検出が不十分で `E-003`（R60W0014）の判定が業務と一致しない。
- 根本原因: 画面の主キー表示が `araCd` 中心だったため、物理主キーが三鍵複合（`cmpCd`＋`jigCd`＋`araCd`）であることを実装時に単純化してしまった。
- 修正方針: 存在チェックの WHERE を `cmpCd = :cmpCd AND jigCd = :jigCd AND araCd = :araCd` の三鍵一致に修正し、一致時に `E-003` を返す。
- 予防策（ルール）: **主キーの重複判定は物理主キーの構成列を漏れなく全部使う。画面表示キーの一部のみでの存在チェックを禁止する。**
- 関連 R-ID: R-101

### RC-04 LIKE 検索でワイルドカードの ESCAPE が漏れている

- 対応スナップショット: `review_before/RC-04_*.py` ↔ `review_after/RC-04_*.py`
- 問題点: 名称の前方一致検索で `LIKE :araNm || '%'` を組み立てる際、入力値中の `%` と `_` をエスケープしていなかった。`_` を含む名称の検索で意図しないレコードが 0 件または過剰にヒットする。
- 根本原因: ワイルドカードを SQL 側の固定文字列として扱い、入力値を「データ」と「パターン構文」に分離する意識が欠落していた。ESCAPE 句の設計が詳細設計に無かった。
- 修正方針: 検索入力整形時に `%`→`\%`・`_`→`\_`・`\`→`\\` の順でエスケープし、SQL に `LIKE :pat ESCAPE '\'` を付与する。エスケープは共通ユーティリティに集約する。
- 予防策（ルール）: **LIKE に外部入力値を埋め込む場合は ESCAPE 句と入力エスケープ関数を必ず対で適用する。素の `LIKE :val || '%'` を禁止する。**
- 関連 R-ID: R-101

### RC-05 ページングを `OFFSET-FETCH` 固定で実装し ROWID ページングの使い分けが無い

- 対応スナップショット: `review_before/RC-05_*.py` ↔ `review_after/RC-05_*.py`
- 問題点: 一覧検索と CSV ダウンロードの件数取得・ページ取得がすべて `OFFSET-FETCH` で実装され、後方ページほど走査コストが増大した。さらに総件数取得がページ毎に全件集計を再実行していた。
- 根本原因: ページング方式の指針（`doc/01` の `OFFSET_FETCH_ROWID` 報告書、rule 5）を確認せず、実装容易性だけで `OFFSET-FETCH` を選択した。
- 修正方針: 大量件数が想定される一覧は `ROWID` ページングを基礎方式とし、`OFFSET-FETCH` は件数が小さいことが保証される画面に限定する。総件数はページ取得と分離してキャッシュする。
- 予防策（ルール）: **一覧ページングの既定は ROWID ページングとする。OFFSET-FETCH の採用は対象件数の上限を設計書に明記した場合に限る。**
- 関連 R-ID: R-101

### RC-06 REG_STS 判定から必須 15 項目の一部が漏れている

- 対応スナップショット: `review_before/RC-06_*.py` ↔ `review_after/RC-06_*.py`
- 問題点: 登録ステータス（`regSts`）の判定で、必須 15 項目のうち計上系の一部（受払・債務・債権の計上事業場／部署）が検証対象から漏れ、未入力でも `REG_STS='1'`（登録済）に到達した。
- 根本原因: 必須項目リストを実装コード内にバラバラの条件式で記述し、単一の定義（15 項目のリスト）として一元管理していなかった。項目追加時に追随漏れが発生する構造だった。
- 修正方針: 必須 15 項目を定数リスト（1 か所）として定義し、`regSts` 判定はそのリストを走査して全項目充足時のみ `'1'` とする。項目追加はリストへの追記のみで完結させる。
- 予防策（ルール）: **`REG_STS` 判定の必須項目は単一の定数リストで定義し、判定ロジック内に個別の必須条件式を散在させない。**
- 関連 R-ID: R-101

### RC-07 桁数チェックが文字数で行われバイト数定義と不一致

- 対応スナップショット: `review_before/RC-07_*.py` ↔ `review_after/RC-07_*.py`
- 問題点: 名称系項目の入力長を `len(value)`（文字数）で検査していたため、全角文字を 1 文字として数え、DB のバイト数定義を超える値が通過した。登録時に桁溢れで `E-005`（R60E0025）が発生する。
- 根本原因: 文字数とバイト数の混同。業務定義（全角=2 バイト／半角=1 バイト換算）が詳細設計のチェック仕様に落ちていなかった。
- 修正方針: 項目定義のバイト数上限に基づき、全角 2／半角 1 で換算するバイト数チェック関数を共通化して適用する。全角・半角の混在も同一関数で扱う。
- 予防策（ルール）: **入力長は文字数ではなくバイト数（全角=2／半角=1 換算）で検査する。`len()` による文字数チェックを桁チェックとして使わない。**
- 関連 R-ID: R-101

### RC-08 認可判定が UI のボタン活性のみで API 側に無い

- 対応スナップショット: `review_before/RC-08_*.py` ↔ `review_after/RC-08_*.py`
- 問題点: 参照権限のみのロールでも、活性制御を迂回して更新系 API を直接呼ぶと登録・修正・削除が成立した。認可がフロントのボタン `disabled` に依存していた。
- 根本原因: 「権限＝表示制御」と誤解し、画面の活性制御を認可の一次防衛線として設計した。API 層での権限再検証が設計に明記されていなかった。
- 修正方針: 更新系 API の先頭でセッションのロールを再検証し、権限不足時は業務エラーを返す。UI の活性制御は補助（UX）として位置づけ、単独では認可としない。
- 予防策（ルール）: **更新系 API は呼び出し元に関わらず権限をサーバ側で再検証する。UI のボタン活性制御を認可の代替にしてはならない。**
- 関連 R-ID: R-101

### RC-09 通常更新が既存の緊急配信状態（SEND_STS）を破壊する

- 対応スナップショット: `review_before/RC-09_*.py` ↔ `review_after/RC-09_*.py`
- 問題点: 既存レコードの通常修正時に送信ステータス（`sendSts`）を初期値で上書きし、既に立っていた緊急配信（`sendSts` の最優先値）をクリアしてしまった。緊急再配信が行われない。
- 根本原因: 更新項目一覧に `sendSts` を機械的に含め、送信系項目は「業務操作によってのみ変更される」という不変条件を考慮しなかった。
- 修正方針: 更新用の SET 句から送信系項目を除外し、送信系は専用の業務操作（緊急配信操作）でのみ変更する。修正時に既存値は保持する。
- 予防策（ルール）: **送信系項目（`SEND_STS`・`SEND_KBN`）は一般更新 DML の SET 句に含めない。専用操作以外での変更を禁止する。**
- 関連 R-ID: R-101

### RC-10 ロケーション未登録エラーの `error_flg` が 1 固定で 2 を返さない

- 対応スナップショット: `review_before/RC-10_*.py` ↔ `review_after/RC-10_*.py`
- 問題点: ロケーション未登録判定で `error_flg` を原材料（`1`）固定で返し、半製品（`2`）の場合も原材料向けメッセージを表示した。`E-006` / `E-007`（同一エラー ID・`flg` 違い）の出し分けが機能していない。
- 根本原因: 判定区分（原材料／半製品）を分岐条件として設計に保持せず、メッセージ文言の共通化時に `flg` を定数化してしまった。
- 修正方針: 判定結果に応じて `error_flg` に `1`（原材料）または `2`（半製品）を設定し、`flg` に応じたメッセージを返す。区分の判定根拠を詳細設計に明記する。
- 予防策（ルール）: **同一エラー ID で `flg` により分岐するエラーは、全 `flg` 値を設計書に列挙し、実装が全値を返し分けることを単体テストの必須項目とする。**
- 関連 R-ID: R-101

1. 被験者: R60 ドメイン未経験の新人 3 名（本資産の作成・レビューに不関与）。
2. 提示物: 各指摘の `review_before` と `review_after` の差分のみ（`review_comments.md` は非開示）。
3. 課題: 差分を見て「何が問題か」を自分の言葉で記述する（問題点カテゴリの言い当て）。
4. 判定: 新人の記述が記録済み指摘の**主要観点**（下表「主要観点」列）と一致すれば「再現 ○」、部分的または不一致なら「△（未再現）」。
