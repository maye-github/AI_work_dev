# 知識ベース利用手順（初心者版）

> **一言で**：以前どうやったかを知りたいときは、これを聞く。外へ出すものは、これが関所になる。
> **ただし向こうからは話しかけてこない——聞かなければ、何も言わない。**

この文書は初めて使う人向けである。**コマンドを覚える必要はない。** 日本語で話しかければよい。
各節は「いつ使う → 何と言う → AI が何をする → 何が返る」の順で書いてある。

> 中国語版は `知识库使用手顺.md`、本書はその日本語版である。内容は同一で、
> 実装値（コマンド・`doc_id`・画面名）は原文のまま残している。

---

## 0. まず三つだけ理解する（2 分）

### 0.1 庫は二層に分かれている

| 層 | 何を置くか | 現在 |
|---|---|---|
| **会社級** | 顧客が変わっても成立するもの：テンプレート・規約・画面パターン・汎用用語 | 30 篇 |
| **案件級** | その顧客固有の事実：画面カード・モジュールカード・審査記録・旧設計 | 85 篇 |

（件数は変わる。「**知識ベースはいまどんな状態**」と聞けば現在値を返す。）

**なぜ二層か**：会社級は誰でも引ける。案件級はその案件の担当者しか引けない。
混ぜると、A 顧客のものが B 顧客に見えてしまう。

### 0.2 普通の「検索」とは違う

普通の検索はリンクの一覧を返す。この庫は**出典付きの結論**を返し、
**その結論がどれくらい確かか**も添える（§3 参照）。

そして向こうからは押してこない。**聞かなければ、何も言わない。**

### 0.3 三つの単語だけ知っておく

| 単語 | かみくだくと |
|---|---|
| `draft` / `open` | 草稿／検索可能。機械が抽出したものはまず草稿で、**人が見て初めて検索可能になる** |
| `doc_id` | 知識 1 件の名前（例 `TPL-DESIGN-BASIC-001`）。これを書けばその 1 件を指す |
| `ingest` | 索引の更新。**ファイルを直してもこれを走らせなければ、直っていないのと同じ** |

## 1. 5 ステップで慣れる（10 分）

| 步 | やること | どうやるか |
|---|---|---|
| 1 | 自分が誰かを伝える（1 回だけ） | 「**私は李です**」と言う |
| 2 | 一つ聞く | 「**知識ベースで調べて：以前の一覧画面はどう作った**」 |
| 3 | 結果を見る | まず `【推測】` の有無、次に `doc_id` |
| 4 | 言い換えて聞く | 日本語でそのまま聞けばよい。用語は自動で補われる |
| 5 | 出ないときは「出ない」と言う | 「庫に無い」と決めつけない。§4 の順に切り分ける |

> **検索エンジンではなく「昔いた同僚」だと思うこと。**
> 同僚は自分から話しかけてこない。だが正しく聞けば、前回どうやったか、どこで転んだかを教えてくれる。

## 2. 機能別の七つ

以下の各節が一つの機能である。**「何と言うか」だけ見ればよい。** 残りは AI がやる。

---

### 機能 ①　調べる：この件は以前どうやったか

**いつ使う**：新しい画面・新しい機能を任された。ゼロから考えたくない。

> **こう言う**：「知識ベースで調べて：以前の一覧画面はどう作った」
> **または**：「これの先例はある？」

**AI がすること**：日本語の語で引き、関連度順に返し、**根拠の強さ**を添える。

**返ってくるもの**：

```
[PAT-SCREEN-001] 一覧検索画面の標準パターン —— 条件部 + 結果部の並べ方
[r60-001-screens-r60area] ある実画面が当時どう設計されたか
```

**注意**：`【推測】` が付いた項目は**結論として使わない**。文面に無く、システムが推測したものだ。

---

### 機能 ②　探す：テンプレート・共通部品・規約

**いつ使う**：設計書を書くとき、コードを書くとき。

> **こう言う**：「基本設計書のテンプレートはある」
> **こう言う**：「共通部品は何がある」
> **こう言う**：「コーディング規約はどこ」

**返ってくるもの**：

| 欲しいもの | 返る `doc_id` |
|---|---|
| 基本設計の雛形 | `TPL-DESIGN-BASIC-001`（9 節の骨格。埋めるだけ） |
| 詳細設計の雛形 | `TPL-DESIGN-DETAIL-001` |
| 単体テストの雛形 | `TPL-TEST-CASE-001` |
| 結合テストの雛形 | `TPL-INTEGRATION-TEST-001` |
| 共通部品の対応表 | `r60-001-standards-r60common-map`（代表 16 関数。どの場面でどれを呼ぶか） |
| コーディング規約 | `STD-CODING-001` |

**省けること**：すでにある関数を、もう一度作ってしまう事故。

---

### 機能 ③　作る：新しい案件の知識庫を立ち上げる

**いつ使う**：新しい顧客・新しい案件が始まった。

> **こう言う**：「新しい案件の知識ベースを作りたい。案件名は『受注管理システム』、ID は P-ABC-001。」

**AI がすること**：三つの情報（ID・名称・責任者＝あなた）で器を作り、権限台帳に登録する。

```
tools/kb-platform/repo/projects/P-ABC-001/
├── sources/     ← 原本を置く（xlsx/docx/pdf/md/txt）
├── extracted/   ← 機械が抽出したテキスト（草稿。まだ検索できない）
├── knowledge/   ← AI が整理した知識（人が確認すると検索できる）
├── modules/  screens/  standards/  playbooks/  glossary/  review/  chunks/
```

**返ってくるもの**：「できました」と、次にやること。

**注意**：器の作成は**冪等**である。もう一度走らせても、置いたファイルは上書きされない。

---

### 機能 ④　入れる：Excel / Word / PDF を庫に入れる

**いつ使う**：顧客から古い資料をまとめて渡された。

**あなたがやることは一つだけ：ファイルを `sources/` に置く。** そのあと一言。

> **こう言う**：「sources の資料を知識ベースに取り込んで」

**AI がすること**（4 段階。途中で止まってあなたを待つ）：

| 段 | AI がやる | あなたがやる |
|---|---|---|
| 1 | 原本を `.md` に変換し `extracted/` へ。**草稿**として置く | — |
| 2 | 報告を出す：表が何枚・何行・何文字、どこに警告があるか | **原本と突き合わせて抽出漏れを確認** |
| 3 | 確認後、草稿を**検索可能**にする | **ここは人の判断が要る** |
| 4 | 索引を作る。検索できるようになる | — |

**報告はこう出る。見るのはこの三行**：

```
[P-ABC-001] 2 件
  ○ ログイン仕様.docx → login-spec.md  (段落 2 / 表 1 / 字 57)
       ⚠ 抽出が極端に短い — 図や画像だけの可能性があります
  ○ 画面項目一覧.xlsx → screen-items.md  (sheet 1 / 行 6 / 结合 1 / 字 137)
       ⚠ 結合セル 1 箇所 — 結合された内容が落ちていないか確認してください
```

| 見たもの | 意味 |
|---|---|
| `sheet 3 / 行 120` | 原本は 3 シート・120 行抽出——**シートが欠けていないか確認** |
| `结合 14` | 結合セル 14 箇所。**ここが一番落ちやすい**。重点的に抜き取り確認 |
| `字 57` | 抽出文字数。**少なすぎるなら原本が画像**。人が何とかする |

**なぜ草稿のまま検索させないか**：

> 機械の抽出はよく外す（表の列ずれ、結合セルの欠落、PDF の版面崩れ）。
> 誤ったものが検索できてしまうと、AI が引用し、複製し、さらに広げる。**だから人が一度見る。**

**対応形式**：`.xlsx` `.docx` `.pdf` `.md` `.txt`
（PDF は `pdftotext` が必要。無い場合は明示的に失敗する。黙って落ちない。）

**原本を直したら**：もう一度取り込む。内容が変わっていれば**自動で草稿に戻る**ので、もう一度見る。

---

### 機能 ⑤　使う：8 工程の各節点で先例を引く

**いつ使う**：あの 8 工程を回していて、各節点で承認版を出すとき。

> **こう言う**：「節点 3 はどの先例を引くべき？」
> **または**：「この主題の先例を探して」

**AI がすること**：**その節点で必ず読む条目**を告げ、候補を探して文書の `kb_refs` に書き入れる。

**返ってくるもの**：引用の一覧。

```yaml
kb_refs: [TPL-DESIGN-BASIC-001, r60-001-screens-r60login]
```

**決まりは二つ**：

| 書き方 | 意味 |
|---|---|
| ✅ `TPL-*`（雛形）、`PAT-*`（パターン）、`r60-*`（案件事実） | **先例**——写す／突き合わせる対象 |
| ⚠️ `STD-*`（規約） | **守っていることの証明**であり先例ではない。規約は「従う」もので「参考にする」ものではない |

**先例が無いとき**：`kb_refs: []` と書き、**未確定事項に理由を書く**。
空欄のままにしない——空欄と「探していない」は見分けがつかない。

**この検査を通らないと、節点は承認できない。**

### 機能 ⑥　渡す：案件終了時に、使えるものを会社級へ昇格する

**いつ使う**：案件が終わり、「他の案件でも使える」ものを外に出したい。

> **こう言う**：「どれが昇格できるか見て」

**AI がすること**：**レビュー表**を出す。四節からなる。

| 節 | 内容 |
|---|---|
| §0 | 会社級にいま何があるか（種別ごと） |
| §1 | 候補一覧：各行に**建議＋理由＋脱敏後に残る問題の数** |
| §2 | 建議ごとに次にやること |
| §3 | 脱敏でまだ足りない語（置換表に足す） |

**建議は 5 種類だけ。すべて理由付き。**

| 建議 | 意味 |
|---|---|
| `昇格可` | そのまま上げられる |
| `雛形のみ` | 中身はこの案件の事実。形だけ抜ける |
| `要補表` | 先に足りない語を脱敏表へ足す |
| `見送り` | 上げないことを勧める（ただし人が覆してよい） |
| `要人判断` | 規約・用語・雛形のいずれでもない。人が中身を見て決める |

**判定は 5 条**（規則の正本は `promotion-criteria.md`）：

| # | 条件 | 誰が判定するか |
|---|---|---|
| ① | 顧客非依存（顧客名・システム名・関数名を含まない） | 機械が形態を見る。**意味は人が見る** |
| ② | 出所がある（どの原稿のどの節か） | 機械 |
| ③ | **2 案件目で使われた** | 機械が調べる。**ただし建議に留める** |
| ④ | 形が再利用できる（雛形・規約・用語） | 機械 |
| ⑤ | 匿名化済み（検査 0 件） | 機械 |

> **③ は建議であって関門ではない。** 本当に汎用だと判断すれば、そのまま上げられる。
> 道具は「雛形のみ」と表示するだけである。

**そのあと、この順で進む**（AI が一歩ずつ案内する）：

| 段 | 誰が | 何を |
|---|---|---|
| 1 | **あなた** | レビュー表の「勾选」欄に印を付ける |
| 2 | **あなた** | 脱敏の下書きを原本と差し替える（**飛ばせない**。下記参照） |
| 3 | AI | 計画ファイルを作る |
| 4 | AI | 計画を検証する（何も書かない） |
| 5 | **会社の責任者** | 移送を実行する（権限がここで止める） |
| 6 | AI | 索引を更新し、結案記録を作る |

> **なぜ第 2 段を飛ばせないか**：移送コマンドは「ファイルを動かす」だけで、**字を直さない**。
> 原本に `R60` が残っていれば、`R60` のまま会社級へ入る。いまはここで止まる：
> `移送元がまだ脱敏されていません（要修正 37 件）`——差し替えない限り通らない。

**なぜ脱敏するか**：会社級は全案件の共有空間である。顧客名・人名・システム名が混ざれば、
A 顧客の資料を B 顧客に見せることになる。

**脱敏は二つの表で行う**（`tools/kb_local/` 配下）：

| ファイル | 役割 |
|---|---|
| `promote_map.txt` | 置換表：`元 => 先` |
| `promote_denylist.txt` | 遮蔽語：出てきたら止める（顧客名・人名） |

> ⚠ **いまこの二つの表は**模擬データ**である**（`朝日サンプル社`、`山田太郎`）。
> 実案件ではまず実名に差し替えること。差し替えないと脱敏は機能しない。

**機械では扱えないものが二種類ある。人しかできない**：

1. **`file:line` 参照**（`r60util.py:293`）——これは「語」ではなく「実装の所在」である。
   人が「共通ヘッダ部品」のような言い方へ抽象化する。
2. **意味の漏洩**——形態は全てきれいでも、内容がその顧客にしか無いものである場合。機械では見抜けない。

### 機能 ⑦　守る：顧客へ出す前に、社内のものが混ざっていないか見る

**いつ使う**：顧客へ資料を出す前。

> **こう言う**：「これ出して大丈夫」＋ファイル名

**AI がすること**：そのファイルを、庫の中で **L40（`client_only`、顧客側限定）** と
マークされた文書と突き合わせ、**20 文字以上の連続一致**を報告する（閾値は変更可）。

**注意**：**結論は出さない。** 出すかどうかはあなたが決める。道具は証拠を並べるだけである。
また、拾えるのは「長いコピー」だけである。**書き換えたものは拾えない**——唯一の防御線だと思わないこと。

## 3. 結果の見方：根拠の強さ

各結果の頭に付く記号がある。**これは中身そのものより重要である。**

| 記号 | 意味 | どう使うか |
|---|---|---|
| `【推測】` | 文面に無く、推測したもの | **結論にしない**。別途確認する |
| `【差異】` | 文面に不一致が登記されている | 差異の中身を見る |
| `[文書]` | 文書の根拠がある | 使える |
| `[実測]` | 実装を見て確認したもの | **最も確か** |
| `[摘要]` | 検索用に書き直した要約（原文ではない） | 場所を探すのに使い、**結論は正本で確認** |

`【推測】` が出たときは、末尾に「確定値として使う前に別途確認してください」と一行付く。

## 4. 出ないときの切り分け（この順で）

| 順 | まず見る | なぜ |
|---|---|---|
| 1 | **身分を設定したか** | `whoami` 未設定だと会社級しか見えない。案件級は 1 件も出ない |
| 2 | **言い換えて二回** | 文字面で照合する。意味では探さない。庫でよく使う語のほうが当たる |
| 3 | **xlsx / pdf ではないか** | 庫が索引するのは **`.md` だけ**。原本は機能④で取り込む必要がある |
| 4 | **直して `ingest` を忘れていないか** | 「索引は最新か」と聞く。赤なら索引を作り直す |

**出ない ≠ 無い。** 「この言い方では出ない」と言う。「庫に無い」とは言わない。

## 5. 誰が何を変えられるか

| こと | 誰 | どこに書くか |
|---|---|---|
| 会社級の追加・変更・削除 | 会社の責任者 | `owners.yaml` → `company.owner` |
| 案件級の追加・変更・削除 | その案件の PM | `owners.yaml` → `projects.<P>.owner` |
| どの案件を誰が読めるか | 同上 | `owners.yaml` → `projects.<P>.members` |
| 昇格の移送 | 会社の責任者 | `apply` 実行時に検査される |

**`null` は「誰でも変更可」ではなく「凍結」。** 任命が無ければ誰も変えられない。

> **こう言う**：「この変更、私に権限ある？」
> **AI がすること**：現在の差分を権限表と突き合わせ、超えている箇所を一件ずつ告げる。

> ⚠ **これは提出前の注意であって、ファイルロックではない。** ディレクトリを開ける人は見ることも変えることもできる。
> 本当に秘匿したいなら、案件をその案件の担当者だけが触れる場所へ置く——それはファイルシステム側の話である。

## 6. 週 10 分の点検（任意）

> **こう言う**：「知識ベースの点検を走らせて」

AI が 6 項目を確認して結果を返す。

| 点検 | 何を見るか | 赤ならどうするか |
|---|---|---|
| 索引の鮮度 | ファイルを直して索引に入れたか | **すぐ索引を作り直す**（でないと古い内容が出る） |
| 形式 | 字段が壊れていないか | 指示に従って直す |
| 検索品質 | 引くべきものが引けるか | どの語で外れるかを見る |
| 出所 | 会社級に `source_project` があるか | 補う |
| 権限表 | `owners.yaml` が壊れていないか | YAML を直す |
| 引用統計 | 各知識が何回引かれたか | **長期間 0 回のものは「消す」か「使う」の候補** |

## 7. コマンド早見（普段は見なくてよい）

> 上の各節は、一言言えば済む。この節は「自分で動かしたい／切り分けたい」人向けである。

**すべてのコマンドはリポジトリのルート（`src`）で実行する。**
`tools/` の中で実行すると `No module named 'tools'` で落ちる。

### 7.1 日常

| 用途 | コマンド |
|---|---|
| 身分を設定（1 回だけ） | `py -3 -m tools.kb_local whoami --set <名前>` |
| 検索 | `py -3 -m tools.kb_local search "<語>" --as <人> [--project <P>]` |
| 会社級だけ引く | `py -3 -m tools.kb_local search "<語>"` |
| 中日対照表 | `py -3 -m tools.kb_local synonyms` |
| 庫に何があるか | `py -3 -m tools.kb_local stats` |
| 索引の鮮度 | `py -3 -m tools.kb_local freshness` |
| 形式検査 | `py -3 -m tools.kb_local lint` |
| 検索品質 | `py -3 -m tools.kb_local eval --all` |
| 出所の点検 | `py -3 -m tools.kb_local extra report` |
| 対外ファイル検査 | `py -3 -m tools.kb_local external-check <ファイル>` |

### 7.2 立ち上げ / 資料の取り込み

| 用途 | コマンド |
|---|---|
| 新案件の器を作る | `py -3 -m tools.kb_local project-init --id <P-ID> --name "<案件名>" --by <PM>` |
| 取り込み（予行） | `py -3 -m tools.kb_local import --scan --by <PM> --dry-run` |
| 取り込み（実行） | `py -3 -m tools.kb_local import --scan --by <PM> [--project <P>]` |
| 索引を作る | `py -3 -m tools.kb_local ingest --prune` |
| 空の用語集を作る | `py -3 -m tools.kb_promote init-glossary --project <P> --by <PM> --apply` |

### 7.3 8 節点の先例参照

| 用途 | コマンド |
|---|---|
| この節点で何を引くか | `py -3 -m tools.kb_refs show --node <N>` |
| この節点の必読条目（要約つき） | `py -3 -m tools.kb_local node-brief --node <N>` |
| 先例の候補 | `py -3 -m tools.kb_refs suggest --project <P> --query "<主題>"` |
| 1 本を検査 | `py -3 -m tools.kb_refs check <承認版> --node <N>` |
| 全部を検査 | `py -3 -m tools.kb_refs scan` |
| **逆引き：この知識は誰に引かれたか** | `py -3 -m tools.kb_refs cited <doc_id>` |
| **一度も引かれていないもの** | `py -3 -m tools.kb_refs cited --zero` |

### 7.4 昇格

| 用途 | コマンド |
|---|---|
| 候補を列挙 | `py -3 -m tools.kb_promote candidates --project <P>` |
| **レビュー表（建議＋理由＋勾选欄）** | `py -3 -m tools.kb_promote review --project <P> --as <人>` |
| 勾选から計画ファイルへ | `py -3 -m tools.kb_promote review --project <P> --as <人> --plan-out <plan.yaml>` |
| 計画の検証（書かない） | `py -3 -m tools.kb_promote plan --from-plan <plan.yaml> --by <人>` |
| 雛形を抜く（形だけ） | `py -3 -m tools.kb_promote skeleton <成品.md> --out <模板.md> --source-project <P>` |
| 匿名化の検査 | `py -3 -m tools.kb_promote check <ファイル>` |
| 脱敏の下書きを作る | `py -3 -m tools.kb_promote draft <ファイル>` |
| 遮蔽語の候補 | `py -3 -m tools.kb_promote denylist --project <P>` |
| **移送（会社の責任者）** | `py -3 -m tools.kb_promote apply --from-plan <plan.yaml> --by <会社責任者> --apply` |
| 結案記録 | `py -3 -m tools.kb_promote close --project <P> --apply --by <PM>` |

### 7.5 権限

| 用途 | コマンド |
|---|---|
| 誰が変えられ、誰が読めるか | `py -3 -m tools.kb_acl show` |
| この差分に権限があるか | `py -3 -m tools.kb_acl check --by <人> --from-git` |
| 権限表の自己点検 | `py -3 -m tools.kb_acl verify` |
