1. 这套东西是什么

一句话：8 个 AI 干活的节点，你在每个节点拍板。

你给一份「输入」 → AI 出「初稿」 → 你审查挑错 → 你承认 → 变成下一节点的「输入」

就这一句话，连做 8 次，就是「需求 → 设计 → 编码 → 测试 → 发布」的全流程软件工程。

  • AI 负责「把散的变整齐」——读文件、写初稿、跑检查。
  • 你负责「判断整齐得对不对」——这是别人替不了的，也是这套框架存在的理由。
  • AI 出的一定是草稿。 你不点头，它不能进下一步。这不是客套，是机器强制的。

4. 编号只能从 ids.yml 发，发号和回答都由人跑命令

先说明一个词：台账（台帳）
台账 = 按条目顺序登记的原簿，不是叙述文。这套骨架里有两本：
- ID 台账 = docs/00_registry/ids.yml（谁发过什么号）
- 进度台账 = docs/00_plan/coach/<模块>/n01〜n09.yml（每个节点到哪一步、谁批的）
它有三个特点，也就是为什么不能手改它：
1. 只有一个写入口（tools/registry.py），别人只能查；
2. 只增不改（作废用 void，不删号、不重号）；
3. 它是"这一类事实"的权威记录——问"这个号发过没有"，看它，不看聊天记录。
但它会落后于现实。 旧案件的分析就吃过这个亏：tools/kb-platform/repo/projects/P-R60-001/07-traceability.md 里写着
「台帳に無いから実装も無い、と推論してはならない。台帳の方が古い」。
所以本框架不靠"台账说没有就是没有"，而是用 trace_check（gate1 查野号、gate2 查闭包）
和 registry trace（查台账与矩阵是否对得上）去比对。

所有 R / Q / F / I / D / L / E / TC / CR / BUG 编号只能从 docs/00_registry/ids.yml 发。
自己编的号叫「野号」，trace_check 的 gate1 会拦下（红线①）。
（演练的教学号段 R-201 / F-201 / I-301… 是故意的例外：不登记台账，也不参与正式追溯。）

  • 编号3 位起步、连续、不复用。作废用 void 标记，不许把号再发给别的东西。
  • 别手改 ids.yml。 发号、改状态、回答、标失效，都用 tools.registry（默认是 dry-run，

加 --apply 才写盘）：

  • AI 不会替你发号，也不会替你回答。 回答需要「回答人」的编号，AI 代填就失去意义（红线③）。

它只负责把该跑的命令摆到你面前。

改内容和改状态是两回事

这是最容易混的一点，单独拎出来讲。

三个「状态」别混

谁改什么时候变
成果物内容（正文、02 的答案、open_questions 的文字）AI（你说就改）你说完它就改
节点进度（nNN.yml 的 state / approved_by）in_progress 等由 coach 按磁盘产出维护；approved 只在承认时写approved 必须你明确说「承认」并报上编号
文档状态（YAML 里的 status: draft → baselined）人跑 tools.registry（实战）baselined 前不能有未回答的 Q（红线③）

关键：改内容 ≠ 承认。 你让 AI 改 02 的答案，它改的是文件内容，
state 那一行纹丝不动，还是 in_progress / awaiting_review。

怎么跟 AI 说

你说AI 做什么
「Q-001 客户回了：12 位」演练：写进 02 和 open_questions.answer；实战：把 registry answer ... --by 你 的命令给你，你跑。阻塞解除，state 不变
「这条我们自己定：按每页 20 条」记为 C 类裁定（裁定 + 理由），写进 02 / open_questions
「这里不对 / 漏了 / 写错了」直接改成果物，然后重出一份审查摘要给你看
「这两条是一回事，合并」合并并留痕（哪条并到哪条），不静默删除
「这一条得问问客户」记为 A 类，在 03_客户確認依頼書 里生成问题；实战登记 block: true
「退回节点2」改 state 回到节点2；不删已有文件（留改修证据）

① 你说：「Q-005 客户回了，密码有效期 90 天」
      ↓
② AI 改 02 的答案（实战再给你 registry answer 的命令）
      ↓

      ↓

第 ③ 步是自动的 —— AI 改完内容不该直接问你要「承认」，得先把改了什么重新摆给你看。

为什么非要分开

因为你确认的对象是「内容」，不是「AI 说它改好了」。

如果 AI 改完内容就自动把 state 改成 approved，那等于「AI 自己批准了自己」，
而且你根本没机会看它改成了什么样。

一句话记住：你说 → AI 改内容 → 你重看 → 你说「承认」→ 才写 approved_by。

审阅时发现问题，先别说「承认」

说了就进了承认版；之后要改就得走「指摘环」（立案、算影响面、标失效、定向重做），代价高得多。
直接把问题说出来，它会分流：

审阅 → 发现问题 ─┬─ 要问客户 → A 类 / Q（block）→ 节点卡住，等回答
                 ├─ 它能改   → 改完 → 重出摘要 → 你再看
                 └─ 你拍板   → C 类 / 未决事项 → 记下裁定 → 改完 → 重出摘要
                                            ↓
                                    都没问题了 → 你说「承认」
