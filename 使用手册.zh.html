六条通用规则 业务规则

先记这六条，后面所有节点和 skill 的行为都是从这里推出来的。

1. 入口只有一个，推进只能靠你

/trans-cosmos-ai-lifecycle-coach

每次开新对话都打这一句。 它会自己读磁盘，告诉你现在在哪个节点、第几步，然后给你一张卡片。

  • AI 不会自己进入下一节点。 即使它觉得「这一步做完了，可以接着做」，也必须等你说。
  • 一次只给一张卡片、一步。 不会一口气甩 8 个节点给你。
  • 说法自由。 下面这些只是举例，意思到了它就懂：
你的意思随口怎么说（举例）

不必背「标准词」。它不会因为你没说对词就装听不懂；真没听懂时，它应该先问你，
而不是瞎猜着往下走——这是规矩，不是礼貌（铁则 15）。

2. 每个产出都是草稿，承认 才往下走

AI 产出的东西永远是草稿。你审查、挑错、让它改；只有你明确说「承认」，流程才往下走。

承认时它会问你叫什么（例如 SE-001）。必须答。 它记的是「谁拍的板」，
这是责任凭证（approved_by）。填了 AI 的名字，这份承认就作废——红线③：AI 是执行主体，人是责任主体。

你审完 → 说「承认」→ 它问你的编号 → 你答 SE-001
       → 它写 approved_by → 出交接卡 → 这个会话结束

承认之后开新会话，不要在同一会话里继续下一个节点（理由见「会话和上下文」）。

3. 没有回答的确认事项，节点过不去

每个节点的未确定事项按 A / B / C 分类：

区分谁决定回答长什么样
A客户客户持有的资料/事实的回答
B我方提案，客户批准提案 + 依据 + 请批准的点，不是「事实描述」
C我方内部裁定裁定 + 理由，不要写成「提案」口吻

关键：分类 ≠ 决定。 把 A/B/C 分好了，不等于事情解决了。
A 要客户的回答，B 要客户的承认，C 要我方的裁定内容——三类都齐了，节点才能承认（铁则 18）。

  • 记录在 02_確認事項一覧.md（演练，以节点1 为中心）/ docs/10_requirements/answer-reconciliation-<R-ID>.md（实战）。
  • 对客户的 A/B 出 03_客户確認依頼書（AB類），对内的 C 出 03_技術者検討課題（C類）。
  • 回答回来不能直接往 02 里抄：要走「接收 → 比对 → 人裁定 → 反映」四段，

比对记录写在 02_回答受領チェック.md（演练）/ docs/10_requirements/answer-reconciliation-<R-ID>.md（实战）。
跳过比对，AI 的推测就会被当成客户的回答流进设计。

  • 实战案件的阻塞权威在 docs/00_registry/ids.yml（block: true 且 answer 为空），查：
  py -3 -m tools.registry blockers
  • 演练的例外：教学号段 Q-201… 不登记台账，所以 registry blockers 永远是空的。

演练里阻塞项只记在 nNN.yml 的 open_questions，作为承认前的检查项，不使用 blocked 状态。
（这是机制与教材的贴合处，见 reports/drill/R60Login/README.md 坑 1。实战不受影响。）

4. 编号只能从 ids.yml 发，发号和回答都由人跑命令

所有 R / Q / F / I / D / L / E / TC / CR / BUG 编号只能从 docs/00_registry/ids.yml 发。
自己编的号叫「野号」，trace_check 的 gate1 会拦下（红线①）。
（演练的教学号段 R-201 / F-201 / I-301… 是故意的例外：不登记台账，也不参与正式追溯。）

  • 编号3 位起步、连续、不复用。作废用 void 标记，不许把号再发给别的东西。
  • 别手改 ids.yml。 发号、改状态、回答、标失效，都用 tools.registry（默认是 dry-run，

加 --apply 才写盘）：

py -3 -m tools.registry alloc R --key "R60Area 检索画面" --apply
py -3 -m tools.registry alloc Q --key "采番位数" --kind question --block --relates-to R-101 --apply
py -3 -m tools.registry answer Q-001 --text "12 位" --by SE-001 --apply
py -3 -m tools.registry set-status R-101 --to baselined --apply
  • AI 不会替你发号，也不会替你回答。 回答需要「回答人」的编号，AI 代填就失去意义（红线③）。

它只负责把该跑的命令摆到你面前。

  • docs/00_plan/coach/<module>/nNN.yml 是机制生成物，也不要手改；要改就通过 coach。
  • 键名有坑：coach 的状态文件里引台账 Q 号用 q_ref，不能写 q_id / related_ids，

否则 gate1 会把值当成「ID 声明」，未登记就判野号。

  • 中文视图要写自然中文，避免「中式日文」；但实现值（画面固定文案、字段名）保持日文原文，

改内容和改状态是两回事

这是最容易混的一点，单独拎出来讲。

三个「状态」别混

谁改什么时候变
成果物内容（正文、02 的答案、open_questions 的文字）AI（你说就改）你说完它就改
节点进度（nNN.yml 的 state / approved_by）in_progress 等由 coach 按磁盘产出维护；approved 只在承认时写approved 必须你明确说「承认」并报上编号
文档状态（YAML 里的 status: draft → baselined）人跑 tools.registry（实战）baselined 前不能有未回答的 Q（红线③）

关键：改内容 ≠ 承认。 你让 AI 改 02 的答案，它改的是文件内容，
state 那一行纹丝不动，还是 in_progress / awaiting_review。

怎么跟 AI 说

你说AI 做什么
「Q-001 客户回了：12 位」演练：写进 02 和 open_questions.answer；实战：把 registry answer ... --by 你 的命令给你，你跑。阻塞解除，state 不变
「这条我们自己定：按每页 20 条」记为 C 类裁定（裁定 + 理由），写进 02 / open_questions
「这里不对 / 漏了 / 写错了」直接改成果物，然后重出一份审查摘要给你看
「这两条是一回事，合并」合并并留痕（哪条并到哪条），不静默删除
「这一条得问问客户」记为 A 类，在 03_客户確認依頼書 里生成问题；实战登记 block: true
「退回节点2」改 state 回到节点2；不删已有文件（留改修证据）

完整走一遍

① 你说：「Q-005 客户回了，密码有效期 90 天」
      ↓
② AI 改 02 的答案（实战再给你 registry answer 的命令）
      ↓
   → 阻塞解除了，但 state 还是 in_progress
      ↓
③ AI 重新出一份审查摘要给你（内容变了，你得重看）
      ↓
④ 你看完说「承认」
      ↓
⑤ 它问你的编号，你答 SE-001，才写 approved_by
      ↓
⑥ 它出交接卡，这个会话结束；下一个会话才能进下一节点

第 ③ 步是自动的 —— AI 改完内容不该直接问你要「承认」，得先把改了什么重新摆给你看。

为什么非要分开

因为你确认的对象是「内容」，不是「AI 说它改好了」。

如果 AI 改完内容就自动把 state 改成 approved，那等于「AI 自己批准了自己」，
而且你根本没机会看它改成了什么样。

一句话记住：你说 → AI 改内容 → 你重看 → 你说「承认」→ 才写 approved_by。

审阅时发现问题，先别说「承认」

说了就进了承认版；之后要改就得走「指摘环」（立案、算影响面、标失效、定向重做），代价高得多。
直接把问题说出来，它会分流：

审阅 → 发现问题 ─┬─ 要问客户 → A 类 / Q（block）→ 节点卡住，等回答
                 ├─ 它能改   → 改完 → 重出摘要 → 你再看
                 └─ 你拍板   → C 类 / 未决事项 → 记下裁定 → 改完 → 重出摘要
                                            ↓
                                    都没问题了 → 你说「承认」

会话和上下文：一个节点一个会话

状态全在磁盘上，会话本身是无状态的。

你需要的状态存在哪
做到哪了docs/00_plan/coach/<module>/nNN.yml 的 state / steps_done
谁负责同上，owner

它读完 n01.yml～n09.yml、handoff.md 和实际产出，给你当前那一步的卡片。

② 照卡片做

卡片上的四件事按顺序做：

  1. 打开 📂 指的文件（没有就跳过）；
  2. 复制 📋 那一段给 Claude（或直接让它派给节点执行体）；
  3. 等产出，核对 📤 的完整路径；
  4. 对检查项：机器能查的它自己跑，[ ] 里必须由你判断的，你要真的看。

③ 推进与审查

  • 这步做完 → 说 下一步。
  • 到了「你在这里审查」的步骤，它会先问你：逐项审 / 自己填 / 跳过。
  • 逐项审：它一项一项问，你答「对 / 不对 / 这是 C」，它替你写进该节点的审查文件（节点1 是 02_確認事項一覧.md，节点2 是 02_审查结果.md）。
  • 自己填：你直接改文件，它等。
  • 跳过：会记「审查未实施」，但不等于承认。
  • 发现问题就直说。它会分成「要问客户 / 它能改 / 你拍板」三条路。

④ 承认（唯一的签字动作）

一个节点做完了，你说 承认。它问你的编号，你答（例如 SE-001）。
它写入 approved_by，跑一遍 coach_brief，出交接卡，写 handoff.md，然后这个会话结束。

承认之前，实战要确认 registry blockers 为空；演练要确认 open_questions 里
每一条的 answer 都填了（不是只有 category）。

⑤ 换会话，进下一节点

新开会话 → 先看播报 → 打 /trans-cosmos-ai-lifecycle-coach → 拿下一张卡片。

⑥ 出口门禁（每个节点都跑）

py -3 -m tools.trace_check --strict

要看到 Exit 0。想看详细报告：

py -3 -m tools.trace_check --strict --report reports/trace.json
输出末尾还会带 seal=（冻结后不许再出现真实资产名）和 freeze=（冻结记录是否完整）两项
辅助检查，用来盯演练的冻结边界，不算在 6 道门禁里。

⑧ 来了指摘

说 指摘。走「立案 → 影响面 → 人裁定回哪个节点 → 重做 → 回归 → 再纳品 → 知识沉淀」。
别手动去改上游文件——那会留下一堆不知道要不要重做的下游。

卡住了怎么办

现象原因怎么办
/trans-cosmos-ai-lifecycle-coach 打不出来skill 是懒加载等一会儿，或重启 Claude Code；也可以直接说「开始 AI 全链路」
一开对话没有开机播报钩子被关掉，或执行失败打入口命令；或 py -3 -m tools.coach_brief
卡片说「n0X 未承认」前提节点没承认先回那个节点；这是红线②的机械拦截，不能跳
承认时它一直问「你是谁」approved_by 必须是人的编号答 SE-001 之类的编号。填 AI 名字无效
节点过不去，说还有未回答事项A/B/C 分好了，但 answer 空着分类 ≠ 决定。A 问客户、B 要批准、C 要我方裁定；全都填上（铁则 18）
演练里 registry blockers 永远是空的教学号段不登记台账（坑 1）演练看 nNN.yml 的 open_questions；不要照字面用 blocked（会死锁）
trace_check 报 gate1用了未登记的野号用 tools.registry alloc ... --apply 登记；不要删成果物里的引用，也不要手改台账
trace_check 报 gate3，且 6 道门里有 4 道同时 FAIL.yaml 末尾多写了 ---，safe_load 把它解析成第二个文档只保留文件开头那一个 ---。.md 才需要前后两个。用 --report 看 stats.error 定位，别一次改一堆文件
trace_check 报 gate5YAML 定义层写了 camelCase（如 cmpCd）定义层用 snake_case，接口层才用 camelCase
trace_check 报 gate6写了真实 IP / 密码 / 客户实数据的形式改成占位符（IP_1 / PWD_1 / VAL_1）；需要脱敏时用 mask_demo。没过不许提交
gate4 的 field_count 对不上I-ID 数与生成列数不一致查 D-043 的字段定义和 I-ID 是否同步；不要改生成器来凑数
.zh.html 没生成执行体漏了让它补；py -3 -m tools.gen_view <file>.zh.md -o <file>.zh.html，生成后删 .zh.md
生成了日文 .html违反媒体规约删掉。只保留 .md（日文）和 .zh.html（中文）
gen_formal.book 报 Exit 2输出路径里含 docs把 --out 换到 reports/。docs/** 不许有 .xlsx
Excel 没更新机读源比 Excel 旧，或钩子没跑py -3 -X utf8 tools/gen_formal/auto.py --force
手滑改了 ids.yml / nNN.yml这两个都不是手改的地方用 tools.registry；状态文件通过 coach 改。先 registry verify 看坏在哪
AI 说「我帮你继续下一步」不可能，它被锁住了推进必须你自己敲；它只能提醒
上下文快满了单节点就会吃很多 token先承认、再换会话；新会话打入口命令就能续上（状态在文件里，不在对话里）
跑着跑着被 compact 了自动压缩会丢「刚才在做什么」别在半路换；先收尾再换。已经 compact 了就重跑 coach_brief 对一下位置
会话直接 API Error: 400上下文超过模型上限（曾发生 1,017,698 token）该会话已不可恢复；开新会话，状态不会丢
好几个模块，不知道该做哪个有多个 docs/00_plan/coach/<module>/coach 会问你，别让它猜。一个人一个模块
这个节点是别人负责的owner 不是空也不是你不要动；说 换人 走交接，理由记进 note
想跳过审查先往下可以，但会留记录它按「未实施」记，approved_by 仍为空；未实施 ≠ 已承认
改了上游，下游不知道没标失效让 AI 先标 mark-stale 并算影响面；clear-stale 之前都算「没改完」
文档和实际命令对不上手册会过时以 py -3 -m tools.<x> --help 和 SKILL/rules 为准；发现不一致就改真源，不要改生成物
