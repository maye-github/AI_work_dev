# 07 追跡台帳 — 向こうは Excel で人手管理していた（★最も示唆が大きい）

> **このファイルの結論**：向こうの追跡は**手で維持した Excel の一覧表**である。
> **実装から乖離している**（§3・§4）。骨架が `ids.yml` ＋ `trace_check` を使う理由の**実証データ**がここにある。
> **対比のとき、「台帳に無いから実装も無い」と推論してはならない。台帳の方が古い。**

## 2. `画面一覧` シートの読み方（【実測】）

**列**：`A:No. | B:画面ID | C:画面名 | D:ビュー | E:コンポーネント | F:サービス | G:備考 | I:担当`

- **`A` 列は「章見出し」と「No.」が混在**する（例：`A:会社・事業場・製造列等関連` / `A:共通系`）。
  **No. は 1〜129**（【実測】末尾 `r143 A:129 | B:r60ServerJobRef`）。
- **画面は業務領域ごとに章立て**されている（会社・事業場・製造列等関連 ／ … ／ **共通系**）。
- **`D` / `E` が `-` の行は「view もしくは component を持たない」**（支援画面など）。
- **`G:設計書なし、参照なし` の行がある**（【実測】`R60SesModelItemSup` / `R60SesModelKonHmkSup`）。
  → **設計書が存在しない画面が実在する。** これらは**設計書から重做できない**（[§5](#5-重做の入口になる画面)。

**R60Login の行（【実測】`r141`）**：

```
A:127 | B:R60Login | C:共通マスタログイン | D:R60Login.vue | E:- | F:R60LoginService.ts
```

> **【実測】実物と一致**：`Front-end/src/views/R60Login.vue` ✅ ／ `Front-end/src/service/R60LoginService.ts` ✅ ／
> コンポーネント無し（`E:-`）✅。
> ★ **`A:127` は No. であって R-ID ではない。** **向こうには「要求 ID」という体系が無い。**
> 本章の [07] の中心的な論点である（[§6](#6-骨架との対比)。

## 5. 重做の入口になる画面（【実測】から導ける選別）

| 区分 | 判定材料 | 重做の可否 |
|---|---|---|
| **設計書があり、実装もある** | `画面一覧` に view/component/service があり、`50.設計書` に `画面設計書` がある | ✅ **重做可能**（R60Login はここ） |
| **`設計書なし、参照なし`** | `G` 列に明記 | ❌ **重做不能**（仕様の出所が無い） |
| **支援画面（`*Sup`）** | `E` 列に `*Sup.vue`、`D` が `-` | ⚠ **他画面から呼ばれる部品**。単独では重做しにくい |
| **`入力支援画面使用マトリクス` に載る** | 同書の 2 番目のシート | ⚠ **呼び出し側との整合が要る** |

> **★R60Login を選んだのは正しい**：設計書（`50.設計書/…_89_R60Login_….xlsx`・8 シート）・
> 実装（view / service / controller）・単体テスト仕様（`60.単体テスト` 9 シート）・
> A/B レポート（`03_AI/AB_Reports/reports/R60Login/summary.md`）の **4 点が揃っている**。

## 6. 骨架との対比（★このファイルの主眼）

| 論点 | 向こう（R60 実案件） | 骨架（trans-cosmos-ai） |
|---|---|---|
| 追跡の器 | **Excel 2 冊（人手）** | **`docs/00_registry/ids.yml`（単一ソース）** |
| ID 体系 | **No.（1〜129）のみ。要求 ID が無い** | **R / F / I / D / L / E / TC の 7 種** |
| 検査 | **人が目で見る**（集計行と実物の突き合わせ） | **`trace_check --strict` が機械検査** |
| 追跡の向き | **画面 → view/service/controller（片方向）** | **R→F→I→D/L→E→TC の双方向閉ループ** |
| 乖離 | **実測で −4 / −67 / −1 / −12（§3・§4）** | `orphan_ids=[]` / `chain_complete=true` が合格条件 |

> ★★ **この対比が本知識庫で最も重要な発見である。**
> **向こうの台帳は「人の記憶を補助する表」であり、機械が守る仕組みではない。**
> だから **`generateUrl` / `menu` の 2 端点が普通に抜け落ちる**。
> **骨架の紅线①（野号禁止）・⑤（出典なき TC 禁止）・⑥（`trace_check` なき commit 禁止）は、
> まさにこの乖離を防ぐための装置である。**
>
> **【推測】** 向こうも**不完全さを認識していた**と考えられる。根拠は
> `doc/03_AI/AB_Reports/`（旧 Java ↔ 新 FastAPI の**機械的な応答比較**）であり、
> **台帳を信じず、実行結果を突き合わせる方向へ逃げている**。**これは正しい判断である。**

### 6.1 われわれの対比で使う軸（混同しないこと）

| 軸 | 向こうが測ったもの | **われわれが測るもの** |
|---|---|---|
| 比較の相手 | **旧 Java 実装**（Struts） | **人間が書いた新実装**（Vue3/FastAPI） |
| 問い | **移植は忠実か** | **設計書からの再実装が、人間版とどこで分岐するか** |
| 手段 | 同パラメータ・同 DB で応答を突き合わせ | 成果物を**逐項で突き合わせ**、分岐を分類 |

> **★測る軸が違う。** 向こうの A/B が「移植の忠実さ」、われわれの対比が「生成の再現性」である。
> **向こうの A/B 結果（✅/⚠️/🔷/💥…）を、そのままわれわれの合格判定に流用してはならない**（[02](02-architecture.md) §8）。

## 7. 使い方（実務手順）

1. **画面 ID を決める**（例：`R60Login`）。
2. `画面一覧` を **`grep B:R60Login`** で引く → **view / service のファイル名が分かる**。
3. `API一覧` を **`grep B:R60Login`** で引く → **イベント名の候補が分かる**。
   **★ここで止めない。**
4. **実物を数える**：`ls Front-end/src/{views,components,service}/*` と
   `grep -nE '@router\.' api/…/routers/<画面ID>Controller.py`。
5. **台帳より実物が多い分を、【差異】として記録**する（[08](08-deviations.md) の様式）。
6. **設計書（`50.設計書/画面設計書/<No.>_<画面ID>_*.xlsx`）の `No.` は `画面一覧` の `A` 列と一致**する
   （例：R60Login = **`_89_`**、台帳の `A:127` とは**別の採番**）。
   **★`画面一覧` の No. と設計書ファイル名の番号は一致しない。ファイル名で探すこと。**
