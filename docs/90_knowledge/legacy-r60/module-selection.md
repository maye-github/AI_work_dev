# 教材モジュール選型 — 簡単／中等／複雑の 3 つを選ぶ

> **位置づけ**：`learning-plan-3modules.md` は W1=`R60Area`、W2=`R60Code`、W3–W4=`R60Item` を
> **仮の既定値**として置いていた。本ファイルは、その既定値を**実測で比較した結果**である。
>
> **★本ファイルは提案であり、計画の改訂ではない。** どの 3 つを採用するかは人が拍板する（红线③）。
> 拍板後に `learning-plan-3modules.md` §10 を更新する。

---

## 1. 方法

**「全部のモジュールを深く学ぶ」はしない。** 56 冊の設計書・61 冊の単体テスト仕様に対して
7 類カードを作ると 300 枚を超え、その大半は検索されない。代わりに **2 段階**で選ぶ。

| 段 | やること | 出力 |
|---|---|---|
| 第 1 段（機械） | 56 冊の sheet 構成、view／router／service の行数、AB レポートの記号集計 | `reports/module-survey/design-sheets.tsv`・`impl-size.json`・`ab-status.json` |
| 第 2 段（AI 調査） | 候補 **13 モジュール**の設計書・単体テスト仕様・AB を読み、5 観点で採点 | `reports/module-survey/scores/<module>.yaml` |
| 第 3 段（人） | 本ファイルの推薦を見て 3 つを拍板 | `learning-plan-3modules.md` 更新 |

- 調査担当：`.claude/agents/legacy-module-surveyor.md`（本セッションで新設。次回起動から自動で使える）。
- **採点は 0〜5。根拠（`sheet=…; row=…`）を必ず持つ。** 根拠の無い点は付けていない。
- **実装コードは読まない。** 実装一致は AB レポートの実測記号だけで判定する。
  「実装を読んで設計の欠落を補う」ことを禁じる（設計書と単体テスト仕様が正）。

### 1.1 5 観点

| 観点 | 意味 |
|---|---|
| `doc_completeness` | 標準 sheet（概要・項目内容・単項目チェック・項目間チェック・イベント・業務処理説明・項目移送表）が揃い、業務処理説明が十分長いか |
| `design_consistency` | 同一事実が複数 sheet で食い違わないか（番号・用語・項目名） |
| `impl_alignment` | AB レポートの実測。✅/🔷 のみ＝5、⚠️/SKIP あり＝3、💥/🚫＝1、**AB 無し＝null（未測定）** |
| `teachability` | 顧客固有知識なしで業務ルールを説明できるか |
| `complexity` | 画面数・端点・テーブル・主従・アップロード・一括・sim・外部連携の実測 |

## 3. 推薦

### 3.1 簡単 — **R60Ssk（部署マスタメンテナンス）**

| 項目 | 実測 |
|---|---|
| 設計 | 17 sheet。単項目チェック 6 件、項目間チェック 3 件 |
| 実装 | view 868 行 / router 885 行 / service 42 行 |
| AB | ✅3 🔷3 ⚠️0 💥0 🚫0 ⏭️2 |
| 構造 | 1 画面＋修正モーダル、1 テーブル、主従なし、sim なし、アップロードなし |

**理由**：4 つの simple 候補のうち、**設計が揃い・実装が動き・業務ルールが最小**の唯一の組み合わせ。
`R60Code` は可教学性 5 だが、**単項目チェック／項目間チェックの sheet を持たず**（doc=3）、
AB が全 8 端点 404 である。`R60Area` は設計は良いが search が 500。
**「教材の正」と「人版の参照」の両方を満たすのは Ssk。**

### 3.2 中等 — **R60Plc（ロケーションマスタメンテナンス）**

| 項目 | 実測 |
|---|---|
| 設計 | 17 sheet。業務処理説明 354 行、単項目チェック 40、項目間チェック 9 |
| 単体テスト | **635 項目** |
| 実装 | view 1,378 行 / router 3,083 行 / service 47 行 |
| AB | 🔷1 ⚠️0 💥0 🚫0 ⏭️2（head のみ実測、更新系は SKIP） |
| 構造 | 1 画面＋マスタ項目モーダル、1 テーブル、起動イベント 11、sim なし |

**理由**：**検索・新規・複製・修正・削除・登録の全ライフサイクル**を 1 モジュールで通せる。
`R60DC` は新規・複製・削除を持たず、条件反転が 2 件ある。`R60Jig` は 2 テーブルだが番号ずれと
項目名破損がある。**R60Area が参照しているマスタ**でもあり、Area のカードを読む副産物として
Plc の知識が効く（`R60_Get_Plc_Infomation_FNC`・ロケーション検索画面）。

### 3.3 複雑 — **R60SesModel（生産モデルマスタメンテナンス）**

| 項目 | 実測 |
|---|---|
| 設計 | 35 sheet。業務処理説明 **1,935 行**、項目移送表 12 枚＝**実テーブル 6** |
| 単体テスト | **760 項目** |
| 実装 | view 1,904 行 / router 5,929 行 / service 98 行 |
| AB | **レポート無し（未測定）** |
| 構造 | 検索＋明細一覧＋マスタ項目（ヘッダ）＋マスタ項目（明細）の**主従**、6 テーブル |

**理由**：complex の要素（主従・複数画面・複数テーブル）を満たしつつ、`R60Item`（router 8,715 行）や
`R60Ikt`（11,633 行・6 画面・アップロード）より**教材として扱える規模**に収まる。
設計自洽 4 で、番号の飛び（17→21）以外に大きな矛盾は無い。

**★但し書き**：AB レポートが無いため、**実装が設計に一致しているかは未測定**である。
後で「人版と AI 版を対比する」訓練に使う前に、**工程 07 相当の AB 実測を 1 回走らせる**必要がある。
これは「不合格」ではなく「未測定」である（`impl_alignment: null`）。

### 3.4 AB 404 の読み替え（★本調査で実際に誤読した点）

AB レポートは 404 を「端点不存在」と表示するが、**それは測定時の API インスタンスの事実**であって、
**リポジトリの実装の事実ではない**。本調査の初版はこれを「実装欠落（impl=1）」と読んだが、誤りだった。

実測で確認した事実（2026-10-19）：

| モジュール | `main.py` への登録 | router の prefix | AB が要求したパス | 結論 |
|---|---|---|---|---|
| `R60Maker` | あり（`main.py:48,132`） | `/R60Maker`（`:23`） | `/api/R60Maker/init` 等 | パス一致。**未実装ではなく未測定** |
| `R60Code` | あり（`main.py:40,124`） | `/R60Code`（`:25`） | `/api/R60Code/init` 等 | パス一致。**未実装ではなく未測定** |

- したがって両モジュールの `impl_alignment` は **`null`（未測定）** に訂正した（`scores/*.yaml` も更新済み）。
- **判定規則**：`500` は実装の失敗（測定できた）、`404` は「その測定環境に無かった」であり、
  **実装の有無を単独では証明しない**。404 を見たら `main.py` の `include_router` と router の prefix を必ず突合する。
- 時系列は不明（`D:/AI_work` は Git 管理外）。AB 測定（2026-06-12）時点で未登録だった可能性は残る。
  いずれにせよ**現物は動かせる状態にある**ため、「設計のみ」と切り捨てる根拠は無い。

### 3.5 各難度を 2 モジュールに増やす場合（拡張案・**未拍板**）

最小構成（3 つ）に対する**追加候補**。各難度で「主教材＋補完教材」の 1 対にする。

| 档 | 主教材 | 追加（補完） | 補完で学ぶこと | 弱点と扱い |
|---|---|---|---|---|
| 簡単 | `R60Ssk` | **`R60User`** | 権限・ロール、帳票系の入り口。Ssk の純 CRUD に対する「制約が増えた CRUD」 | 可教学性 3。権限用語の補足が要る（補足自体を教材にする） |
| 中等 | `R60Plc` | **`R60Maker`** | **新規／複製／修正の 3 モード**、被参照 2 表、重複、排他、緊急配信、論理削除。17 カラムの移送表 | AB 未測定。**書式の見本として最も「普通のマスタ」に近い**（ユーザー指摘どおり典型） |
| 複雑 | `R60SesModel` | **`R60KkuChi`** | **12 画面（P1–P12）の画面差分**と仕様の網羅。1 テーブルを多数画面で使い回す設計 | 複雑さは反復であって業務ルールの深さではない。**「網羅性」教材**と明示する |

- **`R60Maker` を選ぶ理由（実測）**：標準 sheet が揃い（業務処理説明 318 行）、イベント 13、
  単項目チェック 12、項目間・DB 整合チェック 7（HIT0 件・上限 3000 件・被参照・排他・重複）、
  移送表 17 カラム。**1 画面のマスタメンテとして過不足なく、典型的**である。
- **`R60User` を選ぶ理由**：Ssk と同程度の規模（端点 7、1 表）で、**権限という別軸**を持つ。
  Ssk だけだと「CRUD の型」しか学べない。User で「誰が何をできるか」が設計に入る。
- **`R60KkuChi` を選ぶ理由**：設計自洽 5（13 候補中最高）。12 画面の差分を 1 つの仕様に畳む訓練になる。
  `R60Item`（6 表・外部連携）は規模と 500 のため**第 3 候補**に回す。
- **工数の注意**：カードは 1 モジュール 7 類。6 モジュールで約 42 枚（R60Area の 7 枚を除く）。
  **フルで書くのは主教材 3 つ＋`R60Maker`** とし、`R60User`・`R60KkuChi` は
  **4 類（概要／項目／業務ルール／レビュー）に絞る**案を推す。全部を同じ厚さで書くと、
  検索されないカードが増えるだけになる（§1 の理由と同じ）。

## 4. 落選理由（重要なものだけ）

| module | 落選理由 |
|---|---|
| `R60Area` | 設計 17 sheet・560 テストで良好だが、**AB で search が 500**。学習の「正」には使えるが、「人版参照」には使えない。**カードは書式見本として残す**（削らない）。 |
| `R60Code` | 可教学性は最高（汎用コード値マスタ）。しかし**チェック系 sheet が無く**（doc=3）、明細表の移送定義も欠ける。AB 404 は**未測定**であって実装欠落ではない（§3.4）。**設計読解の副教材**としては有用だが、simple の主教材にはしない。 |
| `R60Item` | 規模最大級（router 8,715 行）で complex の要件は満たすが、**init/search が 500**。AB 修正後に再評価。 |
| `R60Ikt` | 6 画面・アップロード・一括で規模過大。さらに**項目移送表に、業務処理説明が更新するテーブルの定義が無い**。教材の正解が定まらない。 |
| `R60KonHmk` | チェック 130 件・テスト 1,733 項目と重いが、**設計のコピペ誤り**と**単体テスト仕様が別モジュールを参照**している疑い。 |
| `R60KkuChi` | 設計自洽 5 は優秀。ただし複雑さは **P1–P12 の反復**であり、業務ルールの深さではない。**「網羅性」教材**としての再利用を推奨。 |
| `R60DC` / `R60SezRet` | sim 区分があるため規則上 complex。構造は medium 相当で、`R60Plc` の代替にはなるが第一候補ではない。 |

## 5. 3 モジュールの役割分担（案）

| 档 | モジュール | 主に学ぶこと | 後の練習への転移 |
|---|---|---|---|
| 簡単 | `R60Ssk` | 1 画面 CRUD、検索条件、単項目／項目間チェック、排他の最小形 | 画面 1 枚の業務マスタを 8 工程で通す |
| 中等 | `R60Plc` | 全ライフサイクル、入力支援画面との連携、被参照、複数チェックの順序 | 他マスタから参照される側の設計 |
| 複雑 | `R60SesModel` | 主従（ヘッダ／明細）、複数テーブルの整合、大量項目の整理 | 構造の分割（1 画面を複数サブ単位へ切る） |

> **6 モジュール案（各難度 2 つ）の場合は §3.5 を参照**。上表の「主に学ぶこと」に
> 補完教材の軸（権限／3 モード／画面差分）を足す形になり、置き換えではない。
>
> **R60Area の扱い**：すでに書いた 7 類カードは**書式の見本**として残す。
> 3 モジュールのカードを書くときのテンプレート兼、`R60Plc` との参照関係の実例になる。
> 教材としては「設計は読めるが実装は壊れている」という**反面教材**の位置づけにする。
