# 能力：技術的な未確定事項を AI が代答する仕組み（答える側）

> **出所**：ユーザーの指示（2026-10-20）。R60Login 節点1 で未確定事項を一括で
> 「AI 合理案」に埋めた直後、
> 「**以后如何能够替我作答大多数技术相关的问题、这正式 AI 存在的意义对不对**」
> との指示を受けて起票した。
>
> **本項は `requirement-review-capability.md` の裏面である。**
> あちらは「**問いを立てる**能力」（`requirement-interrogator`・51 レンズ）、
> こちらは「**答えを出す**能力」。**片方だけでは、結局すべて人が答えることになる。**
> 問いを 23 件立てても、23 件が人に返ってきたら工数は増えるだけである。

## 1. 実測：今回の 71 条はどう答えたか（2026-10-20・R60Login 節点1）

| 区分 | 件数 | 内訳 |
|------|------|------|
| 未確定事項 Q-201〜Q-219 | 19 | **A 5 / B 8 / C 6**（初版 A 12 / B 7 / C 0） |
| 顧客未提及事項 | 15 | **A 7 / B 4 / C 4**（初版 A 10 / B 5 / C 0） |
| 独立審査指摘 | 37 | ①7 / ②28 / ③2（**A 6 / B 14 / C 17**、初版 A 18 / B 14 / C 5） |
| **合計** | **71** | **A 18 / B 26 / C 27**（初版 A 40 / B 26 / C 5） |

**回答の出所**：設計書 31 ／ 分析資料 4 ／ 実装 31 ／ 模擬 5。

**手順は 4 段だった**（再現可能な形で書く）：

1. **問いを分解する** — 「これは何を決めれば閉じるのか」を 1 文で書く。
   （例：Q-205「Session をどこに置き、いつ捨てるか」）
2. **出所を探す** — 顧客文書 → 既存設計書 → 既存実装 → 骨架規則 → 業界慣例、の順。
3. **案にする** — 出所が決めてくれない部分は、**こちらで具体値まで埋める**。
   「〜を検討する」で終わらせない。「idle 30 分・絶対 8 時間」まで書く。
4. **等級を付ける** — §3 の E1〜E4。**付けた等級を成果物に残す。**

**71 条すべてに答えを入れた。空欄は 0。** うち 5 条は模擬（＝出所が無く、
AI が値を置いた）。**残る作業は「人が何条直すか」の測定だけである。**

## 2. 結論1：A/B/C は「誰が知っているか」ではなく「誰が案を作れるか」で分ける

本次の最大の判断はここだった。**A の大半は B か C に移った。**

| 従来の切り方（誤） | 本項の切り方（正） |
|---|---|
| 「Session の期限は顧客が決めること」→ A | 「**期限の案はこちらが作れる**。顧客はその案を承認すればよい」→ **B** |
| 顧客に「方式を教えてください」 | 顧客に「**方式はこう提案します。貴社の規約に反しませんか**」 |
| 「URL エンコードの要否は顧客に確認」→ B | 「**顧客は読んでも判断できない**。当方の実装内で閉じる」→ **C** |

- **A に残るのは「顧客しか持っていない資料・事実」だけ**：標準規約・マスタ・
  他システムの I/F 仕様。**そこから先（選型・運用の決め事・異常時の挙動・非機能の水準）は B。**
- **B と C の分かれ目は「顧客の業務・運用・統制に触れるか」。** 触れるなら B（提案して承認をもらう）、
  触れないなら C（当方の内部で決める）。例：暗号化方式は**対外互換に縛られるので B**、
  URL エンコードや文字コードは**当方の実装内で閉じるので C**。
- **判定は「C → B → A」の順に疑う。** まず「これは顧客に聞かなくてよい内部の決め事ではないか」を疑い、
  次に「案を作れるのに顧客へ丸投げしていないか」を疑う。残ったものだけが A／B である。
- **理由は工数ではなく印象である。** A が並ぶほど「考えずに聞いている」と映り、
  B が並ぶほど「考えたうえで提案している」と映る。**C は顧客の視界に入れない**——
  判断できない質問を出すのは、B ではなく単なる時間の浪費になる。
- **件数の目安（におい試験。機械判定はしない）**：**A ≦ 1/4、C ≧ 1/3**。
  A が多いのは「調べていない・考えていない」サイン、C が少ないのは「内部で決めるべきことを
  顧客に投げている」サインである。**実測（R60Login 節点1）**：初版 **A40/B26/C5**
  → 是正後 **A18/B26/C27**。**AI の初版は A に寄り、C がほぼゼロになる。**（`RC-SK-06`）
- **分類を変えたら、回答の形態も変える。** A の答案は「資料にこう書いてある」（事実記述）、
  B は「こうすることを提案します」（提案＋根拠＋ご承認いただきたい点）、C は「こう定める」（裁定＋根拠）。
  **分類だけ直して中身を A のまま置くと、提案のつもりの事実記述が残る**（2026-10-20 の是正。
  R60Login では A→B 19 件・A→C 5 件・B→C 22 件を書き直した）。規則は `rules/02` §4.1。
- **分類した ≠ 決まった。** B は「案ができた」であって「顧客が承認した」ではない。
  したがって対客媒体では必ず **「弊社の想定（ご確認ください）」** と書き、
  **A 類は顧客の回答が揃うまで `baselined` にしない。**
  C は当方の裁定として `03_技術者検討課題（C類）` に残し、**設計評審の門で顧客の目に触れさせる**
  （`rules/02` §4.1 の既定どおり、確認依頼書には載せない）。

## 3. 結論2：答えには等級がある。等級を偽るのが最も危険な失敗である

| 等級 | 出所 | 例（R60Login） | 使える場面 |
|------|------|----------------|-----------|
| **E1** | 顧客の公式文書の明文 | 要求書 §3.2「起動区分は半角数字 1 桁」 | そのまま答えにしてよい |
| **E2** | 既存システムの設計書・実装 | 実装が `errorCode="0"/"1"/"2"` を返す | **`migration` のみ**。`greenfield` では**佐証に留める** |
| **E3** | 骨架規則・既存案件の先例 | `rules/03` §5 の `ALLOWED_SORT_FIELDS` | そのまま答えにしてよい |
| **E4** | 業界慣例・AI の推論 | 「95 パーセンタイル 3 秒」 | **「提案」と明記して**答える |

### 3.1 今回起きた事故（この等級表の根拠）

骨架の硬約束 `rules/00` §1 が、**R60 の暗号化方式を「AES-256-ECB」と書いていた**。
実際は「各桁 +1 → 当日 `yyyymmdd` を整数加算 → `_` で連結」であり、
復号は `R60_DECRYPTION_FNC`。**AES ではない。**

- **これは E4（当時の思い込み）を E3（骨架規則）の席に座らせた事故である。**
- 席が違えば、**全案件がその規則に従う**。誤りが 1 件で済まず、増殖する。
- 是正（2026-10-20）：`rules/00` §1・`spec.md`・`rules/01` §5・`case-profile-R60.yaml`・
  `glossary.yml`・`tasks.md`・節点2 の入力例・`answer-key.md`。飛輪記録は **RC-SK-05**。

**規則化**：**E4 を E1〜E3 の席に書いてはならない。**
推論で埋めた値は「提案」「想定」「案」の語を必ず伴わせる。
機械的には検出できない（`A/B/C` と同じ理由で gate 対象外）ので、**書き方の層で守る。**

### 3.2 `greenfield` では E2 を使えない（本骨架の要）

- **`greenfield` に旧版は存在しない。** だから E2 は「答えの出所」にならない。
- **E2 を答えの出所にした瞬間、AI に答案（人版）を渡したことになり、対比が成立しない**
  （＝本骨架が最も避ける汚染。`agent-chain-walkthrough` の 2026-10-14 事故と同じ構造）。
- **R60Login は試点 #0（汚染あり）である。** 今回の 71 条は E2 を大量に使っているので、
  **この節点の成果は「フローが回ること」の検証には使えるが、「AI の能力測定値」には使えない。**
  節点2〜8 の産出も同じ扱い（`case.yml` 汚染源 3）。
- **実案件（顧客支給の要求書）では E2 が無い。** そこで初めて、E3＋E4 だけで
  どこまで答えられるかが問われる。**本項の設計はその前提で書いている。**

## 4. 代答エンジンの設計：既定答案ライブラリ（Answer Defaults）

**「大多数の技術問題」は新規ではない。** 期限・エラーコード・ログ・HTTPS・
ページング・冪等・同時数・可用性——**同じ問いが案件ごとに再発する。**
再発する問いに毎回ゼロから答えるのは、能力ではなく**無駄**である。

### 4.1 1 条の形（機械可読・`docs/90_knowledge/answer-defaults/*.yaml`）

```yaml
- key: session.timeout
  question_pattern: ["セッション", "タイムアウト", "session", "超时", "ログイン保持"]
  default_answer: "サーバセッション＋HttpOnly Cookie。idle 30 分、絶対 8 時間。"
  rationale: "共用端末での放置リスク。OWASP の session timeout 慣例。"
  evidence_tier: E4                 # 顧客規約に定めがあれば E1 に昇格する
  answer_class: B                   # 提案して承認を求める
  invalid_when:
    - "顧客の標準規約にセッション期限の定めがある → A に昇格し、規約値を採る"
    - "既存システムと SSO で連携する → 連携先の期限に従う"
  conflicts_with: []                # 既存規則があれば規則 ID を指す（内容は複製しない）
  changed_by: []                    # 人が直した履歴＝飛輪の入口
```

**設計上の要点は `default_answer` ではなく `invalid_when` である。**
「いつ使ってはいけないか」を書けない既定値は、**自信を持って間違える装置**になる。

### 4.2 既存規則とは複製せず、指す

ページング（`ROWID`）・ソート白名单・冪等性・snake/camel 分区は**すでに `rules/` にある**。
ライブラリは**その規則 ID を指すだけ**にする（`conflicts_with` / `see_also`）。
**同じ既定値を 2 箇所に書かない**（NFR-1）。規則が変わればライブラリは自動で追随する。

### 4.3 処理の 3 層

| 層 | やること | 出力 |
|---|---|---|
| 1. 分類 | A/B/C を決める。**迷ったら B** | 「誰が決めるか」ではなく「案を作れるか」で判定 |
| 2. 検索 | ライブラリを引く。既存規則を引く | 命中 → 既定答案＋`invalid_when`＋等級 |
| 3. 合成 | 未命中なら E4 で案を作る。**必ず「案」と書く** | 回答＋「先例なし」の印。**この印が次の 1 条の候補になる** |

**未命中は失敗ではない。** 未命中を記録しなければ、同じ問いに毎回ゼロから答えることになる。
**2 回目に同じ問いが来たら、それは既定値になるべき問いである。**

### 4.4 品質ゲート（6 条）

1. **等級を偽らない**（E4 を E1〜E3 の席に置かない）。
2. **`invalid_when` の無い条を登録しない。**
3. **上流の承認済み成果物と衝突したら上流が勝つ**（既定値で承認済み設計を上書きしない）。
4. **A 類は顧客回答が揃うまで `baselined` にしない。** AI 案は「想定」と明記する。
5. **値は具体まで書く。**「検討する」「適切に設定する」で終わらせない。
6. **機密値は既定値にしない**（鍵・接続情報・実 IP は E1 でも成果物に書かない）。

## 5. 測定：AI が本当に代答しているかは、3 つの数字でしか分からない

| 指標 | 定義 | 意味 |
|------|------|------|
| **命中率** | 人が**一字も直さず**通した条数 ÷ 総条数 | 「代答になっていた」割合。**これが主指標** |
| **降級率** | A に落とした条数 ÷ 総条数 | 低いほど「考えて提案できている」 |
| **返工率** | 人が直した条数 ÷ 総条数 | 高い項目は既定値が悪い（＝ライブラリを直す） |

**R60Login 節点1 の初期値**：総条数 71、空欄 0、模擬 5（E4）、降級（A のまま）**18**（是正前 40）。
**ただし降級率が低いこと自体は成果ではない**——A を C に落としただけなら、顧客の負荷は減るが
当方の判断責任は増える。**C の裁定が設計で破綻しないかは設計評審で見る**（`rules/02` §4.1）。
**命中率は、ユーザーが承認時に何条直したかで決まる。** 承認前に数字を書かない（推測になる）。

**測り方**：承認版を作るとき、`02_確認事項一覧.md` の各行に
`ai_answer` / `human_edit`（無し／有り＋差分 1 行）を残す。
**「直した」という事実そのものが、次の既定値を良くする材料である。**

## 6. 実装の順序（提案・未実施）

| 段 | 内容 | 状態 |
|---|---|---|
| **A** | 本節点で実際に使った既定値を `answer-defaults/` の初版にする（10〜15 条） | 未実施。**次にやるならここ** |
| **B** | `requirement-interrogator` の後段に「答える」ステップを接続する（同一 skill の §4 か、別 skill `answer-writer`） | 未実施 |
| **C** | 人が直した差分 → `changed_by` に 1 行 → 既定値を更新（飛輪の入口を「缺陷」から「代答の修正」へ拡張） | 未実施 |
| **D** | 命中率・返工率を節点ごとに記録し、低い項目だけ人に残す | 未実施 |

**順序の理由**：A を飛ばして B を作ると、**中身の無い skill** ができる
（`requirement-review-capability.md` §5 が「レンズが無ければ agent を増やしても中身が空」と
書いたのと同じ理由）。**ライブラリが先、道具は後。**
