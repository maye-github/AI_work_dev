### RC-L01 画面ルート接頭辞と API 端点接頭辞が同じ文字列で書かれ、上流と食い違ったまま承認された

**事象**（再現手順）

1. 節点2 承認版（v2.0.2〜v2.0.4）の §1 画面概要・備考① に「画面のルート接頭辞は `/R60Login/`」と記載されていた。
2. 同じ文書 §6 イベント４(9) は遷移先ルートを `/R60/<gmnId>` と記載し、§7 は API 端点を `POST /R60Login/init`・`/R60Login/login`・`/R60Login/generateUrl` と定めていた。
3. 上流 R-201 の遷移 URL は `/R60/Pages/index.jsp?...` であり、画面側は `/R60/` である。
4. したがって **画面ルートと API 端点の接頭辞が同一文字列**になり、適用すると両者を区別できない。

**影響**

- 発見は**工程04（框架構築）着手時**。節点4 は節点3 の端点定義を正として `/R60/{gmnId}`（画面）と `/R60Login/`（API）を分けて最終確定し、§6.1 に衝突を注記した。
- 節点5 の製造コード、節点6 の TC、節点7 の IT はいずれも `/R60/{gmnId}`（画面）と `/R60Login/`（API）で書かれており、**下流へは波及していない**（2026-10-27 に `grep` で確認）。
- 上流の記述は v2.0.5（2026-10-27）で 1 行だけ訂正した。**他の記述は変えていない。**

**原因**（規則 06 §2 の問 2）

- 節点2 v2.0.0 の**構成全面改訂**（「基本設計書（画面編）」の骨格へ再配置）の際、旧版の記述を §1 概要へ持ち込んだが、**同一文書内の §6・§7 と突き合わせる検査が無かった**。
- 既存のどの門番が捕まえるべきだったか：`trace_check` の gate1（野号）・gate3（front-matter 7 字段）・gate5（snake/camel）はいずれも**自然文の用語整合を見ない**。規則 02 §9 の上流移送検査は**節点間**の移送を見るが、**同一文書内の自己矛盾は対象外**である。

**対策**（規則 06 §2 の問 3〜5）

- **再発するか**：する。文書を再構成するたび、旧版の記述を新しい節へ移す作業で同種の矛盾が生じ得る（v2.0.0 は全面再配置、v2.0.1 は 16 件の落下復元を経ている）。
- **機械で検出できるか**：**部分的に可能**。ルート・端点・固定文言・ステータス値といった**実装値を 1 表に集約**し、本文は表を参照する形にすれば、表以外の箇所に同じ値が現れたことを `grep` で検出できる（NFR-1 の単一ソース原則の延長）。
- **他の場所にも同じ穴があるか**：ある。節点3〜8 の承認版はいずれも実装値を本文へ直接書いており、同種の重複定義が起こり得る。
- **規則化する層**：**紅线ではない**（紅线は 7 条固定）。`.claude/rules/02-requirements.md` §9（上流欄位の移送検査）へ「**同一文書内の実装値の一貫性**」を 1 項追加するのが適切。**検査の追加実装は人の承認後**とする。
- **今回は「記録のみで閉じる」部分がある**：上記の規則追加・検査追加は**未実施**であり、本記録は起案である。実装したとは書かない。

> **判定はしない。** 本記録の採否・規則化の可否は人が決める（紅线③）。

### RC-L02 処理の実行主体に、その主体が実行できない処理を割り当てていた（2 件）

**事象**（再現手順）

1. **文言の取得主体**：節点2 承認版 §7.5 と節点3 §3.7・§5.7・§5.8 が「利用者向け文言はクライアントがメッセージ管理情報から取得する（SQL-6）」と定めていた。**ブラウザは DB へ接続できず SQL を実行できない。**しかも §1.3 が端点を 3 本に固定しており、文言を取るための端点も無かった。
2. **当日鍵の日付の取得元**：節点3 §2.7 は L-206（暗号化）を 1 本に統合し、呼出元に L-207（クライアント）を含めた。同じ文書 §8.4 は「当日鍵の日付判定は JST。端末時刻が JST でなくても影響しない」とする。**クライアントが暗号化する以上、クライアントはサーバの JST 日付を持たない。**
3. どちらも**工程05（製造）のステップ1 で発覚**した。製造側は直さず停止して報告した（紅线②）。

**影響**

- 製造の着手が止まった。裁定の結果、**取得主体をサーバへ移す**（節点3 §5.7・§5.8）／**文言は既存 3 端点のエラー応答に載せる**（節点2 §7.2 に `I-321` を追加）ことで解消した。
- **端点は 3 本のまま。節点1（顧客の要求書）への変更は生じていない**——該当なし（E-201／E-207）は顧客明文どおり `errorCode` のみを返し、文言はクライアントの固定表示とする（C）。
- 上流の修正は節点2 v2.0.4・節点3 v1.0.2、番号の確定は v2.0.6／v1.0.3（2026-10-27）。

**原因**（規則 06 §2 の問 2）

- 設計が**「誰がやるか」を書いたが、「その主体にできるか」を検査しなかった**。gate1〜gate6 はいずれも ID・字段・命名・機密を見るが、**主体と処理の実行可能性の整合は見ない**。
- 規則 02 §9 の上流移送検査は「上流の行が下流に現れたか」を見るが、**現れた内容が実行可能かは対象外**である。
- 2 件が同じ工程で同時に出たことは、**偶然ではなく同じ穴**の証拠である。

**対策**（規則 06 §2 の問 3〜5）

- **再発するか**：する。詳細設計は「どこで・誰が・何をする」を書くため、主体の欄を埋めるだけで満足しやすい。
- **機械で検出できるか**：**部分的に可能**。設計文書に**「主体」列**（クライアント／サーバ／DB／運用）を持たせ、**主体ごとに許される操作の一覧**（例：クライアント＝HTTP のみ、DB 接続・SQL 実行は不可）を 1 表に固定すれば、主体×操作の組合せを機械的に照合できる。
- **他の場所にも同じ穴があるか**：ある。節点3〜8 の設計文書は主体を自然文で書いており、同種の組合せが他にもあり得る。**未検査である**（本記録は起案であり、全件を洗った主張はしない）。
- **規則化する層**：**紅线ではない**（紅线は 7 条固定）。`.claude/rules/03-design-coding.md` に「**主体と操作の整合**」を 1 項追加するのが適切。**規則追加・検査追加は未実施**である。

> **判定はしない。** 本記録の採否・規則化の可否は人が決める（紅线③）。
