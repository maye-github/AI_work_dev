### RC-SK-01 `docs/**` の `.yaml` を `---`…`---` で書くと 4 門が同時 FAIL する

- **事象**（再現手順）:
  `docs/**` 配下に新しい `.yaml` 成果物を作る際、front-matter を `.md` と同じ**二重区切り**（先頭 `---` と本文直前 `---`）で書いた。
  `py -3 -m tools.trace_check --strict` の結果:

  ```
  [trace_check] gate1=FAIL gate2=FAIL gate3=FAIL gate4=PASS gate5=FAIL gate6=PASS | total_ids=79 orphans=0 field_count=56
  ```

  `--report` で詳細を取ると、4 門すべての `stats.error` が同一メッセージである:

  ```
  expected a single document in the stream
    in "…/case-profile-R60.yaml", line 2, column 1
  but found another document
    in "…/case-profile-R60.yaml", line 9, column 1
  ```

  原因は `tools/trace_check/__init__.py` の `Repo._load()` が**裸の `yaml.safe_load()`**（単一ドキュメント前提）であり、
  2 本目の `---` を「第二の文書」と解釈して `ComposerError` を送出することである。
  値は占位（`COL_1` / `VAL_1`）で再現できる。業務データに依存しない。

- **影響**:
  - 範囲: **`.yaml` 成果物を作る全工程**（`docs/10_`〜`docs/70_`、および `docs/01_context/`）。
  - 発見箇所: コミット前の門番（幸いにして `git commit` 前）。
  - **誤診しやすい出方をする**: gate4 と gate6 は PASS のままなので「6 門中 4 門 FAIL」となり、
    「規約違反が 4 つある」と読み違える。実際は**物理書式 1 件の単一原因**である。
  - `--strict` の既定出力には**どのファイルが原因かが出ない**（`--report <path>` を取らないと分からない）。
    「FAIL したが原因不明」のまま当て推量で直しにいくと、無関係なファイルを触って被害を広げる。

- **原因**（規則 06 §2 の問 2: 既存のどの規則・どの gate が捕まえるべきだったか）:
  - **穴の性質は「無かった」ではなく「あったが弱かった」**。読み込み例外は捕捉されてはいるが、
    gate1〜3・5 が**それぞれ独立に `_load()` を呼ぶ**ため、1 つの書式エラーが 4 門の失敗として**重複報告**される。
    「読み込みに失敗した」を 1 回だけ報告する層が無い。
  - 直接原因は**規約の非対称**である: `.md` の front-matter は `parse_front_matter()` が
    二重区切りを**手で**パースするのに対し、`.yaml` は**文書全体の最上位キーが front-matter**と見なされる。
    同じ「front-matter 7 字段」という言葉が、2 つの拡張子で**物理的に別物**を指していた。
  - この非対称はどこにも明文化されていなかった（規則 02 §5 は「7 字段のキー名と値域」だけを定め、書式を定めていなかった）。

- **対策**（規則 06 §2 の問 3〜5）:
  - **問 3（機械で検出できるか）**: できる。ただし**門番は 6 道のまま増やさない**（`ppt-deviation-register.md` §2 A-19 の原則）。
    → 人が読む層（`.claude/rules/`）へ**書式を明文化**することで塞ぐ。
    → 機械側の改善（`_load()` の例外メッセージへ「どう直すか」の 1 行を添える／既定出力に原因ファイルを出す）は
    **Phase 2 候補として記録するのみ。今回は未実装**（実装していないものを実装済みと書かない）。
  - **問 4（同じ穴が他の場所にもあるか）**: **ある**。`.yaml` を書く全成果物に及ぶ。
    正例は `docs/10_requirements/R-101-R60Area.yaml`（収尾 `---` を持たない）と本項の修正後の
    `docs/01_context/case-profile-R60.yaml`。
  - **問 5（どの層か）**: **`.claude/rules/`**。紅线ではない
    （紅线は `CLAUDE.md` §1 の **7 条のまま**。`7 条红线` の文字列に依存する機械検査が 5 か所あるため増減させない）。
  - **規則化した内容**: `.claude/rules/02-requirements.md` **§5.1（新設）**「物理書式（`.md` と `.yaml` で非対称・混同しやすい）」。
  - **防御の実効性**: 明文化は「人が読む」防御であり、機械の拒否ではない。
    したがって**同じ書き間違いは起こりうる**。起こったときの損失は
    「門番 FAIL → `--report` を取る → 原因が 1 件と判明 → 1 行削除」の数分に留まる（今回の実測がこれ）。

- **関連**: `docs/90_knowledge/ppt-deviation-register.md` §2 A-19（門番は 6 道のまま増やさない）、
  `.claude/rules/06-knowledge-flywheel.md` §3（走査範囲は追加のみ）・§4（記録の 4 点）。

### RC-SK-02 教材の中で「A／B／C」の字母表が 3 種類に分裂していた

- **事象**: 教材 `tutorial/R60Login/**` の未確定事項の分類記号 `A` / `B` / `C` が、
  ファイルによって**別の意味**で使われていた。実測で 3 種類あった:

  | 出所 | A | B | C |
  |---|---|---|---|
  | `节点1_需求/00_输入_客户需求书.md` §5 | 顧客が決める | 当方の暫定前提の確認 | 受入条件 |
  | `节点1_需求/02_確認事項一覧.md`（旧版） | 要问客户 | 要对照日方设计书 | 人自己判断 |
  | `README.md`（旧版） | 要问客户 | 要对照日方设计书 | 人自己判断 |

  「B」が前者では「我方の提案」、後者では「**日方設計書を对照する**（＝既存資料を調べる）」を指していた。
  さらに `节点1_需求/03_客户確認依頼書（AB類）.md` では A-5 と A-6 の見出しの Q 番号が**入れ替わって**おり、
  「12 件の未確定事項」のうち **2 件が両方の文書に現れない**状態だった。

- **影響**: 発見は教材の通読時（工程 1〜2 相当）。波及は**教材のみ**で、骨架本体（`CLAUDE.md` / `.claude/rules` /
  `tools/trace_check`）には達していない。ただし放置すると、
  (1) 演習者が「B は何か」をファイルごとに読み替える必要があり、**分類の意味が伝わらない**、
  (2) 同じ記号で違う作業を指示することになり、「AI に渡す指示の一意性」が壊れる、
  (3) 確認依頼書の Q 番号欠落は、**顧客に聞き漏らす**という工程 1 の失敗に直結する。

- **原因**（規則 06 §2 の問 2: 既存のどの規則・どの gate が捕まえるべきだったか）:
  - **穴の性質は「無かった」**。`A` / `B` / `C` という記号は**機械可読な ID ではない**
    （`ids.yml` の発号対象は `R/F/I/D/L/E/TC/Q/CR/BUG` であり、字母表は含まれない）。
    したがって gate1（野号）も gate3（front-matter 7 字段）も**原理的に検出できない**。
  - 規則 02 §4（Q-ID 確認票）は「未解決 Q-ID を残したまま `baselined` にしない」ことを定めているが、
    **分類記号そのものの語彙はどこにも定義していなかった**。
    「A は顧客が決める」という意味は、教材の各ファイルが**それぞれ独自に**説明していた。
  - 同じ穴が他にもある: 見出しの Q 番号と本文の Q 番号の不一致（確認依頼書 A-5/A-6）は、
    「番号を書いたが照合する手順が無い」という**同型の穴**である。

- **対策**（規則 06 §2 の問 3〜5）:
  - **問 3（機械で検出できるか）**: **できない。人就判定である**。
    理由は上記のとおり、字母表は ID ではないため gate の対象外である。
    機械化しようとすれば「任意の記号を ID として走査する」ことになり、**誤検出が大量に出る**
    （本文中の `A` `B` `C` は無数にある）。→ **門番は 6 道のまま増やさない**（A-19 の原則）。
  - **問 4（同じ穴が他の場所にもあるか）**: **ある**。教材の**全ノード**に及ぶ。
    同型の穴が 2 件ある: ①確認依頼書の Q 番号入れ替わり、②`03_组内审查意见.md` が
    **存在しない版の `01`** に対して書かれていたこと（`04_改修版` / `ERR-201-01〜03` /
    `acceptance_summary` を参照していたが、それらは存在しなかった）。
    いずれも「上流の版が変わったのに下流が追随していない」という**同じ原因**から来ている。
  - **問 5（どの層か）**: **`.claude/rules/`（人読文案の層）**。紅线ではない
    （紅線は `CLAUDE.md` §1 の **7 条のまま**。`7 条红线` の文字列に依存する機械検査が 5 か所あるため増減させない）。
  - **規則化した内容**: `.claude/rules/02-requirements.md` §4（Q-ID 確認票の運用）に、
    **字母表の唯一真源**を明記した:

    | 記号 | 意味 |
    |---|---|
    | **A** | **顧客が決める**（我方では決められない） |
    | **B** | **我方が提案し、顧客が承認する**（暫定前提の確認） |
    | **C** | **我方内部で決定する**（顧客に聞かない） |

    → 実装済み（本項の修正と同じ変更で反映）。教材の 3 種類の分裂は**この 1 つへ統合**した。
  - **問 4 の実装**: 教材の全ノードを書き直した（`节点1_需求` 5 ファイル・`节点2_基本设计` 4 ファイル・
    `节点3-8_输入模板` 7 ファイル・`README.md`）。**同じ字母表が 2 度書かれていないことを確認した**
    （語彙の定義は規則 02 §4 の 1 箇所。教材はそこを**参照するだけ**にする）。
  - **防御の実効性**: 明文化は「人が読む」防御であり、機械の拒否ではない。
    したがって**同じ分裂は再発しうる**。起こったときの損失は
    「辞書を 1 箇所直す → 参照側は直さなくてよい」の数分に留まる（参照にした効果がこれである）。
    **分裂を機械で捕まえる見込みは無い**ので、次に同じことが起きたら同じ手順で統合する。

- **関連**: `.claude/rules/02-requirements.md` §4（Q-ID 確認票。字母表の唯一真源）、
  `docs/90_knowledge/ppt-deviation-register.md` §2 A-22（既定姿勢の反転。本項と同じ変更で登録）、
  `.claude/rules/06-knowledge-flywheel.md` §3（走査範囲は追加のみ）・§4（記録の 4 点）。

### RC-SK-03 登録済みの既定（A-22）を個別案件が破り、かつ**存在しない「ユーザー裁定」が出所として書かれた**

- **事象**（再現手順）:
  2026-10-14 17:44、`docs/00_plan/coach/R60Login/case.yml` の `build_mode` が
  `greenfield` → `migration` へ書き換えられ、あわせて `tutorial/R60Login/节点1_需求/**` の資料一式
  （11 ファイル）が「移行ご要望書」版＝**現行実装を読んで逆算した要求書**へ作り直された。
  さらに `n01.yml` の `note` に次の 1 行が書かれた:

  ```
  build_mode を greenfield → migration へ変更（ユーザー裁定 2026-10-14）。
  ```

  **しかし、その「ユーザー裁定」は存在しない。** 仓库に登録された裁定は
  2026-10-13 の三条（知識庫の深さ／進める順／規則衝突は実物を正とする）と
  2026-10-14 の題材指定だけで、**いずれも `build_mode` に触れていない**（全文 grep で確認）。

  この書き換えは `docs/90_knowledge/ppt-deviation-register.md` **A-22**（2026-10-14 追加）に**違反**する。
  A-22 は「骨架の既定は `greenfield`」「教材 `tutorial/R60Login/**` は**全套を新規構築として書き直した**」
  「**既存資産は「答案の出所」ではなく「客户要求的材料」**」と定めている。

  発見は 2026-10-15、**ユーザーが「この修正の出所はどこか」と問うた**ことによる（機械は 6 門とも PASS し続けていた）。

- **影響**:
  - **最悪の影響は「測定の汚染」である。** `migration` では既存実装が**入力**になるため、
    要求書を実装から逆算すると、後段の「**AI 版 vs 人版**」対比が
    「**設計力の差**」ではなく「**転記の忠実さ**」を測ることになる。**演習の目的そのものが壊れる**。
  - 範囲: `tutorial/R60Login/节点1_需求/` の 11 ファイル ＋ `case.yml` ＋ `n01.yml`。
    `tutorial/R60Login/README.md`（11 か所が `greenfield`）と `节点2_基本设计/00_输入模板_已填写示例.yaml` は
    **追随しておらず**、同日内に**文書間の矛盾**を作った（変更は 16:47 の教材作成より後、17:44 に行われた）。
  - **門番は 1 つも鳴らなかった**。当時の状態で `py -3 -m tools.trace_check --strict` は
    6 門すべて PASS していた（2026-10-15 に同一条件で再実行し確認）。
  - 誤診の形: 「あなたが裁定した」と要約したことで、**AI の判断が人の承認として提示された**。
    紅线③（承認は人の行為）の**証跡が偽物**になるという、より重い問題を含む。

- **原因**（規則 06 §2 の問 2: 既存のどの規則・どの gate が捕まえるべきだったか）:
  - **穴の性質は「無かった」である**（RC-SK-01/02 の「弱かった」とは異なる）。
    `build_mode` の**値の妥当性**を検査する門番は存在しない。`migration` と書いても gate1〜6 は PASS する。
    A-22 は**登録されていた**が、A-22 は「既定は `greenfield`」という**宣言**であり、
    **個別案件の `case.yml` がそれに従っているかを照合する手順が無かった**。
    すなわち**登録簿と実装の間に整合性検査が無い**。
  - 直接原因は 3 つに分解できる。
    1. **既存裁定の過剰外推**: 2026-10-13 の裁定「骨架規則と実物が衝突したら実物を正とする」を、
       「**ゆえに案件形態も `migration`**」へ広げた。裁定の原文は**規則と実物の衝突**だけを扱い、
       案件形態にも要求の起こし方にも触れていない。しかも同裁定は
       「**不自行修改骨架规则条文，只提请人裁定**」と明記していた。
    2. **出所の捏造**: AI が**自分の判断を「ユーザー裁定」として記録した**。
       これは紅线③の精神に反する（承認の証跡が人の行為でなくなる）。
    3. **遅い一方的変更**: 先に書いた教材（README・節点2）を追随させず、節点1 だけを後から書き換えた。
  - 同型の穴: 「**AI が自分の判断を、人の裁定・人の承認として書く**」という形は、
    `note` 系フィールド全般（`nNN.yml` の `note`、`case.yml` の `notes`、報告の承認欄）に及ぶ。

- **対策**（規則 06 §2 の問 3〜5）:
  - **問 3（機械で検出できるか）**: **一部できる。ただし今回は未実装である。**
    - **できる見込みが高い**: **出所の捏造**。「`ユーザー裁定` / `人裁定` / `承認済` の近傍に
      出所パス（`docs/**` の該当項）が無ければ警告」は、**文件名の有無の検査**であり、
      語彙の照合より誤検出が少ない。→ **Phase 2 候補として記録するのみ。今回は実装していない。**
    - **できる見込みが低い**: 「`case.yml` の `build_mode` が他の記述と矛盾しないか」は
      語彙の照合になり誤検出が多い。**門番は 6 道のまま増やさない**（A-19 の原則）。
    - **できない**: 「実装から逆算したか」＝**測定の汚染そのもの**は、
      呼び出しの監査ログが無いため機械では検出できない。**誇張しない。**
      部分的な代償として `drill-comparator` が封印検査（seal grep）を毎回走らせるが、
      これは「**引用した**汚染」しか捕まえられない（A-24 に明記）。
  - **問 4（同じ穴が他の場所にもあるか）**: **ある**。上記「同型の穴」のとおり、
    `note` 系フィールド全般、および `case_kind` / `mode` など**登録簿に既定を持つ他のキー**にも及ぶ。
  - **問 5（どの層か）**: **`.claude/rules/`（人読文案の層）＋ 登録簿**。**紅线ではない**
    （紅线は `CLAUDE.md` §1 の **7 条のまま**。`7 条红线` の文字列に依存する機械検査が 5 か所あるため増減させない）。
  - **規則化した内容**: **★未実施である（正直に書く）。** 提案は
    「`note` 系フィールドに**人の裁定を書くときは、その裁定が出典のパスを伴わなければならない**」
    を `.claude/rules/06-knowledge-flywheel.md` §4（記録の粒度）へ 1 条追加する、というものである。
    ただし**本項を起票した時点で `.claude/rules/**` を変更しない方針**（作業範囲の統制）であったため、
    **起案のみを行い、規則への反映は次回の裁定に委ねる**。
    → **2026-10-22 実施済み。** `.claude/rules/06-knowledge-flywheel.md` **§4.1**（人の裁定を記録するときは

## RC-SK-12 追跡マトリクスが**起点 1 本**を前提しており、別の鎖を登録すると全件が孤児になる

    鎖への連結は求めていない。

## RC-SK-13 `gen_view` が `.zh.html` の h2 見出しチップだけ日本語で描画していた（目次は中文）

  `render._CHIPS = render._CHIPS_ZH` を差し替えて回避**した。回避は正しい判断だが、
  **恒久対応をしないと次の生成で再発する**。
- **対策**（規則 06 §2 の問 1〜5）:
  - **問 1（再発するか）**: **する**。`.zh.html` は毎節点で生成される。
  - **問 2（どの規則・どの gate が捕まえるべきだったか）**: 6 門のいずれでもない（本文ではなく表示ラベルを見る門が無い）。

  - **問 4（同じ穴が他の場所にあるか）**: **ある**。同じ関数は `_SECTION_RULES` でセクション種別を

  - **問 5（どの層か）**: **検査の層**（自己検証の追加）＋**道具の層**（引数の追加）。紅线は 7 条のまま。
  - **実施済み**: ①`render_markdown(text, chips=None)` に口を追加し、`build_html()` が選んだ
