# 「基本設計書（画面編）」の標準構成（参考書準拠）

> **出所**: 登録簿 `docs/90_knowledge/ppt-deviation-register.md` **A-31**。
> ユーザー指示（2026-10-21）——
> 「基本設計書は参考書（実案件の `doc/02_INPUT/50.設計書`）の内容に倣って書く。顧客に見せる文書なので、
> 節点1 の出力をそのまま焼き直したものにしない」「Excel も参考書の Excel に倣って生成する。簡素にしすぎない」。
>
> **この文書の位置づけ**
> - **体裁の値（列幅・結合範囲・色・罫線）の唯一真源は `tools/gen_formal/book.py`**
>   （`SHEET_PLAN` / `SHEET_COLS` / `ITEM_SPANS` / `EVENT_SPANS` / 様式定数）。本文書は値を**複製しない**。
> - 本文書が持つのは「**なぜその形か**」「**何を写してはいけないか**」「**どう検証するか**」である。
> - 参考書そのものは**読取専用の実案件資産**であり、ここに業務内容を転記しない。

---

## 1. 適用範囲

- **画面単位の基本設計書**（節点 2）に適用する。`build_mode` は問わない（`greenfield` / `migration` 共通）。
- 詳細設計書（節点 3）・単体テスト仕様（節点 6）は**別の様式**であり、本構成を流用しない。
- 対象外: バッチ・帳票・API 単体の設計書（参考書の「画面編」に対応物が無いため）。

## 3. 主要シートの列構成

### 3.1 画面項目内容（16 論理列）

参考書は 15 列（3 段表頭）。本骨架は**末尾に `項目ID` を足して 16 列**とする——I-ID との対応を
別表に逃がすと単一ソース（NFR-1）が崩れるため。

```
No. ／ 項目名称 ／ 種別(属性) ／ I-O ／ 必須 ／ エンティティ型 ／ 桁 ／ エンティティ名 ／
項目名 ／ 画面表示型 ／ 桁 ／ 位置 ／ ソート ／ 表示形式 ／ 表示・入力仕様 ／ 項目ID
```

- 2 段表頭。上段の帯は `基本情報 / 種別 / 入出力 / エンティティ / 画面表示 / 表示・入力仕様 / 項目ID`。
- 「ヘッダー部／検索条件部／ボタン部」等の**構成部の区切り行**を挟む（§4.2 の構成部と一致させる）。
- **エンティティ列は論理名**。物理名・物理桁は節点 3 で確定する（`工程03 で確定` と書く）。
- 参考書固有の列（`位置 / ソート / 表示形式`）で上流に根拠が無いものは **`-`**。**推測で埋めない。**

### 3.2 イベント一覧（7 列）

```
No. ／ イベント名称 ／ 種別(属性) ／ 分類 ／ 処理概要 ／ 例外処理 ／ 備考
```

- 1 画面あたり 4〜8 件が目安。`分類` は「初期表示／入力／ボタン／終了」等、**上流の語を使う**。

### 3.3 業務処理説明（3 帯 × イベント）

- **イベント 1 件 = 1 ブロック**。各ブロックは `入力 / 処理 / 出力` の 3 帯に分ける。
- 処理の手順は `(1) (2) (3)`、子手順は `(2-1)` と一段下げる。
- **イベント一覧の各行と 1 対 1 で対応**させる（番号を揃える）。片方だけ足さない。

### 3.4 画面概要

- **ラベル／値の表**（左に項目名、右に内容）。通常の一覧表にしない。
- 参考書の項目: サブシステム名／画面ID／機能名／画面名／画面概要／前提条件／排他条件／
  利用対象者・利用者権限／使用頻度／画面区分／備考。
- 埋まらない項目は `-`（空欄にしない。空欄は「未検討」と区別できない）。

### 3.5 変更履歴

- 先頭に**文書ヘッダ塊**（書類 REF.NO.／書類名／作成日／更新日／初版／版数／責任者・査閲・担当者）。
- 続けて**更新履歴表**（No.／バージョン／更新内容／更新日／更新者）。版ごとに 1 行、新しい版を末尾に足す。

## 4. 体裁（`book.py` が唯一の定義）

| 要素 | 値 |
|------|-----|
| フォント | `Meiryo UI`（等幅が必要な箇所のみ `Consolas`） |
| 表頭の塗り | `#99CCFF` |
| 中見出しの塗り | `#CCECFF` |
| 先頭データ行の塗り | `#CCFFFF` |
| 罫線 | 表頭の底辺のみ `double`、データ域は縦 `thin`・横 `hair` |
| 用紙 | A4 横向、列幅の合計は `TOTAL_WIDTH=132.0` を等分 |
| 固定 | 画面項目内容は表頭直下、イベント一覧は表頭直下で凍結 |

> **md に体裁を書かない。** 結合幅・塗り・罫線は md の見出しと表から機械的に決まる。
> md 側に「ここは黄色で」等の指示を書くと、二重定義になる（NFR-1）。

## 5. md → xlsx の対応規則（`md_book.parse`）

| md | xlsx |
|----|------|
| `## N. 見出し` | シート（`SHEET_PLAN` の対応表で振り分け） |
| `### 小見出し` | 帯（バナー）または中見出し行 |
| markdown 表 | 結合セル群（シートごとの `*_SPANS` で列幅を決める） |
| 箇条書き・段落 | 折り返しテキスト行 |
| 空行 | スペーサ行（高さだけ確保） |

- 節の番号（`## 4.`）は**シート名に使わない**。番号を振り直すとシート名が変わるため。
- 見出しの文言を変えると帯の文言も変わる。**用語を変えるときは md を直す**（xlsx を直さない）。

## 6. 写してはならないもの（★最も重要な節）

| 禁止 | 理由 |
|------|------|
| **参考書の業務内容**（項目・値域・条件・メッセージ・判断） | それは人版の業務判断であり、写すと「AI の設計」ではなく「転記」になる。**構成だけを倣い、事実は上流承認版から取る**（D1） |
| **`<画面名>Action` シート**（関数名／引数／返却値） | Struts 固有の実装構造。`greenfield` では技術選型が未確定であり、紅线④に触れる。代わりに**スタック非依存の「処理モジュール」**（処理名／入力／出力／機能概要）を置く |
| **顧客の会社名・ロゴ・ページフッタ・雛形図形** | 顧客の識別子。生成物に顧客の体裁を騙る要素を入れてはならない |
| **参考書のファイルパスそのもの** | 節点成果物には書かない（封印範囲の実パスは `case.yml` の汚染源登記に置く。RC-SK-09） |
| **具体的な製品名・フレームワーク名**（処理モジュール欄） | 紅线④。工程 04 で人が承認するまで固定しない |

> **迷ったら「上流に書いてあるか」で決める。** 書いていなければ `-` か「未確定事項」へ出す。
> 参考書の同じ位置に答えらしきものがあっても、**それは使わない**。

## 7. 生成と検証

```bash
# dry-run（既定。何も書かない）
py -3 -m tools.gen_formal.book --md tutorial/<case>/节点2_基本设计/05_承認版_基本设计书.md

# 生成（reports/ 配下のみ）
py -3 -m tools.gen_formal.book --md <同上> --out reports/<…>.xlsx

# 自動（通常は Stop フックが呼ぶ）
py -3 -X utf8 tools/gen_formal/auto.py            # 更新分だけ
py -3 -X utf8 tools/gen_formal/auto.py --dry-run  # 対象を見るだけ
```

- **Stop フックで自動再生成される**（`.claude/settings.json`）。対象は `tutorial/<case>/<節点>/` で
  **最も番号の大きい**基本設計書 md（`05_承認版_…` 等）。旧稿（`01_` / `04_`）は履歴なので自動対象外。
  出力は `reports/_auto/<case>/<節点>/<stem>_预览版.xlsx`。**md が xlsx より新しくなければ何もしない。**
  `_预览版` は目視用の下書きの印であり、顧客へ出す正式版は節点8 で `_正式版` を付けて別に出す。

- **`docs/**` へは書けない。** 出力パスに `docs` を含めると Exit 2。`docs/**/*.xlsx == 0` は CP-R-3 の合格条件。
- **生成物を手で編集しない。** 直すべきは md（規則 00 §11）。
- **冪等**: 同じ md からはバイト単位で同じファイルが出る（zip 時刻と `docProps/core.xml` を固定）。
  2 回生成して `sha256sum` が一致することを確認できる。
- **目視の 3 点**（人が見る）: ①画面項目内容の表頭が 2 段結合か ②イベント／業務処理がイベント単位で
  分かれているか ③画面概要がラベル／値の表か。

## 8. 再構成するときの内容保全（RC-SK-08 の再発防止）

章立てを作り直すと、**結論は残ったまま「限定句・注記・数値」が静かに落ちる**。
機械の門番（6 道）は構成変更を検出しないため、次の 3 段を必ず踏む。

1. **先に台帳を作る。** 旧版の `##`／`###` 見出しごとに「そこに書かれている結論・数値・条件・
   メッセージ・Q 番号」を列挙し、**新節のどこへ行くか**を 1 行ずつ書く。台帳が無いまま書き始めない。
2. **再構成後にキーワード突合。** 旧版から拾った特徴語（数値・固有名・注記の語）を列挙し、
   新版に**すべて存在するか**を `grep` で数える。0 件の語は欠落として扱う。
   **grep は補助であり判定ではない**——言い換えられた語は拾えないため、次の 3 と併用する。
3. **独立レビュー。** `spec-reviewer` に「旧版 → 新版の内容保全」だけを目的として渡す（他の観点を混ぜない）。
   報告は「落ちた項目・増えた項目」に限定させる。

- **落ちた項目は新版へ戻す。逆方向の削除（上流事実の削除）は行わない。**
- 記録: `docs/90_knowledge/review_diff_assets/_skeleton/review_comments.md` **RC-SK-08**。
