### 1.2 backend

- **提案**: Python 3.12 + FastAPI + Pydantic v2 + SQLAlchemy Core（`text()`。ORM マッピングは使わない）+ oracledb（Thin）
- **状態**: 提案（承認待ち）
- **根拠（R60Maker の承認済み設計事実）**:
  - SQL は明示的に手書きし、値はすべて `:BIND` の名前付きプレースホルダで受ける（05 §4.1〜§4.11）。動的ソートは白名单 {MAKER_CD, MAKER_NM} で担保し、外は固定ソートへフォールバックする（05 §4.4・裁定 Q-314）→ ORM の自動生成に委ねず、SQL 本文をそのまま保持できる構成が要る。
  - 6 端点（`/init`・`/search`・`/download`・`/initEdit`・`/delete`・`/edit`）はすべて POST・JSON 応答で、HTTP ステータスはすべて 200、判定は本文の `errorCode`（0／1／9）と `errorId`（4 桁）を正とする（共通部品仕様 §9.1・05 §5）→ status と本文を明示制御できる HTTP 層が要る。
  - L-212 は 6 端点すべての前にセッション（30 分）・オンライン可否（平日 7:00–22:00 JST）・権限（MKR01〜MKR03）・入力チェックの順で検証し、1 つでも失敗したら後続を実行しない（05 §2.1・共通部品仕様 §10.1）→ 前処理を 1 箇所に集約できること。
  - 権限は利用者 1 名 1 コード（MKR01／02／03。上位は下位を含む）で、端点別の可否表に従う（共通部品仕様 §4.1・§4.2・05 §2.1）→ 端点別の権限検証を宣言的に書けること。
  - `ReferenceChecker.check`（被参照・読み取り専用・冪等）と `EmergencyDispatcher.dispatch`（非同期・受付 ID を返して即復帰・業務トランザクションをロールバックしない）を呼ぶ（共通部品仕様 §5・§6）→ 外部の共通処理パッケージを差し込める構成が要る。
  - CSV は UTF-8（BOM あり）・CRLF・ヘッダ行あり・一覧 5 列で、排他情報を含めない（05 §2.7 手順④）→ 文字コードと改行を明示制御できること。
  - 接口層は camelCase・定義層は snake_case で、未定義項目は拒否する（`.claude/rules/03-design-coding.md` §2・§4）→ 変換を 1 箇所に閉じ、余剰入力を弾けること（Pydantic v2）。
  - 文字コードは UTF-8、日時は JST、表示形式は YYYY/MM/DD hh:mm:ss、端末時刻は使用しない（NFR §2 #17・共通部品仕様 §1.1・05 §3.1）。
  - 一覧検索 3 秒以内（95 パーセンタイル・サーバ処理時間）・同時 50 セッション（NFR §2 #4・#8）→ 非同期 I/O で足りる規模。
- **一般論（E4）**: 言語（Python）とフレームワーク（FastAPI）の品種選定自体は設計から決まらない。
- **備考**: ORM のモデル定義は作らない（物理定義は 05 §1 の表・列が唯一真源であり、二重定義を避ける）。頁送りは OFFSET/FETCH を例外採用し、安定順序のため物理行識別子を末尾に付す（05 §4.4・裁定 Q-313）。物理方言は承認後に確定する（追跡は `n04.yml` の `open_questions`）。

### 1.3 database

- **状態**: 提案（承認待ち。製品の当否・版・エディションは運用標準待ち）

  - 05 §1 は型を論理型（文字列／数値／日時）で示し、物理型はスタック承認後に確定する → VARCHAR2(n CHAR)／NUMBER／DATE 等へ写す。製品固有の型名を設計へ書き戻さない。

  - 文字コードは UTF-8（NFR §2 #17）、タイムゾーンは JST（共通部品仕様 §1.1）。日付・時刻を SQL に埋め込まない（05 §5）。

- **一般論（E4）**: 製品（Oracle）・版・エディションの選定自体は設計から導けない（顧客の運用標準が優先する）。

## 4. 構建と CI の草案

### 4.1 ローカル門番

| 門番 | コマンド | 目的 |
|---|---|---|
| 追跡・機密 | `py -3 -m tools.trace_check --strict` | gate1〜gate6。`--skip` による門隙突破を禁止（紅線⑥） |
| 機密単独 | `py -3 -m tools.trace_check --strict --only-check secrets` | 1 件でもヒットしたら commit 禁止（紅線⑦） |
| 先例参照 | `py -3 -m tools.kb_refs check <承認版> --node 4` | STD／先例の記録を検査する |
| サーバ単体 | `pytest` | 工程06 の TC を実行。テスト 0 件を緑と読まない |
| クライアント単体 | `vitest run` | 同上 |
| 型検査 | `vue-tsc --noEmit` | ビルドより前に失敗させる |
| ビルド | `npm run build`（= `vue-tsc --noEmit && vite build`） | 零 error（構築ゲート相当。本骨架の門番ではない＝規則 04 §9.1） |
| 依存固定 | `npm ci` / `pip install -r requirements.txt` | lockfile の差分をレビュー対象にする |

### 4.2 CI 常設門番への移行思路

- ローカル門番を**そのまま CI 常設門番へ写す**。CI（ubuntu-latest）では `python -m tools.xxx`、ローカル（Windows）では `py -3 -m tools.xxx` と表記が違うだけで、同じ検査である（規則 00 §9）。
- 人手の commit 前チェックを CI の**必須ジョブ**にし、`--skip` は CI でもローカルでも禁止する（紅線⑥）。
- 本骨架が持つ品質ゲートは **G1（静的検査）相当のみ**であり、G2〜G5（構築・Console・スモーク・画像対比）は未実装である（規則 04 §9.1）。上表のビルド／型検査は**案件側 CI へ接続する前提の草案**であり、本骨架の門番（6 道）を増減させるものではない。
- 承認前でもゲートを緩めない。ローカルで通したことを理由に CI 側を外さない。

## 6. 承認前に人が判断する点

- 各提案が R60Maker の承認済み設計の事実に根拠を持つか（greenfield。従来構成と同じであることを根拠にしていないか）。とくに database の製品・版と infra の製品選定は設計から導けない（一般論 E4）点を含めて判断する。
- `approved_by` に人の識別子が入っているか（紅線③④。空なら次工程へ進めない）。本稿は空のまま提出している。
- 実在の環境値が無いか（IP・ホスト名・URL・接続文字列・バケット名・テナント名・利用者識別子）。占位のみか。
- シークレットが「取得方式」と「格納先の種別」までで止まっているか（実値・実パス・接続文字列が無いか）。
- `trace_check` 門禁が流水線に残っているか（`--skip` 禁止。承認を理由にゲートを緩めていないか）。
- 共通部品を画面側で再実装しない構成か（共通部品仕様 §1.1）。
