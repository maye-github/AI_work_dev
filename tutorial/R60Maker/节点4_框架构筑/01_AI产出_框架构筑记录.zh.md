### 1.1 frontend

- **提案**：Vue 3（Composition API + `script setup`）+ TypeScript（strict）+ Vite + PrimeVue + Pinia
- **状态**：提案（等待批准）
- **依据（R60Maker 已承认的设计事实）**：
  - I-333（下拉框 10／20／50／100・默认 20）、I-328（确认・错误对话框）、I-332（复选框）、I-334（切换按钮）、I-337／I-338（分页链接）、I-340／I-342（可排序表头）→ 需要一整套选择、输入、按钮、对话框、列表、分页的 UI 基盘（05 §2.4・§3.1）。
  - E-219 会改变该项目的背景色并移动焦点（05 §5）→ 需要能按项目改样式并控制焦点。
  - 接口层为 camelCase、定义层为 snake_case（05 §1）。I-347／I-349 显示的不是代码而是名称（05 §3.1）→ 采用能以类型防止混淆的 TypeScript（strict）。
  - L-221 的活性控制（权限・检索结果・行选择・模式・删除状态）与 L-222 的迁移请求由客户端主导（05 §2.10・§2.11）→ 需要保存画面状态的层。
  - 检索条件由画面保持，分页操作时重新检索（05 §2.4 步骤②）→ 放置画面内状态存储（Pinia）。
  - CSV 响应（L-218）要区分文件与错误 JSON 并保存（05 §2.7 步骤⑤）→ 需要能处理 Blob 响应。
  - I-323 显示服务器时间（JST・YYYY/MM/DD hh:mm:ss）（05 §3.1）→ 不使用终端时间进行显示控制。
  - 调用共通部品 CommonHeader（公司名・部门名・用户名分项绘制）与 Pager（上部・下部两处）（共通部品仕様 §1.1・§3.1・§3.2）。
  - 支持浏览器为 Edge 120 以上／Chrome 120 以上，最低分辨率 1366×768，同时 50 会话（NFR §2 #1〜#3・#8）→ 构建目标可限定为现行 Chromium 系，无需旧浏览器 polyfill。
- **一般论（E4）**：品种（Vue／PrimeVue／Pinia）的选择本身，以及画面迁移方式（路由还是模态）无法由设计决定。
- **未确定**：共通 UI 库 v3.0 的包名・取得方式（Q-317）。

### 1.2 backend

- **提案**：Python 3.12 + FastAPI + Pydantic v2 + SQLAlchemy Core（`text()`。不使用 ORM 映射）+ oracledb（Thin）
- **状态**：提案（等待批准）
- **依据（R60Maker 已承认的设计事实）**：
  - SQL 明示手写，所有值以 `:BIND` 命名占位符接收（05 §4.1〜§4.11）。动态排序由白名单 {MAKER_CD, MAKER_NM} 保证，之外回退到固定排序（05 §4.4・裁定 Q-314）→ 需要不交给 ORM 自动生成、能原样保持 SQL 本文的结构。
  - 6 个端点（`/init`・`/search`・`/download`・`/initEdit`・`/delete`・`/edit`）全部为 POST・JSON 响应，HTTP 状态一律 200，判定以本文 `errorCode`（0／1／9）与 `errorId`（4 位）为准（共通部品仕様 §9.1・05 §5）→ 需要能明确控制 status 与本文的 HTTP 层。
  - L-212 在 6 个端点之前按会话（30 分）・在线可否（平日 7:00–22:00 JST）・权限（MKR01〜MKR03）・输入检查的顺序验证，任一项失败则不执行后续（05 §2.1・共通部品仕様 §10.1）→ 需要能在一处集中前处理。
  - 权限为每名用户 1 个代码（MKR01／02／03。上位包含下位），按端点可否表执行（共通部品仕様 §4.1・§4.2・05 §2.1）→ 需要能以声明方式编写端点权限验证。
  - 调用 `ReferenceChecker.check`（被参照・只读・幂等）与 `EmergencyDispatcher.dispatch`（异步・返回受理 ID 后立即返回・不回滚业务事务）（共通部品仕様 §5・§6）→ 需要能接入外部共通处理包的结构。
  - CSV 为 UTF-8（带 BOM）・CRLF・有表头・列表 5 列，不含排他信息（05 §2.7 步骤④）→ 需要能明确控制字符编码与换行。
  - 接口层为 camelCase、定义层为 snake_case，拒绝未定义项目（`.claude/rules/03-design-coding.md` §2・§4）→ 将转换封闭在一处，并拒绝多余输入（Pydantic v2）。
  - 字符编码 UTF-8、时间 JST、显示格式 YYYY/MM/DD hh:mm:ss、不使用终端时间（NFR §2 #17・共通部品仕様 §1.1・05 §3.1）。
  - 列表检索 3 秒以内（95 百分位・服务器处理时间）・同时 50 会话（NFR §2 #4・#8）→ 异步 I/O 足以应对的规模。
- **一般论（E4）**：语言（Python）与框架（FastAPI）的品种选择本身无法由设计决定。
- **备注**：不创建 ORM 模型定义（物理定义以 05 §1 的表・列为准一真源，避免重复定义）。分页例外采用 OFFSET/FETCH，为稳定顺序在末尾附加物理行识别子（05 §4.4・裁定 Q-313）。物理方言在批准后确定（Q-318）。

### 1.3 database

- **提案**：Oracle Database（参照・更新的 6 张表。产品・版本・版本类型遵循客户运维标准）
- **状态**：提案（等待批准。产品是否合适・版本・版本类型待运维标准）
- **依据（R60Maker 已承认的设计事实）**：
  - 05 §4.4・裁定 Q-313 规定，分页的稳定顺序附加物理行识别子（例：ROWID）。ROWID 是 Oracle 的物理行识别子，是设计所设想方言的旁证（但 05 §0・§4 明记「物理方言由工程04 确定」，并非确定值）。
  - 05 §4.1〜§4.11 的所有值以 `:BIND` 命名占位符接收 → 与 Oracle 原生绑定记法一致（既不是 `?` 也不是 `%s`，不夹转换层）。
  - 05 §1 以逻辑型（字符串／数值／时间）表示类型，物理型在技术栈批准后确定 → 映射为 VARCHAR2(n CHAR)／NUMBER／DATE 等。不把产品固有类型名写回设计。
  - 05 §4.1〜§4.11 对 6 张表（D-207〜D-212）做 SELECT／INSERT／UPDATE、内部结合、唯一约束（仅制造商代码）、ORDER BY del_flg, maker_cd 的稳定顺序即可 → 可用标准 SQL 与 OFFSET/FETCH 表达。
  - 字符编码 UTF-8（NFR §2 #17）、时区 JST（共通部品仕様 §1.1）。不把日期・时间嵌入 SQL（05 §5）。
  - NFR §2 #4・#8（3 秒以内・同时 50 会话）／以参照为主的 6 张表 → 小规模。备份（每日全量・35 天／每月 12 个月・NFR §2 #16）・监视・许可遵循客户运维标准。
- **一般论（E4）**：产品（Oracle）・版本・版本类型的选择本身无法由设计推导（优先客户运维标准）。
- **备注**：连接使用 oracledb 的 Thin 模式（客户端不安装 Oracle Client）。连接信息从环境设定／密钥管理注入，本记录不写（占位 `TBL_1/COL_1@PWD_1:PORT_1/SID_1`）。

## 4. 构建与 CI 草案

### 4.1 本地门禁

| 门禁 | 命令 | 目的 |
|---|---|---|
| 追踪・机密 | `py -3 -m tools.trace_check --strict` | gate1〜gate6。禁止用 `--skip` 突破门禁（红线⑥） |
| 机密单独 | `py -3 -m tools.trace_check --strict --only-check secrets` | 命中 1 件即禁止 commit（红线⑦） |
| 先例参照 | `py -3 -m tools.kb_refs check <承認版> --node 4` | 检查 STD／先例的记录 |
| 服务器单元 | `pytest` | 执行工程06 的 TC。不把 0 件测试读作绿色 |
| 客户端单元 | `vitest run` | 同上 |
| 类型检查 | `vue-tsc --noEmit` | 在构建之前失败 |
| 构建 | `npm run build`（= `vue-tsc --noEmit && vite build`） | 零 error（相当于构建门禁。不是本骨架的门禁＝规则 04 §9.1） |
| 依赖固定 | `npm ci` / `pip install -r requirements.txt` | 将 lockfile 的差分作为评审对象 |

### 4.2 向 CI 常设门禁迁移的思路

- 将本地门禁**原样写入 CI 常设门禁**。CI（ubuntu-latest）用 `python -m tools.xxx`，本地（Windows）用 `py -3 -m tools.xxx`，只是表记不同，检查相同（规则 00 §9）。
- 将人工的 commit 前检查设为 CI 的**必须作业**，`--skip` 在 CI 与本地均禁止（红线⑥）。
- 本骨架具有的品质门禁仅为 **G1（静态检查）相当**，G2〜G5（构建・Console・冒烟・图像对比）未实现（规则 04 §9.1）。上表的构建／类型检查是**接入案件侧 CI 前提的草案**，不增减本骨架的门禁（6 道）。
- 批准前也不放宽门禁。不因本地通过而移除 CI 侧。
