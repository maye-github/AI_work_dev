## 1. 対象と前提

### 1.1 対象

対象は**6 端点**（`POST /R60Maker/init`・`/R60Maker/search`・`/R60Maker/download`・
`/R60Maker/initEdit`・`/R60Maker/delete`・`/R60Maker/edit`）。
経路は**承認済み設計 §2.0（2026-11-10・CR-006）が唯一の出所**である。
実装は 6 ルータを `prefix="/R60Maker"` で登録し（`backend/app/main.py:103-108`）、
前端の基底も `/R60Maker` に集約している（`frontend/services/makerApi.ts:126`）。

- **前置き（`/api` 等）をコードに埋めない。** デプロイ時のリバースプロキシ接頭辞は環境設定であり、
  アプリは `/R60Maker/<name>` で受ける（設計 §2.0）。旧版は実装がルート直下・FE が `/api` 前置という
  第三の解釈を採っていたが、CR-006 で解消した（§8.3 旧 #1）。
- **要求本文を受けるのは `/download` 以外の 5 端点。** `/download` は**要求本文を受け取らない**——
  最後に実行した検索条件だけで CSV を作る（要求 §6 の例外段落・BUG-005、設計 §2.0）。§8.3 旧 #4。
- **`X-Session-Id` は共通部品が注入する**（要求 §8 #9・設計 §2.0）。本画面は自前で作らない。
  注入されない構成ではセッション系（E-221）は**未観測**である（§8.1 #2）。

**結合**＝複数の層（画面・API・DB・セッション・CSV）を跨ぐ受け渡しを観測するもの。
**総合**＝利用者の一連の操作が終端（一覧反映・画面終了）まで到達することを観測するもの。
単一ロジックの入出力は節点6 の TC-222〜TC-246 が担う。**本節点では焼き直さない。**
本節点が突くのは「順序」と「境界」である——複数 API を順に叩いたときの状態遷移、画面 ⇄ API の往復、
排他・同時実行、実際の DB 実行とトランザクション境界。

### 1.2 A/B 比較を行わない理由（`greenfield`）

本案件は `build_mode: greenfield` であり、比較対象たる旧版が存在しない。
したがって **A/B 比較を行わない**（規則 04 §7.1）。**本書に A/B の節を置かない。**
`doc/03_AI/AB_Reports/reports/<モジュール>/summary.md` は作成せず、健康度スコアも閾値も設けない
（規則 04 §7.1「閾値だけを後付けで作らない」）。

代替は **受入基準の充足判定**である（§5）。期待値の出所は「承認済みの要求（R-202）」と
「承認済みの基本設計（F-202）」であり、判定は**一致比較ではなく充足判定**になる。
実行結果の記録先は `tutorial/R60Maker/节点7_结合测试/verification.md` である
（A/B ではないため `summary.md` を使わない。規則 04 §7.1）。**本書はその記録を作らない。**

### 1.3 データの扱い

入力・期待値はすべて占位（`COL_1`／`VAL_1`／`EMP_1`）で示す。実データ・実 IP・接続情報を書かない
（規則 01・紅线⑦）。表の件数や `rev_no` も「増えた／変わらない」という**関係**で書き、実値を書かない。

### 1.4 数値の扱い（単一ソース）

非機能の目標値は `tutorial/R60Maker/节点2_基本设计/05_承認版_基本设计书.md` §11 の該当行が唯一の定義である。
**本書に数値を転記しない**（二重定義の回避）。本書は「どの行を・どの条件で・何を測るか」だけを書く。

## 6. 事務境界と非機能の観測

### 6.1 事務境界

「動くか」ではなく「壊さないか」を見る。**書込を発行するのは `/edit` と `/delete` の 2 端点だけ**である
（入力模板 `db_transaction_boundary`・設計 §2.9／§2.8）。実装では読取 4 端点が `engine.connect()`、
`/edit`・`/delete` が `engine.begin()` を用い、`/edit` は INSERT／UPDATE、`/delete` は UPDATE のみを発行する。

| # | 確認項目 | 手順 | 期待 |

| 1 | 読取 4 端点が SELECT のみであること | `/R60Maker/init`・`/R60Maker/search`・`/R60Maker/initEdit`・`/R60Maker/download` の実行区間で発行 DML を記録し文種を分類する（手段は §8.2 #6） | `INSERT`／`UPDATE`／`DELETE`／`MERGE` が **0 文** |

| 3 | 論理削除であること | `/delete` の DML を記録する | `UPDATE ... SET del_flg='1'` のみ。**物理 `DELETE` は 0 文** |
| 4 | 成功時のみコミットされること | `/edit`・`/delete` の前後で DB を読む | 成功時は確定。**例外時はロールバック**（`rev_no` が増えず、行が残らない） |

### 8.4 観測範囲の裁定（2026-11-10・人）

**本節点の観測範囲は API 級まで。** 画面に表示される値・ダイアログ操作・置換先画面の種別は
**観測しない**（承認済みスタックにブラウザ自動化が無いため。§8.2 #3）。

- **理由**：スタックへの追加は紅線④の対象であり、本節点で勝手に足さない。
  足さない代わりに、**足りない観測を「実施した」と書かない**。
- **代償（明記する）**：E2E-207 のうち「置換先の画面が SessionErrorScreen／
  OnlineControlErrorScreen のどちらか」は API では観測できない。`errorId` 9999/9001/9002 の
  返却までを検証し、**置換先の実体は未観測**とする。
- **波及**：節点8（リリース判定）は、この未観測分を**残課題として引き受ける**。
  「画面が正しく置換されること」を合格条件に含めるなら、先に工程04 でスタックを決める必要がある。
- **これは品質の妥協ではなく、観測可能な範囲の明示である。** 未観測を未観測と書く方が、
  ブラウザを入れずに「E2E 合格」と書くより安全である。
