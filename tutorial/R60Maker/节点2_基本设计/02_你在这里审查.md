## 一、需求追溯（缺一项链条就断）

- [ ] **F-202 确实挂在 R-202 之下**，功能名称与承認版一致。
  - 为什么必须人看：AI 会「顺手」改一个看似更顺的名字。名字一旦和承認版对不上，追溯链就是假的，
    而 `trace_check` 只查编号，查不出名字。
- [ ] **画面 SCR-201（検索）／SCR-202（マスタ）的责任划分**与你理解一致。
  - 为什么必须人看：SCR-202 是独立画面还是 SCR-201 的一部分，AI 分不清；分错了，后面的工作量与该测什么全错。
- [ ] **I-322〜I-354 共 33 件全部出现在 §4**，且**没有发明 I-34 以后的编号**。
  - 为什么必须人看：这是 R60Maker 特有的坑（D-MK-01）。骨架的 I-201..I-256 是**别的体系**，
    混进来就是野号；而「マスタ画面 9 項目」目前没有 I-ID（Q-306），AI 很容易顺手编一个。
- [ ] **★ 逐项对照节点1 承認版**：上游表里**每一行**你都能说出「写在本设计书哪一节哪一行」。
      重点看 4 种**非 Q 欄**（最容易漏，出了事也最难发现）：
      1. 限定句（「〜のみ」「〜に限る」「〜を除く」）
      2. 内部值符号系（画面上 `Y/N` 与内部 `1/0`）
      3. 形状（端点路径、固定部分、桁数）
      4. 否定与例外（「〜しない」「〜のときは除く」）
  - 为什么必须人看：R60Login 的实测里，漏掉的 3 件**全部**是这类非 Q 欄。AI 抄 Q 表很勤，抄限定句很懒。

## 二、业务正确性（AI 最容易想当然的地方）

- [ ] **検索 0 件の扱い**：Q-263 裁定「0 件も成功扱い」と一致しているか（業務エラーにしていないか）。
  - 为什么必须人看：要求書 §3.5 と §3.2 が字面上ぶつかっており、裁定は Q-263 にある。
    AI は §3.5 だけ読むと「0 件はエラー」と書く。
- [ ] **権限マトリクス**（`download`・`delete` は MKR03 のみ、`edit` は MKR02 以上）が設計に写っているか。
  - 为什么必须人看：这是受領資料的判断，且**権限错配在测试里很难被发现**（测试账号往往权限正常）。
- [ ] **排他判定**が `lastUpdateDatetime` と `revNo` の**両方一致**になっているか（片方だけになっていないか）。
- [ ] **削除**が「論理削除＋被参照チェック＋キー重複（削除済みも存在とみなす）」の 3 点を満たしているか。
- [ ] **緊急配信**が「コミット確定後に非同期で起動」になっているか（コミット前に起動していないか）。
- [ ] **一覧に「登録ステータス」列が無い**（Q-284 已裁定）。追加されていたら上流へ戻す。
- [ ] **メッセージ文面が存在性・内部値を漏らさない**（特にエラー系 12 件）。
  - 为什么必须人看：这是安全问题不是格式问题。AI 默认会写「該当データが存在しません」——这就泄露了。
