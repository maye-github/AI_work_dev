## 一、需求追溯（缺一项链条就断）

- [ ] **F-202 确实挂在 R-202 之下**，功能名与承認版一致。
  - 为什么必须人看：AI 会「顺手」改一个看起来更顺的名字。名字一旦和承認版对不上，追溯链就是假的；
    而 `trace_check` 只查编号，查不出名字。
- [ ] **画面 SCR-201（検索）／SCR-202（マスタ）的责任划分**和你的理解一致。
  - （画面名原文为日文，按原文实现。）
  - 为什么必须人看：SCR-202 是独立画面还是 SCR-201 的一部分，AI 分不清；分错了，后面的工作量估算和测试范围全错。
- [ ] **I-322〜I-354 共 33 件全部出现在 §4**，并且**没有发明 I-34 以后的编号**。
  - 为什么必须人看：这是 R60Maker 特有的坑（D-MK-01）。骨架里的 I-201..I-256 是**另一套体系**，
    混进来就是野号；而「マスタ画面 9 項目」目前没有 I-ID（Q-306），AI 很容易顺手编一个。
- [ ] **★ 逐项对照节点1 承認版**：上游表里**每一行**你都能说出「写在本设计书哪一节哪一行」。
      重点看 4 种**非 Q 欄**（最容易漏，出了事也最难发现）：
      1. 限定句（「〜のみ」「〜に限る」「〜を除く」这类缩小适用范围的措辞）
      2. 内部值与符号体系（画面上是 `Y/N`、内部是 `1/0` 这种）
      3. 形状（端点路径、固定部分、位数）
      4. 否定与例外（「〜しない」「〜のときは除く」）
  - 为什么必须人看：R60Login 的实测里，漏掉的 3 件**全部**是这类非 Q 欄。AI 抄 Q 表很勤，抄限定句很懒。

## 二、业务正确性（AI 最容易想当然的地方）

- [ ] **检索到 0 件时的处理**：与 Q-263 的裁定「0 件也算成功」一致吗（有没有写成业务错误）？

    AI 只读 §3.5 的话，会写成「0 件是错误」。
- [ ] **权限矩阵**（`download`・`delete` 仅 MKR03，`edit` 为 MKR02 以上）有没有写进设计？

- [ ] **删除**是否满足「逻辑删除 + 被参照检查 + 键重复（已删除的也算存在）」这 3 点。
- [ ] **紧急配信**是不是「提交确定之后异步启动」（不是提交之前就启动）。
- [ ] **一览里没有「登録ステータス」列**（Q-284 已裁定）。如果被加上了，要退回上游。
- [ ] **消息文面不泄露存在性与内部值**（尤其错误类 12 件）。
  - 为什么必须人看：这是安全问题，不是格式问题。AI 默认会写「該当データが存在しません」——这就泄露了。
