## 0. 30 秒看懂这套流程

```
你给 AI 一份「输入」  →  AI 产出「初稿」  →  你逐项审查挑错  →  组内提意见
                                                                  ↓
                        下一节点的「输入」  ←  承认版  ←  你承认  ←  AI 按意见改出「改修版」
```

**AI 负责「把散乱变整齐」，人负责「判断整齐得对不对」。** 这条循环连做 8 次，就是软件开发的
全流程。编号（`R-201 → F-201 → I-301… / L-201 / D-201 → TC-201…`）是串起整条链的钩子。

### 4.1 节点 1 · 需求理解

**① 打开什么**
[`节点1_需求/00_输入_客户需求书.md`](节点1_需求/00_输入_客户需求书.md) —— 先读懂「原始需求有多乱」。

> 它有 **6 处暧昧点**：①加密在前端还是后端 ②没输入社員コード时怎么办 ③失败几次锁定
> ④Session 超时多久 ⑤密码策略完全没提 ⑥多事業場用户默认用哪个。
> 这些地方就是 AI 要帮你揪出来的。这一步你不用做任何事，**看懂"乱"在哪**就行。

**② 复制这段给 Claude**

```
请阅读 tutorial/R60Login/节点1_需求/00_输入_客户需求书.md

把它整理成「需求结构化表」，要求：
1. 给需求一个编号 R-201
2. 拆成：背景 / 業務規則 / 輸入項 / 輸出項 / 異常処理 / 不做的事(Non-Goals)
3. 客户写得含糊、矛盾、缺失的地方，全部列成「待確認事項」，编号 Q-201、Q-202…
4. 用表格，不要大段文字
5. 同时输出一份 YAML 机读版（键名一律 snake_case）

输出到 tutorial/R60Login/节点1_需求/：
  - 01_AI产出_需求结构化表.md   （给人看）
  - 01_AI产出_需求结构化表.yaml （给机器看，后续节点都吃这个）
```

> ⚠️ **不要说**「用 `code-from-design-trans-cosmos-ai` 技能处理」。那个技能是 **R60Area（R-101）** 的
> 设计→制造流水线专用的，而且要求 R-ID 已登记在 `ids.yml`。本教程的 `R-201` 是教学号段、
> **没登记**，一执行就会在第一步被拒收。节点 1 请用上面这段提示词。

**③ 产出什么**：`01_AI产出_需求结构化表.md` + `.yaml`
重点看两处：①散乱需求是不是变成条目清晰的表？②**待確認事項（Q-201…）列出来了吗**——这就是 AI 替你省的脑力。

**④ 检查什么**：打开 [`02_你在这里审查.md`](节点1_需求/02_你在这里审查.md)，逐项打勾。核心三件事：

- [ ] 待确认事项里，**哪些要问客户，哪些我们自己拍板**？（AI 不敢替你决定）
- [ ] 有没有**客户没说但我们必须做的事**？（AI 只看得到纸上写的）
- [ ] 编号 `R-201` 是不是合规的？（不能自己乱编号）

> ⚠️ **这一步不能跳。** 需求理解错了，后面 7 个节点全部白做。

**⑤ 承认版（人拍板）**

```
请读 01_AI产出_需求结构化表（.md/.yaml）／02_確認事項一覧.md，
整理为承认版 04_承認版_需求结构化表.md：
1. §11 待確認事項の各項に、02 の「区分」「回答」「裁定」を反映する。
   分類は 02 に人が書いた値を用いる。AI 素案は別欄に残す。
   02 で空欄の項目があれば、整理せずに止めて報告する（勝手に埋めない）。
2. 顶部加「承認記録」表（版本 / 日期 / 承認者役割 / 承認状態 / 備考），
   承認者用角色＋代号表示（SE・A / PG・B / テスター・C / PM・D 四行）
3. front-matter の status を baselined、version を 1.0.0
```

**✅ 节点 1 完成** → `04_承認版_需求结构化表.md` 就是**节点 2 的输入**。

| 1 | **键名一律 snake_case** | YAML 的键只能是小写+下划线；`stfCd` / `gmnId` 这类 camelCase 只允许出现在「值」里 |
| 2 | **不写真实敏感值** | 员工号用 `EMP_0001`、值用 `VAL_1`、IP 用 `IP_1`、口令用 `PWD_1`、表名用 `TBL_1` |
| 3 | **人是责任主体** | 模板末尾的 `human_review_required` 就是「AI 不能替你拍板」的清单，逐条确认后才能走 |

## 7. 常用问答

**Q. 我可以不用这份教程，直接做我自己的需求吗？**
可以。把 [`节点1_需求/00_输入_客户需求书.md`](节点1_需求/00_输入_客户需求书.md) 换成你的真实需求书，
后面的步骤一模一样。**只需换编号**（例如 `R-301`）。

**Q. 那以前给客户交的 Excel 呢？**
`01_AI产出_需求结构化表.md` **就是那份 Excel 的内核**——以前你手写 Excel，现在 AI 生成这张表。
要变成客户收的日文 Excel，用 `py -3 -m tools.gen_formal.gen_excel --dry-run --module R-101`。
**目前只做 dry-run（校验列数对不对），还没有真的吐 .xlsx**——那要等客户提供正式模板（属 Phase 2）。
关键原则：**只维护这一份机读源，Excel 由它生成，绝不两头手改。**

**Q. 客户习惯直接在 Excel 上用红笔改，怎么办？**
**不要禁止，改成「受控回流」——把客户的手引到一个安全的出口。**
做法：**正文只读，另附一张「指摘シート／レビュー欄」**，客户只在那一栏写意见（每行带**行番号**或
**R-ID** 引用），AI 只读那一栏 → 改机读源 → 重新生成。

```
 机读源 .md/.yaml（唯一真源）
        │ ① 生成（单向，只读）
        ▼
 日文 Excel 正文（客户不改正文）
        │ ② 客户只在另附的「指摘シート」里写意见（每行带 行番号 / R-ID）
        ▼
 指摘シート（意见回线，独立文件）
        │ ③ AI 只读这一栏
        ▼
 改机读源 → 重新生成 Excel（回到 ①）
```

本目录的 [`节点1_需求/客户確認依頼書.md`](节点1_需求/客户確認依頼書.md) 就是这个思路的**实物样板**
（A=客户决定 / B=我方暂定前提的确认 / C=验收条件，全部都带填写栏）。

> ⚠️ **不要**做的是：客户红笔改完 Excel → 直接把那份改过的 Excel 丢给 AI「转成 .md」。
> 那正是本流程明令禁止的**双向回路**（依据 `docs/00_plan/spec.md` FR-3「严格单一数据源，禁手改日文版」）。

**Q. 怎么知道我做对了？**
每个节点的「你在这里审查 / 模板的 human_review_required」就是验收清单。
另外随时跑 `py -3 -m tools.trace_check --strict`，全 PASS 说明编号链条没断。

**Q. 「承认」是口头说说吗？**
不是。承认版文件顶部有「承認記録」表格，写清版本 / 日期 / 承认者。以后出问题能追溯到谁在什么时候点头的。

**Q. 组内审查意见一定要用这个格式吗？**
不一定，但**建议**用「指摘者 + 问题 + 希望怎么改」三段式——AI 读结构化意见改得最准。
参照 [`节点2_基本设计/03_组内审查意见.md`](节点2_基本设计/03_组内审查意见.md)。

**Q. 我觉得某个节点没必要做。**
可以跳过，但要知道代价。比如跳过节点 3（详细设计），AI 在做节点 5（编码）时会**自己去猜处理逻辑**——
**猜错了你更难发现**。

## 8. 这套流程到底省了什么

| | 以前 | 现在 |
|---|---|---|
| 写文档 | 人工写 Excel/Word | AI 出初稿，你只改 |
| 审查意见落实 | 人对着意见逐条改 | 意见喂给 AI，一句话改完 |
| 找人问需求细节 | 口头问、邮件问 | AI 先列出「待确认事项」，你只挑重点问 |
| 追溯「这条代码对应哪个需求」 | 翻文档找 | 编号串起来，一条命令查到底 |

**你省下的是「写字」的时间；你把时间花在「判断」上**——判断需求对不对、设计合不合理、测试够不够、
能不能上线。**这才是这套东西的意义。**
