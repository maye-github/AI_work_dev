3.4 登录的判定

将「ユーザーＩＤ」中输入的社員コード加密后发送，在服务器侧解密并确认员工是否存在。

用于判定能否登录的，仅是社員コード本身是否存在（以及该员工未被逻辑删除）。
所属、权限、有效期不用于判定能否登录。

确认存在后，将公司、事業場、姓名等信息保存到 Session，以便后续业务画面参照。

员工不存在时，不允许登录并按错误处理（§5）。此时跳转到会话错误画面。

输入检查：「ユーザーＩＤ」须为必填且半角 7 位（§3.2 #3）。
位数或字符种类不符时，也不允许登录并按错误处理（与不存在的社員コード同等对待）。

3.5 画面跳转

  • 登录成功时：打开所选画面。同时将権限区分（§3.2 #7）继承到跳转目标。
  • 按下 メニュー 按钮时：跳转到菜单画面。同时继承 起動区分（§3.2 #4）。

跳转目标的确定及跳转方式（同一窗口／另一窗口）依据本公司标准规约（§3.8）。

3.6 跳转 URL 的输出

通过「URL出力」按钮生成包含加密后社員コード的 URL，并显示在画面的「URL」栏中。

该 URL 也会在其他系统自行组装并跳转过来时使用，因此参数的排列顺序与值必须严格按指定执行。

http://<host>:<port>/R60/Pages/index.jsp?stfCd=<暗号化された社員コード>&stfKbn=<起動区分>&gmnId=<画面ID>&kgnKbn=<権限区分>
参数值
stfCd加密后的社員コード（方式依据 §4.4）
stfKbn起動区分原样（1 / 2 / 3）
gmnId画面主数据的画面ID 原样
kgnKbn権限区分：Y＝更新あり ／ N＝更新なし
主机与端口因环境而异，因此本需求书中记为 <host>:<port>。

4. 接口（API）

共 3 个端点。全部为 POST。路径为 /R60Login/<name>。

4.1 列表

#端点对应事件作用
1POST /R60Login/init事件 1返回初始显示所需的信息（画面候选项、権限区分候选项）

4.2 POST /R60Login/init

Request{"params": {}} — 没有输入（初始显示不依赖输入）
Response{"errorCode", "pageList": [{"value","label"}], "kbnList": [{"value","label"}]}
pageList从画面主数据获取（仅有效项）。显示顺序由主数据的维护决定
kbnList更新あり／更新なし 的候选项（值与 §3.6 的 kgnKbn 相同）
预处理运行状态的检查（§3.7）。不可则为业务错误

4.3 POST /R60Login/login

Request{"params": {"stfCd", "stfKbn", "gmnId", "kgnKbn"}}
stfCd已加密的社員コード（在画面侧加密后发送）
处理① 解密得到明文的社員コード ② 确认员工是否存在（§3.4） ③ 获取公司、事業場、姓名等并返回
Response（成功）{"errorCode":"0", "userInfo": {...}, "mngInfo": {...}}
Response（无对应项）{"errorCode":"1"} — 不返回其他字段
预处理运行状态的检查（§3.7）

4.4 POST /R60Login/generateUrl

Request{"params": {"stfCd", "stfKbn", "gmnId", "kgnKbn"}}
stfCd★明文的社員コード。在服务器侧加密
处理加密社員コード，按 §3.6 的格式组装 URL 并返回
Response{"errorCode":"0", "url": "http://<host>:<port>/R60/Pages/index.jsp?stfCd=…&stfKbn=…&gmnId=…&kgnKbn=…"}
预处理运行状态的检查（§3.7）
★stfCd 的处理因端点而相反。 /login 接收已加密的值，
/generateUrl 接收明文。请勿混淆。
社員コード未输入时，/generateUrl 会将 "NaN" 作为社員コード处理。

4.5 社員コード的加密

  • 将当日日期（yyyymmdd）用作密钥材料（设为仅在当日有效的值）。
  • 解密在服务器侧进行。
  • 必须与 §3.6 的跳转 URL 格式兼容（因为其他系统会组装本 URL 并跳转过来）。
  • 方式及密钥的运维由贵方提出方案（须满足上述兼容性）。
