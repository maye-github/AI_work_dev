## C-01　暗号化の主体が 2 経路に分かれている点

| 項目 | 内容 |
|---|---|
| 論点 | ログイン処理は画面側で暗号化済みの社員コードを受け、URL 出力処理は平文を受けてサーバ側で暗号化する。暗号化の実装が 2 経路に分かれると、方式の変更時に片方だけが更新される恐れがある。 |
| 裁定 | 両経路の構成は維持する。暗号化・復号の処理を 1 本の共通関数に集約し、画面側とサーバ側の双方から同じ関数を呼ぶ。方式・鍵の導出・分割規則は 1 箇所だけに定義する。 |
| 根拠 | ご要望書 §4.3（画面側暗号化）、§4.4（サーバ側暗号化）、§4.5（暗号化方式）。 |
| 設計への反映 | 詳細設計に「暗号化共通関数」を 1 つ定義し、ログイン系と URL 出力系の両方から参照させる。単体テストは、同じ入力から両経路が同じ暗号化結果を返すことを確認する。 |
| 備考 | 既存案件の関数名は参考にしない。本案件（新規構築）の命名で新規定義する。 |

## C-02　権限区分リスト（kbnList）をマスタ駆動とするか 2 値固定とするか

| 項目 | 内容 |
|---|---|
| 論点 | 初期表示は権限区分のリストを返すが、ご要望書 §3.2 #7・§3.6 では権限区分は「更新あり／更新なし」の 2 値とされている。マスタで可変にするのか、固定 2 値とするのかが不明確である。 |
| 裁定 | 2 値固定とする。内部値は `1`（更新あり）／`0`（更新なし）、URL へ渡す値は `Y`／`N` とする。変換は 1 箇所で行い、内部値と URL 値の二重管理を避ける。 |
| 根拠 | ご要望書 §3.2 画面項目 #7、§3.6「遷移 URL の出力」。 |
| 設計への反映 | 初期表示の応答に 2 値のリストを含める。権限区分のマスタテーブルは作らない。変換関数を詳細設計に明記する。 |
| 備考 | 将来 3 値以上が必要になった時点で変更要求（CR）として扱う。 |

## C-03　権限区分の初期値「更新あり」の運用リスク

| 項目 | 内容 |
|---|---|
| 論点 | 権限区分の初期値が「更新あり」であるため、利用者が選び忘れると更新権限のまま遷移する。業務上の事故につながる可能性がある。 |
| 裁定 | ご要望書の指定どおり、初期値は「更新あり」を維持する。画面上で現在の選択値が明確に分かる表示とし、運用注意事項として記録する。顧客への追加質問は行わない。 |
| 根拠 | ご要望書 §3.2 画面項目 #7 が初期値を指定している。 |
| 設計への反映 | 権限区分の選択状態を視認できる表示にする。リリースノートの「運用上の注意」に、選び忘れ時の影響を記載する。 |
| 備考 | 初期値を「更新なし」へ変える場合は、要求変更として顧客の承認を得る。 |

## C-04　文字コード・URL エンコード・タイムゾーン

| 項目 | 内容 |
|---|---|
| 論点 | 暗号化した社員コードをクエリ文字列に載せるが、文字コード・URL エンコードの要否・使用可能文字・タイムゾーンが規定されていない。 |
| 裁定 | 文字コードは UTF-8。暗号化後の社員コードは数字と `_` のみで構成するため、追加のパーセントエンコードは行わない。他のパラメータは英数字のみとし、URL 予約文字を含めない。日時は JST とする。 |
| 根拠 | ご要望書 §3.6「遷移 URL の出力」、§4.4「遷移 URL の生成」。 |
| 設計への反映 | URL 生成関数の出力を検証し、数字・英字・`_` 以外が含まれる場合はシステムエラーとして扱う。結合テストで URL の文字種を確認する。 |
| 備考 | 暗号化方式の変更で `_` 以外の記号が出力される場合は、本裁定を見直す。 |

## C-05　非同期 API の二重送信抑止

| 項目 | 内容 |
|---|---|
| 論点 | ログイン・URL 出力などのボタンは非同期 API を呼ぶが、二重送信の扱いが要求書に規定されていない。連打により複数のログインや URL 生成が走る可能性がある。 |
| 裁定 | すべてのボタン処理の先頭で送信中かどうかを判定し、送信中は後続の処理を実行しない。API 呼出直前に送信フラグを立て、`finally` で必ず解除する。 |
| 根拠 | ご要望書 §3.3「イベント」、§4.1「イベントと API の対応」。 |
| 設計への反映 | 共通の送信抑止部品を新規定義し、ログイン・メニュー・URL 出力・閉じるの各イベントから呼ぶ。異常終了時もフラグが解除されることを単体テストで確認する。 |
| 備考 | 既存案件の共通関数名は参考にしない。本案件の共通部品として同等機能を新規定義する。 |

## C-06　画面タイトルの固定値と文書名の表記ゆれ

| 項目 | 内容 |
|---|---|
| 論点 | 画面タイトルは「共通マスタ　ログイン」（全角空白入り）と指定されているが、文書名は「共通マスタログイン」で表記が一致しない。 |
| 裁定 | 画面に表示する固定値は「共通マスタ　ログイン」（全角空白入り）とする。文書名は表記ゆれとして許容し、画面表示には用いない。 |
| 根拠 | ご要望書 §3.2 画面項目 #1「タイトル」の指定が画面表示の正である。 |
| 設計への反映 | 画面項目定義の初期値として全角空白を含む文字列を登録する。単体テストの期待値も同じ文字列とする。 |
| 備考 | 全角空白は目視で判別しにくいため、テストでは文字コードで比較する。 |

## C-07　入力仕様の細部（桁下限・文字種・正規化）

| 項目 | 内容 |
|---|---|
| 論点 | 起動区分は半角数字 1 桁・初期値 3、ユーザー ID は半角数字・最大 7 桁と指定されるが、桁数の下限、範囲外の扱い、前後空白、全角文字、貼付け時の扱いが未規定である。 |
| 裁定 | 起動区分は 1／2／3 のみを有効とし、範囲外は入力エラー。ユーザー ID は半角数字・最大 7 桁（7 桁固定ではない）・必須。前後の空白は trim せず、全角・非 ASCII は入力時に除去する（貼付けも同じ）。 |
| 根拠 | ご要望書 §3.2 画面項目 #3・#4、§3.4 入力チェック。 |
| 設計への反映 | 入力コンポーネントで半角変換を行い、後続処理には半角英数字のみを渡す。入力エラーの表示位置と文言は画面項目定義に含める。 |
| 備考 | trim しないのは、空白を許容する既存運用との互換のため。 |

## C-08　ログイン処理で使わない 3 引数の扱い

| 項目 | 内容 |
|---|---|
| 論点 | ログイン処理は 4 つの入力を受けるが、処理で使用するのは社員コードのみで、起動区分・画面 ID・権限区分は未使用である。受け取った上で無視してよいか、検証すべきかが不明確である。 |
| 裁定 | サーバ側では社員コードのみを使用し、他の 3 値は検証も保存もしない。3 値はクライアント側で遷移先の決定・権限保持・メニューへの引継ぎに使用する。**`stfKbn` はメニュー画面（MenuCommon）のクエリに使用する**（実装確認済み）。 |
| 根拠 | ご要望書 §4.3 の処理は社員コードの存在確認のみ。 |
| 設計への反映 | ログイン処理の入力定義から 3 値を除外せず受け取るが、処理では参照しない。サーバとクライアントの責務を API 仕様書に明記する。 |
| 備考 | 将来サーバ側で権限検証を行う場合は、要求変更として扱う。 |

## C-09　URL 欄の編集値と上限超過の扱い

| 項目 | 内容 |
|---|---|
| 論点 | URL 欄は生成 URL の表示欄でありながら利用者が直接編集でき、編集値の用途と、生成 URL が上限 150 文字を超えた場合の扱いが未規定である。 |
| 裁定 | 編集は可能とするが、編集値は表示用であり遷移には使用しない。150 文字は受付上限として維持し、**生成 URL が 150 文字を超える場合は切捨てずにエラー**とする。半角は ASCII 印字可能文字とする。**この裁定は当方の C 裁定であり、顧客要求の明文ではない。** |
| 根拠 | ご要望書 §3.2 画面項目 #10、§3.3、§3.5。切捨ては遷移先の URL を壊すため（E4）。受付上限は画面レイアウトの都合である（E3）。 |
| 設計への反映 | 遷移には常に再生成した URL を用いる。編集値はコピー用途に限定する旨を画面仕様に記載する。URL 長が 150 文字を超えた場合はエラー表示とし、遷移しない。 |
| 備考 | 生成 URL の実測は **86〜87 文字**（単測の付録で確認）で、上限には達しない。旧実装は長さ検査・切捨て・エラーを行っていない（測定値）。 |

## C-10　当日鍵のタイムゾーンと日跨ぎ

| 項目 | 内容 |
|---|---|
| 論点 | 「当日の日付を鍵の材料に用いる」「当日内でのみ有効」の基準タイムゾーンと、日跨ぎの扱いが未規定である。 |
| 裁定 | 基準はサーバの日本標準時（JST）とし、日付の切替は 0 時とする。前日に生成した URL は復号失敗となり、業務エラーとして Session エラー画面へ遷移する。システム日時の表示も同じ時刻系とする。 |
| 根拠 | ご要望書 §4.5、§3.6。 |
| 設計への反映 | 鍵導出はサーバ時刻のみを参照する（端末時刻を使わない）。日跨ぎの境界を単体テストに含める。 |
| 備考 | 他システムが前日 URL を保持する運用がある場合は、運用側で当日中に再取得する。 |

## C-11　初期表示・API 失敗時の画面挙動と遷移主体

| 項目 | 内容 |
|---|---|
| 論点 | 初期表示の失敗、ログイン失敗（業務エラー・復号失敗）、稼働不可のときに、どの画面へ誰が遷移させるかが未規定である。 |
| 裁定 | 初期表示の失敗はシステムエラー画面、業務エラー・復号失敗は Session エラー画面、稼働不可はオンライン利用エラー画面へ遷移する。判定と遷移はクライアント側が行い、遷移時にエラーコードと利用者向けメッセージを渡す。自動再試行はせず、再読み込みボタンを表示する。3 回連続で失敗した場合は運用ログに記録する。 |
| 根拠 | ご要望書 §3.4、§5。 |
| 設計への反映 | サーバは判定結果（エラー区分）を返すことに徹し、画面遷移を持たない。遷移先のルート名を詳細設計に定義する。 |
| 備考 | 自動再試行を入れないのは、稼働不可時に負荷を増やさないため。 |

## C-12　システム日時の取得元・更新頻度・閉じる文言

| 項目 | 内容 |
|---|---|
| 論点 | システム日時の取得元（サーバ／端末）、更新頻度、12／24 時間表記、および閉じるボタンの確認文言が未規定である。 |
| 裁定 | クライアント端末時刻を `YYYY/MM/DD HH:mm:ss` 形式・24 時間表記で表示し、1 秒ごとに更新する。閉じる確認文言は「画面を終了してよろしいですか？」とする。 |
| 根拠 | ご要望書 §3.2 画面項目 #2、§3.3 #5。 |
| 設計への反映 | 時刻表示は共通部品として新規定義し、他画面から再利用できる形にする。 |
| 備考 | 端末時刻のずれが業務上の問題になる場合は、サーバ時刻同期の要否を別途検討する。 |

## C-13　環境ごとの host／port の設定管理

| 項目 | 内容 |
|---|---|
| 論点 | 遷移 URL の host・port・context が環境依存とされるが、管理方法が未規定である。 |
| 裁定 | ソースコードに固定せず、環境設定ファイルまたは環境変数で管理する。開発・検証・本番で同一のソースを用いる。 |
| 根拠 | ご要望書 §3.6。 |
| 設計への反映 | 設定項目の一覧と既定値を詳細設計に定義し、環境ごとの差分は設定側に閉じる。 |
| 備考 | 設定値そのものは本資料に記載しない（機密管理は別途）。 |

## C-14　画面遷移のブラウザ制約（ポップアップブロック）

| 項目 | 内容 |
|---|---|
| 論点 | ログイン成功時に新規ウィンドウ／タブで開く方式は、ブラウザのポップアップブロックで失敗する可能性がある。 |
| 裁定 | 新規ウィンドウ／タブを基本とし、開けない場合は同一ウィンドウへ切り替えるか、利用者に案内を表示する。 |
| 根拠 | ご要望書 §3.5 は遷移方式を標準規約に委ねている。 |
| 設計への反映 | 遷移処理の戻り値を確認し、失敗時に代替動作へ切り替える。結合テストでポップアップブロック有効時の挙動を確認する。 |
| 備考 | メニュー遷移は同一ウィンドウのため、本項の対象外。 |

## C-15　URL 出力時に社員存在確認を行わないこと

| 項目 | 内容 |
|---|---|
| 論点 | URL 出力処理には社員の存在確認がなく、存在しない社員コードでも URL を生成できる。意図した仕様かが不明確である。 |
| 裁定 | URL 出力は暗号化と URL 生成のみを行い、存在確認はしない。存在確認はログイン処理で行う。 |
| 根拠 | ご要望書 §4.4 の処理は暗号化と URL 生成のみ。 |
| 設計への反映 | 責務を API 仕様書に明記し、存在確認を重複して実装しない。結合テストでは「存在しない社員コードでも URL が生成される」ことを確認する。 |
| 備考 | セキュリティ上の懸念が出た場合は、要求変更として扱う。 |
