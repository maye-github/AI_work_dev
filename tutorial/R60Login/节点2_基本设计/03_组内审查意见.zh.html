「明確な」の具体化は我方の設計なので、当方が決めてよい（C 類）。E-201 の処理を
「稼働停止であることが利用者に分かる専用の提示を行い、ログイン画面には留めない」と書き、
その根拠として BR-201-01 を引くこと。

意见-02　【SE】　Q 番号の扱いと、暫定値の置き方を直す

意见-04　【PG】　エラー処理に抜けがある（復号失敗・DB 接続失敗）

  • 指摘：两个缺口。

① E-202（復号失敗）は「回登录画面」としか書かれておらず、復号の入参が何か・異常時に何をするかが無い。
② 手順①の稼働チェックは DB を使うが、DB 接続そのものに失敗した場合の扱いが無い（E-206 は Session 生成失敗しか書いていない）。

  • 希望怎么改：
  • E-202：入参は I-301 stfCd（画面側で暗号化された社員コード）であることを明記し、異常時は

E-202 として扱いログイン画面へ戻す。ログ出力時は敏感値を占位化する。

  • E-206：DB 接続取得失敗もシステムエラーとして扱い、底層の例外を利用者に見せず、運用ログへ記録する。
  • 注意：復号の実施主体（画面側で暗号化し API 側で復号する）は、节点1 Q-206 の当方提案であり顧客承認待ちである。

承認済みの事実として書かないこと（「当方提案・承認待ち」と注記する）。
