## 2. 論理設計（L-201〜L-208）

### 2.1 全体の処理順序

```
イベント１ 初期表示
  クライアント: 画面生成（I-301・I-302・I-305）
  → L-201 稼働判定 ──不可──▶ E-206（オンライン利用エラー画面）
  → /init → L-202 候補取得・初期値 ──失敗──▶ E-204（システムエラー画面）

イベント２ ログイン
  L-207 入力チェック・暗号化（API より前）
  → /login → L-201 稼働判定 ──不可──▶ E-203
            → L-203 復号（L-206）→ 社員検証 → 情報取得 → Session 生成
            → 応答（I-316・I-317）
  → L-204 遷移先解決・遷移（クライアント）

イベント３ メニュー（/login を共用。専用端点なし）
  L-207 → /login → L-201 → L-203 → L-204（同一ウィンドウで SCR-202）

イベント４ URL出力
  L-207（URL 出力用の検査）
  → /generateUrl → L-201 稼働判定 ──不可──▶ E-203
                 → L-205 正規化 → L-206 暗号化 → URL 組立 → I-310 表示

イベント５ 閉じる
  L-208 確認 → Session 破棄要求 → 画面を閉じる
```

**順序は固定である**（上流 §6 イベント２「順序は固定」）。①稼働チェック → ②復号 → ③社員検証 →
④社員情報取得 → ⑤Session 生成 → ⑥遷移先の解決。**クライアント側の入力チェックと暗号化は ① より前**に行う。

**ログイン時の暗号化（L-207）が使う当日の日付（JST）は、端末時刻だけでは決められない。**
初期表示の `/init` 応答（HTTP `Date` ヘッダ）を基準に算出する（§2.7・§8.4）。

- 業務データを更新しない。**ロールバック対象の更新は無い**。
- **ログに暗号化値・復号後の平文を出力しない**（上流 §11）。

#### 2.4.1 停止条件（ログイン試行ロック）

上流 節点2 §11「ログイン試行 5 回／10 分でロック。10 分後に自動解除」（**区分 B 提案**）を実装粒度に落とす。
**BUG-002 の是正で追加した**（v1.0.5・2026-10-27）。**E を増やさない**——ロック中の応答は E-201 と同じ形式を再用する（§6.1 の注記）。

| 項目 | 内容 |
|---|---|
| 目的 | 同一利用者による短時間の反復試行を止める（上流 §11） |
| 計数の単位 | **復号に成功した社員コード**。保持するキーは社員コードの **SHA-256**（プロセス起動時に生成する salt 付き）。**平文の社員コードを保持しない** |
| 認証失敗と数える事象 | **ステップ3 の社員照会が 0 件（E-201）のみ** |
| 数えない事象 | E-204（画面マスタ取得の失敗）・E-205（復号失敗）・E-208（DB 障害等）。前者は基盤障害、後者は識別子の不正であり、**同一利用者の試行と見なさない**。**§7.6 の「E-204 連続 3 回で運用ログ 1 件」（裁定 Q-230）とは別の計数である**——同じ「失敗」でも対象も目的も違う |
| 窓 | **直近 10 分**（滑り窓）。10 分を超えた失敗は計数から外す |
| 停止条件 | 窓内の失敗が **5 回に達した時点**でロックを成立させる |
| ロック中の挙動 | **ステップ3 の照会を行わない**。応答は **E-201 と同じ形式**（`errorCode="1"` のみ・HTTP 200・Session エラー画面）。**ロック中であることを利用者へ示さない**（§6.2 の「存在有無・入力の正否を推測させない」に合わせる） |
| ロックの範囲 | **当該社員コードのみ**。他の社員コードの試行は妨げない（画面・端末・IP では判定しない） |
| 解除条件 | **ロック成立から 10 分の経過で自動解除**。人手の解除操作は設けない |
| 成功時の扱い | ステップ3 が 1 件以上なら、当該社員コードの計数を **0 に戻す** |
| 保持先 | **プロセス内**（節点4 OQ-05 の「本件は単一インスタンス」裁定に従う）。**多インスタンス化する場合は外部ストアが必要**であり、構成変更（CR）となる |
| ログ | ロックを成立させた 5 回目の失敗で**運用ログ 1 件**（時刻・画面ID・結果コード・インスタンスID・要求 ID。**社員コードは出さない**）。**ロック中の試行はアクセスログのみ**（結果コード `1`） |
| 境界 | B-44〜B-46（§7.11） |

**順序・冪等性**

- 計数は**照会の結果を受けてから**行う（照会の前に加算しない）。したがって **5 回目の失敗は通常の E-201 として応答し**、ロックが成立する。**6 回目の試行から照会を行わない**。
- **ロック中でも復号は行う**。ロックのキーが社員コードであり、復号しないとキーが決まらないため。復号に失敗すれば E-205 であり、**ロック判定へ到達しない**（ロック中の失敗試行としても数えない）。
- 同一社員コードへの同時要求は、計数の加算と判定を**1 つの排他区間**で行う（競合で 5 回を超えて通さない）。

| 1 | L-201 を呼ぶ。不可なら E-203 で終了する | 不可 → 以降を行わない |
| 2 | I-303 が未入力なら、文字列 `"NaN"` を社員コードとして扱う | **入力エラーとしない**（Q-214）。**暗号化を適用せず** `stfCd=NaN` をそのまま URL に載せる（裁定 Q-231） |
| 3 | 入力済みなら、前後空白は **trim せず**、全角・非 ASCII を半角へ変換して**除去する** | Q-210。正規化はこの 1 箇所で行う（他で再実装しない） |
| 4 | 正規化後の値の妥当性を判定する | **半角数字 1 桁以上**なら可。数字以外が残る／0 桁なら不可（裁定 Q-231）。**7 桁固定は課さない** |

**組立主体と判定主体はサーバである。** URL の組立（ステップ 6）と 150 桁判定（ステップ 7）は
`generateUrl` がサーバ側で行う。クライアントは応答 I-310 を**そのまま表示するだけ**で、
**URL を組み立て直さない・桁判定をやり直さない**。超過時はサーバが返す `1`／`R60W0001` を
E-210 の通知として表示する。scheme／host／port／context はサーバの環境設定から取得する
（裁定 Q-233。上流 §7.1 の記述を採り、上流 §6 イベント４(6)(7) の「クライアントが組み立て桁判定する」
記述は採らない）。

URL の形（プレースホルダ・上流 §6 イベント４）：

```
{scheme}://{host}:{port}/{context}/{route}?stfCd=VAL_1&stfKbn=VAL_1&gmnId=VAL_1&kgnKbn=VAL_1
```

### 2.7 L-206 社員コード暗号化・復号（共通処理・1 本に統合）

| 項目 | 内容 |
|---|---|
| 目的 | 平文→暗号化（URL 生成時）と暗号化→平文（ログイン時）を 1 本の共通処理で行う |
| 呼出元 | L-203（復号）・L-205（暗号化）＝**サーバ**／L-207（ログイン時の暗号化）＝**クライアント**。**日付の供給元は呼出元ごとに固定する**（下の「入力」） |
| 入力 | 平文社員コード又は暗号化文字列。**当日の日付（JST・`yyyymmdd`）を引数で受け取る**（C・`03-design-coding` §7.1 の冪等性）。**日付の供給元は呼出元で固定する**：サーバ（L-203・L-205）は**サーバの JST 日付**／クライアント（L-207）は **`/init` 応答の HTTP `Date` ヘッダとの差分で補正した JST 日付**（§8.4）。サーバ応答から日付を得られない場合のみ、端末の UTC エポックから換算する |
| 出力 | 暗号化文字列又は平文社員コード。失敗は例外 |
| 前提 | 算式・境界規則の唯一の定義は**上流 §10.3**。**AES-256-ECB ではない** |

**算式（上流 §10.3 の転記。判断を加えていない）**

| # | 処理 | 規則 |
|---|---|---|
| 1 | 各桁を +1 する | **1 桁に切り詰めない。** 桁が `9` のときは `10`（2 文字）を出力し、**次の桁へ桁上げしない** |
| 2 | 4 桁超なら分割する | **境界は 5 桁目で固定**（1〜4 桁目＝前ブロック、5 桁目以降＝後ブロック） |
| 3 | 各ブロックを文字列化する | 先頭桁はゼロ埋めなし、**2 桁目以降は 2 桁ゼロ埋め**で連結する |
| 4 | 各ブロックの変換値に当日の `yyyymmdd` を**整数加算**する | 当日鍵の日付は JST・当日内のみ（Q-216）。**日付は引数で受け取る**（呼出元が供給・上の「入力」） |
| 5 | 5 桁以上（複数ブロック）は `_` で連結する | ブロックが 1 つのときは `_` を付けない |
| 6 | 復号は上記の逆順で行う | 復号も同じ 1 本の処理に置く（上流 §10.2(a)-1） |

**検算（上流 §10.3 の例を手順に落としたもの・導出）**

| 段 | 値 |
|---|---|
| 入力 | `1234567`／当日 `20251201` |
| +1 | `2` `3` `4` `5` `6` `7` `8` |
| 分割（5 桁目で固定） | 前＝`2,3,4,5`／後＝`6,7,8` |
| ゼロ埋め連結 | 前＝`2`+`03`+`04`+`05` = `2030405`／後＝`6`+`07`+`08` = `60708` |
| 日付加算 | 2,030,405 + 20,251,201 = **22,281,606**／60,708 + 20,251,201 = **20,311,909** |
| 連結 | `22281606_20311909`（上流 §10.3 の例と一致） |

**境界の取扱い（上流 §10.3 の規則）**

- `9999` → `10`+`10`+`10`+`10` = `10101010`（**桁上げしない**）。
- 4 桁ちょうど → 分割しない（`_` なし）。5 桁 → 4＋1 に分割（`_` あり）。
- **暗号化文字列の長さ（数字 7 桁の入力に対する上限）＝17 桁**（導出）。前ブロックの最大 `10101010`（8 文字）＋`_`＋後ブロックの最大 `101010` に日付を加えた 8 桁 ＝ 8+1+8。
  **`"NaN"` は暗号化しないため、暗号化文字列の長さは 0**（URL には 3 文字 `NaN` が載る・裁定 Q-231）。

**分岐・例外**

| # | 条件 | 処理 | E-ID |
|---|---|---|---|
| 1 | 復号失敗（不正な暗号化値） | Session エラー画面へ | E-205 |
| 2 | 当日鍵の日跨ぎ（前日に生成した暗号化値を翌日に復号） | 同上。**翌日は業務エラー**（Q-216） | E-205 |
| 3 | 暗号化失敗 | システムエラー画面へ | E-209 |
| 4 | クライアントがサーバの日付を得られない（サーバ応答が無い・`Date` ヘッダが無い） | 端末の UTC エポックから JST を換算して処理を続ける。換算結果がサーバと食い違えば行 1（E-205）になる（§8.4） | E-205 |

**順序・冪等性**

- 同一入力＋同一日付 → 同一出力（決定的）。**乱数・現在時刻・UUID を埋め込まない**（`03-design-coding` §7.1）。
- 日付は引数として注入できる形にし、テストで固定できるようにする（C）。**クライアント（L-207）は暗号化の直前に、
  直近のサーバ応答から得た差分で補正した JST 日付を渡す**（§8.4）。補正してもずれた場合（日跨ぎ・端末の時計の進行不良）は
  復号失敗として E-205 になる（B-33）。
- **当日鍵の実値・平文／暗号化前後の実値はログに出さない**（上流 §11）。鍵の取得方式は工程04 の構成承認時に確定する（§9）。

## 5. SQL テンプレート

### 5.1 共通方針

1. **値はすべてバインド変数（`:name`）で受ける。** 実値・実コードを SQL 本文へ書かない。f-string 等で値を連結しない。
2. **列名・表名を利用者入力から組み立てない。** 本画面に**動的ソートは無い**（並びは `ORDER BY disp_order, gmn_id` の固定）。
   したがって `ALLOWED_SORT_FIELDS` のような白名单は**適用対象が存在しない**（`.claude/rules/03-design-coding.md` §5）。
   将来ソート機能を足す場合は設計変更（CR）であり、本節点では行わない。
3. **SELECT のみ。** INSERT／UPDATE／DELETE を持たない（§3.1）。
4. **型・桁は §3 のとおり。** 日付・時刻を SQL に埋め込まない（当日鍵は SQL の外で扱う・L-206）。
5. **バインド値は `:name` のまま残す。** 実体は環境設定又は裁定値（Q-227／Q-234）で与える。
6. **上流 Q-208 のコード値を要する箇所は、本節点の SQL には無い**（コード区分による結合を行わない）。
   将来必要になった場合は `:code` で受け、値は上流 Q-208 の指定による（本書に再掲しない）。

### 5.2 SQL-1 稼働判定（L-201）

```sql
-- 稼働判定。呼出元: /init・/login・/generateUrl の先頭（3 端点すべて）。
-- 0 件・無効値・例外はすべて「稼働不可」（E-203 / E-206）。
SELECT operation_flg
  FROM SYS_CMN_TBL
 WHERE cmn_key = :operation_key;
```

- `:operation_key` — 稼働フラグの行を特定する共通キー。**キー値は環境設定で与える**（裁定 Q-234。設計に実値を書かない）。
- 0 件を「可」と読み替えない。**0 件は不可**（上流 §6(0-2)）。

### 5.3 SQL-2 画面候補の取得（L-202）

```sql
-- 画面候補。有効行のみ・表示順の昇順。全社共通（利用者で絞り込まない）。
SELECT gmn_id,
       gmn_nm
  FROM GMN_MST
 WHERE valid_flg = :valid
 ORDER BY disp_order, gmn_id;
```

- `:valid` — 有効フラグの「有効」値は **`1`**（裁定 Q-234）。
- `ORDER BY disp_order, gmn_id` の第 2 キーは**順序を安定させるため**（C）。同一 `disp_order` の行があっても結果が揺れない。
- 件数を固定値（59 等）で扱わない（Q-211）。

### 5.4 SQL-3 社員検証（L-203）

```sql
-- 未削除（del_flg = :not_deleted）の該当行が 1 行でもあれば「存在」とみなす。
-- 0 件は E-201（応答は E-207 の形式。詳細コードは返さない・裁定 Q-235）。
SELECT 1
  FROM STF_MST
 WHERE stf_cd  = :stf_cd
   AND del_flg = :not_deleted;
```

- `:stf_cd` — 復号後の社員コード（L-203 ステップ 2 の結果）。
- `:not_deleted` — **`0`**（裁定 Q-227 で確定）。
- `stf_cd` は PK のため**最大 1 行**。件数の集計は不要。

### 5.5 SQL-4 社員情報の取得（I-316・L-203）

```sql
-- I-316 の 6 項目。社員マスタと組織・事業場マスタを複合キーで結合する。
SELECT s.stf_cd,
       s.stf_nm,
       o.cmp_cd,
       o.cmp_nm,
       o.jig_cd,
       o.jig_nm
  FROM STF_MST s
  JOIN ORG_JIG_MST o
    ON o.cmp_cd = s.cmp_cd
   AND o.jig_cd = s.jig_cd
 WHERE s.stf_cd  = :stf_cd
   AND s.del_flg = :not_deleted;
```

- **内部結合（INNER JOIN）**である。結合先が無い行は返らない。その 0 件は **E-201 と同じ扱い**とする（裁定 Q-237）。
- 結合は 2 表で足りる。コード・メッセージ管理マスタは含めない（裁定 Q-238）。文言は SQL-6 で取得する（サーバ実行・§5.7）。
- 返却は最大 1 行（`stf_cd` は PK、`ORG_JIG_MST` の主キーは `cmp_cd`+`jig_cd`）。

### 5.6 SQL-5 管理情報の取得（I-317・L-203）

```sql
-- Q-229 の裁定: I-317 の 5 項目は社員マスタから参照取得する（本画面は更新しない）。
-- SQL-4 と同一の往復にまとめてよい（結果は同じ・上流 §6 イベント２(7)）。
SELECT scmp_cd,
       sjig_cd,
       ji_kjo_ksn_flg,
```

### 5.7 SQL-6 エラー文言の取得（サーバ側・エラー応答の共通処理）

```sql
-- 利用者向け文言の実体はメッセージ管理情報から取得する（上流 §9.2・Q-206）。
-- 実行主体はサーバのみ。クライアント（ブラウザ）は DB に接続できず、この SQL を実行しない（C）。
SELECT msg_txt
  FROM CD_MSG_MST
 WHERE msg_id = :error_detail_code;
```

- **呼出元はサーバである。** エラー応答を生成するすべての処理（L-201〜L-205）が、返す `errorDetailCode` を
  引数として本 SQL を実行する（特定の L に紐づく SQL ではない）。
- `:error_detail_code` — I-319 の値（`R60W0001`〜`R60W0004`／`R60E9999`）。**値はバインドで渡し、本文へ連結しない。**
- 戻りは `msg_txt` 1 行（0〜1 行）。
- **0 件のとき**：**コード文字列をそのまま利用者に見せない**（上流 §9.2）。代替表示は下の
  「0 件のときの代替表示」で定める。
- **文言の行き先は確定した（v1.0.2）**：サーバが取得した `msg_txt` は、**エラー応答の `I-321` に
  載せて返す**（上流節点2 v2.0.4 の応答項目。**`I-xxx` の番号は人が発番する**＝紅线①）。
  **端点は 3 本のまま**であり、文言取得用の端点は設けない（§1.3）。
- **該当なしはこの限りでない**：`/login` の該当なし（E-201／E-207）は、上流 §4.3 規則 23・§8 E-07 の明文
  （**顧客の要求書に明記**）により **`errorCode` の `"1"` のみを返す**。文言も `errorDetailCode` も載せない。
  したがって **E-201／E-207 では本 SQL を実行しない**。文言は**クライアントが固定文言を表示**する（C）。
- **E-202 のクライアント検出時も同じ**である：API を呼ばないため文言はサーバから来ない。
  クライアントの固定文言を表示する（C）。`/generateUrl` のサーバ検出時は文言を載せて返す。
- **0 件のときの代替表示（C・v1.0.2 で確定）**：上流に規定が無いため、次のとおりとする。
  **汎用のシステムエラー文言**（上流 §9.1 の E-204／E-208 と同じ「システムエラーが発生しました。
  画面を再読み込みしてください。」）を表示し、**`errorDetailCode` と `msg_id` を運用ログへ記録する**。
  **コード文字列そのものは利用者に見せない**（上流 §9.2）。**代替表示は文言の一次情報ではない**——
  マスタ整備の不備を示す運用上の兆候として扱う。

> **本 SQL を用いる E-ID**：E-203・E-204・E-205・E-208・E-209・E-210（および `/generateUrl` の E-202）。
> **用いない E-ID**：E-201・E-207（該当なし。応答は `errorCode` のみ）、E-202 の**クライアント検出時**。

### 8.2 Session

- サーバ側に保持し、**識別子のみ HttpOnly Cookie** で持たせる（上流 §11・Q-205）。

- 破棄は L-208。**破棄できなくても失効で回収される**（裁定 Q-228）。

### 8.3 通信・暗号

- API は **HTTPS 必須**（開発環境のみ http 許容）。URL の scheme は環境設定（上流 §11・Q-215）。
- 暗号化は L-206 の 1 本に統合する。**AES-256-ECB ではない**（上流 §10.3）。
- **当日鍵の実値・格納場所を本書に書かない。** 取得方式は工程04 の構成承認時に確定する。
- 鍵の日付は JST・当日内のみ（Q-216）。日付はテストで固定できるよう引数化する（C）。**日付の供給元は §2.7 のとおり**（サーバ／サーバ応答）。

### 8.4 時刻と文字

- 当日鍵の日付は **JST** であり、**時刻の権威はサーバにある**（上流 Q-216。日付の取得元をサーバに一本化する）。
  画面の I-302 は**クライアント端末の時刻**（Q-218）であり、**両者は別物**である。
- **ログイン時の暗号化（L-207）はクライアントで行うが、日付は端末時刻だけでは決めない。** クライアントは
  `/init` 応答の HTTP `Date` ヘッダ（サーバ時刻）と自端末の UTC エポックとの差を保持し、暗号化の直前に
  その差で補正した JST 日付を L-206 へ渡す（C）。したがって**端末のタイムゾーン設定・時計のずれは当日鍵の
  判定に影響しない**（ずれはサーバ応答で補正する）。サーバ応答から日付を得られない場合のみ端末の UTC エポックから
  JST を換算し、その結果がサーバの日付と食い違えば復号失敗（E-205）となる（B-33）。
- 文字コードは UTF-8。URL はパーセントエンコード不要（上流 §12 #8・Q-201）。
- 入力の正規化（全角→半角・非 ASCII 除去・**trim しない**）は **L-207 の 1 箇所**で行う。他で再実装しない。
