| 状態 | 提案（承認待ち） |

**Auth0 を採らない判断の根拠（設計のどこから導いたか）**

| # | 出所 | 設計の事実 | 判断 |
|---|---|---|---|
| 1 | 05 §8.2 | **サーバ側に保持し、識別子のみ HttpOnly Cookie** で持たせる。保持は 11 項目のみ | クライアントがトークンを保持・送信する認証方式は、この明文と両立しない |
| 2 | 05 §2.9 ステップ 3・§10.5・裁定 Q-232 | 破棄の要求先は**顧客の共通基盤の Session 管理機能**（本画面専用の端点を追加しない） | 外部 IdP のログアウト端点は破棄要求の宛先ではない |
| 3 | 05 §4.1・I-307、§2.9 ステップ 2 | ログイン可否は**社員マスタに未削除の該当行があるか**で決める。権限区分は社員マスタ由来 | 外部 IdP が返す主体情報を判定に使う余地が無い |
| 4 | 節点2 承認版 §12・§11 | パスワード関連（変更・有効期限・複雑性）は**対象外**（NG-02）。社員コードのみでログインし、**なりすまし対策はネットワーク層・端末認証に委ねる** | IdP が担うはずの認証要素（パスワード・MFA）が要件に無い |

**一般論（E4）に属する部分**：認証基盤という**製品の選定**は設計から決まらない。
ただし「採らない」という**結論自体は 05 §8.2 の明文（設計由来）**であり、当方の好みではない。

> **作業票 n04 §3 ステップ2 の指示文について**：同文面は「既存栈として Auth0／AWS S3 を記録する」としているが、
> これは `migration`（既存スタックの確認・記録）を前提とした記述である。本演習は `greenfield` であり、
> 上流 05 §8.2 がサーバ側 Session を定めているため、**本記録は Auth0 を提案しない**。
> 同様に **AWS S3 は本案件の設計に登場しない**（05 に成果物出力桶の規定が無い）ため採らない。

## 3. 設計から導かれる実装規約

上流の設計を**実装で壊さないため**の規約である。**上流の値を変えるものではない**（05 §9）。

### 3.1 識別子 — 物理名は大文字

| 規約 | 内容 | 根拠 |
|---|---|---|
| 表名 | 業務対象の英字略号 ＋ `_MST`（マスタ）／`_TBL`（非マスタの共通表） | 05 §3.1（裁定 Q-227） |
| 列名 | snake_case。接尾辞は `_cd`（コード）／`_nm`（名称）／`_flg`（1 桁フラグ）／`_id`（識別子）／`_kais`（回数）／`_order`（順序） | 05 §3.1 |
| 大小文字 | **Oracle は非引用の識別子を大文字へ折畳む。** したがって**物理名はすべて大文字**で作成し、アプリからの参照も大文字で統一する | 05 §3.1（大小文字の実装規約はスタック承認後に反映） |
| 名前の実体 | 変えない。05 §3 の表・列の**名称そのもの**が唯一真源 | 05 §3.1・§9 |

- **05 §3 の物理名は既に大文字表記である**（例：社員マスタ `STF_MST`、画面マスタ `GMN_MST`）。
  Oracle の折畳みと方向が一致するため、**名称を書き換える必要は無い**。定義層の表記（snake_case・小文字）は
  文書上の論理表記であり、物理は大文字である。
- 引用識別子（`"..."`）で小文字を作らない。**折畳みに逆らうと、参照のたびに引用が必要になり事故の元になる。**

### 3.2 型 — 製品非依存の表現から写す

| 上流の表現（05 §3.1） | 物理型（本記録の写像） | 例 |
|---|---|---|
| 文字列(n) | `VARCHAR2(n CHAR)` | 社員コード `VARCHAR2(7 CHAR)`／社員名 `VARCHAR2(60 CHAR)`／コード類 `VARCHAR2(6 CHAR)` |
| 数値(p) | `NUMBER(p)` | ログインアクセス回数 `NUMBER(9)` |
| 1 桁フラグ | `CHAR(1)` | `del_flg`／`valid_flg`／`ji_kjo_ksn_flg`／`ta_kjo_ksn_flg` |

- **`n CHAR` は文字数指定**である（バイト数指定にしない）。日本語の名称（社員名 60）を桁で数えるため、
  バイト指定では桁が足りなくなる。
- **1 桁フラグの格納値は 2 系統ある。** `del_flg`／`valid_flg` は `0`／`1`（0＝未削除／0＝停用）、
  `ji_kjo_ksn_flg`／`ta_kjo_ksn_flg` は `'Y'`／`'N'`（05 §3.2・裁定 Q-234）。**型は同じ `CHAR(1)` だが値域が違う。
  混用しない。** 画面の `Y`／`N` と内部値 `1`／`0`（I-307）はさらに別系統である（05 §4.4）。
- **製品固有の型名を上流設計へ書き戻さない**（05 §3.1）。写像は本記録（工程04）にだけ置く。

### 3.3 日付・時刻 — `NLS_DATE_FORMAT` 固定

| 規約 | 内容 | 根拠 |
|---|---|---|
| セッション設定 | `NLS_DATE_FORMAT = 'RR-MM-DD'` を固定。**変更禁止** | 規則 00 §2 |
| SQL への埋込み | 日付・時刻を SQL に埋め込まない。当日鍵は SQL の外で扱う | 05 §5.1 #4・L-206 |
| タイムゾーン | サーバは Asia/Tokyo。当日鍵の日付判定は JST | 05 §8.4 |
| 端末時刻との区別 | I-302 は**クライアント端末の時刻**であり、当日鍵の判定とは**別物** | 05 §8.4 |

- 日付リテラルを SQL に書かない方針のため、`NLS_DATE_FORMAT` の影響は現れにくい。それでも
  **セッション固定値として設定する**（規則 00 §2。案件横断の硬約束であり、例外を作らない）。

### 3.4 バインド — `:name` ネイティブバインド

| 規約 | 内容 | 根拠 |
|---|---|---|
| 記法 | 値はすべて `:name` の**名前付きバインド**で受ける。`?`／`%s` へ変換しない | 05 §5.1 #1 |
| 禁止 | f-string 等で値を SQL 本文へ連結しない。実値・実コードを SQL に書かない | 05 §5.1 #1 |
| 識別子 | 列名・表名を利用者入力から組み立てない | 05 §5.1 #2 |
| 実体 | バインド値の実体は環境設定又は裁定値（Q-227／Q-234）で与える | 05 §5.1 #5 |

- oracledb は `:name` をそのまま受け取れるため、**変換層を挟まない**。SQLAlchemy Core の `text()` は
  SQL 本文をそのまま保持する（§2.2 根拠 1）。

### 3.5 SELECT のみ

| 規約 | 内容 | 根拠 |
|---|---|---|
| DML | **SELECT のみ。** INSERT／UPDATE／DELETE を持たない | 05 §3.1・§5.1 #3 |
| 帰結 | 排他制御・被参照チェック・重複チェック・コミット／ロールバックの設計を持たない | 05 §3.8・§1.2 |
| 5 表 | すべて read。結合は SQL-4 の内部結合、順序は `ORDER BY disp_order, gmn_id` の固定 | 05 §3.7・§5.3 |
| 白名单 | 動的ソートが無いため `ALLOWED_SORT_FIELDS` は適用対象が存在しない | 05 §5.1 #2 |

### 3.6 命名の 3 層（camelCase／snake_case／UPPER）

| 層 | 表記 | 例 | 根拠 |
|---|---|---|---|
| 画面・接口（TS） | camelCase | `stfCd`／`gmnId`／`kgnKbn` | 規則 03 §4・05 §4.2 |
| 定義層・Python 変数 | snake_case | `stf_cd`／`gmn_id`／`kgn_kbn` | 規則 03 §4・05 §3.1 |
| DB 物理名 | UPPER（snake_case を大文字化） | `STF_CD`／`GMN_ID` | 05 §3.1＋§3.1 本節 |

- **変換点は 1 箇所だけ**（`BaseCamelModel` の `model_config` 4 行固定。規則 03 §2）。手書き変換を散在させない。
- **3 系統の符号を混同しない**：画面 `Y`／`N`、内部 `1`／`0`（I-307）、フラグ列の `0`／`1` と `'Y'`／`'N'`（05 §4.4・§3.2）。

### 3.7 冪等性（生成・再実行）

- 同じ設計入力（L／D／E）から生成されるコードと差分は、**何度生成しても同一**であること（規則 03 §7.1）。
- **現在時刻・乱数・UUID・順序不定の反復を出力へ埋め込まない。** L-206 の日付は**引数注入**（05 §2.7）。
- 起動時に非決定的な値を設定値へ埋め込まない。

## 6. ビルドと CI 草案

### 6.1 ローカル（開発者端末・Windows）

| 手順 | コマンド | 備考 |
|---|---|---|
| 導入（frontend） | `npm ci` | lockfile どおりに入れる（`npm install` で差分を作らない） |

### 6.2 CI（常設門番への移行）

| # | ゲート | コマンド | 意味 |
|---|---|---|---|
| 1 | 追溯・機密の門番 | `python -m tools.trace_check --strict`（CI は `ubuntu-latest`） | ローカルの `py -3` と表記が違うだけで**同じ検査**（規則 09 のコマンド表記差）。門番は 6 道のまま（`gates_run = 6`） |
| 2 | 機密の単独実行 | `python -m tools.trace_check --strict --only-check secrets` | **1 件でもヒットしたら commit 禁止**（紅线⑦） |
| 3 | 型検査 | `npx vue-tsc --noEmit` | ビルドより前に失敗させる |
| 4 | 単体テスト（サーバ） | `pytest` | **テスト 0 件を緑と読まない**（未整備を合格にしない） |
| 5 | 単体テスト（クライアント） | `npx vitest run` | 同上 |
| 6 | ビルド | `npm run build` | 零 error（構築ゲート相当。本骨架の門番ではない） |
