## 1. 判据：规格书里几个组件

| 出处 | 原文 | 含义 |
|---|---|---|
| §11.2 组件④ | 「ナレッジベース（RAG）：過去案件・用語辞書・設計規約・既存ソースを検索し、流用できる資産を提示する」 | 知识库与 RAG 是**同一个组件** |
| §11.1 / §11.1.1 | 知識層（内容）＋ データ・コンテキスト層（ベクトルDB）；「知识库层：RAG」＝这两层 | 内容与索引是同一根柱子的两层 |
| §12.2 | 「RAG基盤：用語辞書と過去案件を横断検索できること（例：ベクトルDB ＋ 全文検索）」 | 规定能力，不规定引擎 |
| §11.3.2 | 「会社レベルとプロジェクトレベルの2階層」 | 知识必须分层 |
| §13 KPI⑥ | 「知識資産：ナレッジ登録数、RAG検索のヒット率、過去資産の再利用率」 | 命中率必须可测 |

由此：`tools/kb-platform` = 组件④本体（唯一检索入口）；`tools/rag` = 组件⑤「評価・ガバナンス」里的检索尺，
不是第二个知识库。两个都在，但只有一个是入口。

## 2. 改动了什么

| 文件 | 改动 |
|---|---|
| `tools/kb_migrate.py` | 抽出 `write_digest()`；**摘要节标题统一前置模块名**；**id 行与正文合并为一片**；移设后也能重建摘要（此前只有移设那一趟才生成） |
| `tools/kb-platform/repo/projects/P-R60-001/chunks/*.md` | 7 篇摘要按上述规则重生成 |
| `tools/kb-platform/repo/projects/P-R60-001/rag-usage.md` | 补「位置づけ変更」注记；订正一条已失效的指标说明；`updated_at` 2026-10-28 → 2026-10-29 |
| `tools/kb-platform/repo/eval/golden.yaml` | 删掉 Q001 重复的 `project:` 键 |
| `tools/kb-platform/VENDORED.md` | 增「在规格书里是哪一个组件」节；「怎么用」补摘要重建 |
| `tools/rag/README.md` | **新建**：定位为尺子、语料不在本目录、当前基线 |
| `reports/kb-export/p3_probe.py` | **新建**：逐题打印"命中的是哪个模块"，题目直接读 `golden.yaml` |

两处修改的动因：

1. **节标题不带模块名** → 同一标题（如「教材としての再利用パターンと反パターン」）在 4 个模块的摘要里重名，
   命中后看不出是谁的。
2. **每个小节被切成两片**（一片只有 `` `R60Maker:screen:search-items` / `screen` ``，一片是正文）。
   chunker 按空行切段，而生成器在 id 行和正文之间留了空行。R60Maker 摘要 45 条 → 91 个 chunk，多出来的就是这些。

### 3.5 生成器可重复运行

```bash
py -3 -m tools.kb_migrate --apply && md5sum        # 与上一次 diff 的 md5 比较
```

两次运行 `git diff -- tools/kb-platform/repo` 的 md5 相同（`2516e331b334e965d66c73467d28bc17`），
即 `--apply` 幂等（规则 03 §7.1）。

## 4. 结论

1. `tools/kb-platform` 与 `tools/rag` **都有价值，但不是并列的两套系统**：前者是规格书 §11.2 组件④，
   后者是组件⑤ 里的检索尺。知识只从 kb 进，rag 不新增语料。
2. 摘要串味已修复：12 题全部命中正确模块，且正确小节在 12 题中 12 题排第 1。
   kb 侧 `recall@5` 保持 1.000，`MRR` 0.938 → 0.958。
3. `tools/rag` 一个字节没动，其指标也未变——这保证了"kb 变好"不是靠改尺子得来的。
