## 1. 80 题金标 → kb 检索（规格书 §13 KPI⑥ 的口径）

### 1.1 为什么另写一个适配器

`py -3 -m tools.rag eval` 测的是 **rag 自己的索引**——尺子测自己。
KPI⑥「RAG検索のヒット率」要测的是**正本库**（§11.2 组件④ ＝ `tools/kb-platform`）。
所以写 `tools/kb_eval.py`：**读同一份 `eval/gold-qa.yaml`，把问题喂给 kb 的 `search`**。

金标不复制第二份。80 问的唯一真源仍是 `eval/gold-qa.yaml`。

### 1.2 命中怎么对号

金标的 `expected_chunk_ids` 是 rag 的 chunk id（如 `R60Ssk:screen:overview`）。
kb 侧的摘要每个小节的第一行就是 `` `R60Ssk:screen:overview` / `screen` ``（`write_digest` 生成），
所以**取得片段的正文里出现该 id 就算命中**——精确字符串对应，不是模糊匹配。

### 1.3 实测

```bash
py -3 -m tools.kb_eval --json reports/kb-export/kb_eval_80.json
```

```
gold=80  top_k=5  recall@5=0.863  MRR=0.672  top1_module=76/80

  R60KkuChi      n=10  recall=0.800  mrr=0.483
  R60Maker       n=15  recall=0.867  mrr=0.800
  R60Plc         n=15  recall=1.000  mrr=0.794
  R60SesModel    n=15  recall=0.800  mrr=0.589
  R60Ssk         n=15  recall=0.933  mrr=0.722
  R60User        n=10  recall=0.700  mrr=0.533
```

对照（同一批题，rag 自己测自己）：

```bash
py -3 -m tools.rag eval
```

```
filtered by module recall@5=1.000 strict=1.000 mrr=0.901 unsupported=0.000
unfiltered         recall@5=0.863 strict=0.863 mrr=0.645 unsupported=0.000
```

| | recall@5 | MRR |
|---|---:|---:|
| rag（指定 module） | 1.000 | 0.901 |
| rag（不指定 module） | 0.863 | 0.645 |
| **kb（不指定 module）** | **0.863** | **0.672** |

### 1.4 这组数字怎么读

- **kb 不给 module 参数，所以只能和 rag 的 unfiltered 比。** 两者 recall 完全相同（0.863），
  kb 的 MRR 略高（0.672 vs 0.645）。**这说明 kb 的检索没有因为换索引而变差，也没有变好多少。**
- **0.863 不是「1.0 掉了」，而是「不告诉它哪个模块」的真实水平。** rag 的 1.000 是**指定模块后**
  把语料先限定到一个模块再排序，那是「已经知道答案在哪个模块」的条件。
- **有 11 题未命中，绝大多数是同一个模式**：问题问「R60User 的设计事件是几件」，
  取得第 1 位是 **R60SesModel 的事件小节**。即检索器认出了「设计事件」这个话题，
  但不知道问的是哪个模块。**这是模块盲检索的固有局限，不是切片坏了。**
  若要改善，方向是让调用方带上模块（8 工程的节点本来就已知模块），而不是继续调排序权重。
- **不能对外宣称「kb 检索命中率 86.3%」** 而不带「未指定模块」这个前提。带上模块后未测，
  不应假定等于 rag 的 1.000（两者检索器不同）。

## 2. 金标粒度：结论是「不改」

P3 的遗留里写着「金标是 doc 级的，看不出『模块对、小节错』」。查清后的结论：

| 文件 | 题数 | 粒度 | 测谁 |
|---|---:|---|---|
| `tools/kb-platform/repo/eval/golden.yaml` | 24（12 demo + 12 RQ） | **doc 级**（`expected_doc_ids`） | kb 自己的回归 |
| `eval/gold-qa.yaml` | 80 | **chunk 级**（`expected_chunk_ids`） | 检索质量（KPI⑥） |

**80 题本来就是 chunk 级的**，`tools/kb_eval.py` 也是按 chunk 判的。
所以「金标太粗」的问题在 80 题这一侧不存在。

**不做的事**：不把 80 题转成 `golden.yaml` 的 doc 级形式（那是**降级**，会把已经有的粒度丢掉），
也不给 `golden.yaml` 加 `expected_heading` 字段（80 题已经覆盖了这个需求，再加一份就是两处定义）。

**尚未覆盖的盲区**：`golden.yaml` 的 24 题仍是 doc 级，RQ008 那种「模块对、小节错」它看不见。
这 12 题的补充观测由 `reports/kb-export/p3_probe.py`（逐题打印前 5 位小节）承担。
**这是已知缺口，不是已解决。**

## 5. 结论

1. **KPI⑥ 有了可重复的口径**：`py -3 -m tools.kb_eval` → recall@5 0.863 / MRR 0.672（未指定模块）。
   与 rag 的 unfiltered 同 recall、MRR 略高。**不得省略「未指定模块」这个前提。**
2. **金标粒度不需要改**：80 题已是 chunk 级；24 题的 doc 级盲区用 `p3_probe.py` 补，属已知缺口。
3. **company 昇格完成且不污染项目检索**：lint OK 92、eval PASS、80 题指标不变。
