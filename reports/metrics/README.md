# reports/metrics/ — §13 KPI 基准值快照

## 这是什么

实施规格书 §13.1 定了 6 个 KPI 维度（①生产效率 ②质量 ③AI 利用率 ④覆盖度 ⑤交付周期 ⑥知识资产）。
这个文件夹里存的是**从本仓库机器可测出来的基准值**，一个日期一份。

| 文件 | 内容 |
|---|---|
| `2026-10-28.md` | 人读版（Markdown，6 个维度一张总表 + ④⑤ 的分项） |
| `2026-10-28.json` | 机器读版（同内容的 JSON） |

## 怎么再生成

```bash
py -3 -m tools.metrics                                   # 打到屏幕上
py -3 -m tools.metrics --out reports/metrics/<date>.md \
                       --json reports/metrics/<date>.json # 存档一份
py -3 -m tools.metrics --self-test                       # 自检（3 项）
```

**不要手改这两个文件。** 它们是生成物，下次生成会盖掉手改的内容。
要改口径，改 `tools/metrics.py`。

## 三个要知道的前提

1. **目标值这里没有。** §13 自己写着「目标值不要一开始定高，先在试点测基线，再设改善目标」。
   所以本目录只放**基线**，不放目标。等有了基线和实际项目数据，再由人定目标。
2. **测不了的维度就写「测不了」。** ①生产效率需要工时记录，仓库里没有；
   ②质量的手回率、③AI 生成物的采纳率/修改率都需要人来记。这些写「❌ 测不了」并注明原因，
   **不编数字**。
3. **⑤ 交付周期目前只有演练案件（R60Login）能测。**
   真实案件没有在每个节点记录 `approved_at`，所以测不出来。要测真实案件，
   得先在 `docs/00_plan/coach/<案件>/nNN.yml` 里记 `approved_at`（这是流程要求，不是本工具的缺口）。

## 读这份快照时最该看的一行

`2026-10-28.md` 的 ⑤ 里，节点 4（框架构建）的「距上一节点」是**负数**。
那不是算错，是**承认顺序和节点编号不一致**（后序节点先被承认了）。
规格书要求 8 工程按顺序推进，红线②（无设计不制造）管的就是这个顺序。
**改不改由人裁定**——不能靠改记录来「装作按顺序走过」。
