## 0. 一句话

**这个文件夹不是一个软件，是四样东西叠在一起：**

1. 一套**给 AI 读的工作制度**（什么不许做、每件事按几步做）
2. 一套**质检仪器**（做完拿去验，不合格不放行）
3. **两个样例工程**（一个是"照着填的样板"，一个是"真跑过一遍的录像"）
4. **一堆跑完留下的材料**（旧系统扫描件、临时输出、自动备份）

**你的框架只有第 1、2 样。第 3、4 样是它们产出的东西。**

所有"乱"的感觉，都来自这四样混在同一个根目录下，没有任何一处写清楚"哪部分是哪部分"。

## 2. 它是怎么干活的：8 个节点，每个节点一次签收

拿一件真事说：客户说"我要一个登录画面"。

```
客户需求书（一页纸）
   │
   ├─ ① 要件理解   提炼成编号 R-201；用 51 个视角审一遍，挑出"它没说清的地方"
   │               → 出一份《确认事项一览》交给人回答
   │               → ★ 人签字（n01.yml 里 approved_by = SE-001）才能往下走
   │
   ├─ ② 基本设计   从 R-201 展开：功能 F-201、画面项目 I-301~I-3xx
   │               → ★ 人签字
   │
   ├─ ③ 详细设计   SQL、字段、边界值、错误 E-201~、逻辑 L-201
   │               → ★ 人签字
   │
   ├─ ④ 框架构筑   用什么技术（这一条必须人拍板，叫"红线④"）
   │               → ★ 人签字
   │
   ├─ ⑤ 制造       按设计写代码。设计里没写的，不许自己发挥
   │               → ★ 人签字
   │
   ├─ ⑥ 单元测试   每个功能至少 8 个用例（正常3 / 边界2 / 异常3）
   │               → ★ 人签字
   │
   ├─ ⑦ 结合测试   串起来跑
   │               → ★ 人签字
   │
   └─ ⑧ 发布运维   上线 + 出问题怎么退回来
                   → ★ 人签字
```

**全流程只有三条规矩**（就是你说的"7 条红线"里最核心的三条）：

1. **上一步没签字，下一步不开工**
2. **每个产出物必须有编号，编号只能从 `ids.yml` 领**（不许自己编）
3. **每次提交前必须跑 6 道门，跑不过不许提交**

其它四条红线都是这三条的具体化（不许跳门、不许外传机密、不许擅改技术栈、用例必须有出处）。

**这就是整个框架。** 剩下的 700 个文件都是为这三条规矩服务的。

## 3. 一把钥匙：仓库里有 5 个"世界"

**这一段是全篇最重要的。** 你觉得乱，是因为同一个概念在五个世界里长得不一样。

| 世界 | 在哪 | 是什么 | 谁用 | 能不能删 |
|---|---|---|---|---|
| **① 制度层** | `.claude/` ＋ `tools/` | 给 AI 的规矩和工具 | AI 每轮自动读 | **不能** |
| **② 目标层** | 规格书 ＋ 使用手册 ＋ `CLAUDE.md` | 给人看的目标与说明 | 人 | **不能** |
| **③ 样板层** | `docs/10~80_`（编号 R-101 系列） | 一次真实案件的**写法示范** | 人照着填 | 不能，但可以加标记 |
| **④ 演练层** | `tutorial/R60Login`（编号 R-201）＋ `reports/drill` | **真跑过一遍的录像** | 人（证明框架能跑） | **不能——这是唯一的实证** |
| **⑤ 附赠层** | `docs/90_knowledge/legacy-r60` ＋ `reports/module-survey` | R60 旧系统的资料 | 只对 R60 有用 | **可以整块剥离** |

### 3.1 为什么有两套编号？R-101 和 R-201 是什么关系？

这是最容易卡住的地方，我直接说清楚：

| 编号 | 是谁写的 | 写来干什么 | 在哪 |
|---|---|---|---|
| **R-101 / F-042 / D-043 / L-014 / TC-001..008** | **骨架作者手写的** | 照着真实模块 R60Area 写的**一份完整样板**，让人知道模板该怎么填 | `docs/10_requirements/` … `docs/60_integration_test/` |
| **R-201 / F-201 / I-301… / TC-201…** | **AI 在演练时写的** | 走一遍全流程，看它能不能跑通 | `tutorial/R60Login/` |

**两套编号不连续、前缀不同，是故意的**——它们是两个不同的工程，混在一起会导致追溯链断掉。

还有第三套：`R60Area`、`R60Login`、`R60Maker`…… 这些是**旧系统的真实模块名**，不是我们发的号，是客户系统里的名字。

### 3.2 演练那套是"假的"吗？

是**虚拟的**，但不是玩具。要说清楚：

- 客户需求书是**倒推**出来的——从 R60 的真实系统反推一份"客户当初可能这么写"的需求书
- 倒推只做这一步。要求书冻结之后，**下游 8 个节点都不许再去看 R60 的代码**
- 这样才可能测出"AI 自己写，会和人类专家写的不一样在哪"

**而且仓库里诚实记着 5 个污染源**（`docs/00_plan/coach/R60Login/case.yml` 的 notes 里）：
其中 3 个是中途被要求去参考了真实实现。所以这份录像**证明的是"流程能跑通"，不是"AI 质量好"**。

这个区别很重要：如果有人拿它当"我们的 AI 有多强"的证据，那是错的。仓库自己写明了。

## 4. 逐块说：为什么存在，删了会怎样

### 4.1 `.claude/rules/`（7 本，105KB）—— 员工手册

**为什么存在**：AI 每轮对话开始时自动读这 7 本。里面写"不许做什么"：不许自己编编号、不许跳门、不许把机密发出去、不许改技术栈、成果物不许出现两种说法。

**删了会怎样**：AI 不知道规矩，会开始自己编编号、漏掉门禁、把机密写进文件。

**唯一的问题**：7 本加起来 105KB，加上 `CLAUDE.md` 的 12KB，**每轮对话开头就有 117KB 的规矩**。这就是为什么 AI 有时候抓不住重点——不是它不听话，是东西太多。**这是将来要改的地方，不是要删的地方。**

### 4.2 `.claude/skills/`（5 个，18 个文件）—— 作业指导书

**为什么存在**：rules 说"不许怎样"，skills 说"这件事按哪几步做"。最核心的是 `trans-cosmos-ai-lifecycle-coach`：你打 `/trans-cosmos-ai-lifecycle-coach`，它就自动算出"你上次停在哪一步"，然后出下一步的卡片。它的 9 个作业票在 `nodes/n01..n09.md`。

**删了会怎样**：8 个节点没有具体做法，只剩空规矩。

**要注意的**：`code-from-design-trans-cosmos-ai` 和 `legacy-r60-navigator` 这两个**只对 R60 有意义**。将来卖给别的客户，这两个是"附赠的"，不是"框架本身"。

### 4.3 `.claude/agents/`（14 个）—— 外派专员

**为什么存在**：一个节点如果全都塞进主对话，上下文会爆掉。所以每个节点有一个专员：你把任务交给他，他在**自己的房间**里干，干完只回你 15 行结论。

**删了会怎样**：8 个节点全挤进主对话，做两三个节点上下文就满了。

**一个必须知道的点**：专员的"引用数"永远是 0。因为系统是靠**描述**自动匹配的，不是靠文件路径。**所以不能因为"没人引用它"就删掉。**

### 4.4 `tools/`（41 个文件）—— 质检仪

**为什么存在**：

| 工具 | 干什么 | 什么时候用 |
|---|---|---|
| `trace_check` | **6 道门**：编号对不对、追溯链断没断、字段齐不齐、命名对不对、机密有没有 | 每次提交前 |
| `gen_view` | 机读文件 → 中文网页（就是你现在看的这种） | 每个节点做完 |
| `gen_formal` | 机读文件 → 日文正式 Excel | 自动（每轮结束） |
| `registry` | 发编号、判阻塞、作废 | 人要新编号时 |
| `impact` | 给一个编号，倒查上下游会影响谁 | 客户提修改时 |
| `masking` | 脱敏 | 发给外部之前 |
| `rag` | 在旧案件知识里搜 | 查旧系统时 |
| `ingest` / `legacy` | 把旧 Excel / 旧案件搬进来 | 一次性 |

**这一块的结构最清楚**，但不是「一个都不用动」。真正不能动的只有 6 个：
`trace_check` / `registry` / `impact` / `gen_view` / `gen_formal` / `masking`。

可以清理的：`tools/trace_check.py`（18 行薄启动器）与 `tools/trace_check/__main__.py` 是**重复入口**；
`ingest`（7 文件）、`legacy`（4 文件）是**一次性迁移工具**，搬完就不需要了。

> **订正（2026-10-28）**：原文写「零重复、零孤岛，一个都不用动」，是错的。
> 依据：意见表 4-7「不一定」；复核确认存在重复入口与一次性工具（见 `reply-to-review_2026-10-28.md` 4-7）。

## 5. 三个最容易误解的地方

### 误解一："这是给客户用的产品"

**不是主力。** 它的定位是**内部骨架**：AI 怎么按照制度干活。客户交付的是"用这套骨架做出来的项目文件"（像 `docs/10~80` 那样），不是骨架本身。

所以骨架里带不带 R60 的旧资料，不影响交付能力——但影响你把它交给第二个客户时的干净程度。

### 误解二："tutorial 是教学玩具，可以扔"

**它是唯一走完 8 个节点、6 道门全过的实证。** 扔了以后，你无法向任何人证明这套框架跑得通。

而且它自己诚实记着 5 个污染源——这份诚实本身就是资产。

### 误解三："reports 里 300 个文件都是记录，都得留"
