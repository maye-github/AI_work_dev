## 2. 发现一：框架层混入了案件事实

### 2.1 先定分界

同一份资产里，「方法」和「事实」必须分开：

| 类别 | 判据 | 例子 | 归宿 |
|---|---|---|---|
| **公司级（方法）** | 换一个案件仍然成立 | 8 工程顺序、红线、门禁、A/B/C 分类、E1–E4 证据等级、受控回流、51 个审查视角 | 框架层（`.claude/`）与方法论文档（`docs/90_knowledge/`） |
| **案件级（事实）** | 出现具体画面名/表名/函数名/项目数才成立 | R60 画面卡、R60Common 16 函数、ACTION_ID 40 个、R60Area 56 项目、R60 的 DB/API | 知识库 project scope |

判据可以压缩成一句：**「这句话换到另一个客户的另一个系统，还成立吗？」** 不成立就是案件事实。

### 2.2 量化：框架层里的 R60 出现次数

| 文件 | 次数 | 性质 |
|---|---:|---|
| `.claude/skills/code-from-design-trans-cosmos-ai/SKILL.md` | 70 | **案件事实进了正文**（见 2.3） |
| `.claude/skills/trans-cosmos-ai-lifecycle-coach/SKILL.md` | 26 | 多为教材路径 `tutorial/R60Login/…`；SKILL.md:47 已声明「固有記述は例であり規則ではない」 |
| `.../nodes/n02・n03・n01` | 20 / 19 / 19 | 同上，教材举例 |
| `.claude/skills/requirement-interrogator/references/lenses.md` | 16 | QA 票出处的引用 |
| `.claude/skills/legacy-r60-navigator/SKILL.md` | 13 | **整篇都是案件** |
| `.claude/skills/virtual-requirement-author/SKILL.md` | 8 | 例子绑定 `D:\AI_work` |
| `.claude/agents/*` | 1–3 | 举例 |
| `.claude/rules/*` | 2–14 | 见 2.5 |

**判断**：coach 与 agents 的第 1–3 次出现属「举例」，可保留；**需要动的是 3 个 skill**（code-from-design、legacy-r60-navigator、virtual-requirement-author）。

### 2.3 个案：`code-from-design-trans-cosmos-ai`（418 行）

它的适用范围原文（L31）：

也就是说，**框架的「设计→制造」主技能，实际上被限定在了一个案件的单个画面上**。逐节拆解：

**最严重的一条**：[rules/03 §3](../../../.claude/rules/03-design-coding.md#L49) 写着

也就是说，**规则文件把「案件事实」指定成了框架内的唯一真源**。同一指针还出现在 [node4-framework.md:36](../../../.claude/agents/trans-cosmos-ai-node4-framework.md#L36)。这条不处理，R60 的 16 个函数名会被下一个案件原样继承。

### 2.6 表述问题：「附赠资产」

来源句在 [00-index.md:15](../../../docs/95_legacy/r60/00-index.md#L15)：

## 4. 发现三：两套检索引擎并存

| 维度 | `tools/rag` | `tools/kb-platform` |
|---|---|---|
| 语料 | 344 条 chunk（AI 摘要） | `repo/` 下的 `.md` |
| 切块 | 预先切好（人工/AI 编制） | 自动（见出し/表行/代码块） |
| 检索 | SQLite FTS5 + 日文 n-gram | hash n-gram 向量 + RRF + rerank |
| 评测 | 80 题金标，hit@5 **1.0 / 0.8625**，MRR 0.9015 | 12 题（上游 demo），**未跑过** |
| 权限 | 无 | `conf_level` 数值比较 |
| front matter | 无（自建 schema） | 必需 8 键 |
| 维护方 | 本仓库自建 | 上游（公司级） |

两个都留着，就会出现「同一个问题，两个工具给两个答案」，而**哪个是准的没人能说清**。这正是用户担心的那类混乱。

但**不能简单删掉 `tools/rag`**：它的 344 条 chunk 是**AI 撰写的摘要**，不是原文切片——

```text
grep -c "教材モジュールの中等" docs/95_legacy/r60/screens/R60Plc.md   → 0
而在 chunks/R60Plc.jsonl 里能找到这句话
```

原文里没有的东西，删了索引就真没了。

## 5. 发现四：三条硬约束（决定方案形态）

### 5.1 知识不能搬进 `tools/`

```text
tools/trace_check/__init__.py:285   SCAN_BASES = ("docs", ".claude", "tutorial")
tools/trace_check/__init__.py:689   targets += [p for p in tools_dir.rglob("*.py")]
```

`docs/**`、`.claude/**`、`tutorial/**` 都受 gate1（野号）/ gate3（front-matter）/ gate6（机密）保护；
而 `tools/` 下**只有 `.py` 进机密扫描**。

**所以：把知识 `.md` 搬进 `tools/kb-platform/repo/`，它们就跳出了机密红线⑦的扫描范围。**
[rules/06 §3](../../../.claude/rules/06-knowledge-flywheel.md) 明令「走査範囲を狭める変更をしてはならない」，这条必须先解决。

（旁证：`tools/kb-platform/README.md` 等上游文档**现在就已经**不在扫描范围内——这是既存的洞，不是本次造成。）

### 5.2 `status` 词表冲突：一份文件无法同时满足两个 lint

实测：合并后的 front matter 送 kb lint → `OK`（多余键它不检查）。
但 `status` 这一个键被两个体系同时占用，且词表只有 `draft` 一个交集：

| 体系 | 允许值 | 检索条件 |
|---|---|---|
| 骨架 gate3 | draft / open / **baselined** / changed / done / void | — |
| kb-platform | draft / review / **active** / deprecated | 只返回 `active` |

后果：一篇文档若标 `baselined`（骨架合法），kb 检索**一条都搜不到**；若标 `active`（kb 可检索），gate3 直接判 `status 値不正`。

**结论：「一份文件两用」不成立**，除非改引擎或改门禁。这条是方案设计的硬边界。

### 5.3 kb 只索引 `.md`

`collect_docs()` 只取 `*.md`。36 个模块 YAML 卡要进库，必须在导出时**渲染成表格式 Markdown**——顺带正好符合上游指南 §4.5「項目定義表は 1 行 = 1 chunk」。

## 8. 结论

1. 用户的两点意见**成立**，且第一点比表述更深：不只是「称呼」问题，而是**案件事实占据了框架的方法位置**。
