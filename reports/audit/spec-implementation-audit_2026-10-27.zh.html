七、三份方案（单独列）

7.1 模拟网关（只做接口）

先说清为什么接口就够：今天的执行体是 Claude Code 本身，工具层零调用。真正需要网关的只有两处——RAG 的向量化和重排、以及换供应商时的接口缝。所以只按这两处设计，不做无用的通用抽象。

要做的四样东西：

文件作用
docs/01_context/gateway.yaml配置。密钥只写环境变量名，绝不写值
docs/40_framework/gateway-contract.md给公司的一页接口契约
tools/gateway/providers/三个实现：OpenAI 兼容、离线桩、公司服务
tools/gateway/__main__.py命令：ping / chat / embed，全部支持 JSON 输出

给公司的契约只要求 OpenAI 兼容（chat/completions 加 embeddings 两个接口）。如果公司给的是私有协议，只改 providers 一个文件，上层不动。

三条硬约束写进代码，不靠自觉：

  1. 外发必过脱敏，开关不可关闭（红线⑦）。
  2. 密钥只从环境变量取。
  3. 每次调用留审计日志，记用途、关联编号、模型、耗时、token、是否脱敏，不记正文（正文可能含机密）。

离线桩必须能在完全断网的情况下让整条链路跑通。

7.2 RAG 本地知识库（只做接口）

现状：切块已经固化，12 个必填字段（含来源路径、来源位置、关联编号、机密等级），词法检索加评测集 80 题。

这套 chunk 结构设计得比多数 RAG 项目好——来源路径加来源位置加关联编号，天生支持"引用到节"和"追到编号"。不要推翻它，接口就以它为准。

接口契约三条（换提供方也不能变，否则引用会碎）：

  1. 每条命中必须能拼出 文件#位置 形式、人可以核对的出处。
  2. 每条命中必须带关联编号，能落回登记表（这正好接红线⑤）。
  3. 分数只用于排序，不允许跨提供方比较绝对值（不同算法尺度不同）。

三层提供方：本地词法（现在默认）→ kb-platform → 公司服务，外加一个离线桩给 CI 用。

真正的难点不在检索，在语料生产：现在的 chunk 是一次性手工做的。需要一条"机读源 → 切块 → 补字段 → 建索引 → 评测回归"的流水线，否则每加一个案件都要手做语料，不可持续。

7.3 kb-platform 接入

用途方式理由
读（检索）命令行 search --json，包成一个提供方不把 numpy 和 FastAPI 装进骨架，门禁保持纯标准库；进程隔离，崩了不影响门禁
写（入库）产物先放暂存目录 → lint → ingestlint 是唯一能挡住"元数据不合法"的闸，不能跳
服务态它的 build_router() 挂到公司网关骨架侧只换提供方

为什么不直接 import 它的库：那会把 numpy 变成骨架的硬依赖，trace_check 这些纯标准库工具从此要装科学计算栈——为了检索牺牲门禁的可移植性，不划算。

八、任意节点入口（核心设计）

8.1 你要的，和现有机制的冲突

你要的是：客户直接给了一本基本设计书 → 从节点 3 开始。

现有机制挡在两处：

  1. 当前节点永远取"前置已满足且未批准的最小号"，所以永远从节点 1 找起；
  2. 前置没批准就不启动，并且明写"不承认例外"。

有一种"手工绕过"——把外部设计书塞进节点 2 的目录，再把前两个节点手工改成已批准。这条路必须明确禁止：它是在伪造批准证据，直接把红线③变成空话，而且框架根本不校验批准来源。

所以正确做法不是绕过，是让这种情况成为一种合法状态。

8.2 引入与"批准"并列的新概念：外部接收

批准（approved）外部接收（adopted）
谁产出我方外部（客户或上游）
谁签我方评审人我方责任人，并记录提供方
含义"我们认可它正确""我们按它做，而且知道它缺什么"

两者在下游等效可用（都拿它的产物当输入），但在证据上必须能区分——出问题时才能回答"错在我方还是错在来件"。

8.3 入口流程六步

① 登记     原件只读放进案卷，记哈希、提供方、日期
② 体检     用 51 个视角扫这本设计书，输出"它没说清什么"
③ 适配     抽出功能项和画面项，用发号工具换成我方编号，出对照表
④ 判定缺口 人看体检结果：哪些必须问客户才能开工，哪些可以带着走
⑤ 签收     状态置为外部接收，签收人必须是人的编号
⑥ 起跑     coach 从起始节点出第一张卡

第 ③ 步不能省。 外部文档几乎不可能自带我方编号、关联字段和追溯链。不做适配就直接用，等于让门禁从第一天起就是红的，或者逼人去跳门。

8.4 机制只改一处

前：前置节点未批准 → 不起动（不承认例外）
后：前置节点未批准、且未被外部接收 → 不起动

8.5 与七条红线的关系

红线外部接收模式下
① 野号禁止不放松。外部编号必须先换成我方编号，对照表留档
② 无设计不制造不放松。从节点 5 起跑等于前四个节点全部外部接收，每份都要有缺口清单
③ 无批准不进下一节点语义扩展：外部接收也要人签收，AI 不得自签
④ 技术栈不得擅改外部设计书隐含技术栈，节点 4 必须记录"栈来自来件"
⑤ 用例必须有出处不放松。设计书里没有错误编号，节点 6 就会缺字段，由第 ③ 步补出来
⑥ 无门禁不提交不放松
⑦ 未脱敏不外发不放松；来件本身可能含真实值，第 ① 步入库前先过脱敏

一句话：外部接收改变的是"谁产出"，不改变"要有出处、要有人签、要能追溯"。
